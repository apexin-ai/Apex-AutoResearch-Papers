## 3. 科研目标达成度分析

### 3.1 Idea → Findings 的逻辑链
- **原始 idea**（IDEA_BRIEF）: "首个将谱坍缩监测连接到闭环 budget-constrained 自适应 mix 控制"，核心实验是 4 条件（spectral-guided / calibration-guided / fixed 50/50 / no-intervention）共享同一 real-data 预算的 budget-fixed 再分配。
- **最终 paper**: "三阶段谱坍缩特征化 + SLV 作为低成本指标 + prevention–detectability tradeoff + r_crit phase diagram"。原 Claim 4（controller 胜出）变成了 Claim 3（controller 必然失效的负面结果）。
- **Reframe 次数**: 至少 3 次（D013 主线后移、D019/D020 controller 降级、D022 short→long、D027 C5 降级）。**第一次 reframe 发生在项目启动后 36 小时**，是被实验数据强制的，不是被 reviewer 强制的。
- **是否回答了原始问题**：部分是。原始问题"自适应分配是否优于均匀分配"被实验否定（controller 在 ≥20% real data 下 Δ_t < τ 全程不触发）。论文最终回答的是"为什么自适应反应式控制器在此设置下不可行"+"r_crit 在哪里"，是合理的科学转向。

### 3.2 实验设计的科研严谨性
- **可证伪性**: ✓ controller MVP criterion 提前定义（adaptive 比 fixed_mix 多 ≥3 ppl），结果失败被诚实接受。
- **Baseline**: ✓ 包含 pure_collapse / fixed_mix / adaptive；ablation 包含 r ∈ {0, 0.2, 0.25, 0.3, 0.5}。但 D026 删除 linear_increasing 条件丢失了"闭环 vs 开环"的关键对照（Reviewer 在 R2 中确实拿这点攻击）。
- **统计**: 弱。多数条件 1-2 seeds，Round 4 critical MF-1 直接指出 3 seeds + 无 bootstrap CI/permutation test 不足以支持 r_crit ∈ (0.25, 0.3] 的"区间精度"措辞。直到 D040 (5/25 提交当天) 才安排 bootstrap CI 作业，但用户已经叫停。
- **Cherry-picking 风险**: 中等。r=0.2 二 seed 之间 D-4 轨迹差异巨大（seed42 V-shape recovery vs seed43 单调下降），D037 选择"维持 single seed + hedge"而不是更新到 2-seed mean，理由是"页面零余量下风险过高"。这是工程约束击败统计严谨性的典型案例。
- **MP bias**: γ = n/d ≈ 0.98 时 Marchenko-Pastur 失真未在最初论文中讨论，Reviewer Round 3 W1 直接指出。这是设计期就该考虑的问题被遗漏。

### 3.3 Findings 的质量与 Novelty
- **三阶段特征化**: genuinely novel（SIGMA 只跑了 3 代不可能观察），cross-arch 复现强化（exp_020 GPT-2-medium 完全复现 Gen 2 peak）。
- **SLV 作为指标**: paper 自己承认 SLV = 0.5 × log det G（与 SIGMA Track I 等价），增量价值争议。Round 2 C1/Round 4 D1 中 R2 一直坚持 "scalar reduction of SIGMA"，R1 反驳 "SIGMA 短窗口物理上看不到三阶段"。
- **Signal attenuation paradox**: paper 自己也指出生态学文献早已讨论 intervention 抑制 warning signals (Scheffer 2009/2012)，Reviewer Round 1 MF4 把它从"qualitatively distinct failure mode"压回"已有 EWS 文献的具体实例化"。
- **r_crit phase diagram**: 6 个 mixing ratio 把 r_crit 定位到 ±0.05，"phase diagram" 一词暗示的精度高于实际数据支撑的粒度，Round 3/4 都被批。
- **Reviewer 评分**: 4 轮均 3.0 / Findings，Soundness 3/5, Excitement 3/5, Reproducibility 4/5。Reproducibility 高分（3 seeds CV<1.3%、完整 hyperparameter 文档、AI disclosure）是项目最稳的得分点。

### 3.4 研究效率
- **直接贡献论文的实验**: exp_001/004/006/007/008/009/010/011/012/013/015/016/017/018（核心 phase diagram + multi-seed） + exp_020/022c/023（cross-arch）≈ 17/30 ≈ 57%。
- **探索性弯路产出 negative result**: exp_003 (controller bug 重启 3 次)、exp_005 (k=20 sensitivity, killed for compute)、exp_014 (r=0.25 seed43, 磁盘满崩溃)、exp_026/exp_027 (DDL 当晚启动后被 SSH 失联标 failed) — 这些是工程问题，没产出科学价值。
- **GPU 时间损失估算**: M002/M003 三次重启 ~5h；M007 双实例降速 ~10h；M013 磁盘满崩溃恢复 ~3h；M017 ghost process 1h；M016 unauthorized retrain ~6h；累计 ~25h ≈ GPU 总预算 8%。
- **决策成本**: 40 个 D-编号决策 / 9 天 ≈ 4.4 / 天，但其中 D003-D034 多数是 reactive 修正（D006/D031/D034 撤回前序决策）。决策更新成本被高估，因为 Director 经常每次 reset 都要重读全部 decisions.yaml 重建 context。

### 3.5 论文与实际科研的匹配度
- **过度包装**: 中等。Round 4 MF-3 指出标题 "Early Warning Signals" 暗示实时监控能力，但论文自己证明在 r ≥ 0.3 时信号消失、在 r=0 时不需要 EWS、只有 0 < r < r_crit 这个最难检测的区间才有部分价值。**核心 claim 与标题暗示存在结构性矛盾**。
- **Negative result 报告**: 诚实。controller 失败被显式作为 C3，并且分析得很细。
- **D-4 高方差被显式讨论**（memory.md 记录 CV 远高于 SLV），并用作 SLV 优越性的论证。
- **Claims vs evidence**: r_crit 区间记号 (0.25, 0.3] 在没有 bootstrap CI 的情况下精度被 reviewer 直接质疑。abstract 中 r_crit 用离散集 {0.2, 0.5} 而 §3.2 用区间 (0.25, 0.3]（记号不一致）是 Round 4 MF-1 中被两个 reviewer 都点出的低级错误。

- 角色定义最清晰、价值最稳定。tool 分布 ssh_read_only 2045 (主导) + ssh_execute 0（从不写）+ reviewer_post_to_director 385（唯一升级路径）+ ScheduleWakeup 90（自主轮询）。这是教科书式的 read-only audit 模式。
- 抓到的 bug 链 M002/M003/M004/M005/M006/M008/M011/M016/M017/M018 全部由 Reviewer 首发。其中 M002 (controller 预算+pool 三层 bug) 和 M017 (ghost process) 是 forensic-level 调查。
- M011 撤回 D030 时用论文形式定义 (EMA α=0.5) 验算 S̃_2 < S̃_1，直接保住核心 claim。
- M009 自纠错：Reviewer 自己在下一轮 wakeup 时发现之前的 sign-error 判定基于错误记忆（用了 Δ̃_t - Δ̃_{t-1}），主动撤回。**没有 Director 反向施压触发**，是 self-audit 模式。

**问题**：
- **从 review 漂移到 analysis**：Reviewer 经常做"独立重算 2.43×"、"独立做 phase diagram topology 命名"、"独立做 alternative EWS 分析"。这些本该是 Agent/Worker 做的事被 Reviewer 接管，导致后来这些分析变成 Reviewer 自己要 review 的内容，**责任边界模糊**。
- **M009 sign-error 假撤回链**: Reviewer 在 5/18 撤回了正确的 sign-error 判定（基于对原始公式的误记忆），如果 Director 当时按撤回结论改回，论文里就会留 sign error。Director 也没去查 git diff 核实 — 互信但缺校验。

### Paper Agent (5 sessions, 3.3k turn, 17 errors)
**做得好**：
- paper_compile_and_check 44 次 — 高频 LaTeX 编译验证。
- spawn_worker 11 次（让 paper-worker 写章节），try 了分工。

**问题**：
- session_count = 5 太少：累计 11,642 min 中很多时间是 idle/wakeup，但分到的 turn 只有 3.3k，是 Director 的 1/4。Paper Agent 在"页面飘了"、"abstract 200 字"、"AI 味"这些图文格式问题上**显著依赖用户兜底**（任泓赫 / 周俊伟 / 运维消息）。
- 没有把 Reviewer 已验证的 21 篇 literature_map.yaml 转化为强制约束 → M008 幻觉引用直接污染 Related Work。
- 5/24 Round 3 截稿前还在改 abstract 词数（用户提醒 "200 word" 才发现 195）— 自我格式检查覆盖不足。

### Worker (380 sessions, 26.5k turn, 42 errors)
**做得好**：
- ssh_read_only 7075 + ssh_execute 1660 = 8735，是 SSH 操作主力。
- update_registry 70 次 — 有注册习惯但远不及 Agent (408)。

**问题**：
- **结构性 cleanup 缺陷**: 64 nohup 启动 vs 48 kill -9 + force_killed，结构性少清理。所有 nohup 命令都是裸 `nohup python ... &`，没有 setsid / PID file / process group / trap cleanup。Worker session 结束后启动的进程不可达。这是 M001/M016/M017/M018 的共同根因。
- **路径下划线/连字符**: 全局统计中 `spectral_collapse_ews`（下划线，本地正确）出现 34,436 次，`spectral-collapse-ews`（连字符，服务器正确）只出现 33 次。Worker 默认抄本地项目名，需要 Director 实时纠正。
- **每次只改一个变量**: M015 exp_022 三次启动失败 — 第一次修路径丢 conda，第二次仍失败，每次只改一个变量没有重组完整命令链。
- **任务范围扩张**: M016 "找 Gen 10 checkpoint 跑 SVD" → fallback "从头重训 10 代" — Worker 默认"完成任务比 escalate 重要"。
- **平行启动 = 假 ghost**: M017 PID 986901 不是 daemon 重启而是另一个 worker session 用相同 nohup 命令字符串平行启动，因为 worker 无法发现 sibling 进程。

### 协作摩擦点
- **Director ↔ Agent**: Agent 汇报粒度问题 — M010 "样本生成中"被 Agent 总结为"Gen 4 完成"。Director 没有要求 Agent 强制以 results JSON 实际记录数为准。
- **Director ↔ Reviewer**: 信任度过高 — M009 sign-error 撤回 / M011 raw SLV 推翻 EMA 时 Director 不查 git diff 也不查论文形式定义。
- **Agent ↔ Worker**: M003 修复指令没强制 diff 反馈。M016 "禁止启动训练"没有在分析任务模板里硬约束。
- **Paper Agent ↔ Reviewer**: M008 引用幻觉本应在 commit 前由 Reviewer audit，实际是 Round 1 reviewer 发现的（外部）。

## 5. 关键发现

按严重程度排序。

### F1 [HARNESS, CRITICAL] Worker 启动的后台进程没有"claim before launch"原语，导致结构性 ghost / unregistered job 问题

**证据**:
- M001 (5/17): exp_003 孤儿进程 PID 77668 与正式实例 PID 78074 并行写同一 checkpoint 目录。
- M013 (5/21): 磁盘 132G 占用直到 IOError 才发现 — 训练脚本没有 pre-launch disk check。
- M016 (5/24): ε-clipping worker 在 GPU 0 启动 10 代重训练与 exp_023 抢资源。
- M017 (5/25): exp_024 PID 986896 被 kill 后 PID 986901 以相同命令字符串在 8h 后从另一个 worker session 启动；forensic 调查发现没有 daemon/cron/tmux，是**平行启动**。
- M018 (5/25): nohup 后台 SV 提取 + r=0.2 重生成占 GPU 但 registry 显示 0 RUNNING。

**根因**: Worker 用 `nohup python ... > log 2>&1 &` 裸启动，无 setsid / PID 文件 / 进程组 / 退出 hook；`register_artifact` 是 post-hoc 写入，不是"我现在占用 GPU N 跑 command X"的活动声明。`submit_training_job` 有标准进程管理但 Worker 在 fallback 路径下 bypass 它。

**严重程度**: 直接导致 ≥25 GPU·h 浪费，并多次产生"registry 显示空闲但 GPU 实际繁忙"的调度幻觉（包括在 DDL 前 24h 的关键时段）。

**改进建议**:
1. 新增 MCP 原语 `claim_gpu_slot(server, gpu, command, expected_duration)` → 写入 registry running_jobs 表后才放行 `ssh_execute` 长时间任务；超时未续约自动释放。
2. 强制所有 nohup 启动必须用 `setsid + PID file + trap EXIT cleanup`，由 spawn_worker 模板封装，Worker 不能自己手写 nohup 命令字符串。
3. 启动 GPU 任务前必须先 `nvidia-smi` 检查实际占用，与 registry 双因子确认。

### F2 [HARNESS, HIGH] Reviewer 是项目"执行良知"，但 review/analysis 边界模糊导致责任错位

**证据**:
- Reviewer 抓到 M002/M003/M004/M005/M006/M008/M011/M016/M017/M018，其中 M002（controller 三层 bug）是通过 static code audit + 结果 JSON 交叉验证完成的 forensic-level 工作。
- Reviewer 主动做了原本不属于 review 范围的分析：独立重算 2.43× → 1.67%/gen（D033 采纳）、独立做 alternative EWS topology 命名（D023 采纳）、独立 EMA 重算 r_crit（D029/D031 采纳）。
- M009 Reviewer 撤回时基于对原始公式的误记忆（实际原始 commit 80441c5 是正确的），如果 Director 接受撤回会引入错误。Director 没查 git diff 也没拒绝撤回 — 全靠 Reviewer 下一轮自纠。
- Reviewer 30/35 HARD_LIMIT_REACHED 出现 ESCALATED_SILENT (8 次) — Director 经常对 Reviewer post 不及时响应。

**根因**: Reviewer 的 prompt 让它做 active diagnosis 而不仅是验证 Director 已提结论，导致 Reviewer 经常变成"事实上的副 Director"。Director 对 Reviewer 的输出又没有强制的核实步骤（查 git diff / 重读论文定义）。

**严重程度**: 项目成果的可靠性事实上锚定在 Reviewer 的工作质量上。M009 这种 self-audit 修复说明 Reviewer 本身可能出错，没有第二层校验。

**改进建议**:
1. Reviewer 撤回 CRITICAL 判定时，Director 端必须有硬性的 `verify_via_git_diff` 步骤后才能采纳。
2. 把 Reviewer 提出的"独立重算结论"标注为 `proposed_analysis` 而不是 `verified_finding`，Director 派 Worker 复现后才转为 verified。
3. Director response SLA：Reviewer post 后 N 分钟无响应自动升级，避免 ESCALATED_SILENT 累积 8 次。

### F3 [HARNESS, HIGH] 没有"我还剩多少时间/算力"的内部 budget tracker，需要人类做时间兜底

**证据**:
- D022 (5/18 中) 用户随口一句"你有两张卡，还有好多天才 DDL"直接触发 short → long paper 扩张到 197h 实验排期。Director 没有独立的"剩余 GPU·h 能不能塞下 long paper 工作量"测算。
- D040 (5/25 21:49) 在 DDL 当晚 ~26h 余量时仍安排三线并行：bootstrap CI（CPU，快）+ GPT-2-medium r=0 seed43/44 全 10 代（≈ 10 GPU·h × 2 = 20 GPU·h）+ paper framing 重定位。GPT-2-medium 全 10 代物理上不可能在 DDL 前跑完。
- 用户 5/25 19:31 必须直接说"这都啥时候了，还做实验呢？""我准备直接投了，不要再做了"才停下。
- exp_026/exp_027（DDL 当晚启动）因 SSH 失联被自动标 failed，留下两个无用的 registry 条目。

**根因**: Director 没有 budget primitive：剩余 GPU·h、剩余工程时间、修复一个 bug 的预期耗时。Decision rationale 中经常出现"时间可行"这种定性判断但没有量化。

**严重程度**: 直接导致 DDL 当晚资源浪费，也是用户介入最频繁的窗口。

**改进建议**:
1. 新增 `time_budget_left()` / `gpu_hours_left()` 工具，Director 在每个排实验决策前自动调用。
2. Decision schema 强制要求 `wallclock_estimate` 字段，被并入 budget 计算。
3. DDL 前 24h 自动触发 "freeze new experiments, only finish in-flight" 模式。

### F4 [HARNESS, HIGH] Worker SSH 命令缺乏组合性 — 路径、conda、环境变量、GPU 参数每次重写易错

**证据**:
- M014 (5/24): exp_022 用 `/root/spectral-collapse-ews` 应为 `/root/spectral_collapse_ews`（实际两种都有，Worker 经常抄错），同时 `--gpu 0` 与 `cuda:1` 分配不一致。
- M015 (5/24): exp_022 第一次修路径时丢掉 conda activate；第二次仍失败。Worker "每次只改一个变量"模式。
- 全局 grep: `spectral_collapse_ews`（错误的本地下划线版）34,436 次 vs `spectral-collapse-ews`（服务器正确连字符版）33 次。Worker 默认抄本地项目名。
- M005 (5/17): 裸 nohup 启动绕过 submit_training_job 标准进程管理，监控钩子误判 failed。

**根因**: SSH 命令是 Worker 自由组合的字符串，没有模板/strong typing。命令链至少包含 4 步（conda activate, cd, env vars, python），任何一步缺失都直接失败。

**严重程度**: 累计 ≥4 次实验启动失败重试，每次 ~30 min Director-Worker 来回沟通成本。

**改进建议**:
1. `spawn_worker` 模板必须包含 `remote_run(project_id, conda_env, gpu_idx, command)`，Worker 不能自由写 nohup 字符串。
2. 项目命名前期统一：本地与服务器路径用同样的 ID（在 project.config 里写死，禁止下划线/连字符双写）。
3. M005 学到的教训：自动监控不应对 manual-launched 实验生效，需要 `monitoring_mode` 字段。

### F5 [MODEL, HIGH] Paper Worker 在没有强约束时大量幻觉引用（Related Work + Introduction 50% 错误）

**证据**:
- M008 (5/17–5/21 持续暴露): Related Work 14 处 cite 中 7 处幻觉（bib key 编造、论文内容编造）；Introduction 3 处幻觉；全文 ≥10 处虚假引用。
- 这发生在 literature_map.yaml 已经有 21 篇已验证条目的情况下 — Worker 没有强制从这里选。
- 同类问题在 ML 论文写作场景普遍存在（多个项目反复观察）。

**根因**: Model 默认行为是"凭训练知识写最像 related work 的段落"，而不是"只引用我能验证存在的文献"。Paper Agent prompt 没有把 "只能用 literature_map.yaml + references.bib 中已有条目" 写成 hard constraint。

**严重程度**: 如果未被 Reviewer 抓到，会直接 desk reject。被 Reviewer 抓到后引发 ~1 天重写 Related Work + 全文 cite 审计成本。

**改进建议**:
1. Paper writing skill 默认加 hard rule: "任何新 \cite{} 必须先 WebSearch 验证 + 写入 references.bib，否则 lint fail"。
2. Pre-commit hook：grep 所有 `\cite{}` key vs references.bib，缺失 key 自动阻断 commit。
3. 区分 model 能力问题（必然发生，需 guardrail）vs harness 问题（一次性配置）。这是 model 问题，guardrail 不能省。

### F6 [MODEL, MEDIUM] Director/Agent 在压力下接受 Agent 不严谨的汇报，无主动核实习惯

**证据**:
- M010: Worker "样本生成中"被 Agent 汇报为"Gen 4/5 完成"，Director 没要求以 results JSON 实际记录数为准。
- M011 (D030): Agent 用 raw SLV 报告 r=0.25 "单调上升"得出 r_crit < 0.25，Director 直接采信而没对照论文 EMA 形式定义验算。Reviewer 在下轮拦截。
- M009: Reviewer 撤回 sign-error 判定基于对公式的误记忆，Director 没去查 git diff（实际 commit 80441c5 是正确修复），差点采纳错误撤回。

**根因**: 压力下默认信任下游角色的总结，不查 raw evidence。这是 model 行为问题（人类研究者也会这样）但在自动化系统中没有强制核实步骤会放大错误传播。

**严重程度**: 中。所有这些都被 Reviewer 兜底了，但兜底机制依赖 Reviewer 不出错（M009 已经显示 Reviewer 也会出错）。

**改进建议**:
1. Director-side 强制核实步骤：bound/threshold 判定必须显式标注使用的指标版本（raw vs EMA-smoothed vs normalized）。
2. 关键 claim 修改前自动 `git diff` 对应代码/论文段落。
3. Decision schema 加 `evidence_source` 字段（registry / results JSON / paper.tex line / git commit），不接受 free-text rationale。

### F7 [HARNESS, MEDIUM] 项目自检/合规项需要用户兜底，paper-audit 子角色未充分使用

**证据**:
- 5/24-5/26 用户/运维消息推送：AI 使用披露（要求"不要改动以下文本，直接复制粘贴"）、ARR OpenReview 表单提示、S3 backup、anonymized repo push、引用幻觉自查、缩写定义检查、ACL 模板对齐、forward reference 检查。
- Layer 1: paper-audit-visual 2 session 11 min，paper-audit-content 2 session 8 min，paper-audit-review-visual 4 session 11 min。**总计 ~30 min 用于 paper audit，与 Paper Agent 11,641 min 不成比例**。
- 任泓赫 / 周俊伟 micro-fixes：figure legend、abstract 195/200 字、dash overuse "AI 味"、附录表格飘页 — 都是格式问题被用户提醒后才修。

**根因**: 投稿 checklist（AI disclosure / anonymization / forward reference / cite consistency / ACL format）不是 harness 自动跑的硬约束，依赖人工触发。paper-audit 子角色被设计但未在 Paper Agent loop 中强制调用。

**严重程度**: 单个 issue 不致命但累计是 DDL 前 48h 用户精力的主要消耗。如果 ARR desk check 抓到 anonymization 或 AI disclosure 不合规会被 reject。

**改进建议**:
1. paper-audit-content / paper-audit-visual 应作为 Paper Agent 每次 commit 前的强制 lint，而不是依赖外部触发。
2. Submission checklist 转为 yaml schema，Director 在 submit 前必须 go-through。
3. AI disclosure / anonymization 等模板化文本应该作为 project config 写死，复制粘贴时少改动。

### F8 [MODEL, MEDIUM] 4 轮 reviewer fresh review 始终给 3.0 — 主要问题是 framing 错配 + 统计严谨性，不是数据缺失

**证据**:
- Round 1 (5/21) = 3.0; Round 2 (5/23) = 3.0; Round 3 (5/24) = 3.0; Round 4 (5/25) = 3.0。**4 轮 fresh review 评分完全不变**，尽管期间补了 cross-arch、bootstrap CI（部分）、多 seed、记号统一等。
- Round 4 MF-3 直接指出 "Early Warning Signals" 标题与"r ≥ r_crit 时信号消失"的核心发现存在结构性矛盾 — 这是 framing 问题，不是补实验能解决的。
- Round 4 MF-1 指出 r_crit 在 Abstract 是 {0.2, 0.5} discrete set 而 §3.2 是 (0.25, 0.3] interval — 这是基础写作 consistency，4 轮没改过。

**根因**: Paper Agent / Director 在每轮 review 后修补具体 issue 但不重新思考 framing。例如 R2 Round 2 已经说 "controller 从未闭环部署" + EWS framing 设错了 expectation，但论文最终也只是把 controller 标为 "testbed" 不改标题。

**严重程度**: 是项目"为什么 3.0 → 3.5 不上去"的核心解释。最后封版前还在改具体 issue 而不是 reframe。

**改进建议**:
1. 每轮 review 后 Paper Agent 必须输出 "structural issues vs surface issues" 拆分，structural issues 必须重新讨论 title/framing。
2. Director 应主动调用 Reviewer 做 "如果改标题为 X 这些 critical 是否都消失" 的反事实模拟，而不是逐条修。
3. 接受"3.0 → 3.5 必须 reframe 而不是补实验"作为决策准则。

### F9 [HARNESS, MEDIUM] Director 重启即重读全文 — boot 上下文消化成本结构性高

**证据**:
- Director 8 次 BOOT_STARTED + 29 BOOT_COMPLETE（重启 + retry），平均每次 boot 后要读 decisions.yaml (635 行) / mistakes.yaml (251 行) / registry.yaml (2504 行) / memory.md / paper_framing.md (260 行)。
- Layer 1: Director output token 4.3M / 12.9k turn ≈ 333 token/turn — 这个比值显著高于 Worker (10.5M / 26.5k ≈ 396) 但低于 Agent (6.3M / 14.6k ≈ 431)，说明 Director 多数 turn 是对话而非操作，但每次 boot 后的 catchup 占了相当 token 预算。
- Ralph timeline 显示 Director 每次 HARD_LIMIT_REACHED 后必须写 handoff_length_chars ~ 2400 字符的硬约束/进度/上下文文档。

**根因**: Director 没有持久化 working memory，每次 reset 都重建。handoff 文档要重新写"硬约束 / 红线 / 当前状态 / 下一步"。Loop 设计是 "boot → consume context → act → handoff"，但 context 消化成本是项目持续时间的线性函数。

**严重程度**: 中。9 天项目 Director 有效活跃时间 = (14813 min - boot context 时间)，但 catchup 时间难以测量。

**改进建议**:
1. Working memory tier 1: handoff 文档；tier 2: pinned summary（项目核心 claim + 当前阶段，~500 字）；tier 3: full decisions.yaml （only on demand）。boot 时只读 tier 1+2。
2. Decision/mistake 自动摘要：每天生成 "今日要事" 而不是让 Director 自己浏览全部历史。

### F10 [INFRA, LOW] AutoDL SSH 端口波动 + HF 网络偶发问题，已在 skill 中沉淀

**证据**:
- exp_026/exp_027 在 DDL 当晚因"SSH check failed 5x — last error: [Errno None] Unable to connect to port 18314 on 36.103.198.204"被标 failed。
- M017 调查中 worker 报告"模型加载时遇到 HuggingFace 网络不可达，但成功从本地缓存加载"。
- ssh-env-setup skill 中已经记录 AutoDL 端口波动、network_turbo、HF_HUB_DISABLE_XET=1 等经验。

**严重程度**: 低。已经有 skill 沉淀，且 5/25 DDL 当晚的 SSH 失联客观上配合了用户的 kill switch（如果 SSH 通了，会跑更多无效实验）。

**改进建议**: skill 已存在，只需 Worker 启动新 host 时主动加载 ssh-env-setup。

---

## 总结一句

**这个项目最大的"对"和"错"都源于同一件事：Reviewer 角色被设计得太强**。它替 Director 抓住了所有关键 bug 和统计陷阱（F2），让项目在 controller failure 后干净 reframe 到 3.0 / Findings；但同时它也吸收了本应属于 Agent / Worker / Paper Agent 的 analysis 与 audit 工作（M008 引用幻觉、M016 unauthorized GPU、M017 ghost process 都是 Reviewer 首发），使得**其他角色的 review-self / fix-self 能力没机会成长**。一旦 Reviewer 在某个具体判断上出错（M009 撤回），项目就没有第二层校验。论文最终卡在 3.0 而不是 3.5 的原因，不在数据也不在算力，而在 framing 错配（F8）和"如何系统性地改 framing"这个能力 Director / Paper Agent 都不强。
