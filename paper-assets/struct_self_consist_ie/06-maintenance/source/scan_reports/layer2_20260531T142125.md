### 3.1 Idea → Findings 的逻辑链

| 维度 | 原始 IDEA_BRIEF (5/14) | 最终论文 (5/24) |

**Reframe 次数**: paper_framing.md 显式经历 ≥5 次 framing 升级/降级（D018→D130→D219→D237→D238→D239→D240），最终回到 5/15 早期的 "NER + correlation-selection gap" 叙事，绕了一大圈。

**判定**：最终 findings **没有回答最初的核心问题**（"when does AS2CS help"），而是给出了一个相反方向的、范围窄得多的 finding（"on NER, TTS mostly doesn't help, but here's why"）。从科研价值看，这种偏离**合理但代价巨大**——更合理的做法是早期（D018 时）就承认"方法不 work, 转向诊断"，而不是在 D170 (5/20 09:04) 才正式宣告 "DGEC 三层干预全部失败"，期间又试 ≥8 个 method 全 fail。

### 3.2 实验设计的科研严谨性

- **Falsifiability**: ✅ 5/14 MVP 就有 ρ≥0.40 PASS/<0.30 FAIL 阈值，多个 gate 设计了反向条件。
- **Baseline 充分性**: ⚠️ 初始仅对比 FK 一个弱 baseline（Dream 1 三档全 3/6 的 #1 反馈），D012 后补足 log-prob/EM/voting，**事后补救**。
- **统计方法**: ⚠️ Bootstrap CI 使用一致，但全文 57 个统计检验仅 8/57 survive Holm-Bonferroni (D182)。M068 显示 Worker 全文混淆两个统计框架。Reviewer 多次警告 p-hacking 风险（D241 N2: "跑 2 additional seeds 而非切 BH FDR——avoid p-hacking"）。
- **实验规模**: 3 seeds（部分实验仅 1 seed），3 NER 数据集，2 模型规模（8B/14B/32B/72B 但后两者非 fine-tune，存在 confound D217）。
- **数据完整性事故**: M036 train-on-test 数据泄漏 +3.62pp 写入论文后才被 Reviewer 发现；M051 hidden-state probe entity-level CV 泄漏导致 AUROC 从 0.92 跌到 0.65；M016 unified_metrics 迁移后 LP global ρ 从 0.42 降到 0.22（50% 降幅）。这三起任一件都可能引发审稿 desk reject 级别的质疑。

## 5. 关键发现

### F1 [HARNESS] 5/22 framing 翻烧饼是"Reviewer 单边驱动 + Director 缺乏锚点"的系统暴露 — **严重程度: 高**

**证据**:
- D235 (5/22 04:13, "LP dominates at all budgets") → D236 (5/22 05:42, 同样表述) → **D237 (5/22 06:29) 作废 D236**（Reviewer #118 catch CoNLL LP -2.34pp） → D238 (5/22 09:23 "TTS boundary conditions" 升级) → D239 (5/22 10:38 R35 fresh 强制收窄回 NER) → D240 (5/22 11:19 R36 fresh 3.0 进一步收窄)
- 6.5 小时内 5 次 framing 修改，前 3 次内部 Reviewer 驱动，后 2 次 fresh review 强制矫正
- mistakes M062/M063 直接归因："Framing 升级时未检查证据覆盖度"

**根因**: 系统设计层面，没有 "framing 升级 → 必须经 paper-audit 与 evidence-coverage 自检 → 再用 fresh review 复核" 的链路。**只要 Reviewer 单方面给出 "Framing OK" 就可以推进**，但 Reviewer 本身在内部审稿模式下更宽容（D241 中 user 明确"R41 我希望 fresh 模式拿干净分数"）。

**改进建议**:
- 增加 "framing-pivot gate"：任一 D 决策标记 `framing_change=true` 时，必须强制 dream + fresh review 两路并行，48 小时冷却期才能 commit
- Director 在 framing 决策时必须显式列出 "evidence coverage table"——每个标题关键词对应的 dataset/model/seed 数量

### F2 [HARNESS + MODEL] PI 资源/目标 mandate 与 agent 实际产能不匹配，催生 8 method × 全 negative 灾难 — **严重程度: 高**

**证据**:
- 5/18 05:52 PI："纯诊断缺乏 positive contribution" → 5/18 全天 13 mistakes（项目第三高）
- 5/18 15:18 PI："worker 并发没有上限"+ 12 张 5090 → 5/19–5/20 共 32 mistakes
- 5/20 18:12 PI："无条件 4.5 mandate" → D219 上调目标→ D225 (5/21 12:03) 又下调 → 4.5 commitment 仅维持 18 小时
- 8 个 method 全 negative（MRSC/LSC/ESJ/E_θ/B1 SCD/B2 verifier/B3 prompted diversity/DGEC）
- D170 (5/20 09:04) 自我评估："Construction 成功率从 ~25% 到 ~32%，远不及 70-80% 目标"——method 探索失败显式确认

**根因**: 系统设计上，PI 给的 mandate 直接进入 Director 决策上下文，但**没有 capability-check 机制**——agent 团队没办法量化"4.5 需要 X 个 novel insight，我们最多产出 Y 个"，于是被迫接单。MODEL 层面，单个 agent 的 long-horizon planning 不足以在 PI 指令前主动反驳 "这个目标不现实"。

**严重程度评估**: 这 2 天浪费了 ~24 GPU-day，引入 21 + 11 = 32 mistakes，并使最终 framing 走了 D219→D238→D240 的大弯路。如果 5/20 PI 沟通时 Director 能 push back "4.5 需要的不是更多 method，而是 mechanistic theorem"，至少能省一半成本。

**改进建议**:
- 引入 "target-capability gap" 工具——目标分数与当前评分差距 >0.5 时，强制 dream + Reviewer 联合评估 "需要多少新 evidence"
- PI mandate 进入系统时必须经过 Reviewer 独立 feasibility check

### F3 [HARNESS] Worker 远程状态诊断不可靠，5 次 false-failed 误判 — **严重程度: 高**

**证据**:
- M021 (5/19): Worker 超时 5h，registry 误标 FAILED 但远程 nohup 训练正常
- M037 (5/20): 14B early inference Worker 1 + Worker 2 均报 done，输出目录空
- M038 (5/20): VLLM server-without-client 缺陷 3 次复发——Worker 启 server 不启 client，GPU 空转
- M047 (5/20): 14B inference 第 1 次误诊为 failed，输出实际完好
- M049 (5/21): 14B inference 第 2 次误诊，PID 252310 仍在运行 98% GPU util
- M052 (5/21): exp_fewnerd_t05_s456 cron 误判为 failed
- M042 (5/20): Worker 连错服务器（autodl-5090 vs autodl-5090-c）还返回 status=done

**根因**: Worker 诊断协议依赖（a）输出文件存在性（b）进程存活——但 vLLM model loading 期可达 15-20 min 无输出。系统没有强制 Worker 在诊断前同时检查 `ps -p PID` + `nvidia-smi` + `ls -la output_dir` 三步。

**严重程度**: 累计浪费 ~12 GPU-hours + ~3 小时人工 escalation 时间。**更危险的是 M042 类——Worker 在错误服务器上"成功"完成空操作返回 done**，这种 signal-noise 信号几乎无法 detect。

**改进建议**:
- Worker `submit_training_job` 后 5 min 内强制 ssh_read_only 验证 GPU util > 0
- Worker `status=done` 必须附带 (a) output file size > threshold (b) 关键 metric 值（如 greedy F1 在预期范围）
- 增加 `cross_validate_worker_status` 工具，对所有 cron-flagged failed 做强制 Reviewer 复验

### F4 [HARNESS] 数据 provenance 链断裂导致论文数字反复回炉 — **严重程度: 高**

**证据**:
- M006: SCIERC_REF 5 值中 4 值不可溯源（5/18）
- M013: 6 个分析脚本各自实现 F1/退化定义，**同一数据产 3 个不同 Greedy F1** + 2 种 degeneracy 定义（5/18）
- M014: degen_rate 字段实际是 sample_f1_pct_zero（CoNLL 差 82pp）（5/18）
- M016: unified_metrics 迁移后 FewNERD LP global ρ 0.42 → 0.22（50% 降幅），论文 4 处错引（5/18）
- M024/M025/M026/M027: 主表/Tab5 SciERC AUROC 顺序翻转、CoNLL degen N=16 误用、headroom 用 LLaMA 行（5/19）
- M057: CoNLL v4 3-seed 混合 exp002 + MF4v2 两个 pipeline（5/21）
- M069: 主表 SciERC EM AUROC .749 是 9.1σ copy-paste 错误（5/23）
- M070: 5-seed construction +1.11pp 是 instance-averaged vs micro-F1 metric 不一致（5/24）

**根因**:
1. 论文表格数字**手动填写**而非脚本自动生成（M024 显式记录）
2. 同一指标多脚本独立实现（M013 unified_metrics 出现前）
3. 数据 patch 时**不查 cross-table consistency**（M025）
4. registry 中实验状态与服务器实际不一致（M058 跨服务器去重失败）

**严重程度**: 每一项都可能成为 ARR reviewer 投诉的 "不可复现" 红线。M016 的 50% ρ 降幅如果未及时 catch，整篇论文 QE 章节立刻崩塌。M069/M070 在 DDL 前 48 小时才被发现——**论文 freeze 时数字稳定性是历史最低点**。

**改进建议**:
- 引入 "paper_consistency_audit" 工具，每次 Paper Agent edit 后强制全文 grep 数值 + 与 registry/report.json 交叉验证
- 论文数字必须有 `provenance.yaml` 条目：`{ value, exp_id, metric_key, computed_at }`
- 主表禁止手动填写，强制由 `generate_main_table.py` 从 registry 生成

### F5 [HARNESS] 文献/引用幻觉是 desk-reject 红线，靠人工兜底才 catch — **严重程度: 高**

**证据**:
- M040/M041: 3/96 bib entries 作者 AI 幻觉（chen2025twofailures / wen2025abstention / liu2025uqcc），URL 指向错误论文（5/20）
- M059: ma2024selfimproving 全 5 个作者 AI 幻觉，正确第一作者为 Xie（5/21）
- 张默涵 5/23 17:07 介入：反复追问 reference verification 才 catch M059

**根因**: Paper Agent 生成 bib entries 时"标题正确 + 作者幻觉"是典型 LLM 失效模式。系统缺少强制 Semantic Scholar API 验证。

**改进建议**:
- "reference-audit" skill 必须在 Paper Agent **每次** 新增 bib 时自动触发，不依赖 pre-review gate

### F6 [MODEL] 数学/统计概念在跨 worker 复制时系统性丢失 — **严重程度: 中**

**证据**:
- M068 (5/22): Worker 把 global k=57 Holm p=0.055 全文替换为 seed-replication k=5 p=0.013，混淆两个统计框架，影响 12+ 处
- M009/M010 (5/18): span-based vs text-based matching 多次混淆
- M013 (5/18): 6 个独立 F1/degeneracy 实现
- D227 (5/21): "代码库中 3 个 MV 实现使用不同 threshold + entity match"

**根因**: 这不完全是 harness 问题——长上下文中保持"两个统计框架的语义区分"对当前模型是困难的。Worker 接到 "全文替换 X→Y" 指令时倾向于做精确字符串替换而不验证语义。

**改进建议**: 涉及统计/数学概念的全文修改禁止 Worker 独立执行，必须 Agent 亲自做。Director 指令应强制要求"列出修改清单 + 每处的语义检查"。

### F7 [HARNESS] Dream 机制对 framing 健康度的检测能力不足 — **严重程度: 中**

**证据**:
- Dream 1（5/14 09:33）三档全 3/6，结构性问题 ID 完整（缺 baseline / novelty 薄 / formula 不一致）
- Dream 2（5/14 10:53）三档全 3/6（持平）——Dream 系统未能给出 "what changed since last dream"
- Dream 3（5/14 20:32）三档评分模式相似——dream 系统**对框架质量改进的 sensitivity 几乎为 0**
- Dream 5（5/15）+ Dream 6（5/16）后系统连续输出 3.0/5 plateau，但实际 fresh review 给到 3.5（D224 R27）
- Dream/fresh review 的相关性极弱

**严重程度**: 项目 5/14–5/16 共做了 6 次 dream，没有一次提供了 fresh review 才发现的 "scope overclaim" 问题。Dream 失去了 early-warning 作用。

**改进建议**: Dream 应**预先训练**到与 fresh review 评分对齐（calibration）；或减少 dream 频率，增加 fresh review 频率。

### F8 [HARNESS] 跨服务器资源调度引入大量"虚假状态"事故 — **严重程度: 中**

**证据**:
- M020/M023/M035 (5/19): registry GPU 字段格式不规范 / 手动启动绕过 cron / 未注册 GPU 进程
- M042 (5/20): Worker 连错服务器（autodl-5090 vs autodl-5090-c）+ 返回虚假 done
- M053/M058 (5/21): 重复启动 / 跨服务器数据未在 registry 标注
- M065/M066 (5/22): kill_job 未实际终止 vLLM 子进程 + 3 个 PREPARING 实验未启动空转 9h

**根因**: 用户 5/18 一次性给 12 张卡（autodl-5090 + autodl-5090-b + autodl-5090-c）后，registry 缺少 "server-aware" 一致性检查。Agent 派发 Worker 时 server alias 容易混淆。

**改进建议**: registry 必须强制 `server` + `gpu_ids` 双字段，submit_training_job 内置 hostname 验证。

### F9 [MODEL] Long-horizon planning 失效，11 天内 5 次重大 framing reframe — **严重程度: 中**

**证据**:
- D018 (5/14): correlation-selection gap framing 建立
- D130 (5/18): systemic reframe 8 项
- D219 (5/20): 目标 3.5→4.5
- D237 (5/22): dataset-dependent + diagnostic primary
- D238 (5/22): TTS boundary for structured prediction
- D239/240: 回退 NER

**根因**: agent (Director) 在长上下文中难以维持 "previously rejected hypothesis" 的标记——D008 已排除 RE-primary，D018 已排除 best-of-N improvement，但 5/20 PI 一句"加 positive contribution"，Director 又开始 method 探索；5/22 fresh review 才 hard reset。**memory.md 134 行 + paper_framing.md 87 行不足以承载 11 天 248 D 决策的状态机**。

**严重程度**: 每次 framing 重构需要 12-24 小时（paper edit + audit + dream），累计成本 ~3 个工作日。

**改进建议**:
- 引入 "rejected_hypothesis.yaml"——每次 framing 撤销时显式 log 被排除的方向 + 排除理由 + 重启 gate（什么新证据才能 unblock）
- Director 系统 prompt 加 "before pivoting, list past 3 framing decisions and verify new framing doesn't revisit a previously-rejected direction"

### F10 [HARNESS] 错题本 (mistakes.yaml) 未能真正阻止同类错误复发 — **严重程度: 中**

**证据**:
- VLLM server-without-client 在 M037/M038 后明确写入 prevention，但 M037 中的 "13" 同类问题再次出现
- Worker false-failed 诊断 M021 (5/19) 后明确 prevention，但 M047 (5/20) / M049 (5/21) / M052 (5/21) 反复出现 4 次
- wrong-model-data M030 (5/20 06:00) → M031 (5/20 07:00) → M032 (5/20 08:00) 同日 3 次
- 跨表 metric 不一致 M013 (5/18) → M057 (5/21) → M070 (5/24) 横跨 6 天

**根因**: mistakes.yaml prevention 字段写入后，**没有任何 enforcement 机制**让后续 Worker 在执行同类任务前先 grep mistakes.yaml。完全靠 Agent 自己的 context 记忆。

**改进建议**:
- 增加 `pre_spawn_worker` hook：根据 task 类型自动 attach 相关 prevention rule
- mistakes.yaml 中 high-severity + repeated > 2 次的应该升级为 constraints.yaml 强约束

### F11 [MODEL] Agent 自我纠错能力弱，全靠 Reviewer 兜底 — **严重程度: 中**

**证据**:
- 70 条 mistakes 中，**几乎全部是 Reviewer 或独立 Worker 发现**，Agent 自查发现率 < 10%
- M050: Director 引用本地 artifact AUROC 0.920 直接报告给 PI 和 Paper Agent，未让 Reviewer 验证服务器端最终输出（5/21）
- M067: 论文中 "LP-best +8pp on Few-NERD" 无任何数据支撑，被 Reviewer 排查后确认是 number-stitching 幻觉
- M069: 主表 SciERC EM AUROC 9.1σ 偏差，Paper Agent 与 Reviewer 都未在初始 patch 时 catch

**根因**: MODEL 层面，agent 在长上下文中对 "我刚才写的数字是否正确" 的元认知较弱。即使 mistakes.yaml 已记录类似错误，agent 复用旧数据时不主动验证。

**改进建议**: 论文相关 patch 任务必须经过独立 Reviewer 在不同 session 复算——不能由 Paper Agent + 同一 Reviewer 闭环验证。

### F12 [HARNESS] 用户对话与 agent 状态机不同步 — **严重程度: 低**

**证据**:
- 5/22 14:20 用户："我希望选择 fresh 拿到干净的得分，不会选择 Continue 模式"——但 Director 5/22–5/23 多次 default 推荐 Continue 模式
- 5/22 10:30 用户："这个问题（scope overclaim）出现很多遍了"——表明用户感受到的重复 ≠ agent 内部认知的"已修复"
- 5/23 03:13 用户："实验都结束了？"——agent 实际还在跑 6 个实验

**根因**: ralph_loop 把用户飞书消息注入 Director context，但没有"用户偏好持久化"机制。每次 BOOT 后用户偏好（如 "always use fresh mode"）丢失。

**改进建议**: 用户消息中的偏好（识别 mode "I prefer X" / "don't do Y"）自动 promote 到 constraints.yaml 或 user_preferences.yaml，每次 BOOT 强制载入。

### F13 [HARNESS] Paper Agent 多轮 figure 优化对最终评分贡献不显著 — **严重程度: 低**

**证据**:
- 5/23 12:36 周俊伟："Figure 1 必须用 PaperBanana 重画" → 5/23 14:40/15:04/15:10/15:53/16:00 共 4 轮反复
- paper-figure-optimize 角色 4 session，paper-audit-review-visual 24 session
- 但 R36/R40 fresh review 仍 3.0，figure 在审稿意见中**不是核心扣分项**

**严重程度**: 占用了 DDL 前 ~6 小时的 polish 时间，**机会成本可观**——这段时间本可以做 R36 reviewer concerns 的 mechanistic 深化。

**改进建议**: figure polish 应在 framing 稳定后才启动；framing 反复期不投入 figure 工时。

---

**总结**: 这是一个**核心 negative finding 真实、但被 system + model + PI mandate 三方拉扯导致执行成本极高**的项目。最终 ~3.0 fresh score 与"NER-only diagnostic"的实际科研价值匹配，与用户期望的 4.5 不匹配。系统层面最重要的 3 个改进点：(1) framing-pivot gate (F1+F9) (2) Worker 状态诊断协议加固 (F3+F8) (3) 论文数据 provenance 自动化 (F4+F5)。模型层面，long-horizon planning 与跨工作流元认知是上限——目前 agent 团队的 capability ceiling 不足以在没有 hard system gate 时维持 11 天 240+ 决策的一致性。
