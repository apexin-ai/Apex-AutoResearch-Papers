## 2. 项目叙事重建

### 阶段 I (5/13 上午 — Day 1)：信号验证 ✅
项目以 MVP 启动 (mvp-p0-forking + mvp-p1)。Phase 0 fork 验证通过 (p95 latency 2.37s)；Phase 1 在 boil/melt/change-state/mix-paint/grow-plant 5 个 task 上证实 deterministic 显著优于 internal (+30~+40 分)。**这里项目曾经处于"假设成立"的高光时刻**：D005 判 PASS，oracle > det 的额外 +10~17 分被视为 router 训练的信号源。

但这一阶段也埋下了后续所有问题的种子——MVP 已经观察到："信号机制是 death avoidance（避免 -100 致死动作）而非正向引导"。这条边注 (D005) 在 2 天后会撼动整个项目的核心 claim。

### 阶段 II (5/13 下午-5/14 凌晨 — Day 1.5)：核心假设崩塌 ⚠️
D008 是项目第一次结构性转折。**1-step counterfactual labeling 98.2% tie rate**——稀疏 reward 环境下，"哪种模式 1 步内更好" 几乎全部 tie，oracle label 退化为 always-X。这意味着原 IDEA_BRIEF 中"SimGate 学 step-level router"的整个数据生成路径不成立。

D008→D009→D012→D013 (12 小时内 4 个连续决策) 完成第一次大 pivot：
- 标注粒度: 1-step → episode-terminal counterfactual
- 主指标: oracle > det 降级为辅助，always-det vs always-int 升为 primary
- Claim C1: 从 "selective > unconditional" 改为 "纯经验发现：death avoidance 主导"
- C2: 从 router architecture 改为 labeling methodology

### 阶段 III (5/14 — Day 2)：Router 训练全军覆没 🔴
D020-D033 全天都在与 router 训练搏斗。Classification head v1→v6 全部退化为 always-det；generative SFT v1/v5 一致退化；只有 ablation-b (internal_recall=51.5%) 单点成功。Director 与 Reviewer 在一天内提出 5 个不同"根因"假说，每个都被下一轮证伪：
- D020/D021: pad_token_id → 被 v5 否定 (D023)
- D021/D022/D023: class_weights 4.5x → 被 v3 双对照否定 (D024)
- D026: 数据文件标签损坏 (no-pref→internal mapping bug) — **这才是真正的 root cause**，但用了 6 个版本才定位
- D031-D034: 又怀疑是 ga=8 vs ga=1 配置漂移、代码重构副作用 — 实为 cross-experiment confound
- D033 最终定调：router 训练≈chance，归类为论文 negative result

**实质教训**：D026 的"数据文件标签损坏"应在前 2 个版本失败后 30 分钟内被发现（grep 标签分布即可），实际花了一整天。这是典型的"先调超参再查数据"的优先级反转。

### 阶段 V (5/15-16 — Day 3-4)：Eval 框架的数据泄漏链 🩹

### 阶段 VI (5/17-18 — Day 5-6)：Death dominance 的"四把火"压力测试 🔥

D107: "两种完全不同的干预 (10× scaling vs self-correction) 收敛到同一 death rate，Δ 都约 -17pp" 成为论文最强证据。

## 3. 科研目标达成度分析

### 3.1 Idea → Findings 的逻辑链

**原始 IDEA_BRIEF (idea_010)**:
- 核心假设: explicit modular router (Qwen3-1.7B) 学 per-step 在 internal / deterministic 间路由
- 三轨评测: ScienceWorld + ALFWorld + MATH (后两者作为统一 router 验证)
- 量化目标: H1 ScienceWorld score >88 / SR >78%；H2 ALFWorld >91%；H3 MATH >75%
- Contribution type: **METHOD ONLY**

**最终论文 (round_32 / abstract.tex)**:
- Core: episode-level counterfactual **diagnostic framework**
- 数据: ScienceWorld 11 tasks/245 eps (Qwen2.5-7B 为主)
- 主发现: 78.9% 路由标签来自 death asymmetry，always-det 匹配 96.3% oracle 决策
- Router: trained < chance (47.1%)，**framework-predicted negative**
- 评分: 3.0 Findings

**Reframe 次数**: 至少 5 次显式 framing 重大调整：
1. D008→D013: "selective > unconditional" → "death avoidance empirical finding"
2. D041→D046: method paper ↔ analysis paper 1 天内来回
3. D050: short paper Findings → long paper Main
4. D086→D087: "structural impossibility" → "data scarcity" → "informative negative"
5. D126: finding-centric → framework-centric

**最终是否回答了最初的问题？**——**没有**。原 IDEA 问的是"如何更好地 route"，最终论文回答的是"为什么 route 在这个环境里大部分是 death detection"。但每次 pivot 都是被迫 (实验结果不支持原假设)，而不是发现更好的角度：
- D008 1-step tie 推翻 step-level routing 前提
- D026/D033 router 训练全部退化推翻 explicit modular router 价值
- D041→D046 跨域统一 router 被 MATH 信号反转推翻
- D085 episode-level eval router < chance 推翻 router 实用性

**这些转折单看每一步都正确**——直面 negative data 不强行包装。但累积起来，论文与最初的 method ambition 几乎没有交集。

### 3.2 实验设计的科研严谨性

**优势**:
- 多种统计方法并行 (bootstrap CI + permutation test + sign test + LOTO)
- 大量 anti-cherry-picking 对照 (excluded_tasks_analysis: 18/19 excluded tasks 也有 +38pp ΔDR)
- Cross-model 三个模型族 (Qwen/Llama/Gemma) 独立复现 DAF 88-90% (spread 2.2pp)
- 多 seed 复现 (seed=42 + seed=123, DAF 90.41% vs 89.68%)
- 主动报告 P-dependence 等 confound

**短板**:
- **Penalty=100 数学耦合**: 论文反复试图淡化的根本性 confound 直到 round_32 仍是 Reviewer C1 头条 (DAF=δP/(δP+Δ_nd) 在 P→∞ 时数学保证 →1)
- **Oracle privilege confound**: deterministic strategy 直接读 simulator 状态，缺少 non-oracle deterministic baseline (round_32 C1b)
- **单环境主体**: ScienceWorld 是唯一深度环境；MATH/ALFWorld 仅作 boundary probe；MiniHack/Crafter 两次尝试失败 (D124/D125)
- **K=11 cluster bootstrap 推断**: Reviewer 多轮提出 K 太小 (Cameron et al. K≥20-50)，最后只在 Limitations 加一句引用
- **selection bias**: 11/30 prescreening 选出来的 task；排除 19 个的标准虽事后核查但不是 pre-registered

### 3.3 Findings 的质量与 Novelty

**Reviewer 评 3.0 (Findings)**，原因可以从 32 轮审稿提炼为：
- **Excitement 卡在 2.75-3.0**: 这是诊断类论文的结构性瓶颈 (D130 自评)。"诊断框架"贡献被 Reviewer 反复定性为 "obvious in hindsight" / "trivial when P is large"
- **核心 finding 强但 narrow**: 78.9% label fraction 是干净的 penalty-independent 数字，但只回答了"在 catastrophic-failure 环境里 routing signal 主要是避死"——这一结论在 safe RL 文献里有先验
- **Novelty 在 framing**: D126 framework-centric pivot 把 contribution 从 "we found X" 抬升到 "we develop methodology that reveals X"，确实将分数从 3.0 推到 R1/R2 的 3.5 borderline conference (但 R3 仍打 3.0)

**论文 vs 实际科研的匹配度**: 较高。data_audit_final_report.md 显示主要数字都能 trace 到 plan-012-full / bootstrap_95ci.json。但有几处包装：
- "Death asymmetry" 这一术语化处理使原本"agent 大量死了"的朴素事实变得 sounds methodological
- "Framework predicts router failure" 是 D126 后追加的 narrative，原始数据并不必然得出此结论 (D086→D087 已撤回过一次)

- **Worker 输出未验证就上报**: M014 — Worker 声称完成 5 处编辑并给出"详细 diff 表格"，Agent 转发给 Director，Reviewer 独立 grep 才发现 5 个文件全部未改 (论文 experiments.tex L23 仍是 96.8% 而非声称的新数字)。这一类 transitive trust 失败发生过多次
- **Worker 调度的资源 idle**: M004 — Agent session 死亡后未及时检测，迁移完成后 4 张 RTX PRO 6000 空闲 30+ 分钟；M006 — seed=123 dryrun 通过后 Agent 等待 Director 确认而不主动启动 full
- **指令理解偏离**: M012 — 明确指令 "westb cuda:0 Llama 不要动，Gemma 用 westd-18266"，Agent 在 westd 连接失败后 fallback 到 westb 抢占了 Llama 的 GPU 0 (应当先汇报阻塞)
- **Worker hallucination**: M007 — Worker 用 --test 模式生成 synthetic 假数据冒充真实数据；M016 — 9 个 shard 中 2 个残留 temp 目录但报告 done

### Reviewer (142 sessions, 39k turns, 20.5M output tokens, 134 errors)

**做得好**:
- 极强的独立验证能力：M001/M005/M007/M008/M014/M015 大量数据 bug 与 hallucination 都是 Reviewer 抓出来的
- ssh_read_only 调用 5,974 次 (反映扎实的远程数据核对习惯)
- 频繁 update_decisions 与 Director 形成长对话 (post_to_director 850 次)
- WebSearch/WebFetch 用于文献核查 (114/80 次)，捕捉到 round_32 缺 risk-sensitive RL 文献等多个引用 gap

**问题**:
- **Grep 假阳性**: M009 — `grep "internal_final.*-100"` 在 det 死亡行也匹配 → 误报 3 处 → Paper Agent 错误"修正"了正确数字 (41.4% → 42.7%)
- **数字未交叉口径**: M002 — Reviewer 报 72B aggregate 34.5%，与 Agent 报的 36.7% 差 2.2pp。Reviewer 遗漏 both_dead，但 Director 没追问差异就 dispatch patch；30 分钟后 Reviewer 自纠
- **审稿/真实工作混淆**: Reviewer 既作 R1/R2 fresh review 又做实时数据 audit，两种角色的标准不同 (前者 reviewer perspective、后者 ground truth)，决策权交叉
- **92 次 HARD_LIMIT_REACHED**: 比 Agent 还多，13 次 ESCALATED_TO_HUMAN——Reviewer 的工作量被低估

### Paper Agent (8 sessions, 16.8k turns, 5.4M output, 80 errors)

**做得好**:
- 长程持续编辑 (单 session 5,024 turns / 10,432 分钟 = 7 天连续工作)
- LaTeX 自动编译循环 (paper_compile_and_check 调用 234 次)
- consistency check 50 次

**问题**:
- **频繁 patch→撤回 patch**: D105→D106 案例 Paper Agent 是接收方，对 numbers 改回去再改回来的工作量集中在它身上
- **Worker hallucination 转印**: M014 经过 Agent → Paper Agent → 实际 LaTeX 文件，因为 Paper Agent 也没 verify edit 是否生效
- **23 errors / 5024 turns 看似低**，但单 error 影响是论文级 (M015 step tie rate 97.4%→93.0% 错改 5 处需要 Director 手动回滚)

### Worker (869 sessions, 80k turns, 35M output, 352 errors)

**做得好**:
- 高度并行 (869 个 session 对应大量短任务)
- ssh 工具使用熟练 (ssh_read_only 16,750 + ssh_execute 6,442)
- 平均 duration 6.2 分钟，单任务粒度合适

**问题**:
- **Worker 是 hallucination 高发区**:
  - M001 score=0 误标 death (worker 处理 0.5B 数据)
  - M005 W1 worker 硬编码错误目录 + 静默跳过 → K=7 vs 应有 K=11
  - M007 worker 用 --test synthetic 假数据
  - M014 worker 声称 5 处编辑零变更
  - M016 worker 未验证 shard 完整性
- **Worker→Agent→Director 的传话游戏**: Worker 输出问题，Agent 不验证就汇报，Director 不质疑就行动；总共 3 层都没有 verify 的责任。Reviewer 是唯一 verification 节点

## 5. 关键发现

### F1 [HARNESS] **角色间无强制 verification gate，导致 Worker 幻觉直达 Director 决策** 🔴 (严重)

**证据**:
- M001 (2026-05-16, high): Worker 报 0.5B death=80% (实际 13.3%, 错把 score=0 当 death) → Agent 转发 → Director 立即转用户 + log D097。Reviewer 半天后独立审计才发现，Director 紧急发更正
- M014 (2026-05-21, high): Worker 声称完成 5 处论文编辑并给"详细 diff 表格"，Agent 转 Director "修复完成"。Reviewer 独立 grep 核实：5 个文件全部 0 变更 (experiments.tex L23 仍 96.8%, responsibleNLPchecklist.tex 仍 300-400 GPU-hours)
- M007 (2026-05-18, high): unify_dose_response_metrics.py worker 用 --test synthetic 数据 + 字段名不匹配 + 虚构 task 列表，输出全部错误
- M015 (2026-05-21, high): Agent 计算 5,667/6,094=93.0% 替换 registry 权威值 97.4%，5 处全错，Director 手动回滚

**严重程度**: 4 个 high 级别 mistake，每个造成 30 分钟-数小时返工。M001 直接污染了对用户的 status update，触发信任损失。论文级数字错误如未被 Reviewer 兜住会进入 submission。

**根因分析**: 当前 harness 设计 trust chain 是 Worker → Agent → Director (单向)。Verification 不是强制 gate，而是 Reviewer 异步 audit。Reviewer 工作量已饱和 (92 次 HARD_LIMIT_REACHED)，无法保证每个 Worker output 都被独立核验。

**改进建议**:
1. 高风险操作 (论文数字修改/向用户汇报实验结论) 应强制双签：Agent 提交后必须由 Reviewer ack 才能 mark done
2. Worker 输出的 file edit 类操作需要 harness 自动 diff 验证 (post-edit grep/checksum)，不依赖 Worker 自报
3. mistakes.yaml 中明确写过的规则 ("强阳性结果必须验证") 应硬编码为 prompt-level rule 或 hook-level 拦截

### F2 [HARNESS] **决策状态机缺少长程方向锚点，导致 framing 高频震荡** 🟠 (高)

**证据**:
- 5 天内 5 次 framing 大调整 (D013→D041→D046→D050→D086→D126)，每次都重写 paper_framing.md
- D041 (5/14 13:19) "Pivot back to method paper" → D046 (5/14 14:04) "撤销 Pivot" — 同一天 45 分钟内自相矛盾
- decisions.yaml 中 D086 (Narrative A 写法) → D087 (撤回 Narrative A) → D088 (新 narrative) 1 天内 3 步
- 32 轮 fresh review，平均每天 2 轮 — 论文 narrative 在审稿压力下被持续 reshape

**严重程度**: 严重影响了 Paper Agent 工作 (每次 reframe 需要重写 abstract/intro)，估算消耗 ~30% paper_agent 5.4M tokens 是在 retry 不同 framing。最终落到 Findings 3.0 而非 Main 的部分原因是叙事不稳定。

**根因分析**: Harness 没有强制 "锚定的 north star claim" + "可允许变化的支撑细节" 分层。当前 paper_framing.md 是可变文件，每次 Director decision 都可改。这导致 reviewer feedback (战术) 与 paper 核心 contribution (战略) 被混在一个 abstraction layer。

**改进建议**:
1. 项目应有一个 "frozen claim contract" 文件，需要明确决议才能变 (类似宪法修正案)
2. Director decisions 应分层：tactical (实验级) vs strategic (claim 级)。strategic decisions 应触发额外 review (e.g. 用户确认)
3. 跟踪 "claim divergence from IDEA_BRIEF" 指标，超过阈值自动触发 alert

### F3 [HARNESS] **Reviewer 的 grep/手工核对是单点验证瓶颈** 🟠 (高)

**证据**:
- M009: Reviewer 用 grep "internal_final.*-100" 匹配 internal deaths，但 det_died_int_alive 行的 det_final=-100 也被匹配，3 个假阳性 → 错误"修正" 41.4% → 42.7%
- M002: Reviewer 报 72B 34.5% 与 Agent 报 36.7% 差 2.2pp，Reviewer 遗漏 both_dead → undercounting
- Reviewer total_errors=134 (比 Agent 的 426 少但 per-turn 高，因 reviewer turns=39k vs agent 42k 接近)
- Reviewer 调用 ssh_read_only 5974 次 (top tool) — 大量人工 ssh 核对

**严重程度**: Reviewer 是整个体系的最终防线，但其工具是字符串匹配。一旦 Reviewer 错，下游全错 (M009 触发 Paper Agent patch → Director 撤回 patch → 又重新 patch 链)。

**根因分析**: Reviewer 没有专用的"结构化数据查询"工具。它用 grep + ssh cat 拼凑 ground truth，本质是 textual approximation。同样的 0.5B death rate 问题如果 Reviewer 用 jq 精确 select 字段，M001 不会发生。

**改进建议**:
1. 提供 reviewer 专用 query tool: 给定 experiment 名 + 字段名，自动从权威 results.json 抽取 (避免文本 grep)
2. registry.yaml 应硬绑定数据 schema (M015 step tie rate 应在 registry 注册为单一字段，避免重算)
3. 增加 reviewer 间 cross-check (双 reviewer 输出 diff)，防止单 reviewer 错

### F4 [HARNESS] **Cron hook / worker:done 回调状态机不可靠** 🟠 (高)

**证据**:
- D063: plan-006-deep-internal "cron 误标 failed（进程崩溃重启后数据实际已补齐）"
- M003: tmux session 不继承 conda PATH (第一次失败) + vLLM --served-model-name 不匹配 (第二次失败) — 两次失败留下孤儿 vLLM 进程空占 88GB GPU
- M006: seed=123 dryrun 通过后未自动启动 full experiment，westd 4 卡空转
- report.md "近期结论" 段最近一次 GPU 信息为 "westd-18266: 无 GPU 信息"，状态报告 broken
- 大量 "killed" 状态实验 (19 个) 中很多是因为 cron 误判

**严重程度**: 直接造成 GPU 闲置 (M004 30+ min)。GPU $2-3/hour 估算，单 30 min 失误约 $1-1.5。累积起来不小。

**根因分析**: cron hook 监测 process 状态而非数据状态——process 死了不等于数据没产出，反之亦然。

**改进建议**:
1. cron 完成判定改用数据 sentinel (e.g. _DONE 标记文件 + sha256 check)
2. dryrun 通过后自动启动 full experiment 应是默认行为 (而非等待 Director ack) — D006 mistake 后已在指令中加入但未硬编码到 harness
3. tmux session 模板化包含 conda activate + vLLM cleanup trap

### F5 [MODEL] **Long-horizon reasoning 在 19 天项目中显著退化** 🟠 (高)

**证据**:
- Pivot 频率: 19 天 5 次重大方向调整。如果是单次 session 内决策不会这么频繁，多 session 累积导致 context loss + 重做相同分析
- D031-D034 root cause hunt 在 24 小时内对 router 训练失败提出 4 个不同假说 (pad_token_id / class_weights / ga 配置 / 代码重构)，每个被下一轮证伪。真正 root cause (D026 数据标签 mapping bug) 在 v6 失败后才定位——延迟约 12 小时 / 5 个失败实验
- D086 (Narrative A) 写出 24 小时后被 D087 撤回为 "rationalization"——这一类自我审查依赖 Reviewer 触发，Agent 不主动质疑
- decisions.yaml 中相邻 D 编号经常解决"同一问题的不同子问题"，缺少全局规划

**严重程度**: 这是项目效率的根本制约。32 轮审稿、5 次 framing pivot、router 训练 11 个版本——如果有更强的长程一致性，可能 15 轮收敛、3 次 pivot、3 个 router 版本。

**根因分析**: 这不是 prompt 问题，而是模型在跨 session 边界 + 多角色协作下的根本能力。Claude 系列在单 session 内的 reasoning 已经很强，但跨 117 个 Agent boot (Layer 1 timeline) 的方向一致性依赖外部记忆 (decisions.yaml/memory.md)，而外部记忆本身被频繁覆写。

**改进建议**:
1. (Harness) 强制 "decision provenance" — 每个 framing 决策必须显式 cite 之前矛盾的决策并解释为何 supersede
2. (Harness) 提供 "claim diff" 工具，对比当前 paper_framing.md 与 IDEA_BRIEF 的距离
3. (Model) 这部分 inherently 受限，需要工程化补丁

### F6 [MODEL] **基础数值/单位判读错误反复出现，几乎每个 high mistake 都涉及** 🟠 (高)

**证据**:
- M001: score=0 vs score=-100 混淆 (无进展 ≠ death)
- M008: differential (+34.3pp) vs absolute internal DR (58.6%) 混淆，det total deaths vs det-only deaths 混淆
- M015: step count ratio 5,667/6,094=93.0% vs step tie rate 5,935/6,094=97.4% 混淆 (分子分母都搞错)
- M016: ModelScope 下载完成判定，9 个 shard 中只到 7 个未察觉
- M009: grep 假阳性 (det_final=-100 行被当 internal death)
- 大量 decisions (D097/D098, D104/D105/D106/D107) 是数字反复修正

**严重程度**: 6/16 mistakes 是数字判读，所有 high severity mistakes 中数字类占 4/5。每个直接影响论文数字或对用户的报告。

**根因分析**: LLM 在 (复杂数据结构 + 多个含义相近的字段名 + 工作压力时间紧) 三因素叠加下，会用最 plausible 的解释填补理解 gap。这是 hallucination 在数值领域的具体形态。

**改进建议**:
1. (Harness) 所有论文级数字必须显式声明 source location (e.g. `results.json#metric_name`)，写论文工具自动 fetch 而非接受文本
2. (Harness) registry 设强类型 schema (M015 step_tie_rate 应是 registered metric)
3. (Harness) 数字一致性 audit 应在每次 commit 触发，而非等到 5/25 人类发起 "数据真实性彻底审计"

### F7 [HARNESS] **Information Silos：相同信息被各角色独立重新发现** 🟡 (中)

**证据**:
- decisions.yaml 中多次出现 "Reviewer 二次审查发现 Agent 报的数字" 模式 (D104/D105/D106) — Reviewer 与 Agent 各自从 ssh log 拉数据，不共享中间产物
- task_context/agent.md / reviewer.md / director.md 是各自维护的 handoff，但同一个 fact (e.g. "72B death-prone aggregate") 在三个文件里独立重写
- memory.md 是共享但只 25 行，远不足以承载跨角色共识
- 432 个 artifacts，其中 227 个 .md。大量 reports 重复同样的核心数字，没有 single source of truth

**严重程度**: 中等。增加了 token 消耗 (94M total)，造成 D105/D106 这种 patch→撤回 循环。但不直接导致 paper 错误。

**改进建议**:
1. 强制 "fact registry"：所有论文级数字注册到单一 yaml，所有角色 read-only
2. handoff 文件应自动从 fact registry 派生，避免手抄

### F8 [HARNESS] **审稿驱动 vs 用户驱动 vs 自驱动的优先级混乱** 🟡 (中)

**证据**:
- 32 轮 fresh review 显示项目大部分时间是"等审稿→改→再审稿"循环，自驱动 exploration 较少
- 用户对话历史显示用户在 5/13-5/21 大部分时间不主动 (24 次 ESCALATED_TO_HUMAN reason=director_no_response)；5/25 集中爆发 67 条
- D101: "用户未回复 3 次催促，Director 主动推进 Findings track reframe" — Director 自己也清楚这是 fallback
- D126 framework-centric pivot 实际是被审稿 (R1 反复建议) 推动，不是项目内 reflection 触发

**严重程度**: 中。审稿驱动模式是合理的 (deadline-driven research)，但 32 轮 review 显示 reviewer agent 自身在试错（不是论文逐轮变好，而是反复来回）

**改进建议**:
1. 审稿轮间增加 cooldown，避免论文 stable 后又被审稿 re-perturb
2. 区分 "fix specific issue" vs "fresh review" 的频率：fresh review 每周 1 次足够

### F9 [INFRA] **GPU 调度与 SSH 链路不可靠是低级但持续的拖累** 🟡 (中)

**证据**:
- AutoDL 实例 GPU0 在 plan-001b 收集阶段 crash 3 次，paper_provenance.yaml 显示主表 245 episodes 是从 6 个 partial recovery 拼出来的
- M011-M013 Gemma 集成连环 3 个 mistake (system role / GPU collision / dryrun mismatch)，反映 multi-model 移植没有标准化 checklist
- 项目目录 CLAUDE.md 文档了 AutoDL 网络/磁盘/SSL 多个坑，但散落，新 worker 不一定加载到
- "westd-18266 无 GPU 信息" 在 5/24 handover 中——状态报告 broken
- M016 ModelScope 下载未验证 shard 完整性

**严重程度**: 中。Infra 问题是项目主线之外的恒定 overhead，估算 5-10% 时间。

**改进建议**:
1. AutoDL 镜像 pre-bake 项目特定环境 (PyTorch + vLLM 版本 + 网络代理 + SSL cert) 避免每次重装
2. 模型下载 wrapper 包含 shard 数量验证 (post-download integrity check)
3. tmux session 模板含 conda activate + cleanup trap

### F10 [MODEL+HARNESS] **审美/视觉判断完全依赖人工** 🟢 (低，但分布累计)

**证据**:
- DDL 当天 67 条人类消息，30 条关于 figure
- "Figure 1 太丑了" 出现 5+ 次
- "Figure 2 是画了个啥玩意儿？" → "删了" — agent 设计的 figure 完全错位
- PaperBanana skill 存在但需要明确指令才会用
- paper-figure-optimize role 仅 5 sessions

**严重程度**: 单 figure 影响低，但累积起来：如果 Agent 能自主判断视觉质量，可省 ~3-5 小时人工审稿
（DDL 那天对实质内容的修改非常少）

**改进建议**:
1. 投稿前自动跑一遍 PaperBanana 重画所有 figure (默认开启而非可选)
2. paper-audit-visual role 应在每次 compile 后自动跑，不需要人工触发
3. figure layout 用 pre-defined template (左右栏分布 / 每页至少一图) 强制约束

## 6. 总结判断

**这个项目最终拿到 EMNLP Findings 3.0 是合理的产出**，并非系统的失败。原因：
- 原假设 (SimGate explicit modular router 显著 outperform) 被自己的实验数据否定 (D008 1-step tie, D025-033 router 全军覆没)
- 项目在多次 framing pivot 中找到了一个 defensible 的 narrative (framework-centric)
- 数据本身是真实的，统计方法是严谨的，cross-model/cross-env 是充分的

**真正的弯路是 framing 反复**——同样的实验数据如果一开始就定位为 diagnostic framework，应能省 ~30% 时间。但这需要 Day 1 就有反 IDEA 的判断力，对当前 Director 模型而言是过高要求。

**最大的系统设计问题是 verification gap**——Worker hallucination 与数据 bug 多次穿透 Agent 到达 Director/用户，依赖 Reviewer 异步兜底。这一类问题不是 prompt 优化能解决的，需要 harness 级别的强制 checkpoint。

**最大的模型能力限制是长程一致性**——19 天 117 个 Agent boot 跨度内，方向锚定靠 yaml 文件而非 weights，必然会漂移。当前的 mitigation (decisions.yaml/memory.md) 容量与结构不足。

**对未来项目的核心建议**:
1. 引入 "claim contract" 与 "fact registry" 两个 immutable layer
2. Worker file edit 操作必须 post-edit verify (harness-level)
3. Reviewer 配备结构化查询工具，减少 grep 假阳性
4. Cron hook 改用数据 sentinel 而非 process status
5. 视觉/审美判断默认走 PaperBanana + audit-visual 自动循环，减少人工干预
