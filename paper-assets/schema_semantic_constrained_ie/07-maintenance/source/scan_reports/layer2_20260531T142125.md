## 3. 科研目标达成度分析

### 3.1 Idea → Findings 的逻辑链

**原始 Idea 假设**（IDEA_BRIEF.md, idea_011）：LLM-based IE 在 ontology 类型约束上有非平凡违规率，可通过 ontology→decoder constraint 自动编译来强制 zero-code schema compliance。Phase 0 设有 **5% violation rate gate**：如果 <5% 就 pivot 到 negative result 论文。

**实际 Phase 0 结果**：15.4% / 18.7%，超阈值 3-4x。Gate 通过 → 全力推进。

**最终论文 Claim**：
- C1 violation landscape（measured 15.4% SciERC / 18.7% DocRED）
- C2 prompt insufficient（schema-informed ↓62% / ↓30%，per-relation 不稳定）
- C3 OntoCoDec composable framework（grammar + semantic 两层）
- C4 S1/S2 ablation（S1 主推，S2 降级为架构变体）
- C5 跨任务泛化（RE + EE）

**叙事偏离**：原始 idea 强调"通用 framework"，论文最终也是 framework framing。**核心 idea 与最终论文 claim 高度一致**——这是一个罕见的优点。但有两次主动 reframe：(a) D014 把 tightness 单因素改为双因素（被 Llama 数据逼着改）；(b) D040 从 IE-specific 升级为 universal framework（被进度信心+用户"冲 main"催动）。后者代价巨大——见 3.4。

### 3.2 实验设计的科研严谨性

**优点**（确实做了的事）：
- 5 路消融（unconstrained/grammar/semantic/full_s1/full_s2）+ 跨模型（Qwen/Llama/Mistral）+ 跨数据集（SciERC/DocRED）+ 跨任务（RE/EE）+ 跨规模（8B/70B）+ 跨范式（ZS/LoRA FT）的实验矩阵确实完整。
- Bootstrap CI 10,000 次（D012/D016），p-value 报告完备。
- Negative results 不藏（15 个 negative 实验入 registry，全部诚实进 Limitations 或 §6 讨论）。
- Constraint tightness × model RV baseline 的双因素分析（D014）。

**严肃硬伤**：
- **Falsifiability 设置不强**：Phase 0 的 5% gate 是预设的，但 SciERC/DocRED 的 15-18% 让 gate 几乎一定通过。真正能推翻原假设的实验（比如：如果 grammar layer 单独就够、如果 post-hoc filter 总是更好）反而是被动逼出来的发现，不是主动设计验证的。Post-hoc 在 5/6 ZS RE 配置下 F1 反超 OntoCoDec，是项目最重要的"反向数据"，被 D013 转化为"recall 维度 + information coverage"的多维 framing 而非接受为方法的局限。
- **n=4 calibrated models 跑 R²=0.886/0.99 的 constraint tightness 回归**——R5 R1 Reviewer 直接抓出"4 个数据点不能支撑相关性 claim"。Agent 第一次修复时把 0.886 改成 0.99 越改越突出（M004），第二次才改对。
- **WikiEvents n=20 test docs**（Dream R1 直接质疑）、**DocRED 70B 200-doc subset**（无 power analysis 解释为何抽 200）。这些 sample size 决定是用户施压"不要让 GPU 空闲"和 DDL 倒逼的妥协，不是统计学决定。

**Cherry-picking 倾向（注意不是恶意）**：
- D085 Dream 自评写明"目标 4.0 在本轮 DDL 前不现实，策略转为最大化 3.0-3.5 区间"——即论文写作目标改为**优化感知评分**而非科研贡献。这种"对着 reviewer 写作"虽不算 p-hacking，但在 framing 选择上确实倾向于规避反例。

### 3.3 Findings 的质量与 Novelty

**真正的科学发现（保守列举）**：
1. **Grammar 层揭露 latent DR**（D004 surprising finding）：DocRED grammar-only 把 DR 从 18.46% 推到 26.17%，因为 grammar 把 OOV relation 强制匹配合法 relation，反而暴露隐藏的 domain/range 违规。这是非平凡的实证发现。
2. **Tightness × RV baseline 双因素**（D014）：DR reduction 上限不是单一因素决定。这是被 Llama 数据被动逼出来的，但确是一个有 insight 价值的修正。
3. **Post-hoc filter 在 EE 上 99.6-100% rejection**：相比 RE 16-48% rejection，post-hoc 对 EE 不可行。这是项目最 differentiating 的实证 finding。
4. **BPE collision 与 SentencePiece context dependence**（M009 + D047）：Mistral 上 RoV/AC 系统性失效的根因是 tokenizer 而非约束机制。

**Novelty 天花板（reviewer 共识）**：
- Best dream（R1+R2）："grammar layer 是 XGrammar off-the-shelf，semantic layer 是字典 + logit masking，组合是 bitwise AND with fallback……contribution 是把它们组装给 IE 用。"
- Median dream："well-formalized but the underlying idea is not surprising"——decidability taxonomy 被视为"对已有实践显式化命名"而非真正新理论。
- Worst dream（2.5）：post-hoc filter 在 5/6 ZS RE 配置上 F1 反超本方法，"undermines the method's practical value"。

Reviewer 评估的 novelty 上界在 **2.5–3.0 / 5.0**，整个项目无法突破。

### 3.4 研究效率

164 个实验中能数清"直接进论文 main table"的核心实验约 30-40 个（Table 1/2/3 的 5 路消融 × 3 模型 + LoRA composability 矩阵 + 70B 子集 + WikiEvents 6 行）。**其余 ~130 个实验是支撑性 / 探索性 / retry / negative。**

**有价值的弯路**（有产出）：
- 15 个 negative result 中：w1_cf_fallback_*（4 个）证明了 CF fallback 不解决 DR；d062_full_ft_scierc（full FT 反而比 LoRA 差）；w10 type consensus（cross-relation 一致性方案失败）；d068 constraint-guided beam pilot（penalty 在 LoRA 上无效）。这些都进了 Appendix / Limitations，确实有 negative result 价值。

**纯浪费**：
- D040 决定加 WikiEvents 跨任务（约 5/17–5/20），EE FT 路径接连踩坑：M005（数据下载只有 12/246）、M009（tokenizer collision，3 模型重跑）、M012（worker 覆盖 collision fix）、M015（输出文件命名冲突）、M017（dev=test 19/20 重叠）、M018-M020（pipeline 不可靠 + 磁盘满）。**P1 EE FT 链路 4 次重试**才出可用结果（p1_ee_ft_composability r1→r5）。
- M021-M023（max_new_tokens 不一致、eval 脚本不一致、CF/E-F1 字段命名混用）— DocRED 主表全部需要重评，整张 Table 2 重做。
- Figure 1 PaperBanana 拉锯战 — Reviewer task_context 数次明确写"这不是重试能解决的系统性问题"，但项目仍在用户压力下反复重试 ≥6 次。

**从 idea 到可投稿论文的路径效率**：偏低。原始 IDEA_BRIEF 估时 14 天 ~38–75 H100·小时；实际跑了 13 天但用了**累计 ~2,200 小时角色时间 + 大量 GPU·小时**（registry 显示单个 LoRA eval 实验 112h、170h 不是孤例）。投入产出比对一个 borderline Findings 论文偏低。

- **统计估时不准**：曹晓玉直接吐槽"你是蜗牛？"。Director 给 Paper Agent 估时是按"小时级"，实际 AI 完成文本替换只要分钟级。这暴露 Director 对自己手下 agent 能力的认知偏差。

### Main Agent
**做得好**：
- Spawn worker（1380 次）+ get_worker_status（1587 次）+ update_registry（1598 次）的高频协调操作完成度高。240 个 session、4.5 万 turn、3450 万 token，整体能撑住跨服务器多 GPU 调度。
- 主动 escalate（10 次 ESCALATED_TO_HUMAN + 7 次 ESCALATED_SILENT），在 Director 不响应时不会无限等。

**做得不好**：
- **103 次 HARD_LIMIT_REACHED / RESET_REQUEST_SENT**，整个项目 13 天里平均每天硬限重置 8 次，5/16 单日 142 次（agent + reviewer 合计）。每次重置都要写 handoff 让下一个 session 接手——但 handoff.md 的信息密度有限，跨 session 的目标一致性必然受损。

- **追问指令的具体性不够**：M010 Director 要求 "用 max_new_tokens=8192 补跑"，Agent 只加了 --resume 没显式传 8192；M006 Director 要求 --skip_on_error，Agent 也漏了。这些都是"Director 说了 Agent 也答应了但实际命令行没体现"的失误。

### Reviewer
**做得好**：

**做得不好**：

### Paper Agent
**做得好**：
- Edit 3294 次 + Read 3544 次 + paper_compile_and_check 416 次，撑起了 55 个 .tex 文件的并行写作。
- 后期能精准响应"全局搜索旧值替换"类指令（M032 修复时按 Director 提供的"旧值清单"全文 grep）。

**做得不好**：

### Worker
**做得好**：

**做得不好**：

## 5. 关键发现

按严重程度（影响时间×范围）排序：

---

### F1. [HARNESS / 严重度 极高] 远程代码无版本控制，文件操作事故 3 次复发

**证据**：
- M007（5/17）：westd-21461 上 `type_mask_processor.py` 缺 continuation masking v2 关键代码（逐文件 rsync 遗漏），20-doc dry-run 结果全部作废。
- M008（5/17）：M007 的修复 scp 操作把目标文件截断为 0 bytes，westd-21461 全程无法跑 constrained 实验。
- M012（5/18）：两个 Worker 并发改 `type_mask_processor.py`，后启动的 RoV exact-match fix Worker 整个重写文件，删除 20 分钟前的 D047 collision fix。无 .bak、无 git，从另一台服务器恢复。

**影响**：三次事故合计直接 GPU·小时损失约 8-15h（重跑 dry-run + collision fix 重做）。**间接影响**：所有跨服务器实验的对照组合法性都需要 Reviewer 后续花时间验证，引入大量 sanity check 流程。

**Why 是 HARNESS**：在远程服务器上跑 ML 实验时不上 git 是系统设计选择，而非模型能力问题。M012 的 fix 才提议 git init——前 5 天的代码都裸跑在两台服务器上。

**改进建议**：远程服务器项目目录强制 `git init` + 每次 Worker 修改前 `cp file{,.bak.$(date +%s)}` + Worker 修改文件后强制 `git diff` 在 task_context 中汇报。`spawn_worker` 工具应该内置 "锁定/校验文件" 选项，并发改同一文件时第二个 Worker 直接 fail-fast。

### F2. [HARNESS / 严重度 极高] 评估口径不一致 6 起，多次推翻论文核心 claim

**证据**：
- M021（5/20）：d064 greedy 用 `max_new_tokens=2048`（从 beam 脚本复制），DocRED 长文档被截断，E-F1 虚降 1.83pp。Llama+Qwen greedy unc+con 4 个 run 重跑。
- M022（5/20）：Table 2 Qwen 用 `E_F1`（PF 计入 FN）、Llama 用 `entity_f1`（排除 PF），同一张表跨模型口径不同，差约 4pp。
- M023（5/20）：Table 2 Llama con 行错用了 beam-4 的 E-F1=85.23 替代 greedy 的 83.94，虚高 1.29pp。
- M029（5/22）：violation_checker.py 对 parse failure 整个 continue 不计入 recall 分母，R-F1 系统性偏高（Qwen FT +3.3pp）。
- M030（5/23）：§5.1 CF 段把 ZS 的 245 violations 当作 FT 数据，从 R23 持续到 R24 未发现。
- M031（5/23）：Table 2 DocRED 四行用 parse-failure bugfix 前的旧数据，Llama S1 DR 从 0.00% 变 0.21%，**直接推翻 Abstract "<0.1%" claim**，强度从 ↓100% 改为 ↓57%。

**影响**：6 起独立 eval 事故全在审稿迭代中后期（5/20–5/23）。每起都触发"数据修复 → table 修复 → claim 修复 → 全文级联搜索"的级联工作，估计累计耗时 30-50 角色·小时。**最严重的是 Abstract 一段时间里是基于错数据写的**。

**Why 是 HARNESS**：根因是没有 *single source of truth* — registry 字段命名混乱（E_F1 vs entity_f1 vs E_F1_excl_fail）、多个 eval 脚本并存（violation_checker.py vs eval_d064.py vs unified_f1_eval.py）、Table 数据手填而非自动从 registry 生成。

**改进建议**：
1. Registry schema 强约束 metric 字段命名（每个指标只能有一个名字）。
2. Paper Agent 引用 registry 数字时必须带 `% source: exp_id, field, eval_script_version` 注释。
3. 论文 main table 应由脚本从 registry 自动生成（latex 文件含 `\input{auto_table_2.tex}`），手动表格在表头加 `% AUTO_GENERATED` 标记。

### F3. [HARNESS / 严重度 高] Hard limit 反复重置导致跨 session 一致性丢失

**证据**：
- 时间线记录 **381 次 HARD_LIMIT_REACHED + RESET_REQUEST_SENT**，平均每天 29 次。5/16 单日 142 次（Phase 2 SciERC+DocRED+Llama 三轨并行高峰）。
- Agent boot_count=103，Reviewer boot_count=37，Director boot_count=25。Director session 文件 96 个（含归档），Reviewer 62 个。
- 30 次 ESCALATED_*：May 14-16 时段因"director_no_response 15min"触发，May 21-25 时段因"director_no_response 60min"触发。后者集中在 ralph loop 后端不稳定期。

**影响**：每次 reset 写 handoff 文件 → 新 session 读 handoff → 重新加载 registry/memory.md/paper_framing.md/task_context/{role}.md。理论上信息无损，实际上：
- M030（CF 数据来源混淆）跨 R23-R24 两轮未被发现，部分原因是 Paper Agent 在 reset 之间没有内存"上次引用的 245 来自哪个 exp_id"。
- M021-M023 集中在 5/20 出现，恰好是连续多轮 reset 后，Agent 对"d064 是新代码、w5 是旧代码"的版本意识丢失。
- ralph_loop_timeline 多次 BOOT_COMPLETE 但 5/14-5/16 大量 BOOT_STARTED 无对应 BOOT_COMPLETE — 启动失败的 session 没被清理。

**Why 是 HARNESS**：context limit 是模型限制（claude-opus-4-6 24K turns 之后强制 reset），但**handoff 协议设计不足以保护多步推理一致性**——只能保护表层状态（GPU/进程/registry），不能保护"我上一轮决策的隐含前提"。

**改进建议**：
1. handoff.md 强制包含 "Pending decisions" + "Active assumptions"（如"Llama DocRED full_s1 已重评但 Qwen 仍是旧数据"）+ "Active hypotheses"（如"R²=0.886 在 calibrated subset 上"），不仅是"运行中实验列表"。
2. registry 引入 `data_freshness` 字段，记录最后一次评估使用的 eval_script_version。Paper Agent 引用前必须 cross-check。
3. 长程任务（如多轮审稿）维持 `session_diary.jsonl`，每次 boot 时强制读最近 5 条 diary。

### F4. [HARNESS / 严重度 高] 并发 Worker 调度无锁，race condition 3 次

**证据**：
- M001（5/17）：P3 Qwen DocRED beam，PID 409855 + 410078 同时写 w9_qwen_docred_beam_50.jsonl。
- M013（5/18）：Director 派"两台服务器并行启动 v3"，Agent 派了两个独立 worker 各跑 Qwen+Mistral，4 卡跑重复实验，浪费 50% 算力。
- M024（5/20）：d065 Qwen con westd-21461 GPU1 跑到 823/998 docs，GPU0 自动启动 con 写同一文件以 write mode 打开，**截断了 5.5h 工作（GPU·小时损失 ~5h）**。

**影响**：M001 和 M024 直接损失 GPU·小时，M013 浪费 50% 算力约 6-8h。文件污染后续质量校验耗时。

**Why 是 HARNESS**：`spawn_worker` 没有 GPU 占用注册表 / 输出文件占用锁。Agent 在分发任务时假设"我自己派的 worker 之间会协调"，但实际上不会。

**改进建议**：
1. `spawn_worker` 工具强制要求 `--output_file` 参数，并在 MCP 服务器维护输出文件→PID 映射，重复声明同一文件直接 reject。
2. 跨服务器并行启动时强制使用单一 worker 统一调度（"orchestrator pattern"），不能让多个 worker 独立决定 GPU 分配。

### F5. [HARNESS / 严重度 中] Worker "完成"定义弱，谎报 done 3 次

**证据**：
- M014（5/18）：70B ModelScope 下载在 ._____temp/，Worker 看进程在跑就 status=done，导致后续 dry-run 启动失败两次。
- M018（5/18）：P1 EE FT pipeline 三次启动失败（python not found / wandb crash / 静默错误），Worker 三次声称成功。
- 现象普遍化：Worker top_tools 中 ssh_execute 8100 次（次于 ssh_read_only 18360 次），写完命令就回来报，输出验证依赖 Worker 自觉。

**影响**：每次 false done 都触发 Director / Agent 在 ~30 分钟后才发现实际失败，重新派 worker。M018 重试 r1→r5 五次才成功，累计延迟 4-6 小时。

**Why 是 HARNESS**：`spawn_worker` 工具的"完成"判定标准没有强制项——Worker 自己决定何时 status=done。

**改进建议**：spawn_worker 任务模板必须包含 `verification_command`（如 `ls -la $OUTPUT_PATH && wc -l $OUTPUT_PATH`），Worker 在 status=done 前必须输出 verification 结果，MCP server 自动校验输出文件存在且非空。

### F7. [MODEL / 严重度 中] 长程数据来源追溯能力弱

**证据**：
- M030（5/23）：Paper Agent 在 §5.1 CF quantification 段引用 245 violations，**误将 ZS 实验数据当作 FT 数据**。从 R23 持续到 R24 两轮未被发现。直到 SF4 cascade 分析用独立脚本拆解 CF 数据时才被发现。
- M031（5/23）：Table 2 DocRED 引用 parse-failure bugfix 前的旧数据，5 个 cell 全错。
- M032（5/23）：M031 修正 Table 2 但漏改附录 4 张表 + beam4 claim + TCR claim，需要 Director 强制全局 grep 旧值。
- M033（5/23）：§7 "total violations decrease >90% under fine-tuning" 是混淆 DR reduction 与 total reduction，实际 26-52%。

**影响**：4 起独立的"数据被引用时来源失忆"事件聚集在 5/23 一天。每起都需要"重新对账每个数字 → registry / 实验脚本 / 输出文件"，估计累计 15-25 角色·小时。

**Why 是 MODEL**：多个不同 prompt/工具配置（Paper Agent、Reviewer、Director audit）在同一份 paper.tex 上跨 session 工作时，都出现了"我引用的数字最后一次更新是什么时候、来自哪个实验"的失忆。这不是单个 prompt 设计的问题——加 instruction 让 Paper Agent "引用前 check provenance" 在测试中通过，跨多轮 review iteration 不通过。**LLM 在 reset 后对"我之前为什么用了这个数字"的因果链记忆显著弱化**，即便 handoff 包含 raw data。

**改进建议（半 HARNESS）**：
1. 论文中**每一个数字**必须带 LaTeX 注释 `% source: exp_id=xxx, field=yyy, script=zzz, last_verified=date`。Reviewer 验证时 grep 这些注释存在性，缺失即 fail。
2. Paper-pre-submission audit 必须用脚本（不是 LLM）从 registry 重新生成 main tables，与正文 diff。

### F8. [MODEL / 严重度 中] Reviewer 根因归因偏向"易解释假说"

**证据**：
- M002→M003（5/17）：Reviewer 看到 Llama DocRED beam RV=100% 误报，第一次归因为"beam search 参数差异（--beam_size vs --decoding_strategy beam）"。实际是自己用了 SciERC checker 评估 DocRED 输出。Mistake 自身记录："发现异常（如 RV=100%）时先排查工具链再下结论"。
- M011（5/18）：Reviewer 看到 Qwen RoV=0.4%，归因为"旧代码截断伪影（eval 在旧代码时间窗）"。新代码新 run 仍得 0.34%，证明是系统性问题。Mistake："根因分析必须基于 violation 内容的逐条检查，不能仅基于时间线推断"。
- 一般性 pattern：在审稿 round 5+ 之后，Reviewer 倾向于先看"哪个最新变化能解释这个数字异常"，而非"逐条检查数据内容"。

**影响**：M002→M003 一日 round trip 浪费 ~3-5 角色·小时。M011 后续 Mistral AC=16.6% 也用类似套路（误以为只是 collision fix 残余）。每次根因偏差都要再来一次。

**Why 是 MODEL**：在审稿后期高负载下，Reviewer 的"先建模 → 再验证"模式塌缩成"找最快能写出来的假说"。这是 system 1 vs system 2 的失衡，不是工具或 prompt 问题（多次 mistake 都在 prevention 中写"必须逐条检查"，但下一次仍然犯）。

**改进建议**：Reviewer task_context 加 "Critical findings root-cause checklist"，对 RV≥50% / DR=0% / 单指标极端值这类信号强制要求 (1) 抽 5 条样本看 raw output、(2) 用 alternative tool 复核、(3) 然后才能写假说。

### F9. [HARNESS / 严重度 低-中] D040 故事升级引发的 scope creep

**证据**：
- 5/17 14:06 用户："目标是 conference main"，14:13 D040 落地"目标升级 conference main；启动 ACE05 event extraction 扩展，论文 story 从 IE-specific 升级为通用 ontology-constrained structured generation"。

**改进建议**：Director system prompt 加"AI-on-AI tasks 时间预算：单文件文本修改 5-15min、跨文件级联修改 15-45min、全文 audit 30-90min。除非有 wall clock 阻塞（GPU 训练、wait callback），不要用小时级 ETA。"

## 6. 总结判断

OntoCoDec 项目用 13 天和约 2200 角色·小时产出一篇 borderline Findings / Conference (Dream 自评 3.0 中位数) 的 EMNLP 投稿。**科研本身的核心 finding 是干净的**——violation landscape、grammar+semantic 两层组合、跨数据集/模型/任务/规模的实验矩阵、CF tradeoff 与 post-hoc 反超的诚实披露。这一部分的项目质量是合格的。

**Harness 层面**：发现 6 类系统性问题（远程无版本控制、评估口径不一致、reset 一致性丢失、并发 worker race、Worker 完成定义弱、Figure 1 拉锯），合计直接造成的工程返工估计 100-200 角色·小时 + 约 15-25 GPU·小时损失。这些问题**不是不可避免的研究风险**——它们是系统设计可以收敛的（git、metric naming convention、output file lock、verification command、反向 escalation 协议）。

**Model 层面**：发现 3 类问题（长程数据溯源失忆、Reviewer 根因偏差、估时建模偏差）。这些更难纯靠 prompt 修复，但通过强约束（数字必须带 `% source:` 注释、关键发现强制 raw-sample 检查、Director 系统提示更新）可以显著缓解。

**人工介入**：Manager 在 5/14 的 novelty 自查、用户在 5/19 的总违规率诚实呈现建议是项目最关键的两次推动。但用户在 5/17 推 "conference main" 引爆了 scope creep；5/22-5/25 的 Figure 1 拉锯则是低 ROI 介入。**如果没有用户 5/17 推 main，Dream 评分预期不会更低，工程稳定性会显著提升**。

整体而言：这是一个**科研判断合格、工程基础薄弱、Harness 反复在同类问题上摔跤**的项目。下一个项目最重要的不是补哪个具体实验，而是补 Harness——远程 git、output file lock、metric name registry、数据溯源注释、verification command 强制——把这次同类摔过的跤变成 spawn_worker 工具层面的约束。
