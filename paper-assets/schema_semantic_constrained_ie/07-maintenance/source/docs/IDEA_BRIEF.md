## Core Problem

Do LLM-based IE systems violate ontology type constraints (relation domain/range, cross-field entity type consistency) at rates sufficient to warrant decoding-time enforcement — and if so, can we automatically compile ontology schemas into efficient decoding-time constraint specifications that enforce semantic validity without degrading extraction accuracy? The first question is empirically unanswered: no prior work has systematically measured ontology constraint violation rates in LLM-based IE. We treat this quantification as a first-order contribution, with a Day 1 pilot study that establishes violation prevalence before committing engineering effort. If violation rates are non-trivial (>5%), the compiled constraint approach is justified. If rates are low (<5%), this is an equally important negative result establishing that modern instruction-tuned LLMs have internalized ontology constraints from pretraining data, and the community should not invest in decoding-time semantic enforcement.

## Opportunity / Why Now

LLM-based IE systems produce structurally valid but potentially semantically invalid outputs: structural validity (valid JSON, correct field names) is now reliably enforced by grammar-constrained decoding (Outlines, XGrammar-2, default in vLLM/SGLang since 2026), but no existing system enforces semantic validity — cross-field type constraints such as relation domain/range restrictions — during autoregressive generation. For instance, an ACE05 PHYS.Located relation requires a PER/GPE Arg-1 and a FAC/LOC/GPE Arg-2; a system that assigns two ORG entities produces structurally valid but semantically invalid output. Three converging developments create a timely opportunity. First, vLLM V1's well-documented LogitsProcessor API enables custom token-level interventions on (num_requests × vocab_size) tensors, and XGrammar-2's GrammarMatcher exposes a composable `fill_next_token_bitmask()` API that returns grammar-valid token masks, enabling external code to intersect grammar masks with additional semantic masks via bitwise AND — making decoding-time semantic enforcement practical without reimplementing grammar-constrained decoding from scratch. Second, The Format Tax (arXiv Apr 2026) demonstrates that prompt-level format-requesting instructions cause an average −3.9pp accuracy drop while decoder-level grammar masking contributes only −1.6pp additional loss across reasoning benchmarks — though critically, this was evaluated only on reasoning/writing tasks (MATH-500, GPQA, ZebraLogic, WritingBench) and not on IE. The recently published Lost in Formatting (Ravikumar et al., EACL 2026) strengthens the IE-specific relevance: across 280+ experiments spanning multiple IE benchmarks and models, changing only the output format shifts F1 by over 40%, demonstrating that the format–accuracy interaction is even more pronounced for IE than for reasoning — making the choice of constraint application point (prompt-level vs. decoder-level vs. two-pass) a first-order design decision for IE systems. Third, the landscape has matured along parallel axes but left a specific gap between post-hoc and decoding-time constraint enforcement: the LLM+ASP Workflow (Tran et al., ICLP 2025) demonstrates that ASP-based post-hoc type constraint checking substantially reduces false positives in LLM-based IE (713→482 FPs on SciERC), validating that type constraints improve extraction quality — but applies them only after generation, meaning type-violating outputs are produced then discarded rather than prevented; ODKE+ (Apple, Sep 2025) achieves 98.8% precision through soft ontology-guided prompting but without guaranteed type compliance; BoostCD/BoostIE (EMNLP 2025) shows that constrained and unconstrained decoding errors are complementary for closed IE but focuses on vocabulary membership rather than ontology type constraints and requires training a boosted combiner; DocRE-TCGL (Neural Networks, 2025) enforces entity type constraints at training time but not at inference; and EnriCo (arXiv 2024) uses ASP solvers for constrained inference on discriminative models but is incompatible with autoregressive LLM generation. No existing system compiles full ontology type constraints (entity type validity, relation domain/range, cross-field type consistency) into finite-state specifications applied during autoregressive decoding. This gap — between post-hoc/soft/training-time constraints and hard decoding-time guarantees — is precisely what compiled semantic constraints fill. The LLM+ASP result is particularly motivating: it demonstrates that type constraints improve IE quality but leaves open whether enforcing them during generation (preventing violations) outperforms enforcing them after generation (filtering violations).

The practical case for decoding-time enforcement over post-hoc filtering is strongest in three IE-specific deployment contexts. (a) **Streaming/real-time extraction pipelines** — in applications such as live news monitoring, social media analysis, or clinical decision support, extraction results are consumed as they are generated; post-hoc rejection wastes generation latency and cannot provide valid alternatives without costly re-generation, while decoding-time enforcement produces valid outputs in a single pass. (b) **Batch knowledge graph population** — when processing millions of documents (as in ODKE+'s 9M Wikipedia page pipeline), post-hoc rejection of type-violating outputs requires re-generation at ~2× cost, and for high-cardinality ontologies like DocRED's 96 Wikidata relations, the post-hoc rejection rate could be substantial (each relation has specific subject-type and value-type constraints), making decoding-time enforcement more compute-efficient at scale. (c) **Safety-critical domains** — in biomedical knowledge extraction (drug-gene interactions, adverse event detection), legal document processing, and regulatory compliance pipelines, even a single ontology-violating extraction can propagate errors through downstream reasoning systems; these domains require guaranteed type compliance rather than statistical compliance, paralleling how type-safe programming languages provide formal guarantees even when most code would run correctly without them. The quantification of violation rates, regardless of direction, is itself a first-order contribution that no prior work provides.

## Landscape (SOTA & Limitations)

**Grammar+semantic constraint paradigm (code generation).** Synchromesh (Poesia et al., ICLR 2022) introduced two-layer Completion Engines combining syntactic and semantic constraints for code generation (SQL, Vega-Lite, SMCalFlow). IterGen (Ugare et al., ICLR 2025) extended this with backtracking via KV cache state restoration when semantic callbacks detect violations, achieving 18.5% improvement over forward-only grammar-guided generation. Both require manual implementation of domain-specific constraint logic. Neither addresses IE ontology constraints or automatic constraint compilation from schema definitions.

**Constrained decoding for IE (vocabulary-level).** GenIE (Josifoski et al., NAACL 2022) pioneered bi-level constrained generation for IE with structural constraints and prefix trie vocabulary constraints, but enforces only entity/relation name validity, not cross-field type consistency. Geng et al. (EMNLP 2023) demonstrated input-dependent grammars for closed IE on Wikidata. Schmidt & Cimiano (Frontiers AI 2024) applied grammar-constrained decoding to clinical IE. Lazy-k (Hemmer et al., EMNLP 2023) explored constrained decoding for token classification IE. SciDC (arXiv Apr 2026) introduced multi-layer decoding constraints for scientific domains using hand-crafted rules. Vukovic et al. (SIGDIAL 2024) adapted chain-of-thought decoding with ontology-constrained output spaces for dialogue relation extraction, using trie-based prefix matching to restrict generated relations to valid ontology terms — conceptually related to our approach but targeting task-oriented dialogue ontologies rather than IE schemas, using CoT branching rather than logit masking, and not handling cross-field type constraints (relation domain/range). None enforce cross-field type constraints (relation domain/range, event argument role-filler types).

**Constrained+unconstrained combination for IE.** BoostCD/BoostIE (EMNLP 2025) is a key recent work combining constrained and unconstrained decoding via learned boosting for closed IE. Phase 1 decodes each input twice (constrained + unconstrained on FlanT5-base, ~250M params); Phase 2 trains an autoregressive boosted model to combine predictions, exploiting error complementarity — constrained decoding suffers from forced token selection while unconstrained produces 60% unrelated triplets and 9% entity misclassification errors. However, BoostCD (a) focuses on vocabulary membership constraints (entity must appear in a KB), not ontology type constraints (entity must match a relation's domain/range type); (b) requires training a separate boosted combiner model; (c) targets small encoder-decoder models, not modern instruction-tuned LLMs; and (d) does not automatically compile constraints from ontology definitions.

**Post-hoc constraint checking for LLM-based IE.** The LLM+ASP Workflow (Tran et al., ICLP 2025; arXiv 2508.12611, updated Jan 2026) is the most direct post-hoc competitor to our approach. It combines LLM generation (GPT-4o) with ASP-based consistency checking for joint entity-relation extraction, using rules like ok_type(S,E,F,R) to verify that relation arguments satisfy domain/range type specifications. On SciERC with only 10% training data, it achieves 35.37% RE F1 (2.5× improvement over baseline), with the ASP checker reducing false positives from 713 to 482. Evaluated on CoNLL04, SciERC, and ADE, it demonstrates that type constraint checking substantially improves extraction quality, particularly for datasets with richer type specifications. However, LLM+ASP operates strictly post-hoc: the LLM generates unconstrained outputs, then the ASP checker filters violations. This means (a) type-violating outputs are produced then discarded rather than prevented, wasting generation compute on invalid outputs — particularly costly in batch KG population pipelines processing millions of documents; (b) the approach cannot redirect the model toward valid alternatives during generation — it can only accept or reject, whereas logit masking redistributes probability mass to type-valid alternatives; (c) it relies on GPT-4o (a closed-source ~1.76T parameter model), making cost and reproducibility concerns for batch processing; and (d) the ASP rules are manually specified per dataset rather than automatically compiled from ontology definitions. OntoCoDec addresses all four limitations: decoding-time enforcement prevents violations rather than filtering them, logit masking redirects probability mass to valid alternatives, it targets open-weight models (Qwen3-8B, Llama-3.1-8B) for reproducibility, and constraints are automatically compiled from schema definitions.

**Constrained inference for joint IE (non-generative).** EnriCo (Zaratiana et al., arXiv Apr 2024) uses Answer Set Programming (ASP) to enforce entity type constraints for joint entity-relation extraction on discriminative span-classification models. On ACE05, constrained decoding improved relation F1 by ~1 point (69.1 vs. ~68). This is the closest prior work to our constraint enforcement goal on ACE05, but uses ASP solvers incompatible with GPU-accelerated batch serving, operates on discriminative models rather than autoregressive LLMs, and requires manual constraint specification per dataset.

**Soft ontology guidance (prompt-based).** ODKE+ (Apple, arXiv Sep 2025) is a production-grade system that dynamically generates ontology snippets tailored to each entity type for LLM-based knowledge extraction. Processing 9M Wikipedia pages across 195 predicates, it extracts 19M facts at 98.8% precision, demonstrating impressive production scalability. However, soft prompting cannot guarantee type compliance — the model may still generate type-violating outputs. ODKE+ represents the 'soft constraint' pole: high precision via guidance, but no formal guarantee of ontology validity.

**Training-time schema compliance.** GoLLIE (Sainz et al., ICLR 2024) fine-tunes Code-Llama to follow annotation guidelines encoded as Python class schemas, achieving strong supervised results on ACE05 (RE F1 = 63.6/67.5/70.1 at 7B/13B/34B). GoLLIE's published Code-Llama checkpoints are available on HuggingFace but are architecture-specific — porting to Qwen3-8B or Llama-3.1-8B would require 40-80 H100-hours of fine-tuning with non-trivial architecture adaptation. Whether decoding-time constraints complement or substitute GoLLIE-style training-time schema internalization is an open empirical question addressable through comparison against GoLLIE's published numbers. DocRE-TCGL (Neural Networks, 2025) enforces entity type constraints during training for document-level RE via a Type-Constrained Graph (TCG) encoding permitted entity-type/relation-type combinations and a Type-Constrained Loss (TCL). Evaluated on DocRED and DWIE, it demonstrates that type-aware training improves quality under long-tail and multi-label setups (up to +6.26%). Ru-LLM (Zhang et al., NLPCC 2025) learns logical rules via Monte Carlo Tree Search to constrain LLM reasoning for document-level RE on DocRED, demonstrating rule-based frameworks can outperform implicit reasoning approaches. SH-ETRs (Expert Systems 2025) learns soft-hard entity type rules for DocRE. All are training-time approaches that require retraining for each ontology change and do not guarantee inference-time compliance.

**Constrained decoding quality degradation.** The Format Tax (arXiv Apr 2026) systematically decomposed constrained decoding quality loss on reasoning/writing benchmarks (MATH-500, GPQA, ZebraLogic, WritingBench): format-requesting prompts cause an average −3.9pp accuracy drop while decoder-level grammar masking contributes only −1.6pp additional loss. Critically, recent closed-weight models show near-zero format tax. However, the paper explicitly acknowledges that 'simpler extraction tasks may show smaller effects' — the transfer of these findings to IE is an unvalidated hypothesis. Lost in Formatting (Ravikumar et al., EACL 2026) provides IE-specific evidence: across 280+ experiments on multiple IE benchmarks and models, output format choice alone shifts F1 by over 40%, with no single format consistently dominating — demonstrating that the format–accuracy interaction is even more pronounced for IE than for reasoning tasks, and reinforcing that the choice of constraint application strategy (prompt-level vs. decoder-level vs. two-pass) is a first-order design decision for IE. Structure Snowballing (Zhou, arXiv Apr 2026) documented cascading formatting errors under strict structural constraints in Qwen3-8B, specifically on HotpotQA multi-hop reasoning with self-reflection: accuracy dropped from 50.0% to 38.0% (12pp) under Outlines-based constrained decoding, with 96/100 first-round self-corrections misdiagnosed as FORMATTING_MISMATCH rather than addressing actual semantic errors. The snowballing mechanism — formatting compliance consuming reasoning capacity in smaller models — is a first-order risk for OntoCoDec's S1 single-pass strategy on Qwen3-8B, though notably the effect was measured on multi-hop reasoning with iterative self-correction (a more reasoning-intensive task than single-pass IE extraction). Le (arXiv Apr 2026) found relevant cross-architecture evidence: Qwen models are more sensitive to schema-level signals than LLaMA models, suggesting snowballing severity may differ across architectures. CRANE (Banerjee et al., ICML 2025) proved that constrained decoding to restrictive grammars limits LLMs to TC⁰ complexity. DCCD (arXiv Mar 2026) demonstrated +24pp gains on GSM8K via draft-conditioned constrained decoding, but was evaluated only on reasoning benchmarks, not IE. These findings collectively motivate strategies that minimize constraint scope — our S2 applies semantic constraints only during the formatting pass — but whether the prompt-vs-decoder quality split transfers to IE is an empirical question our S1/S2 comparison directly addresses.

## Proposed Approach

We develop OntoCoDec (Ontology-Compiled Decoding Constraints), an automatic ontology-to-constraint compiler with a phased execution plan that de-risks the core empirical question before committing engineering effort.

**Phase 0: Violation Rate Pilot Study + Format Tax Measurement (Day 1-2).** Before any compiler implementation, run unconstrained Qwen3-8B and Llama-3.1-8B on ACE05 (entity+relation), SciERC, and DocRED test sets using standard IE prompts with JSON output format. Write a lightweight Python script (~200 lines) that parses model outputs and checks each extracted triple against ontology type constraints: (a) entity type validity — is each predicted entity type in the ontology vocabulary?; (b) relation domain/range — are the argument entity types compatible with the relation's type signature (e.g., ACE05 PHYS.Located requires PER/GPE Arg-1 and FAC/LOC/GPE Arg-2; DocRED's Wikidata relations have subject-type and value-type constraints retrievable via the Wikidata API)?; (c) cross-field consistency — do entity mentions used as relation arguments have consistent types across mentions? Compute violation rates per model, per dataset, and per constraint category. **Additionally, this pilot serves a dual purpose as a format tax measurement for IE:** for each model, compare extraction F1 between unconstrained generation and JSON-grammar-constrained generation (via XGrammar-2/Outlines) on the same inputs, producing the first measurement of the format tax specifically for IE tasks — answering whether the Format Tax's prompt-vs-decoder quality split (−3.9pp prompt, −1.6pp decoder on reasoning benchmarks) transfers to IE, where Lost in Formatting (EACL 2026) shows format sensitivity is even more pronounced. This takes <1.5 days of engineering and <8 H100-hours of compute. **Decision criteria:** (i) If aggregate violation rate >5%, proceed with full constraint compiler (Phase 1-3). If <5%, pivot to the concrete negative-result paper plan described below. (ii) If grammar-constrained extraction F1 drops >5pp vs. unconstrained for Qwen3-8B (consistent with the Structure Snowballing effect), designate Llama-3.1-8B as the primary model for subsequent phases, since cross-architecture evidence (Le, arXiv Apr 2026) suggests Qwen and Llama models respond differently to schema-level constraints. This pilot is itself a methodological contribution — principled de-risking before engineering investment — and produces the first systematic violation rate measurements and IE-specific format tax measurements in the literature.

**Concrete Negative-Result Paper Plan (if violations <5%).** If the Phase 0 pilot reveals low violation rates, the project pivots immediately to a substantive negative-result paper with four components beyond bare violation rate measurement: (i) **Granular violation analysis:** Which specific relation types, entity type combinations, and input complexity levels (sentence length, entity density, relation density) trigger the violations that do occur? This distributional analysis reveals whether violations are uniformly rare or concentrated in specific hard cases — important for practitioners deciding whether to invest in constraint enforcement for their specific ontology. (ii) **Cross-model and cross-prompting sensitivity:** Do violation rates vary across model families (Qwen3 vs. Llama-3.1), model sizes (8B vs. larger via API), and prompting strategies (zero-shot vs. few-shot, JSON vs. code-style output formats)? If violation rates are consistently low across all conditions, the negative result is robust; if they spike under certain conditions, this identifies when constraint enforcement becomes necessary. (iii) **Compiler as guaranteed-compliance safety net:** Even with low violation rates, applications requiring formal guarantees (knowledge graph population for biomedical databases, legal document processing, regulatory compliance) cannot tolerate any violations. We evaluate the compiler's overhead (latency, throughput) on these low-violation scenarios, characterizing the cost of guaranteed compliance — analogous to how type systems in programming languages provide value even when most code would run correctly without them. (iv) **Comparison with post-hoc filtering:** How does the violation rate compare to LLM+ASP's post-hoc rejection rate? If both are low, this strengthens the negative result; if post-hoc filtering catches more issues (because it can also check inter-triple consistency across the full output), this informs which lightweight enforcement strategy is preferable. This plan ensures a publishable paper at EMNLP Findings or the Insights from Negative Results workshop (co-located with EMNLP 2026 in Budapest) regardless of violation rate outcome, with sufficient analytical depth for main track consideration.

**Phase 1: Ontology Constraint Compiler + LogitsProcessor (Day 2-6).** The compiler takes a standard IE ontology schema (JSON or Python dataclass: entity type list, relation types with domain/range type signatures) and emits two constraint components: (1) An EBNF grammar enforcing JSON structural validity and type vocabulary constraints — what CFGs can express. This uses standard grammar-constrained decoding (XGrammar-2 compatible). (2) A stateful type-masking specification for cross-field constraints — what CFGs cannot express. The type-masking component maintains a running entity type registry: as entities are generated, their types are recorded; when relation argument slots are decoded, the registry dynamically restricts valid entity references to those satisfying domain/range constraints, with inheritance-aware matching (e.g., GPE satisfies LOC constraints in ACE05's type hierarchy). We implement a unified LogitsProcessor in vLLM V1 that internally composes both constraint layers: (1) calls XGrammar-2's `GrammarMatcher.fill_next_token_bitmask()` to obtain the grammar-valid token mask, preserving XGrammar-2's optimized TagDispatch mechanism and batch processing capabilities rather than reimplementing grammar-constrained decoding from scratch; (2) computes the type constraint mask from the entity registry; and (3) applies bitwise AND of both masks to the logits tensor. This composable design leverages XGrammar-2's 6-10× per-token speedup for the grammar layer while adding only the incremental cost of the type mask computation and intersection. The processor operates at (num_requests × vocab_size) tensor granularity via vLLM's standard LogitsProcessor API (validate_params, __init__, apply, update_state). **Scoping decision:** The compiler targets entity+relation constraints for ACE05 (7 entity types, 18 relation subtypes), SciERC (6 entity types, 7 relation types), and DocRED (6 entity types, 96 relation types with Wikidata-derived domain/range constraints). DocRED serves as the scalability stress test: its 96 relations produce a substantially larger constraint specification than ACE05 or SciERC, testing whether the compiler and LogitsProcessor scale to realistic ontology sizes. For DocRED, we retrieve per-relation subject-type and value-type constraints from Wikidata's property constraint system and compile them into the same finite-state specification format. ACE05 event extraction (33 event types with typed argument roles) is deferred to Phase 3 as a stretch goal because the compiler complexity (event trigger identification + argument role assignment + role-filler type matching) is disproportionate to the core contribution.

**Phase 2: Experiments (Day 6-10).** Two decoding strategies:

Serves as the direct comparison point. **Structure Snowballing risk mitigation for S1:** Since Qwen3-8B showed a 12pp accuracy drop under constrained decoding on HotpotQA reasoning tasks (Zhou, arXiv 2604.06066), S1 may exhibit similar degradation. However, the snowballing mechanism — formatting compliance consuming reasoning capacity across multi-hop self-correction — is specific to iterative reasoning; single-pass IE extraction is less reasoning-intensive but more structurally complex. Phase 0's format tax measurement directly quantifies this risk for IE before committing to full experiments. If S1 shows severe degradation on Qwen3-8B, we additionally evaluate **soft logit biasing** (adding a large negative bias, e.g., −20, to type-violating tokens rather than masking them to −∞) as a relaxed alternative that still strongly discourages violations while preserving some probability mass on borderline cases, reducing the cognitive load of hard constraints.
