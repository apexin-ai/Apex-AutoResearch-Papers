## 1. 项目概况

- **课题**: From Ambiguity Type to Safety Severity: 在 τ²-bench 上对 6 类 policy ambiguity 与 LLM agent 安全违规之间的因果关系做 matched-pair 实验
- **Venue**: 由 ICLR 2027 切到 EMNLP 2026 (ARR May cycle, DDL 2026-05-25)；正文 8 页 + 26 页附录
- **实验规模**: 17 个 registered experiments，全部 DONE（13 success / 4 negative），平均 retry=0。2,997 episodes (5 models × 300 clause pairs × 2 conditions) 是主数据集，外加 plan_013 model expansion (Gemini/LLaMA) 与 SOPBench/Healthcare cross-benchmark
- **资源消耗**: 365 session 文件、42,881 turns、~25M output tokens、399 tool errors、15,869 minute · role-runtime（≈ 265 小时）。9 个角色（agent/director/reviewer/worker/paper-agent + 4 个 audit 子角色）
- **沟通规模**: Director 群聊 3,117 条、Reviewer 群聊 3,115/2,768 条、Paper Agent 群聊 1,228 条；4 名活跃人类参与者，共 ≥230 条人工 inbound 消息
- **论文状态**: 最终 main.pdf 816 KB / 16 页（8 正文 + 8 附录），64 references，34 轮审稿 (R0-R34)，最终评分 **3.5 (Borderline Conference)**

数字层面这是一个"高效完成 + 高产出"的项目，但评分曲线讲了另一个故事：33 轮可比审稿中，仅有 R5 和 R16 两轮短暂触达 4.0，其余 31 轮全部停在 3.5，R1/R2/R27 甚至跌到 3.0。这是项目质量的关键信号，本报告将围绕它展开。

## 3. 科研目标达成度分析

### 3.1 Idea → Findings 的逻辑链

| 阶段 | 主 claim | 数据支持 | 状态 |
|------|---------|---------|------|
| IDEA_BRIEF (5/20) | 不同 ambiguity type 导致差异化 safety violation；scopal 最高、lexical 最低 | — | **被否定** (mvp_001) |
| MVP 后 (5/20 10:24) | All ambiguity is uniformly nocuous (type effect null) | mvp_001 + diag_001 | **被自己的实验否定** (plan_002) |
| 5-Model 后 (5/20 21:00) | Layer hierarchy: spec >> ling (~19pp) | plan_002 (2-model) | **被自己的实验弱化** (5-model 收缩到 6pp) |
| R14 (5/22) | Type-mechanism dissociation: type 预测 mechanism 而非 violation rate | plan_004 variance decomp + plan_005 mechanism mapping | **保留至终稿** |
| 终稿 | Convergent nocuity + clause-level > type-level auditing | inter_model_nocuity + variance decomp | **保留** |

**逻辑链总评**：原始 idea 的中心假设（type → severity）在第一天就被推翻。后续 5 个月路径上的所有主张都是**对负向结果的二次包装**：

- "Uniform Nocuity" → 数据反对
- "Layer Hierarchy" → 数据弱化
- "Differential Nocuity" → R14 自己承认 0.4% 方差
- "Type-Mechanism Dissociation" → 这才是与数据匹配的 framing，但它本质是**承认 taxonomy 没有 risk-stratification 能力**

最终论文是一个"承认核心假设错了"的研究，但它把这个承认包装成了 contribution（"clause-level > type-level auditing"）。这是**诚实的科研**，但同时也意味着这篇论文的真正贡献 = (1) +34pp 因果效应量化 + (2) convergent nocuity 现象学描述。Taxonomy 本身只剩诊断价值。

### 3.2 实验设计的科研严谨性

**优点**：
- Matched-pair + perturbation control 设计扎实，因果识别可信（plan_010/014 都 PASS）
- 多重统计敏感性：TOST 7 种 margin、Holm-Bonferroni、bootstrap CI、ICC 重复性 (0.919)、5-model + 2-model expansion 共 7 模型
- 显式预承诺 null result scenario（D014/D016 contingency framing）
- Negative results 不被掩盖（mvp_001/diag_001/plan_016 都登记为 negative）

**问题**：
- **信息添加混淆是系统性的而非局部的**。所有 6 类型的消歧版本都比歧义版本长 17-36 词，但论文一直只把 incompleteness 标为有混淆。R27 跌到 3.0 主因就是 Reviewer 指出 confound-free 标签不准确。Coreferential 是唯一干净比较 (+18.7pp)，但论文不愿意收缩到这个下界。
- **Convergent nocuity 与 ambient baseline 比较**只用了 1.7% 的 ambient rate，但 ambient 与 ambiguous 任务的难度结构不同，类比可疑。
- **Type-mechanism dissociation V=0.45** 完全来自 LLM 编码（AC₁=0.62），人工编码 κ=0.15（合并 4-类后 0.38），circularity risk 在终稿仍未充分披露。
- **Judge-model identity 完全交织**——Claude/Qwen3/DeepSeek 全部由 GPT 系 judge 评判，跨判官组排序 ρ=0.09 (排除 auth scope 才到 0.90)。论文以 "judge bias 被差分消除" 为由保留 pooled 估计，但 Reviewer 多次质疑（DIV2 终稿仍存）。

### 3.3 Findings 的 Novelty 与质量

**真正的 novelty**：
- **+34.0pp matched-pair 因果估计**是该领域首个有 perturbation control 的因果证据（R5 reviewer 也确认）
- **Convergent nocuity** 是真有理论价值的现象学描述：41.3% clause pairs 在 ≥3 模型上收敛到同一错误解释，违反 Berry & Kamsties 的 "divergent = nocuous" 默认假设

**包装出来的 novelty**（实质是负向结果包装）：
- "Type-mechanism dissociation" = type 不预测 violation rate 但预测 mechanism。问题：mechanism 编码靠 LLM，dissociation 强度受编码相关性影响
- "Disambiguation channel framework" = 解释为什么 spec-layer 更差。先有结论后有框架，且 5-model 数据后 layer effect 本身只剩 6pp
- "Convergent nocuity" 现象本身有价值，但它需要 ambient baseline 才能 quantify "excess convergence"，而 ambient 的选取是事后

Reviewer 在 R34 给的最终分数 3.5 反映了这个混合状态：方法论 part 4.0 水平，novelty/positioning part 3.0 水平。

- 跨 5 模型并行实验编排顺利（plan_002c + 003a + 003b 在 4 小时内完成）
- 自检质量较高：M002 修复后增加 preflight + validation + error guard
- Worker spawn 与 callback 处理整体可靠（54 个 Agent session、171 个 Worker session，无 crash）

**做得不够**：
- M007 +16.3pp 错误：Agent 计算 Poisson binomial 时出 bug（113/250 而正确 93/250），错误数字被写入论文 3 处后才被 Director 抓出
- 8,928 minutes 总 runtime + 18,295 turns + 6,815 tool uses — Agent 是最重的角色，但**有 5/9 角色 (paper_agent/paper-figure-add/distiller/paper-audit-*) 实质是 Agent 的细分**，整体 orchestration 复杂

### Paper Agent

**做得好**：
- 在 R5 时一次性整合多种证据 (human validation + perturbation + Gemini/LLaMA + 新 discussion) 推到 4.0
- Round 30-34 阶段处理 reviewer minutiae 反应及时

**做得不够**：
- **20+ 次 "你刚才完成了 Director 指令但没有调用 main_agent_post_to_director 汇报结果" 系统提醒**——Paper Agent 的"完成动作但不汇报"是稳定模式。说明 prompt 里的 "post back" 指令优先级不够高，或是 agent 把工作完成本身当成回报。这是显著的 harness 设计问题
- 多次写入 framing 中的数字与权威数据源不一致 (M006 violation threshold、Fig 8b Jaccard 9/10 错误值)

### Worker

171 个 worker session，3,763 tool uses，134 errors（占 tool uses 3.5%）。错误集中在：
- 单 session 错误高的几个：worker_code_plan_009_judge_calibration_framework (15 errors)、worker_code_plan_005_gpt41_analysis (12 errors)、worker_research_taubench_policy_format (7 errors)
- 错误模式："File content exceeds maximum allowed tokens" + "ECONNREFUSED" + tool retry 重复 — 都是 harness 边界问题，不是 Worker 推理质量问题

### 协作模式与摩擦点

- **Director ↔ Reviewer**: 6 个 reviewer loop + 6 director loop，期间有 5 次 WRITE_HANDOFF (loop 间内存压缩)。每次 handoff 都包含完整的"硬约束 / 红线"部分，说明项目 invariants 不能通过文件持久化而需重复注入到 prompt
- **Director ↔ Paper Agent**: paper agent 不通过统一的 callback 而通过 main_agent_post_to_director 反馈，但 paper agent 经常忘记调用 → 系统提醒触发 → 形成无效的"通信调解"反馈环
- **Director ↔ User (人工)**: 用户消息混在 source="feishu:..." 里，与 Reviewer/Agent 消息走同一 channel，没有显式 priority。Director 多次在用户问"有进展吗"时还在处理 review report

## 5. 关键发现

### [HARNESS] F1（严重）API 失败 silent fallback → fake PASS → 下游决策污染

**证据**: M002 (high severity, mistakes.yaml#M001)。plan_010 第一次跑出 120 episodes 全部 API 失败，但 `run_full_study.py` 的错误处理把 `violation_level` 默认为 `"none"`、confidence=0.0，于是 100% 失败的实验呈现为 100% 干净的"PASS"。Worker 没察觉，Director 据此批了 D018 (plan_002 launch)。Reviewer 检查原始数据才抓出。

**严重程度**: 极高。直接污染 ~$30 实验资源 + 把项目 2 小时（plan_002 提前启动）推到错误路径，**但更严重的是它揭示了一个普遍模式**：harness 层默认的 "graceful degradation" 在科研场景下是**反模式**——失败数据被填成合理值反而比明确报错更危险。本项目其他 worker script 是否也有同样模式没被系统性 audit。

**改进建议**:
1. Workspace 级别强制：所有 episode-level scripts 必须有 `--strict-error-mode`，API 失败立即 raise + 写 `status="failed"`，绝不 fallback 到 schema-valid 但语义错误的 default
2. Spawn worker 的 director_protocol 加入一条："Worker 报告 PASS 时，必须包含 `assert n_episodes_with_actual_response >= 0.95 * n_planned` 输出"——Director side 自动 reject 没有此 assertion 的报告
3. Registry 加 schema 校验：experiment 标 success 时必须有 metrics 字段且关键字段非零

### [HARNESS] F2（严重）Fresh-review mode 在长项目中是 net negative

**证据**: 34 轮审稿中至少 28 轮 review_mode=fresh。同一份论文被打过 3.0 / 3.5 / 4.0 三个分数（R1/R5/R6 间隔不到 24 小时）。R5 (4.0) 后没有"基线锁定"机制，下一轮重启评分 0 → 3.5。Reviewer 反复在不同轮次提出又收回同一批 issue（如 "judge confound" 在 R1, R7, R14, R22, R28 都被提）。

**严重程度**: 高。该项目花在审稿循环上的 reviewer/director runtime ≥ 200 小时（按 reviewer 总 3,154 + director 总 2,141 minutes 估计），其中大量浪费在重复发现相同问题。Score 永远在 3.5 ↔ 3.5 之间震荡，没有"已 resolved" 的累积。

**改进建议**:
1. 默认 mode 应该是 continue 而非 fresh。Fresh 仅在重大 framing pivot（如 R14 type-mechanism dissociation）时显式触发
2. Reviewer prompt 加 "Issue Tracker" 状态文件，记录每个 issue 的 (round_raised, round_resolved, severity)。Fresh-review 也要 import 这个状态作为 context，避免重复 raise
3. 评分系统应该有 "高水位回滚阈值"——一旦达到过 4.0，后续 round 不能低于 3.5 除非有新 critical issue。当前震荡说明 reviewer 评分有 ±0.5 的 noise floor

### [HARNESS] F3（高）Paper Agent 不主动调用回报函数

**证据**: feishu_group_oc_c58486bc9afb8c730ded5e31c0e7d639_paper_agent.jsonl 中 system reminder "你刚才完成了 [Director 指令] 但没有调用 main_agent_post_to_director" 出现 20+ 次，跨 3 天。每次出现表示一次延迟回报，Director 在此期间盲飞。

**严重程度**: 高。每次 paper agent 完成 director 任务后到下一次 director check-in 之间的间隔（多次 > 30 分钟）是纯 idle，且 Director 缺这部分信息时往往会基于过时假设做下一步规划。

**改进建议**:
1. Paper Agent system prompt 把 "调用 main_agent_post_to_director 汇报" 从"完成动作后"提到"完成动作前先 plan 一个 post"——把回报作为 task lifecycle 的 entry condition 而非 exit
2. 引入硬约束：paper agent 内部 task ledger 显示 "completed but not reported" 状态时禁止开始下一个 task
3. 或：把 post-to-director 改为 hook（tool 调用后自动触发），不依赖 agent 主动调用

### [HARNESS] F4（高）Reviewer 大量 idle-timeout-reset 循环

**证据**: ralph_loop_timeline.jsonl 中 reviewer 角色 24 次 HARD_LIMIT_REACHED (trigger 大多为 `idle_timeout`，idle 480-720 分钟)，3 次 ESCALATED_SILENT。一个 reviewer instance 在 5-25 早上 11:26 - 15:27 反复请求 reset 但 director 都不应答，最后用户介入。

**严重程度**: 中-高。Reviewer 处于"无 review 任务 idle → 触发 limit → 请求 reset → director 忙 → 又 timeout"循环，消耗系统资源但不产生新审稿。同时，当 director 真的需要 reviewer 时（如夜间提交 paper），reviewer 可能正在 reset 状态。

**改进建议**:
1. Reviewer idle 策略：超过 60 min idle 自动 graceful shutdown（写 handoff 落盘后关闭 session），需要时按 spawn-on-demand 启动
2. 区分 "active review session" 和 "review server"——后者应该是 lightweight worker pool，不持有 conversation context
3. Director 收到 RESET_REQUEST_SENT 应该有 SLA：5 分钟内无响应自动 fallback 到 yes-reset 策略

### [HARNESS] F5（中）Distill skill 引用幻觉污染整个论文链

**证据**: M003。`distilled-research.skill.md` 蒸馏出 3 条完全虚构的引用（DRIP-R 作者/年份/会议全错；PhantomPolicy、AgentPex 同样）并 +5 条元数据错误 + τ²-bench/τ-bench 混淆。这些被 paper_framing.md 不加验证地采用，再写进 paper draft。Reviewer R1 才在 SF-7 抓出，触发紧急 verify + global rename。

**严重程度**: 中。本项目内被及时拦截，但暴露 distill 工具产出**未经验证就进入下游 artifact** 的系统性漏洞。如果 Reviewer 没抓出，投稿带虚构引用是 desk reject 级别。

**改进建议**:
1. distill_papers 工具产出强制经过 reference-audit skill（WebSearch + Semantic Scholar verify）再写入文件
2. paper_framing.md 和 experiment_plan.yaml 加 "external citations" section，所有此类引用必须有 `verified_at` 时间戳和 `verification_source` 字段
3. Reviewer system prompt 加入对 distill 输出的"signature suspicion"：作者/年份匹配过于标准化的引用要求复核

### [HARNESS] F6（中）人工消息与 agent 消息走同一 channel 无 priority

**证据**: 35 条 source="feishu:..."（人工消息）与 reviewer/agent 消息混在同一 jsonl 文件，Director 多次在用户问 "有在做实验吗" 时还在处理别的任务，响应时间不稳定。Ralph Loop 关闭后用户消息处理速度 ≈ 几分钟，开启时可能 30+ 分钟无响应。

**改进建议**:
1. 人工 inbound 应有显式 priority flag，Director 角色 prompt 中要求"人工消息 in <2min ack"
2. 或更彻底：把人工消息 routing 到不同 endpoint，强制 Director session 切上下文
3. ESCALATED_TO_HUMAN 机制实际从未触发 (timeline 仅有 3 次 ESCALATED_SILENT 但都是 reviewer 等 director)。系统**没有 escalate to user** 路径，所有人工干预都是用户主动 ping。这是设计上的方向反了

### [MODEL] F7（高）Director 在压力下倾向于 over-correction（连锁修复）

**证据**: M004 是典型——Reviewer 报告 τ²-bench arXiv ID 错误，Director 误以为是"我们用了 τ-bench"，未读 config.py 就全局 rename τ²-bench → τ-bench。47 分钟后发现错误又全部回滚。M003→M004 是一连串：先纠错 distill 引用，然后纠错纠过头。

类似模式在 framing pivot 链上也出现：D020 (uniform → differential 4 小时) → D024 (5-model 后 layer effect 收缩，但 framing 已经定型) → D025 (R11 后 C2/C3 robustness 又跑 4 个 sensitivity) → D027 (R14 后 type 解释 0.4% 终于反思 framing) — 每一次新数据都触发结构性 framing 调整而非微调。

**严重程度**: 高。每一次大 pivot 牵动 paper_framing.md (253 行) + writing_plan.yaml (259 行) + paper draft (1,227 行) + figures。修改成本是 indecision 成本的好几倍。

**为什么是 MODEL 而非 HARNESS**: 这种"基于单一证据就大改"的模式在多个独立 Director session 中一致出现（loop 1 + loop 2 + loop 5 都有），不是 prompt 工程问题。

**改进建议**:
1. Decisions.yaml 加 "reversal_cost" 字段，凡是 reversal_cost=high 的决策必须 24h cooldown + reviewer 二次确认
2. 重大 rename / global replace 操作走专门 skill，强制先 grep 出所有 hits 让 Director review

### [MODEL] F8（中）数学/统计计算的 silent error

**证据**: M007 Agent 计算 Poisson binomial 时把 113/250 误算成正确的 93/250 应该是 37.2% 不是 45.2%，导致 +16.3pp excess 写入论文 3 处。Director 通过逐项加总 per-type majority_plus_rate 才抓出。M006 violation threshold 用错（any-violation 而非 moderate+critical）也是类似——Director 没 cross-check 阈值定义就写数字。

**严重程度**: 中。两个错误都被抓出来了，但抓出来的方式是**手算复核**，而非系统化校验。如果项目有 50 个数字而非 5 个，漏网概率提高。

**改进建议**:
1. 所有写入论文的统计数字必须有 `data_source` (json file path) + `computation_script` (py file path) 双 reference 在 paper_provenance.yaml 中
2. 论文 pre-submission 检查 hook：自动 reload data_source 重算所有数字，与 paper 中数字 diff
3. 此项目实际有 paper_provenance.yaml lock，说明意图存在，但没有强制使用

### [MODEL] F9（中）框架抗反对意识不足，倾向把负向结果包装为正向

**证据**: 项目核心叙事经历了 4 次 pivot，每次都把"前一个假设被否"包装成新主张：

- mvp_001 type effect failed → "uniform nocuity is informative null"
- plan_002 uniform failed → "differential nocuity"
- 5-model layer effect collapsed → "model × type interaction is star"
- 0.4% variance exposed → "type-mechanism dissociation"

这是 publishing pressure 下的合理行为，但 Director 在每个 pivot 时都把新 framing 立刻 freeze 到 paper_framing.md，没有保留"如果继续 falsify 怎么办"的备选。终稿其实在 R14 已经承认 "type for screening fails" 但论文结构仍围绕 6-type taxonomy 组织。

**为什么是 MODEL 而非 HARNESS**: pivot 决策来自 Director 推理（"how to frame this paper for EMNLP"）。Reviewer 多次质疑 over-claim 但 Director 反复辩护。这反映 Director 模型在"承认 negative 但继续推进" vs "重新审视根本 question" 之间倾向前者。

**改进建议**:
1. 每次 framing pivot 时 Director 必须填写一个 "abandoned claim" 表单：原 claim、证据强度、与新 claim 的 incompatibility — 用以避免新旧 framing 在论文中残留共存
2. Pre-submission 必须 dispatch 一次"红队 review"：assume reviewer believes 你的核心 claim 是错的，他会怎么 attack？

### [INFRA] F10（低-中）OpenRouter 余额耗尽多次阻断实验

**证据**: 5-22 22:26 出现 402 Insufficient balance，Cross-Judge Validation 实验失败；5-21 03:42 OpenRouter 余额不足导致 plan_011 + Ambiguity-Conditioned Safe Execution 暂停。Director 不知道余额，依靠用户充值通知。

**严重程度**: 低-中。每次阻断 10-30 分钟，但累计触发了 5 次用户介入。

**改进建议**:
1. spawn_worker 之前 director 必须 check API budget (添加 `check_api_budget` tool)
2. 余额低于阈值时主动 alert 用户而非等到实验失败

## 总结

policy_ambiguity_safety 是一个在 6 天内完成 17 实验 + 8 页 EMNLP 论文 + 34 轮内部审稿的高速项目。它在**执行效率**上接近最优：MVP 在 1 小时内跑完并发现核心假设破产；5 模型扩展在 4 小时内完成；perturbation control 同步上线；最终论文 16 页结构齐全。

但它在**研究产出质量上停在 3.5**，这个数字稳定到几乎是项目自身的不变量。核心问题不是某一处可修复的 bug，而是**数据本身只支持 3.5 水平的故事**：6-type taxonomy 解释 0.4% 方差，但论文结构围绕该 taxonomy 组织——所以 reviewer 永远会发现"narrative-data mismatch"。

最大的 [HARNESS] 教训：
- F1 silent API failure → fake PASS：最危险的失败模式
- F2 fresh-review noise：30+ 轮空转
- F3/F4 角色生命周期管理：Paper agent 不回报、Reviewer 不死

最大的 [MODEL] 教训：
- F7 Director 倾向 over-correction
- F8 silent math errors 需要系统化校验
- F9 把负向结果反复包装为正向，最终离最初的研究 question 越来越远

如果重做，最大的杠杆是**在 D020 那一刻（5-20 21:00, 5 模型扩展前）就开一次 "我们要不要继续这个 taxonomy 课题" 的 strategic review**。data 已经在告诉项目 "type 没差异"——继续做 5 模型扩展只会把这个结论变得更稳健，不会变得不一样。当时如果转向 "convergent nocuity as the paper" + matched-pair causal evidence，paper 的核心 claim 与数据完全对齐，可能 R5 4.0 → R34 4.0 而非 R5 4.0 → R34 3.5。
