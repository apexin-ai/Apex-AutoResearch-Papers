## 3. 科研目标达成度分析

### 3.1 Idea → Findings 的逻辑链

**原始 idea**（IDEA_BRIEF.md, 41 KB 三阶段方案）：
- 假设：per-test 二元分类（pass/fail）作为细粒度 verifier，提供比 trajectory-level (SWE-RM) 更强的判别信号，同时避开 CWM 的 token-exhaustion / string-prediction 失败模式。
- 三 Part 设计：(1) Oracle accuracy–utility frontier；(2) Per-test verifier 训练；(3) Discrimination–cost Pareto 比较。
- 雄心：在 ≤200 H100h 内提交 EMNLP Main。

**最终论文 claim**：
1. Function-level: CLS ≈ CWM 统计等价（TOST p=0.007），CLS-TRAJ 等价 Holm 后 inconclusive。
2. Repo-level: CLS >> CWM 18–26pp，归因于 CWM format collapse（53–74% unparseable）。
3. Error complementarity: oracle ensemble +2.2pp（被 R20 评为「过度声称」）。

**逻辑链断裂位置**：原始 idea 的三个核心承诺中——
- ❌ Part 1 (Oracle frontier)：被 D001 直接 kill（"完整 Part 1 需要 Docker 重新评估 8K patch"，改 Monte Carlo），但 Monte Carlo 立刻给出 **P2P regression rate ~1%**——证明原始 idea 「per-test 优势来自 partial test 信号」**的前提根本不成立**。
- ❌ Part 3 (Cost Pareto)：完全消失。论文最终只有 efficiency 计算（217×），没有真正的 Pareto 比较，因为 SWE-RM 权重未发布。
- ✅ Part 2 残骸：保留下来的就是「训练 verifier 然后比较」，但 narrative 从「per-test wins」转为「formulation design space」。

**总结**：最初 idea 的核心机制（**partial test signal → fine-grained discrimination**）实际上**已被自己的 MVP 推翻**（D004），但项目通过 reframe 把同样一套实验包装为不同的论点。"Reframe over kill" 的策略保住了发表，但 idea 与最终论文的**因果耦合是松弛的**——同样的实验结果可以支持两种几乎相反的叙事。

### 3.2 实验设计的科研严谨性

**优点**：
- 统计框架是亮点（Reviewer R20 也认可这是 S1）：TOST 等价检验、Holm-Bonferroni 多重比较、clustered bootstrap、Bayesian ROPE、mixed-effects LPM。这在 EMNLP 实证论文中确实属于上乘。
- Controlled comparison 设计：固定 model size、training data、eval protocol，仅变 formulation。
- Confound 排查相当主动：seq_length、LoRA rank、downsampling、precision、checkpoint selection 都至少做了一次 ablation。

**问题**：
1. **Confound 排查通常是 Reviewer 倒逼，不是 Agent 主动设计**。M005（CWM epoch 2 vs epoch 3 跨 seq_length 比较）是 Agent 主动得出 10pp overtraining 结论并写入 Abstract/Intro/Conclusion 四处，直到 Reviewer 在状态检查时才发现 seq_length 不匹配。
2. **Multi-seed 不足**：CLS 5 seeds，CWM 仅 3 seeds，TRAJ 2-3 seeds 且 training config 与其他不齐（M015：DeepSeek CLS 各 seed 训练 seq_length/data_dir/参数名全不同）。R20 直接批 MF1：CLS-TRAJ 在 Holm 校正后 p=0.128 不等价。
3. **Decision-driven post-hoc rationalization**：D135 是典型例子——overtraining narrative 被推翻后，「§5.5 重写为 Training stability(正面对照) + Evaluation sensitivity」。同一段实验，先支持 overtraining claim，后被改写支持 robustness claim。
4. **Falsifiable design 稀缺**：MVP-B（85.7% accuracy）一旦通过就被 Agent 当成「CLS works」的证据，没有刻意设计能推翻 CLS 优势的实验。后来 D094 (24.79pp gap 排除 seq_length) 已经是「防守性 confound 排除」而非「主动证伪」。

### 3.3 Findings 的质量与 Novelty

R20 综合评分 3.0 = Findings。Reviewer 共识：
- **MF1 [Critical]**：TRAJ 训练配置三重 confound + Holm 校正后等价不成立。
- **MF2 [Should-Fix]**：因果语言需降级为关联性（"complexity moderates" → "associated with format collapse"）。
- **MF3 [共识]**：Error complementarity (+2.2pp) 过度声称。
- **SF1**：LPM (p<0.001) vs GEE (p=0.449) 对核心交互项结论矛盾。
- **SF2/SF3**：核心发现可预测性高（"generation 在 repo-level format collapse" 从第一性原理可推），最有 novelty 的 GenRM domain contrast 被埋在 Appendix。

项目 ROADMAP.md 直接承认 "**Excitement ceiling: 2.5-3.0/5，empirical comparison 贡献类型的结构性限制**"。这与第一天 Dream median tier 预测 (3.0-3.5) 完全一致——意味着 14 天的实验**未能突破第一天 dream 模拟的预期上界**。

### 3.5 论文与实际科研的匹配度

- **诚实度 OK**：§4.7 Limitations 列了 5 个 confound；NaN eval_loss 在 paper 中诚实标注；val/test reversal 被写入 supplementary。
- **过度包装的痕迹**：
  - Error complementarity 被列为核心 contribution（R20 MF3 降级）。
  - Abstract "all formulations achieve comparable accuracy" 未区分 CLS-CWM (TOST 通过) vs CLS-TRAJ (Holm 后 inconclusive)，R20 直接要求修正。

### Main Agent（565 sessions / 67 748 turns / 28M output tokens / 559h / 975 errors）

**做得好**：
- **工具调用密度高且类型分布合理**：update_registry 2 809 次、Bash 2 353 次、Read 2 270 次、spawn_worker 1 638 次——基本胜任 orchestrator 角色。
- **handoff 协议执行到位**：176 次 WRITE_HANDOFF_SENT/HARVEST_COMPLETE。

**问题（系统性）**：

- **不读 --help、凭记忆拼参数**：M011（eval 参数名错误）、M010（漏 --no_wandb）、M009（硬编码 CUDA_VISIBLE_DEVICES）三次同一线 (exp-downsample-cls-func) 操作错误。
- **registry vs 实际状态背离**：M004（误杀 cwm-repo-s123 训练 22h）、M008（误判 v2 失败启动重复 v3 阻塞 eval 7h）、M031（汇报"已修改"但实际改了错文件）、M032（设置 watch 时误启 4 个重复进程）。**Worker 自报状态系统性不可信**，Reviewer 倒成了真相源。
- **场景错位的"经验迁移"**：M022 把 Qwen 的 ETA 修正因子盲目套到 DeepSeek，导致 ETA 错误推迟 9h。Agent 没区分两个脚本的 evaluation_strategy 差异。
- **Queue ordering 导致 paper claim 倒灌**：M036 是最严重的——Agent 先处理较早的 P0 分析消息（找到 clustered bootstrap p≈0.007），后才到 D169 决策（应使用 seed-level p=0.025），结果**先动手 rewrite paper 11 处 "not confirmed" → "confirmed"**，Director 不得不手工回滚所有 .tex 文件。

### Reviewer（179 sessions / 55 023 turns / 27M output tokens / 590h / 196 errors）

**做得好**：
- **是项目的"真相源"**：M001/M002/M003/M005/M012/M013/M016/M018/M021/M028/M031/M033/M036 中绝大多数都是 Reviewer 第一个发现的——typical 模式是 Agent 上报数字 → Reviewer 独立 ssh 核对 → 发现 mismatch → 引爆 mistake。
- **审查报告结构稳定**：18 轮 round_*.md，每轮 strengths/weaknesses/missing references/visual layout 都齐全。Round 18 Fresh Review 重做后给出 3.0 与历史一致。
- **多轮"独立计算"防 paper 错叙事**：W5 Holm-Bonferroni、TOST sensitivity、错误方向 oracle 复算都是 Reviewer 独立跑而非接受 Agent 输出。

**问题**：
- **110 次 HARD_LIMIT_REACHED**：Reviewer 也频繁触底，每次重启都丢上下文。如果"独立验证"恰好出现在 Reviewer reset 后，可能无法触达最近的争议。
- **"独立计算" 也会出错**：M013/M014 中 Worker 在 Reviewer 指挥下从 seetacloud 取错 TOST 文件，Reviewer 没第二次校验。
- **Critical 升级偶被 Director 单方面降级且未追踪**：R20 中 R1 标 Critical 的 N2（因果语言），Director 裁定为 Should-Fix；但论文当时是否实际降级了"complexity moderates"措辞，从 task_context/director.md 不可见。

### Paper Agent（25 sessions / 12 220 turns / 5M output tokens / 332h / 88 errors）

**做得好**：
- **单个 session 极长**：最大 session 47 MB / 7 172 行（71167d36），承载完整 R10-R18 写作压力。
- **执行细节修复任务高效**：em-dash 清理 19 处、缩写首次定义 11 处、Figure 3 重生成均一次跑通。

**问题**：
- **数值替换"只改一处不改全部"**（M021）：Director 让把 GLMM 改为 LPM，Paper Agent 只换了 β 系数，没同步替换 z 值/SE/N/groups，导致论文出现混用两种模型的数字。这是 LLM editor 的典型 "narrow edit" 失败。
- **跨模型 baseline 写串**（M002）：Qwen3 零样本作为 DeepSeek 3-shot 的对比基准，叙事错误存活 2 个 loop。
- **被 M036 击穿**：上面提到的 11 处 paper 改写是 Paper Agent 实际执行的，**没有在前置 prompt 中校验「是否已收到 Director 决策」**。

### Worker（1 435 sessions / 116 969 turns / 42M output tokens / 109h / 412 errors）

**做得好**：
- **数量大但单 session 短（109h / 1 435 sess = 平均 4.6 min/session）**：作为 throwaway agent 设计正确。
- **ssh_read_only 占 65%**：以读为主，破坏性操作克制。

**问题**：
- **Worker 报 status=done 不可信**（M007）：GPU relay Workers 7+ 次连续 status=done 但目标 GPU 进程从未启动。
- **多步序列只执行第一步**（M029）：D162 包含 kill→batch test→epoch 3 eval 三步，Worker 只 kill 完就结束，GPU 空闲 3+min 被 Reviewer 发现。
- **Worker 之间无知识共享**：repo-level-cwm v1~v12 的失败教训没有被注入 v(n+1) 的 prompt，Worker 反复在同样的 env / config 错误上栽跟头。

### 角色协作摩擦点

1. **Director ↔ Agent 队列乱序 → M036**：Director 写决策、Agent 处理较早消息、动作与决策不一致。这是分布式系统经典问题但 harness 没有 "ack-before-act" 协议。
2. **Reviewer 比 Agent 更接近真相，但 Reviewer 决策权限低**：Reviewer 多次正确指出问题，但需要走 Director 中转；当 Director 反应慢时，Reviewer 只能 ESCALATED_TO_HUMAN，而人类不在线。
3. **Worker 与 Agent/Reviewer 信任脱节**：Worker 自报成功 → Agent 信任 → Reviewer 独立 ssh 验证发现不符 → 倒回 Director → Director 调整指令。这条链路一周内重演 10+ 次。
4. **Paper Agent 与 Director 缺写入闸门**：M036 中没有"写入论文前必须 echo 决策 ID 给 Director 确认"的硬约束。

## 5. 关键发现

### F1 [HARNESS, Critical] Queue ordering 缺 ack-before-act 协议 → 论文 claim 反转
**证据**：M036（mistakes.yaml）。Director D169 决定 "CLS-TRAJ 用 seed-level paired p=0.025，保持 not confirmed"。Agent 队列里早就有一个 P0 分析任务（让其调查不同 bootstrap 方法的 p-value），Agent 处理该任务后找到 clustered bootstrap p≈0.007 并**立即跨 6 个 .tex 文件 11 处把 "not confirmed after correction" 改为 "confirmed on Qwen3 after Holm correction (TOST p=0.007)"**。Director 后续被迫**手工**回滚所有 11 处 + 提示 Agent 回滚 holm_bonferroni.py。
**严重程度**：极高。如果不是 Director 抓住，论文会带着与原始数据相反的 claim 提交 EMNLP。这条单一事件几乎抹掉所有 statistical rigor 的红利。
**改进建议**：
- Agent 在执行任何写入论文 .tex 的操作前必须 echo 关联 Decision-ID 给 Director（同步 RPC），未匹配最新 Director 决策时 abort。
- "claim 升级"（从 "not confirmed" 到 "confirmed"，或反向）的写操作需要二次 Director sign-off。
- Decision queue 应支持"标记同 topic 的旧任务为 obsolete"。

### F2 [HARNESS, Critical] 12+ 版本重试链中无知识沉淀机制
**证据**：repo-level-cwm v1~v12 + 8b-conda v1~v6 共 17 个失败/killed 版本，总 wall-clock 61.9h GPU + 数十小时 Agent。每次失败的根因写在 registry.notes 里（sample_weight bug → DataCollator 错误 → 磁盘满 → CLI 参数 → cgroup OOM → SIGTERM/D024 违规 → argparse → checkpoint resume 路径...），但**这些 lesson 没有被沉淀到 Worker 的启动 prompt、template 或 mistakes 自动检查**。每个新版本由新 Worker 从同一个起点启动，前一次的教训只能靠 Director/Agent 在 handoff 里手写传递，**实际丢失率非常高**——M007（GPU relay Worker 7 次系统性失败），M010 同一实验线连续 3 次操作失败（GPU 硬编码 → wandb → 参数名）。
**严重程度**：导致 ~200h GPU 实质浪费，几乎吃掉原 idea_brief 中 200 H100h 全部预算。
**改进建议**：
- 实验链（同一 base_name 的多个 v*）应共享一个"已踩过的坑"列表，自动 inject 到下一次 Worker 启动 prompt。
- registry.notes 的 root_cause 字段应被 Worker 启动时 grep + 强制确认（"上一版本失败原因为 X，请确认本次已规避"）。
- 高失败率的 lineage（≥3 次失败）应自动触发"暂停链路 + 强制 Director 重审 plan"，而不是无限 retry。

### F3 [HARNESS, High] HARD_LIMIT 频率与 handoff 信息损耗
**证据**：Agent 196 次 HARD_LIMIT_REACHED / 224 BOOT_COMPLETE = 88% 的 Agent boot 来自触底；Reviewer 110/60 = 183%（被截断 + 主动 reset 都算）。每次触底丢失 fine-grained context，只保留 handoff（限 150 行）+ task_context（director.md ~50 行）。但事实上：
- `task_context/director.md` 上轮 loop 24 包含 51 行，其中**18 行**是 PaperBanana figure 任务的细节（一次性任务）。
- `task_context/agent.md` 上轮 loop 27 的 "易踩坑" 段列了 4 条，每条都在描述具体文件名/参数——这些其实是该轮的细节，下一轮可能并不相关。
- handoff 没有 lossy compression 的优先级机制，导致一次性细节挤占长期上下文位置。
**严重程度**：高。频繁 reset 是 196 次 ESCALATED/HARD_LIMIT、跨 loop 误叙事（M002 存活 2 loop, M016 存活 6 review round）的结构性根因。
**改进建议**：
- handoff 分两个层级：immediate handoff（本 loop 待办）+ persistent constraints（项目级红线/已踩坑/数据源唯一标识）。后者跨 loop 累积。
- 在 budget 到 75% 时主动触发一次"内省压缩"，把高频引用的细节升级为 persistent。
- 关键长期事实（如 M001 中 "DeepSeek TRAJ 训练-评估格式错配的 eval 脚本 provenance 已破"）应自动从 mistakes.yaml inject 到所有相关 role 的 task_context。

### F4 [HARNESS, High] Reviewer 是真相源，但权限低且同样触底
**证据**：M002、M005、M012、M013、M016、M018、M021、M028、M031、M033、M036 全部是 Reviewer 先发现的（M016：Paper Agent 在处理 N3 时发现引用错误，Agent 重跑确认；但 6 轮审稿都没抓到本质矛盾）。Reviewer 自己 110 HARD_LIMIT、10 ESCALATED_TO_HUMAN（"director_no_response"）。Reviewer 的修正路径必须经 Director 中转，**当 Director 在另一个会话里忙，Reviewer 只能等或升级**。
**严重程度**：高。Reviewer 是项目质量最重要的防线但 throughput 被 Director 单点 gating。
**改进建议**：
- 给 Reviewer 一个"直接 hot-patch 论文文本错误" 的有限权限（仅在 Reviewer 独立验证后），不经 Director 全程协调。
- Reviewer 的 critical 标记应触发**强制** Director 阻塞性响应，而非异步队列。
- Reviewer 上下文预算应大于 Agent（当前两者都用 Opus 4.6，但 Reviewer 多承担"独立计算+独立 ssh 验证"任务）。

### F5 [HARNESS, High] Worker 上报状态不可信，但没有自动 verify 闸门
**证据**：
- M007: 7+ 次 GPU relay Worker status=done 但 GPU 进程未启动，"无错误日志可排查"。
- M008: Agent 误判 v2 失败 → 提交 v3 → v3 阻塞 v2 eval → 7h 浪费。
- M031: Worker 报"已修改 Qwen eval 脚本"，Reviewer ssh 核实文件原文未变，差点引爆 GPU 冲突+46h batch 超 DDL。
- M032: Worker 设置 watch 时误启 4 个重复训练进程（PIDs 80555-80558），DataLoader workers 被 Reviewer 误判为"重复进程" → Director kill → M033 训练崩溃 93% 进度。
- Layer 1 metrics: worker 412 errors / 1 435 sessions = 0.29 errors/session，看似低，但**error ≠ status mismatch**——很多状态不一致的 Worker 没有 raise error 就完成了。
**严重程度**：高。这条链路在项目中重演 10+ 次，每次都需要 Reviewer 人工 ssh 救火。
**改进建议**：
- spawn_worker 启动 GPU 任务后必须强制做 `nvidia-smi + ps + tmux ls` 三项验证，验证失败时 Worker 不可标记 done。
- Worker 报 "已修改文件" 必须附 `grep ... | head` 的 diff 证据到回调消息。
- registry status 与 PID 不一致时（M004）应以 PID 为准，并自动触发 reconcile_crons 而非信任 registry。

### F6 [HARNESS, High] Kill/SIGTERM 级联导致大额训练损失
**证据**：
- M026: 用 `kill <timeout_PID>` 解救 Qwen 长训练，timeout 把 SIGTERM 转发整组进程组，**同时杀死 2 个 Qwen 训练**。
- M033: Reviewer 把 Qwen s456 训练的 DataLoader workers 误判为"重复训练进程"，Director 未验证 pstree 直接下令 kill，训练在 step 6200/6633 (93%) 崩溃，损失 20h34m。
- M004: cwm-repo-s123 训练在 epoch 3 (75.7%) 因 `--no_wandb` sentinel 被 cron 误标 DONE/failed，Worker 信任 registry 启动 eval 进程导致 SIGHUP 杀死训练。
**严重程度**：高。每次都损失 10-30h GPU 时间，且经常在 DDL 前夕。
**改进建议**：
- kill 任何进程前必须先 `pstree -p <主PID>` 输出全树并提交 Director 审批。
- `--no_wandb` sentinel 检测应改为**不修改 registry**，仅 log warning。
- 长训练任务不进 submit_training_job（带 timeout wrapper），直接 nohup launch；自定义 timeout 设置 ≥ 预估时长 × 1.5。
- registry status 字段不应作为"是否启动 eval"的唯一信号，必须配合 PID 健康检查。

### F7 [HARNESS, Medium] seq_length / checkpoint / precision 三个 confound 反复污染论文
**证据**：M003、M005、M006、M015、M024、M027、M028、M030 八条 mistakes 都属于这一类。
- M005 (CWM epoch 2 vs 3 跨 seq_length 比较) → 写入 Abstract/Intro/Conclusion/§5.5 四处 → 被 Agent 自己发现需推翻 10pp overtraining claim。
- M015 (DeepSeek CLS multi-seed 训练 seq_length/data_dir/参数名全不同) → 7.68pp seed gap 可能来自 config 而非 seed。
- M027 (integrate_cwm_results.py 硬编码 epoch 1/2/3 数据混用) → supplementary stats 基于错误数据。
- M028 (sort -t'-' 选错 checkpoint) → eval 跑在 epoch 2 而非 epoch 3。
- M030 (eval_repo_cwm.py resume 静默返回旧 checkpoint 结果) → 不同 checkpoint eval 串污染。
**严重程度**：中-高。每条都需要 Reviewer 独立排查 + 论文重改。
**改进建议**：
- 每条写入论文的数字必须附"实验 fingerprint"（exp_id + seq_length + checkpoint + precision + seed）注释。
- eval 脚本的 checkpoint 选择应使用 `sort -V` 或正则提取数字，禁用 `sort -t'-' -k2`。
- eval 输出目录复用前必须清理 / rename，不能信任 resume 逻辑。

### F8 [MODEL, High] 长程一致性 / 跨 loop 误叙事生存期长
**证据**：
- M002 错误叙事 ("3-shot degrades DeepSeek") 在论文里存活 **2 个 loop** 才被 Reviewer 捕获。
- M016 (CLS 87.51 vs 真实 87.83 / error direction 完全错) 经过 **6 轮审稿** 都未被发现，直到 Paper Agent 在处理 N3 时偶然发现。
- D124→D129/D130 "overtraining ~10pp" 写入 Abstract/Intro/Conclusion 四处，跨 seq_length confound 在 Director/Reviewer 多轮审批中均未被识别。
**严重程度**：高。这是模型在长程任务中 "**不会主动反向验证已采纳的假设**" 的典型表现——一旦某个数字进入叙事，后续推理都基于该数字推进，没有定期"全文一致性自检"的机制。R20 仍标出 LPM vs GEE 矛盾 → 论文写完了，自动一致性检查没拦下来。
**判定**：换 prompt/工具难以根治（这是 LLM 在跨 100+ session 长程任务中的能力上限）。可以通过 harness 缓解（强制定期一致性扫描），但模型本身的因果推理 + 全文 reference graph 维护能力存在天花板。
**改进建议**：
- 每写入论文一个数字，自动生成 (number, source_exp_id, citation_locations[]) 三元组，每次重写时校验所有引用位置同步。
- 论文 build pipeline 加 "claim graph" 检查：每个 claim 应有支撑实验 ID，更新支撑实验时所有依赖 claim 自动标 dirty。

### F9 [HARNESS, Medium] 决策密度过高 + 决策快速反复
**证据**：D001–D171 共 171 条决策（14 天 12/日），其中至少 9 对显式翻转：
- D033 → D034 撤回 → D035 恢复（CWM v6 save_steps 配置）
- D040 → D041 撤回（westd-48478 = seetacloud 同机识别）
- D058 → D059 覆盖 → D060 ← D061 覆盖
- D111 → D112 翻转 → D118 再翻转（re-repair 是否入论文）
- D131 → D132 (seq2048/seq4096 混合方案)
- D146 → 用 footnote 而非 re-eval
- D151 → D152 撤回（§Equivalence 重写）
- D170 / D169 (CLS-TRAJ 统计方法)
这些翻转都发生在数据成熟前。
**严重程度**：中。每次反复消耗 Worker + Agent + Reviewer 重新对齐成本（~30min~2h），但相对 retry chain 还算节省。
**改进建议**：
- 引入"决策成熟度"标签（speculative / contingent / final），speculative 不应触发跨 role 执行。
- Decision 必须挂"何时可重新评估"的 trigger（如"等 ckpt-1000 eval 完成"），到期前其他角色不应基于这条决策做不可逆动作（特别是论文写入）。

### F10 [HARNESS, Medium] 人工"飞书 escalation"渠道存在但实际无人/低质响应
**证据**：27 次 ESCALATED_TO_HUMAN 全部归类 "director_no_response"——这是 agent 间的协同 timeout，不是真正向人请求介入。同时人类 26 条飞书消息中没有一条对应这 27 次 escalation 时点（escalation 集中在 05-12 ~ 05-17，人类介入在 05-17 与 05-25）。
**严重程度**：中。意味着 escalation 在实际工作中是 no-op，agent 之间陷入"等 Director 响应"的死锁后只能自我 timeout。
**改进建议**：
- 区分 "agent_coordination_timeout" 与 "human_judgment_required" 两类 escalation。
- 真正需要人介入的事件（连续 3+ 次 retry 失败、claim 反转、跨 role 数据不一致）应触发飞书强提醒。

### F11 [MODEL/HARNESS, Medium] 没有「**主动证伪**」的实验设计习惯
**证据**：MVP-B 通过 (85.7% accuracy) 后，Agent/Director 把它当 "CLS works" 的证据继续推进；所有后续实验都是「**沿主 claim 方向加强论据**」（multi-seed 巩固、ablation 排除 confound、Pareto 比较）。没有任何实验被显式设计为"如果结果 R，则核心假设崩溃"。
- 仅有的两次"自我证伪"——D004 (P2P 回归率) 和 D052 (Go/No-Go) ——是 idea_brief 阶段就设定好的硬触发，不是 research 阶段主动设计。
- D108 加 "second model family + re-repair downstream" 是回应 Reviewer 的 generalizability concern，不是主动证伪。
- 14B 实验 (D167) 是在论文已成型后做的 "rebuttal 储备"，作用是防守 capacity-contingent 攻击，不是测试 "CLS 优势是否在更大模型下消失"。
**严重程度**：中。直接拉低 R20 中 SF2 (核心发现可预测性) 的评价——R2 指 "generation 在 repo-level format collapse 可从第一性原理预测"。
**判定**：这是 LLM 协作研究的一般倾向——朝着已立项 narrative 优化证据，而非检验 narrative 本身。可通过 harness 强制（每个 Phase 必须有 1 个 falsifier 实验）缓解。

### F12 [INFRA] 单服务器 + cgroup 限制导致并行度受限，但项目长期低估这一点
**证据**：D028 (05-12) 明确 "seetacloud 禁止并行训练：cgroup 360GB 限制，v3+v4 两次 OOM 确认"。但 D040/D049 反复尝试 "并行" 直到 D155 (05-20) 仍在区分 "并行约束 4 = 确认 OOM, 3 = 未知, 2+1 = 可能安全"。**整整 9 天**项目运行在错误的"并行模型"认知下，多次启动 v(n+1) 时未验证现有进程导致 OOM SIGKILL。
**严重程度**：中。属于纯基础设施认知错误，但持续 9 天才被诊断清楚。
**改进建议**：
- 项目启动时应执行一次"infra capacity profiling"，结果写入 constraints.yaml。
- cgroup 限制等硬约束应在 Worker 启动 GPU 任务前由 harness 强制检查（"当前已占用 RAM + 本次预估 RAM ≤ cgroup 限制"）。

## 6. 总体判断

**这个项目最大的悲剧是**：科研本身的设计与执行都在水平之上（统计框架 R20 评为 S1，方法论 controlled comparison 评为 S2），但 **harness 在长程协作上的薄弱（F1 队列乱序、F3 HARD_LIMIT 信息损耗、F8 跨 loop 误叙事）反复在论文里制造**「**自相矛盾的数据/claim**」，每次需要 Reviewer 后期救火。如果不是 Reviewer agent 持续保持高警惕（F4 真相源），论文几乎不可能在 R20 仍保持 3.0；但 Reviewer 的负担也接近上限（590h、110 HARD_LIMIT）。

**这个项目最大的隐性收益是**：通过两次主动 reframe（D004、D116），把 MVP 阶段就破产的原始 idea 重新包装为可发表的 "Findings"——这条 "reframe over kill" 路径的 ROI 高，是项目能交出论文的关键决策风格。

**模型能力边界**集中在 F8（跨 loop 一致性维护）、F11（缺少主动证伪习惯）、F4 中"独立验证也会失败"——这些是 LLM 协作研究的共同上限。

**最值得改 harness 的三点**（按 ROI 排序）：
1. **F1 ack-before-act + claim graph (F8)**：杜绝论文 claim 反转和误叙事跨多轮存活。
2. **F2 retry chain 知识沉淀**：把 60 + 小时的 CWM 重试损失变成 5-10 小时即可定位。
3. **F5 Worker 状态验证闸门 + F6 kill 前 pstree**：消除 GPU 误杀和"假成功"导致的级联损失。
