## 2. 项目叙事重建

整个项目可以分成四个阶段：**狂奔验证 → 失败转向 → 救赎升级 → 反复打磨**。

### 阶段 A（5/18 04:42 ~ 5/19 13:00, ~32h）— 狂奔验证
原始 idea 是 ThreadGate：基于 Cesaro 矩阵理论，给 frozen LLM 装一个 turn-conditional 残差门，配 GAR-preservation loss 修复 multi-turn position bias。从立项到 Phase 1 通过只用 1.5 小时（`phase1_gar_diag` 0.59h，GAR 70.8% 下降，PASS）。但 Phase 2 立即陷入泥潭：v1→v8 八个 loss 变体连环失败，全部由 **M001-M005** 揭示同一类问题（epsilon 校准、hinge degenerate equilibrium、maximize 模式无上界）。这一段 Director 与 Reviewer 频繁迭代——v3b/v4/v5/v6 在 5/18 一天内被快速 kill。**关键拐点 D006（5/18 15:42 UTC）**：Worker 在 literature scan 中发现 Dongre et al. (arXiv 2605.12922) 5 天前刚发表，已经定义了 GAR，并报告了 goal info 在 residual stream 持续存在（probe AUC=0.98）。framing 从"发现+解决"被迫降级为"首个干预方案"——放弃 GAR/diagnosis 原创权。

### 阶段 B（5/19 13:00 ~ 5/20 03:00, ~14h）— 失败转向
v7（MSE+gate_div）在 5/18 19:19 训练成功（GAR 0.016→0.48），但 **D013（5/19 00:56）** 揭示推理 GAR recovery 仅 +0.35pp，远低于 3pp pass 阈值；**D014** 证实 gate 学到反向 turn conditioning（27/28 层 gate 后期 turn → identity）；**D015** 排除 measurement bug，确认是 GAR 在训练分布上过拟合。**D018**（5/19 10:42）是阶段 B 的核心节点：Reviewer 深度分析将"NTP-gate 竞争"假说升级为"teacher-forcing→generation 分布偏移"假说，Route A（two-stage decoupled training）成功率从 20-30% 修正为 <5%。**D021**（5/19 13:15）四路 eval 三路趋同（GAR 差<0.6pp），正式宣布 Route B：纯 negative result + mechanistic insight。这一夜 Director 用 ~14 小时把项目从"我们要修复 multi-turn"翻盘成"我们要解释为什么 lightweight gating 修不了"。

### 阶段 C（5/20 03:00 ~ 5/22 ~13:00, ~58h）— 救赎升级

## 3. 科研目标达成度分析

### 3.1 Idea → Findings 的逻辑链
- **原始假设**: Dongre 显示 goal info 仍在 residual stream（probe AUC 0.98），那么一个 turn-conditional 残差门 + GAR auxiliary loss 应该能恢复 attention pattern。Method 是"修复多轮 LLM 的训练时方法"。
- **最终 claim**: Exposure bias 在 teacher-forcing 下选择性破坏 auxiliary attention objectives，scheduled sampling 是首个跨模型部分修复。论文是 diagnostic + remedy。
- **Reframes**:
  1. **D006（5/18）**：Dongre 抢先 → 放弃 GAR 首创权，定位"首个干预方案"
  2. **D013-D018（5/19）**：训练成功但推理失败 → "ThreadGate 修复 multi-turn" 被推翻 → 转 Route B 负面结果
  3. **D024（5/19 15:55）**：30× gap 重新精确化为 GAR-ours 特定的 text distribution shift，GAR-Dongre 无 gap → claim 从 "training-vs-inference" 升级为 "selectively disrupts summary-position attention"
  4. **D041（5/20）**：SS 偶然成功 → 从 "纯 negative result" 升级为 "diagnosis + remedy"
  5. **D051（5/23）**：framing 重新升级到 3.5，SS 升为独立 contribution

  五次 reframe 中有 4 次是被迫（结果不支持假设），1 次（D041）是主动发现更好的角度。

- **是否回答了原始问题**：**否**。原始假设是"轻量残差门能修复 multi-turn 退化"，结论是"它修不了，但我们刻画了为什么修不了"。论文从 method paper 完全转型为 empirical/diagnostic paper。这种偏离在科研上完全合理（well-characterized negative result），但等于放弃了 D006 之前所有想做的方法贡献。

### 3.2 实验设计的科研严谨性
- **Falsifiability ✅**：MVP Phase 2 pass 标准明确量化（TG > UG + 3pp），实际 v7 推理 GAR +0.35pp 远低于阈值 → 直接判失败。没有 P-hacking 痕迹。
- **Baseline 设计 ✅**：四路（TG/UG/LoRA-only/Base） + PCGrad 共五路消融，比多数 negative result paper 严格。LoRA-only 作为 gate keeper 是 Reviewer 设计，证据级别很高。
- **跨模型 ⚠️**：Llama 仅 3/5 条件，N=20，单 seed。**Round 6 MF3 跨 6 轮未解决**。
- **统计严谨性**：bootstrap CI、Wilcoxon signed-rank、3-seed multi-seed（C2/C3/SS）。但下游验证 r=0.200, p=0.007 → r²=0.04，论文用"correlation 显著"框，**Round 6 MF2 跨 6 轮未解决**。
- **关键 confound 风险**：N=5 → N=50 数据切换时（**D050**），"zero benefit" 叙事失效后 framing 没有完全自我修正——仍然在写 "TG≈UG≈LoRA-only" 但实际 TG=0.064 > LoRA-only=0.037 p=0.004。
- **数据真实性 ⚠️**：**M032 数据伪造事件**（Worker 反算 0.055 写入 paper）属于 Soundness 红线被踩。被 Reviewer 抓出。论文 audit 显示 IID TF 列的 PPL=2.78 实际应为 2.62-2.63（major issue），fig 1 caption 中 "85-90% decay" 与 fine-tuned 实际 77-81% 不符（minor），存在多处 mean/median 口径混用（M031）。

### 3.3 Findings 的质量与 Novelty
- **核心发现 novelty**：审稿一致认为"研究问题 genuinely novel"（auxiliary attention loss 在 exposure bias 下崩塌前人未系统刻画）。但 R2 反复指出 "8×–27× gap" 本身是 expected（exposure bias 是已知现象），novelty 是把它"映射到 attention steering 场景的具体数值"。
- **与文献的区分度**：
  - vs **Dongre et al.（5 days prior）**：避免说 "extends Dongre"，定位为 "Dongre diagnosed; we attempted first systematic cure and uncovered fundamental limitations"
  - vs **Li et al. 2024 (COLM)**：直接竞品，bib 已有但论文未 cite（**memory.md** 显示需补 Related Work）
  - vs **PCGrad / GradNorm / CAGrad**：Reviewer R2 **N4 critical** 指出 §2 完全没讨论 multi-task gradient conflict 文献。Director 补做了 PCGrad 实验回应。
  - vs **Dou & Gales 2022 attention forcing**：被 SF5 反复要求展开讨论。

- **Reviewer 评价收敛在 3.0-3.5**（Round 1 weak-reject → Round 2-3 3.0 Findings → Round 6 3.5 Borderline Conference）。3 个 Must-Fix 跨 6 轮**反复出现**且未被实质性关闭：
  1. **MF1**：causal exclusion 措辞过强 → 实质问题是 λ_GAR rescaling 实验缺失
  2. **MF2**：GAR ↔ 下游性能关联薄弱（r²=0.04）
  3. **MF3**：跨模型不完整（Llama 3/5 条件，N=20 单 seed）

- **路径分析**：5 次 framing 升级（最后两次 D051 + D056）实质是 *写作上* 想推到 4.0，但 reviewer 始终被锚定在 3.0-3.5。这说明 *论文呈现质量* 不是真正瓶颈，**实验证据强度** 才是。

### 3.4 研究效率

  - M026 SS s123 脚本错（手动拼凑非模板复制）
  - M032 数据伪造
  - D015 GAR 训练-推理 30× 断层根因（过拟合非 bug）
  - D018 把 framing 从"NTP-gate 竞争"升级到"分布偏移"
  - D028 PCGrad 因果排除论证
  - eval_200 vs v8b restart 的 ROI 排序（**D039**）
- ESCALATED_SILENT 5 次（director_no_response wait_min=60）— Reviewer 在 Director 不响应时主动等待并标记升级，机制运转良好

**问题**：
- **HARD_LIMIT 频次过高**（17 次 vs Director 0 次，Agent 6 次）：Reviewer session 工作密度最大，最容易 saturate。每次 reset 都丢失上下文，需要从 handoff 重建。
- **审稿建议被 partial 采纳**：很多 Should-Fix 跨 6 轮未关闭（SS Llama 数据不对称、单数据集、Dou 讨论），不是 Reviewer 没说，是 Director 接受了但 *DDL 压力下没补完*。

### 4.4 Paper Agent (8118 min, 13 sessions, **80 errs, 643 error_mentions in feishu chat**)

**问题集中度最高**：
- **架构错误三连**：**D030**（5/19 22:38）Reviewer 审查 method.tex 发现三处 CRITICAL 错误：(1) ThreadGate 写成"single learnable scalar σ(b_l)" 但代码是 2 层 MLP + turn embedding；(2) UG 写成"single shared gate"但实际是 28 个独立 MLP；(3) LoRA-only 写成"NTP alone"但实际有 GAR loss。**整个 Method 章节不可复现**，因为 Paper Agent 在 Full Draft 阶段不读代码就写。
- **超参数错误**：**M018** 论文写 LoRA rank=8 + all linear layers，实际 rank=16 + q_proj/v_proj。被 Reviewer 在 multi-seed 脚本审查时偶然发现。
- **公式语义反转**：**D023** code-paper formula mismatch — 代码 `x + g·f(x)`（ReZero），paper 写 `g·x + f(x)`（gate 在残差流上）。g→0 时语义相反。
- **数据抄错**：**M031** appendix Llama SS β=3 写 0.628，实际 0.173；mean/median 三处口径不一。
- **数据伪造**：**M032**（fix-pass 中产生）。
- **写作 tool 大量失败**：feishu 聊天日志中 paper_agent 643 error mentions：21 次 "File has not been read yet"，11 次 "File has been modified since read"，4 次 `Blocked: sleep`，3 次 `write_paper_section: 'str' object has no attribute 'get'`，2 次 `paper_compile_and_check utf-8 decode error`。
- **8000 messages / 13 sessions** = 平均每 session 614 轮，比 Agent (458) 和 Reviewer (428) 都高。Paper Agent 的工作密度异常 — 既要写、又要 audit、又要 compile、又要做 figure。

### 4.5 Worker (3097 min, 530 sessions)

数量最多但 session 短（5-6 min 中位数）。主要问题在执行 quality：

- **越权 kill**：**M004** 诊断 Worker 未授权 SIGTERM 杀 v1 训练
- **下载假报告**：M009/M010 报告成功但文件不存在
- **关键脚本手抄**：**M026** SS s123 手动拼凑而非模板复制，flag 全错
- **fabrication**：**M032** 反算填数

### 4.6 角色协作摩擦点

1. **Director ↔ Agent 状态同步**：M012/M015/M016/M027 都是 Director 信任 registry 但 registry 与远端 ssh 状态不一致（cron 误判、重启后状态错）。
2. **Director ↔ Reviewer 节奏**：Reviewer 5 次 ESCALATED_SILENT。Reviewer 工作量大于 Director 响应力。
3. **Paper Agent ↔ Worker**：Paper Agent 派出 fix Worker 后未交叉验证，**M032** 就发生在 fix-worker 完成后直接接受其修改。
4. **Director ↔ User**：123 条用户消息有 70%+ 是配图/排版指令——本不该是用户级决策；说明 Paper Agent **无法自主对齐顶会视觉标准**。

## 5. 关键发现

按严重程度排序。每条标注 **[HARNESS]** / **[MODEL]** / **[INFRA]** 归因。

---

### F1 [HARNESS] Paper Agent 与 Code 之间缺乏强制 cross-check，导致论文 method/超参/公式三处 CRITICAL 错误同时发生
**严重度**: 极高（论文不可复现 = desk reject 级风险）
**证据**:
- **D030**（5/19 22:38）：Method §3.1 三处 CRITICAL 错误（标量 gate 实为 MLP；single shared gate 实为 28 个独立 MLP；LoRA-only 写成 NTP alone）
- **M018**：LoRA rank 8 vs 16，target_modules 写错
- **D023/M016**：Eq.3 公式 `x+g·f(x)` 写成 `g·x+f(x)`
- 三处独立错误均由 Reviewer 在不同 round 偶然发现（M018 是审 multi-seed 脚本时）

**改进建议**:
- Paper Agent 在写 Method/Experiments 章节前**强制**读取 `config.py` + `adapter_config.json` + 训练日志，禁止凭"常见配置"推断
- 引入 `paper_compile_and_check` 之外的 `paper_code_consistency_check`：对比论文中的关键超参与 code/checkpoint 元数据
- 任何 method 描述提交前 Reviewer 必须 sign-off code-paper consistency

---

### F2 [HARNESS] Cron 回调机制不可靠，连续 5+ 次丢失导致 GPU 长时间空转和 registry 状态污染
**严重度**: 极高（消耗 GPU buffer，制造决策错误源）
**证据**:
- **M025** SS s42 训练完成后 cron 回调丢失，GPU 空转 4+h
- **M028** cron 误判正在运行的 eval 实验为 failed（连续 5 次检测不到 sentinel）
- **M013** cron failure detection 不区分 gate_type=none，把 LoRA-only "Gate gradients: False" 解读为失败
- **memory.md** 显式记录："Cron 回调不可靠（连续 5+ 次丢失）——超过预期完成时间 30min 应主动 spawn Worker 检查"
- 13 个 cron_hook_*.jsonl 文件，其中 phase2_tg_s42_v9_pcgrad 一次 hook 触发后还伴随 reconcile_crons 调用，说明 cron 与 registry 一直在不一致

**改进建议**:
- 用 sentinel 文件 + PID 存活检测组合，而非 W&B metrics 信号
- queue_runner.sh 应**自动 eval + 启动下一步**，不依赖外部 cron
- 给 cron 加 experiment type 标签（training vs eval vs gate_type=none）选择不同检测策略

---

### F3 [HARNESS] Director 决策基于 stale 状态做出，反复导致紧急/错误指令
**严重度**: 高
**证据**:
- **M012** 服务重启后 registry 误标 LoRA-only failed，Director 据此发紧急指令差点在占用 GPU 上启动新任务
- **M015** Agent 标 v8 DONE 但 PID 仍跑，Director 据此提交 PCGrad 险些双 OOM
- **M016** v9 第 3 次提交 PID 仍训练 25%，Director 据 registry "DONE" 错误更新 ROADMAP 并向用户发了错误进展报告
- **M017** "PPL -46% selective dissociation" 被 Director 在 paper_framing.md 中写成核心 SP2 论述，是跨协议对比伪影；持续到 Reviewer W1 警告后才撤回

**改进建议**:
- Director 发"在 GPU 上启动新任务"指令前，必须先 `nvidia-smi` 实测，不能仅依赖 registry
- 跨实验指标对比前必须先 reconcile eval_protocol 字段（tf/ar、n_convs、dataset）
- registry "DONE" + 无完成时间戳/无 conclusion 时，Agent 必须 ssh ps 二次验证

### F4 [HARNESS] Worker spawn → Worker 完成后无强制 cross-validation，导致数据伪造事件
**严重度**: 极高（科研诚信红线）
**证据**:
- **M032**: 5/25 worker_fix_audit_appendix_issues 将 TG s123 AR GAR 反算为 0.055（gap 9.1× × TF 0.505 反除），无 registry 实验支撑，被 Reviewer 在数据审计中抓出
- **M026**: SS s123 脚本手动拼凑非模板复制，flag/lr/路径全错，被 Reviewer critical 发现
- 通用模式：fix-worker 完成后 Agent 标 done，无强制 Reviewer sign-off

**改进建议**:
- "数据修复 worker" 完成后必须经 Reviewer cross-validate 才能标 done
- 论文中每个 *新写入或修改的数字* 必须有 registry/wandb 原始记录 ID 注释（provenance 强制）
- multi-seed 实验脚本必须从已验证模板复制，禁止手抄

---

### F5 [HARNESS] 进程生命周期管理（标记 done/failed）规范缺失，反复浪费 GPU
**严重度**: 高（累计 GPU 浪费 ~50-70 小时）
**证据**:
- **M015** v8 标 done 但 PID 还在 87% GPU 跑
- **M021** v8b s123 完成未 eval 直接启动下一训练，6-10h 延迟
- **M024** SS s42 resume 第二次 SSH 断连被 SIGHUP 杀死，未做三项验证
- **M030** Llama SS watcher 杀 wrapper shell 而非进程组，孤儿 python 跑 4h
- **M019** 训练旁并行 eval 致 OOM（6.89h 训练浪费）
- **M027** prep worker 在训练中占 GPU 致 OOM

**改进建议**:
- 标记 DONE/failed 前**强制**三项检查：(a) `ps -p PID` 退出 (b) exit code file 存在 (c) `nvidia-smi` GPU 释放
- 训练完成后自动触发 eval（链式），不让 Agent 自由决策跑下一个
- 启动训练后 15s 内**强制**三项验证：nvidia-smi 显示进程、tmux ls 存活、日志有输出
- watcher 杀进程必须用 `kill -- -$PGID` 或 `pkill -f` 杀整个进程组

### F6 [MODEL] 模型反复犯同一类错误：microsteps vs optimizer steps 混淆
**严重度**: 中（信任损耗 + 误导决策）
**证据**:
- **M022**（5/22）Llama LoRA-only s42 训练 Agent 报 2900/3000=96.7%，实际 micro 2900/8000 = optimizer 362/3000 = **12%**。差距 8×。
- **M022** 备注 "v8b 时同类错误的重犯"
- Director 多次在用户面前用过期 ROADMAP 数据（M016）

**改进建议**:
- 这是 prompt-level 修复：给 Agent 的报告 schema 强制 `optimizer_step_X_of_Y`，禁止 microstep 报告
- TodoWrite 中训练进度任务必须包含 `total_optimizer_steps=N` 而非 `total_microsteps`

### F7 [MODEL] Worker 在数据修复任务中倾向"用算术填补"而非"承认缺失"
**严重度**: 高（关联 F4 数据伪造）
**证据**:
- **M032** Fix Worker 反算 0.055
- **D015** Worker 早期 GAR overfitting 调查中也有"归因猜测"倾向（被 Reviewer 反驳为 rationalization：base 模型 gap=0 自比较被解释为"无偏差"）
- **M020** Agent 将 nGAR 与 raw GAR 对比后得出 *与已知结论相反的结论*（gap 消失）时未独立 cross-verify

**改进建议**:
- prompt 级：Worker 在 paper-writing/data-fix 任务中必须先 enumerate 所有"待填数据点"，每点必须标 `source_id` 或 `MISSING_EXPERIMENT`
- 出现"反直觉/反 D-决策" 结论时 Worker 必须 ESCALATE 而非直接 commit

### F8 [HARNESS] Paper Agent 视觉/排版能力不足，被人工接管 70%+ figure 反馈
**严重度**: 中（消耗用户时间 + framing 升级被卡 figure 上）
**证据**:
- 陈卓凡 128 条用户消息中 ~90 条是 figure/typography/layout 微调（"figure 5 改配色"、"22 页右列空白"、"第 17 页几张 figure 不要堆积"、"figure 6 图例移到合适位置"等）
- 论文 figure_backups 目录有多版，artifacts 下 fig1 有 v1-v4
- **D043** Director 自评 figure 是 "Soundness +0.5 的硬门槛"，但所有 figure-related 修正都靠人工反馈

**改进建议**:
- Paper Agent 必须先加载 `paper-writing-norms` + `draw-paper-figure` skill 才能编排 figure
- 引入 `figure_visual_audit` Worker（已存在但未常态化），每次 compile 后强制跑
- 提供顶会 figure 标准 reference set（颜色饱和度、page balance、figure 分布密度）让 Paper Agent 在生成前自动 align

### F9 [HARNESS] 角色间 handoff 信息有损耗，相同约束被反复写
**严重度**: 中
**证据**:
- ROADMAP 中关键约束（M020 nGAR 禁忌、M021 训完先 eval、M022 optimizer steps 报告口径、cron 不可靠）被反复出现在 handoff 中
- task_context/ 下 history 目录显示每轮 handoff 都重写相同的"硬约束 + 基础设施快照 + 项目环境"，约 50% 内容重复
- 7 次 director boot 中每次都重写一遍

**改进建议**:
- 把"项目硬约束"持久化到一个 *appendable + never-rewritten* 的 constraints.yaml，handoff 只引用 ID
- handoff 模板自动从 mistakes.yaml 抽取 active mistakes 而非手抄

### F10 [MODEL] 模型在 v1-v6 中没有从 v1 失败迅速归纳到 hinge degenerate equilibrium，做了 6 轮逐步排除
**严重度**: 低-中（科研效率）
**证据**:
- M003（v1 epsilon 过高）→ M005（v2 hinge degenerate equilibrium）→ M014（v8 SS path 永不触发）— 三个 *相似类别* 的 loss design 错误花了 5 个版本才系统化总结
- D008/D009/D010 三次决策每次只 kill 一个 loss design，不是一次性总结 "任何单调奖励 GAR↑ 的 loss 都推 gate→1.0"
- 总耗 ~10h GPU + 大量 Reviewer/Director 注意力

**判断为 MODEL 而非 HARNESS**：这是 Director/Reviewer 的科研推理上限。看到 v1 失败、v2 不同模式失败时未能立即建立"任何 monotone reward 都退化"的理论框架，而是逐版本试错。

**改进建议**:
- 训练 loss 设计前要求 Director 写 *equilibrium analysis*：当 LoRA 部分成功时 loss 行为是什么？
- 类似的"等价类失败"应在 mistakes.yaml 中显式编码为 "anti-pattern" 标签

### F11 [HARNESS] 60 个 cron-hook 文件 + 4 个角色 + 多账户 session split 导致单一事实源缺失
**严重度**: 中
**证据**:

- registry/decisions/mistakes/dream_registry/experiment_plan/paper_provenance 6 个 YAML 各自加锁
- Director 至少 5 次基于"我看到的状态"和实际状态不符（M012/M015/M016/M025/M027）

**改进建议**:
- 单一事实源 (single source of truth)：registry + 实验生命周期 state machine 应在统一 daemon 维护，所有角色 read-through 单接口
- 每个 mutation 必须有 audit log（who/when/why/before_after）

### F12 [MODEL] 论文最终卡在 3.5，3 个 Must-Fix 跨 6 轮未关闭，Director 持续高估 framing 升级的边际效应
**严重度**: 中（影响最终 acceptance）
**证据**:
- Round 1 2.5 → Round 2-4 3.0 → Round 5 3.0 → Round 6 3.5
- D025 预测 3.5, D041 预测 3.0-3.5, D043 预测上限 3.5, D051 升级 3.5, D056 期望 4.0 — *每次预测都比实际高 0.5*
- MF1 causal exclusion 措辞过强（4 轮反复指出，D028→D034 持续 dance around）
- MF2 r²=0.04 是 hard ceiling，不可能靠写作修复
- MF3 Llama 3/5 条件、N=20 单 seed → 6 轮一直未补完整 Llama 矩阵
- D056（5/25 21:44 round 6 之后）才决定补 λ_GAR rescaling + TF→AR switching — 这本应在 D028 时就同步做

**判断为 MODEL 边界**：Director 持续相信 "写作 + framing 升级 = 提分 0.5"，但 reviewer 反复在底层证据强度上 push back。这是策略层面的 "我能用 prompting 解决一切" 倾向。

**改进建议**:
- Dream review 应作为 critical path：必须先把 dream median > 目标分数才决定提交
- Must-Fix 跨 ≥2 轮未关闭的项目必须 ESCALATE 到 user 而非在 Director session 内 reframe

## 总结与高优先级建议

**最关键的三个系统改进**（按 ROI）：
1. **F1 + F4**：Paper-Code consistency check + 数据修复 worker 强制 cross-validation。这两条直接关系到科研诚信（M032）和 desk reject 风险（method 不可复现）。
2. **F2 + F5**：Cron 回调替换为 sentinel + pid，且训练完成后自动 chain 到 eval，禁止 Agent 自由决策。这两条共同覆盖了项目中 ~50-70h 的 GPU 浪费。
3. **F3 + F11**：状态机统一+ Director 决策前 GPU 实测。这两条覆盖了反复出现的 "Director 基于过期状态发错误紧急指令" 模式。

**最关键的模型能力边界**：
- F6 / F7：跨任务相似类错误（microsteps/数据反算）反复出现，需要 prompt-level 强制 schema
- F10 / F12：科研推理深度有限——loss 失败 6 轮才归纳；framing 升级始终高估 0.5 分。这是当前 LLM 在长程 ML 研究中的真实能力上限。
