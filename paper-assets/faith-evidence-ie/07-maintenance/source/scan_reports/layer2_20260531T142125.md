## 3. 科研目标达成度分析

### 3.1 Idea → Findings 的逻辑链
**原始 idea (IDEA_BRIEF)**: 用 GRPO + CED reward 训练 LLM 同时输出 relation triples + 支撑证据；CED 通过 within-document hard negative 解决 NLI faithfulness 的 gameability 问题。Make-or-break 实验是 CED vs flat-NLI ablation，dual publishability threshold：Evi-F1 > 57.34 AND F1 > 53。

**最终论文 (paper_framing 3 贡献)**:
1. RSFT + NLI-based scoring 有效性
2. Decoupling spectrum (GRPO catastrophic > DPO gradual > RSFT none)
3. Evidence tax landscape + variance compression

**Reframe 链**:
- Reframe #1（被迫）: GRPO 全线失败 → 从 "online RL CED" 转向 RSFT (D031/D037)
- Reframe #2（被迫）: D078 CED vs flat-NLI p=0.44 统计不可区分 → CED 降级为 "one possible scoring function"，与 flat-NLI 等效
- Reframe #3（主动）: bf16 GRPO 不 forget (D051) → 从 "online RL fails" 收窄为 "QLoRA artifact"，再泛化为 "decoupling spectrum"
- Reframe #4（被迫）: 4B "capacity valley" (+7.5pp) 由 M027 adapter 错误造成 → D144 修正为 +0.73pp，capacity valley 叙事完全推翻，C5 重写为 "within-family threshold"
- Reframe #5（被迫）: variance compression 17× → 6.5×（M032 混用 k=3/k=1 数据）

**与原始 idea 的偏离**: 原始 idea 的核心技术 (CED reward in GRPO) 完全失败，论文最终核心是这个失败本身（decoupling spectrum）+ 离线替代 (RSFT) + scaling 现象学（evidence tax landscape）。**论文的核心 claim 与原 hypothesis 关系微弱——CED 作为 reward 的 contrastive insight 在论文中只保留为 RSFT 的 scoring function，与 flat-NLI 不可区分**。从科学价值看，这是一个失败 idea 通过 negative result + 现象学发现救出来的论文。

### 3.2 实验设计的科研严谨性

**Falsifiable 设计**：✅ Make-or-break (D076/D078: CED vs flat-NLI t-test) 设计良好且诚实执行——p=0.44 直接接受 null。Dream 模拟（D043/D047）作为投稿前可证伪 gate。
**对照 baseline 设计**：☑️ 部分充分。Baselines 12+ 列出，但 plan_004 DREEAM 自己复现，plan_022 第三个模型家族 / plan_023 DocKS-RAG+LMRC 复现都列为 P2 并未完成。所有 RSFT 与 SFT 同 backbone 同 protocol 比较合规。
**统计方法**：⚠️ 严谨性反复出问题：
- M002, M017 两次 ign_f1/rel_f1 混淆，污染了 ROADMAP + paper_framing + Paper Agent patch
- M005 4 个并行训练磁盘满 → seed 1, 2, 3, 4 全崩
- M035 共享 SFT base 缺陷直到 Round 3 才暴露 → variance compression 由 contribution 降为 observation
- D118 "RSFT 1.7B surpasses 8B SFT" → 修正为 "approaches"
- D155 "consistently reduces" 替代 "substantially reduces"（sign test p=0.0625 n=4 结构性上限）
- D146 4B 3-seed mean=+0.25±0.47pp 用 sample std (ddof=1)，被 Director 纠正过一次（agent.md 红线）
**P-hacking / cherry-picking 倾向**：
- 4B 主表 n=3（去掉 s45），附录透明报告 n=4（director.md 红线明确禁止把 s45 加回主表）。这是诚实的，但意味着 s45 被排除有偏的可能性
- evidence tax 在 dev 用 matched@2048 fair subset，test 用全量 500 docs，两套协议不一致（D147 8B dev=+0.04 vs test=-1.71pp 方向不一致）
- 4B RSFT test tax 唯一正值 (+1.65±0.29)，但 paper 将其框入 "heterogeneous, scale-dependent" 框架内（D153 Version B confirmed）

**实验规模**: 5 scales × 多 seed × 多 protocol 已属重量级；shared SFT base 缺陷削弱了 generalizability claim。

### 3.3 Findings 的质量与 Novelty
- **Original GRPO+CED claim**：已被证伪，但失败本身（QLoRA quantization 在 RL-for-IE 任务上的 catastrophic collapse）+ 跨方法 decoupling spectrum 有发现价值。
- **RSFT**: 诚实定位为 STaR (NeurIPS 2022) 单轮变体（D076-related），不作为方法贡献。
- **Evidence tax landscape (C3)**：跨 5 个 scale + 跨 2 个家族的现象学是项目最有 novelty 的发现——但 D144 "within-family threshold" 替代 "capacity valley" 后，叙事弹性减弱（1.7B 唯一显著获益，4B/8B/14B 都接近 0，threshold 在 1.7B-4B 之间只是 2 点数据）。
- **Variance compression**：6.5–31× 跨 scale 一致是 striking 数据，但 M035 共享 SFT base 缺陷使其降为 observation。
- **EDCR**: 方法级 ρ=-0.965 接近完美相关 → D071 自己承认 "by-construction 混淆"，per-relation EDCR 独立诊断（ρ_evi_f1=-0.064）救回了价值。

**审稿评分轨迹**:
- Dream v1 best/median/worst = 2.5/3.0/2.5
- Dream v2 best/median/worst = 3.0/2.5/2.5
- Round 1 actual review = 3.0
- Round 2 actual review = 3.0 (Findings)
- 项目目标 EMNLP Main (≥4.0) 与实际评分 3.0 (Findings) 之间存在 1.0 分缺口。从科研内容看，原始 CED hypothesis 失败 → 论文重心被迫转移到现象学发现 + negative result framing，这种"救出来"的论文在主会的天花板就是 borderline。

- **5-17/5-18 的 director_no_response 集群**: 16 条 ESCALATED_TO_HUMAN 在 36 小时内 → Director session 在关键 RSFT scaling 高峰期 unresponsive，触发 Agent/Reviewer 多次反复升级
- **M037/M038 flip-flop**: 前 Director session 在 Agent 完成审计前发 CRITICAL → 后 Director session 信任 Agent 错误审计表又 revert → Reviewer 用 registry 行号才确认。**三方信息冲突时未等最可靠来源（registry）**
- **M033 LLaMA 路径 3 个全错**: 从 handoff 记忆中照搬路径而非从 registry 成功实验复制 → 浪费 ~5h Worker 进度
- **M002 4B RSFT gain 错误数字未交叉验证就写入 D088/D094/ROADMAP**: 后由 Reviewer 核实纠正
- **Cron 回调失效（M023/M025）**: Agent 空闲 2h+ 无 harvest，Director 在 WAIT 期间未设短间隔检查

### Main Agent（601 sessions, 63.3k turns, 29M output tokens, 784 errors）

**做得好**:
- 跨 11 天 261 次 boot 保持基本任务连续性
- Top tools: update_registry 3161, read_registry 2355, spawn_worker 1662, post_to_director 1139 → Registry-centric workflow
- 大多数 worker 派发能正常 closure 到 cron callback

**问题**:
- **Session 不稳定**: 245 HARD_LIMIT_REACHED + 245 RESET_REQUEST_SENT 表示**每 ~6 turns 就触发一次硬性 reset/handoff**。每次 reset 都需要重读 task_context/agent.md（58 行）和大量 memory.md。这是 token 消耗 29M 的主因
- **Worker 派发错误率高**: mistakes.yaml 中 M006/M007/M008/M010/M012/M013/M018/M026/M027/M028/M029/M031 共 12 条 worker_dispatch / experiment_design 类错误，多数是"复制粘贴脚本不修改路径/参数"
- **自检能力弱**: 大多数错误 (M002/M017/M026/M032 等数值错误) 由 Reviewer 拦截而非 Agent 自检。Agent 报数往往是从 metrics.json 的位置推断而非字段名提取
- **未授权操作**: M028 Agent 未经审批自行启动 retrain_4b_rsft_ced_s42；M034 Agent 错误执行 registry 批量删除（指令明确"只加 note 不删除"），删除 ~194 条
- **失效 cron 回调（M023/M025）**: Agent compaction 后丢失 cron 注册，连续 2 次出现

### Reviewer（105 sessions, 43.8k turns, 18.4M output tokens, 113 errors）

**做得好**:
- 是项目的**关键防错层**: M002, M003, M012, M013, M027, M032, M036, M037 reverse, M038 都由 Reviewer 拦截/纠正
- top tool ssh_read_only 6608 次 → 重度依赖直接验证而非 Agent 转述

- 9 次 ESCALATED_TO_HUMAN + 高 ssh_read_only 频次 → 在 Director 不响应时仍主动验证

**问题**:
- **ScheduleWakeup 728 次** → Reviewer 大量时间花在自我唤醒等待，效率不高
- 27 sessions 文件平均 2.85MB（p90=7.7MB, max=20MB）→ 单 session 时间极长，token 重负
- **共享 SFT base 缺陷（M035）拖到 Round 3 才发现**: 在 5-18 全 scale RSFT 设计时本应注意到 registry 依赖链问题，Reviewer 早期审查时没追溯

### Worker（1497 sessions, 92k turns, 36M output tokens, 464 errors）

**做得好**:
- top tools: ssh_read_only 20071, ssh_execute 4037 — 比 1:5 健康
- 平均每个 worker session 仅 61 turns、6 个 tool uses → 任务定义粒度合理

**问题**:
- 464 errors（约 31% 错误率，按 1497 sessions 计算）—— 高
- M005 4 task 同时写 checkpoint 磁盘满崩；M019 14B 12h gen 无 resume 全丢；M021 rsync 覆盖 r3 写入的文件——**3 起重大事故均与 worker 写 IO 设计有关**
- Resource_misuse 类错误占比高（M005/M009/M018/M020）

### Paper Agent（17 sessions, 8.6k turns, 4M output tokens, 59 errors）

**问题**:
- M003 Related Work 含幻觉引用 (E-GRPO, R1-RE)，KD-DocRE 误归属为 Re-DocRED 数据集——**LLM 写作典型 hallucinated citation**

- Top tool ToolSearch 111 次 + WebSearch 55 → 大量用于补救引用

### 角色协作摩擦点
1. **Agent → Director 的数据传递不可靠**: M002/M017 数值错误未交叉验证直接写入 decision；M037 Agent 审计表用实验名命名而非真值
2. **Director → Agent 的路径/参数传递不可靠**: M027 / M031 / M033 都是 Director 从 handoff 记忆中照搬错误参数
3. **Director → Paper Agent 的指令缺乏 dry-run 验证**: M036/M037/M038 三次基于错误真值的 CRITICAL 修改
4. **Reviewer 是事实仲裁者但成本极高**: 单 session 平均 2.85MB / 1730 minutes，是 Director (1.06 hours/session) 的 ~10× 时长

## 5. 关键发现

### 5.1 [HARNESS] Session reset 风暴吞噬主要 token 预算 — Critical

**证据**:
- Agent 304 RESET_REQUEST_SENT + 245 HARD_LIMIT_REACHED + 261 boot = **每 6-12 turns 就要 reset 一次**
- Agent output tokens 29M / 63.3k turns = 平均每 turn 458 tokens，但 boot 时需读 task_context/agent.md（58 行）+ memory.md（66 行）+ paper_framing.md（404 行）+ 多次 read_registry/get_project_status
- 单次 boot 重读约 50-100k tokens 上下文，261 次 boot ≈ 20M+ token 仅用于"找回状态"
- 5-17 ~5-18 凌晨 16 条 ESCALATED_TO_HUMAN 全部在 36h 内 → reset 频率太高导致 Director 无法处理积压消息

**严重程度**: 极高。98.6M 项目总 token 中估计 25-35% 用于 session 恢复。
**改进建议**:
- 把 boot 上下文从 "重读所有 md" 改为 "增量 diff" — 仅读上次 reset 后变更的部分
- 拉长单 session wall_time 上限（当前 ~360min → ~720min for Director），减少 boot 次数
- 把 task_context 改为 yaml/json 结构化，让 boot 只读"机器需要的"而非"人类可读的长 markdown"

### 5.2 [HARNESS] 三方信息（Agent 报告 / Director 指令 / Registry 真值）冲突时无优先级仲裁 — Critical

**证据**:
- M037 → M038 G=4↔G=8 三次 flip-flop：前 Director (基于 registry hypothesis 字段误读) → Agent 审计表 (基于实验命名约定) → Reviewer (基于 registry 实际 spec L1015/L1048/L3470) → 最后才确认 G=8
- M002 4B RSFT gain：Agent 报 rel_f1=0.4655 (无法复现) → Director 写入 D088/D094/ROADMAP → 后 Reviewer 核实纠正
- M017 LLaMA RSFT s42 ign_f1=0.5839 (实为 rel_f1) → 污染 D125 evidence tax 计算 / D128 3-seed 统计 / paper_framing / ROADMAP / Paper Agent patch
- M027 Worker adapter 路径错误 → D140 1.7B/4B/8B 全部失效 + D142 reframe 悬空
- M033 Director 级联指令 LLaMA 3 个路径全错 → Worker 自动修正但丢失 5h 进度

**严重程度**: 极高。每个事故造成 5-50 GPU-h 浪费 + Paper Agent 多轮重做。
**改进建议**:
- 数值类报告强制结构化校验: ign_f1 < rel_f1 (DocRED 上恒成立) → invariant check
- 任何写入 decision 的数值必须 hash 到 registry source-of-truth，自动验证
- Critical 指令发出前自动锁住相关 decision，Reviewer 不 sign-off 不解锁
- Agent 报告"参数路径"时必须附带 registry exp_id 引用，禁止从 handoff 记忆中复制

### 5.3 [HARNESS] Worker dispatch 的脚本复制粘贴反模式 — High

**证据**: M006/M007/M008/M010/M012/M013/M018/M026/M027/M031/M033 共 11 条 — Agent 派 Worker 时复制现有脚本但未修改其中的 path/seed/quantize/CUDA_VISIBLE_DEVICES/max_new_tokens 等关键参数。
- M006 Wave1 4 个 critical 一起出现（GPU/路径/save_total_limit/DeepSpeed 矛盾）
- M007/M008 CUDA_VISIBLE_DEVICES 被 ${GPU:-0} 默认值覆盖
- M010 1.7B RSFT s43/s44 adapter 指向 s42 而非 seed-specific
- M012 14B eval 沿用 --quantize 违反 D076
- M026 fair_tax Worker 用 @1024 with-evi（D137 后同类错误）
- M027 1.7B/4B/8B no-evi eval 用 plan_014 训练 adapter 而非标准 SFT + --no_evidence flag
- M031 LLaMA RSFT no-evi max_new_tokens=1024 与配对 with-evi 2048 不匹配

**严重程度**: 高。这些错误平均每次浪费 1-10 GPU-h，累计上百小时。
**改进建议**:
- 派 Worker 时强制使用 templated config（jinja-style），所有变量参数化
- 提交前强制 dry-run: ls 验证路径存在 + diff 对比模板 + nvidia-smi 验证 GPU 空闲
- 建立"adapter 物理隔离命名规则": 训练变体用 plan_XXX_ 前缀，与标准 SFT 隔离（M027 prevention 已提出但未落地）

### 5.4 [HARNESS] Cron 回调在 session compaction 后失效 — High

**证据**:
- M023 14B RSFT train 完成后 cuda:0 空闲 ~17min，Agent 未自动 harvest
- M025 Agent 空闲 2h+，3 个实验完成未 harvest，3 张 GPU 白等（"M023 后未根治"）
- M020 milestone 触发后 3/4 GPU 空闲近 1h
- 5-17 / 5-18 期间多个 ESCALATED_TO_HUMAN 与 Agent idle 重叠
- ralph_loop_timeline.jsonl 中 304 RESET_REQUEST_SENT vs 245 HARD_LIMIT_REACHED 差值 ~60 → 有 60 次 reset 是手动 / cron 触发的

**严重程度**: 高。3 张卡白等 2h ≈ 6 GPU-h 直接损失，叠加 GRPO 阶段意味着 30-50 GPU-h 损失。
**改进建议**:
- Agent compaction 后强制重注册所有活跃 cron（heartbeat 机制）
- 服务端 cron callback 失效检测：cron 触发后 60s 内未收到 Agent reply 则换 channel（urgent_agent_message）
- Director WAIT 间隔不超 30min

### 5.5 [HARNESS] Reviewer 作为唯一防错层 — High

**证据**: 38 条 mistakes 中至少 11 条 (M002/M003/M008/M012/M013/M017/M026/M027/M032/M036/M037 reverse/M038) 由 Reviewer 拦截/纠正。Reviewer session 累计 18181 分钟（约 303 小时）— 是 Agent (989h) 的 30% 但 errors 是 Agent (784) 的 14% (113)，Agent 错误率 vs Reviewer 错误率高 ~2×。
Reviewer ssh_read_only 6608 次 + tail_training_logs 492 次 → 重度依赖物理验证。Reviewer 平均单 session 1730 minutes — Director 的 ~10×。

**严重程度**: 高。如果 Reviewer 因任何原因（session crash、context overflow）失能，错误将直达 paper。M035 共享 SFT base 缺陷直到 Round 3 才被 Reviewer 发现 → 拖延 2 周。
**改进建议**:
- 关键 invariants（ign_f1 ≤ rel_f1, paired protocol 一致性, adapter 路径合规）自动化为 CI 而非靠 Reviewer 人审
- Agent 端在 update_registry 时自动跑这些 invariants
- 把 Reviewer 工作量降低到关键 statistical sign-off + adversarial 角色

### 5.6 [HARNESS] Paper Agent hallucination + 缺乏引用 audit — High

**证据**:
- M003 Related Work 含幻觉引用：E-GRPO (zhao2025egrpo), R1-RE (dai2025r1re), jin2025rl_panacea 不在 literature_map.yaml；KD-DocRE 错误归属 tan2022redocred (Re-DocRED 数据集论文)
- 修复后才采用 reference-audit skill
- M036 Paper Agent Table 3/§4.3 GRPO 超参 3 项错误（G=4 vs G=8, lr, batch sizes）—— 论文已编译多版本

**严重程度**: 高。这是论文上 reviewer.md 红线和 director.md 红线被反复强调的根本原因——但执行靠人审。
**改进建议**:
- Paper Agent 写引用前强制 grep literature_map.yaml + WebSearch 验证
- 所有 hyperparameter 表与 registry spec.command 自动 diff，编译前 block
- 提交 review 前强制运行 reference-audit skill

### 5.7 [MODEL] Agent 的长程一致性 / cross-session memory 失败 — Critical

**证据**:
- M002 / M017 两次相同的 ign_f1/rel_f1 混淆，相隔 3 天 — Agent 没从 M002 学到
- M008 / M033 复制粘贴脚本不改路径，相隔 4 天 — 同类错误
- M026 / D137 已经做了 matched@2048 protocol 升级，Worker 仍用 @1024 with-evi —— 同 session 内的协议没传到下次 worker dispatch
- 261 次 boot 后，许多关键 invariant（如 "evidence tax = no_evi - with_evi，负值=evidence helps"）被反复需要在 task_context/agent.md 中手写提醒
- 5-15 D050 (pivot 到 analysis paper) → D051 翻转，时间间隔 3 小时但 Director 完全没保留 D050 的思考脉络（说明 session 内记忆也有问题）

**严重程度**: 极高。这不是 prompt 问题（task_context.md 明确写"ign_f1 ≤ rel_f1 恒成立"，红线写"evidence tax 定义统一"），是模型在新 session 中无法真正"将这些规则作为 invariant 主动 check"。
**改进建议（可触达的部分）**:
- 把 "Agent 要内化的 invariants" 从 markdown 提示降级为代码层的 wrapper：update_registry 调用时自动做 invariant check，违反则拒绝
- 这是 [MODEL] 的根本问题但可以靠 [HARNESS] 缓解

### 5.8 [HARNESS] 5-17 director_no_response 集群暴露的"角色 wall time 不对齐" — Medium

**证据**: 20 ESCALATED_TO_HUMAN + 5 ESCALATED_SILENT，全部 director_no_response。5-17 22:27 ~ 5-18 02:09 有 8 条 escalation 在 4 小时内。Reviewer 在同期连续提 issue 无人响应。
Agent boot 261 次但 Director boot 仅 27 次 → 8.6:1 — Director session 平均时长是 Agent 的 ~9×（Director 18065 min / 171 sessions = 106 min vs Agent 59349 / 601 = 99 min...）但 ralph_loop max_wall_time 触发频率不一样。Director 26259 turns vs Agent 63353 turns 也表明 Director 节奏更慢。

**严重程度**: 中。在 scaling 高峰期暴露最明显。
**改进建议**: 给 Director 单独的 idle_timeout（更长）和 wakeup 优先级（urgent_agent_message 触发 Director boot 优先于普通 cron）。

### 5.9 [HARNESS] 实验追溯链（exp → adapter → data → registry）缺乏自动化校验 — High

**证据**:
- M027 plan_014 训练 adapter 和标准 SFT adapter 路径相似（含 "no_evidence" 字样混淆）→ Worker 选错 → 1.7B/4B/8B no-evi eval 全错
- M035 RSFT seeds 共享 SFT s42 base 缺陷直到 Round 3 才被 Reviewer 追溯 registry 依赖链发现
- M032 17×→6.5× 修正：因为 k=3 plan_006 entry 没在切换到 k=1 后标记 [SUPERSEDED]
- M010/M011 误判：因为 1.7B 的 scored data 来源（s42 生成）未在 registry 显式标注 dependency

**严重程度**: 高。直接影响科学结论可信度。
**改进建议**:
- registry 每条 experiment 增加显式 dependencies 字段（parent_adapter / source_data / sft_seed）
- update_registry 时自动校验 dependency graph 完整性
- 协议切换（k=3→k=1 / @1024→@2048）时自动给旧 entries 加 [SUPERSEDED] 标签

### 5.10 [HARNESS] 缺少自动化 figure/table 与 registry 的一致性校验 — Medium

**证据**:
- M036 论文 Table 3/§4.3 hyperparameter 与 registry 不一致 → 3 轮 reviewer 反复
- M032 figure 中 variance compression 17× 含 k=3 数据
- audit found 62 项发现 3 项 FAIL (F1 DPO 1ep Rel-F1 33.38→33.37 / F2 method.tex EDCR / F3 fig_spectrum caption)

**严重程度**: 中。
**改进建议**: 论文每个数字标 provenance (registry exp_id + metric path)，编译前自动 diff。

### 5.11 [MODEL] Director "决策"过度导致策略震荡 — Medium

**证据**: 159 条 D-编号，平均 1.7 条/小时；其中 D050↔D051 / D061↔D063 / D068↔D069 / D097↔D098 / D118↔D120 / D134↔D135↔D136↔D137 多组连续修正/翻转。M037/M038 三次 G 值 flip-flop。

**严重程度**: 中。每次震荡都需 Agent/Paper Agent 跟进，浪费 token。
**改进建议**: 任何 reframe 决策强制 "等 24h cooldown + 多方 sign-off" 流程，避免 hot decision。

### 5.12 [INFRA] AutoDL 实例不稳定造成的非线性损失 — Medium

**证据**:
- M019 14B gen 12h、1872/3027 docs 因 bjb2-12179 实例注销而全丢（无 resume 机制）
- M021 rsync 在迁移中覆盖正在写入的文件，r3 5016 条数据面临丢失（最终从 /proc/PID/fd 抢救）
- M005 磁盘满崩 4 任务同时挂掉
- mistakes 多处提到 "AutoDL 实例重启后 SSH 端口会变"

**严重程度**: 中。AutoDL 是已知不稳定环境，但项目早期未把 checkpoint/resume 作为强制要求。
**改进建议**: ssh-env-setup skill 已列了 AutoDL 经验沉淀，但实际 worker 脚本未强制使用增量写盘 + resume。M019 prevention 已提出 ">1h 任务必须有 resume"，应作为 worker submit 时的 invariant。

### 5.13 [MODEL+HARNESS] CED 核心创新失败但项目"救出"论文的能力 — 项目级 Observation

**证据**: 原始 idea 的 make-or-break (CED vs flat-NLI) p=0.44 直接失败；GRPO+CED 也全线失败；但论文最终通过 (1) decoupling spectrum (negative result) + (2) evidence tax scaling 现象学 + (3) RSFT variance compression 救回 Findings 评分 3.0。

**严重程度**: 这不是 problem 而是 observation——agent system 在原始 hypothesis 死亡后能 reframe 出 publishable contribution，体现了一定的"科研韧性"。但代价是 3.0 (Findings) 而非主会评分。

**改进建议**: Dream 模拟 (best/median/worst < 3.5) 应作为更早的 abort signal——D050 当时 pivot 到 analysis paper 的判断其实是对的，被 D051 推翻后项目硬着头皮做 Main，最终落到 Findings。Dream gate 应该更有约束力。

### 5.14 [HARNESS] 用户参与窗口与项目 wall-time 不匹配 — Medium

**证据**: 27 条用户消息全部在前 48h，后续 16 天无人工干预。20 ESCALATED_TO_HUMAN 显示系统知道需要升级但未真正触达。M035 / M027 / M032 等如果有人工每周检查一次都可避免。

**严重程度**: 中。
**改进建议**: 飞书升级机制需要确认实际触达 PI（read receipt）；定期 push 一次"本周 mistakes + 关键 decision" 摘要给 PI 即使无 escalation。

## 总结

faith-evidence-ie 是一个**原始 hypothesis 死亡后通过 negative result + 现象学发现"救出"的论文**项目。在系统设计层面（[HARNESS]）：
- session reset 风暴吞噬 25-35% token 预算（5.1）
- 三方信息冲突时无仲裁机制 → 多次 critical 错误（5.2）
- Worker dispatch 的复制粘贴反模式 → 11 起同类事故（5.3）
- Reviewer 作为唯一防错层 + 关键 invariant 未自动化（5.5/5.9）
- Paper Agent hallucination + 缺乏自动 reference audit（5.6）

在模型能力层面（[MODEL]）：
- 长程 invariant 维护失败（5.7）：同类错误 (ign_f1/rel_f1 混淆 / 复制粘贴 / 协议升级未传) 间隔数日反复出现
- Director 过度决策导致策略震荡（5.11）

在科研产出层面：
- 原始 CED reward + GRPO 路径完全失败但被论文化为 decoupling spectrum（接受）
- variance compression / capacity threshold 这类"现象学"发现是真实的，但 shared SFT base 缺陷削弱了 generalizability claim（M035）
- Dream 评分 (2.5-3.0) 准确预测了实际审稿评分 (3.0 Findings)，应作为更强的 gate

最严重的改进点不是 GRPO 失败（那是科学结果），而是**Worker dispatch 反模式 + 数值传递 + 协议切换** 三类系统性 bug 拖累了 ~30% 的 GPU 时间和论文叙事的反复返工。
