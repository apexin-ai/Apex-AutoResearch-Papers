## 3. 科研目标达成度分析

### 3.1 Idea → Findings 的逻辑链
**原始 idea（IDEA_BRIEF.md, 5/10）**：把多元 conformal prediction（per-DOF Mahalanobis + Adaptive Conformal Inference）做成 plug-in，用结构化 conformal features 喂给一个 learned correction module 修正 VLA action。核心机制：(1) 在线自适应多元 conformal 校准 + (2) 用 per-DOF nonconformity 作为 correction 特征。

**最终论文 claim**：用 K=2 L2 距离（不是 conformal 也不是 Mahalanobis）做二元 gating，决定是否走一个 obs_only conditioned 的 lightweight residual MLP。

**关系评估**：原始 idea 中
- ❌ Per-DOF conformal features → 完全抛弃（D058 + D029，failure）
- ❌ Multivariate Mahalanobis nonconformity → 抛弃
- ❌ Adaptive Conformal Inference (ACI) online update → 抛弃
- ❌ Conformal calibrated coverage → 抛弃，K=2 L2 ρ=0.9979 是统计相关性论证，不是 conformal guarantee
- ✅ "Learned correction module" → 保留，但 architecture 退化为 obs_only MLP（无 conformal feature）
- ✅ "Inference-time refinement of frozen VLA" → 保留
- ✅ "Uncertainty-gated execution" → 保留，但从 conformal threshold 退化为 percentile-based τ

**最终 paper 与原始 idea 几乎是两个项目**。idea 的"conformal"前缀在 final framing 里只剩"calibrated"一词。`paper_framing.md` 自己承认（D170）"消除 K confound" + "Adaptive gating 是核心方法"——这是真实的 finding，但与提案完全脱节。

**reframe 次数**：5 次正式 reframe（D061 → D106 → D131 → D146 → D177），叠加 MC1 framing 5 次微调（D138/D146/D165/D166/D167）。**每次 reframe 都是被迫的**：
- D061 → D072：用户拒绝 K=10
- D072 → D106：obs_only K=1 失败
- D106 → D131：π0.5 ceiling
- D131 → D177：CRM always-on 跨 suite 一致有害

最终 findings 回答的不是最初提出的问题。最初问"能不能用 conformal 做 VLA correction"，最终回答的是"什么时候不该 correct"。偏离是合理的——但偏离程度大到原 idea 的核心组件无一保留。

### 3.2 实验设计的科研严谨性
**falsifiability**：早期 kill criteria 是项目唯一亮点（D029：perdof 不超 argmin 5pp → kill；D030：spatial 全死则砍 spatial），这些 criteria 被严格执行。中期之后 kill criteria 实质消失——5/24 之后所有"负向"结果都被吸收进 "gating necessary" 的 reframing。

**baseline 设计**：MC1 最终 Table 1 是 K-matched 三列设计（D177），消除了 K confound，**这是项目最重的方法论改进**。但代价是 D177 之前 12 天的所有 Table 1 数据全部 invalid（K=10 vs K=2 confound + paired-r2 vs supplementary 混用）。

**统计严谨性**：
- ✅ 8-seed sign test p=0.004（4×2 = 8/8 cells degradation）+ Cohen's d 报告（D177）
- ✅ Spatial 多 seed 配对 paired t-test
- ❌ **p-hacking 嫌疑**：M086 直接显示跨服务器配对 p=0.014 实际同服务器 p=0.438，5/24 才发现
- ❌ **selective reporting**：D149/D152/D156/D157 在 spatial 是否用 s47-49 还是 s42-44 之间反复横跳，最终选了"全部 s42-44 + 论文不提具体 seed"——用户 5/26 00:19 明确指示"在所有正文里不要说用了哪些 seed 只说用了 3 个 seed 就行"。这是 cherry-picking 的合法化
- ❌ **post-hoc reframe**：MC1 5 次改写，每次都把负向 / 不显著的结果合理化为 "gating 的价值"
- ⚠️ **数据 backfill**：D109/D177 之后用 D163 "evaluate.py revert 到 a594db5"，部分 Table 1 数字是从旧 commit eval 出来的，paper_provenance 仅做 cell-level 绑定，未做 git hash 绑定

**实验规模**：每条件 n=3 seeds（用户后期统一指令）。π0.5 全部 n=3。SmolVLA matched-seed n=3，部分 sweep n=5–8。规模不足以支撑 generalizability claim——paper 已诚实标注 "n=3 per condition" + 在 limitations 写。

### 3.3 Findings 的质量与 Novelty
**核心 finding**："Unconditional learned correction on frozen flow-matching VLAs is harmful across all evaluated suites; K=2 pairwise L2 distance is a near-perfect proxy (ρ=0.9979) for K=10 variance, enabling a calibrated gating mechanism that recovers all the harm."

**Novelty 评估**：
- 系统性诊断 "correction always-on 有害" 是新发现，4×2=8 cells 全部 degradation 在该领域是有说服力的失败模式分析
- K=2 ρ=0.9979 vs K=10 variance 是有趣的实证发现，但理论上 K=2 与 K=10 的相关性高并非反直觉——是 incremental finding
- gating mechanism 本身在 selective prediction 领域是 textbook 方法（Geifman & El-Yaniv 2017 等已引）。**架构创新度低**
- ReconVLA / A2C2 / SC-VLA 的明确划界在 D060/D034 完成，positioning 合理

**Reviewer 评价**（D186 自评）："6.5/10，6.5→7 barrier = Novelty × Impact（方法简单 + 仅 LIBERO），非写作/统计可解"。这与论文实际定位（analysis-first paper with method contribution，D179）是诚实匹配的。

**分数低的原因**：不是包装问题，是真实科研贡献的边界——方法本身 trivial（K=2 + percentile threshold），insight 强但适用范围窄（frozen VLA + flow-matching + LIBERO）。

### 3.4 研究效率
1,423 个实验中：
- **直接贡献最终论文的**：≤120 个（Table 1 K-matched 4 suites × 3 conditions × 3 seeds = 36，Table 2 π0.5 4×3×3 = 36，τ-sweep 4 suites × ~5 τ × 3 seeds ≈ 60，加 baseline + supplementary 约 120）
- **探索性弯路**：≥800 个，包括：
  - per-DOF / scalar / direct correction / multi-stage CRM 所有变体（abandoned 之后无 1 个进入论文）

  - OpenVLA 全线（plan_800/801/802/803）+ OpenVLA-OFT 全线

  - 大量 norm sweep（ε=0.03/0.05/0.1/0.2/0.3）在 D118 后无 1 个进入主表

### 3.5 论文与实际科研的匹配度
**Abstract**："Learned post-hoc correction of frozen flow-matching VLA models is harmful by default..."——与实际发现匹配，未过度包装。

**Limitations 部分**（CoRL 2026 要求）扩充至 ~198 词（D186），坦诚承认：
- 不 beat VLA-only（仅 recovery 不 absolute improvement）
- 仅 LIBERO（无真机 / 无其他 sim env）
- 只在 flow-matching VLA 有效（OpenVLA tokenized 无效）
- π0.5 partial recovery（Object 套件 τ-gated 反而低于 always-on）

**Claim 强度匹配**：Spatial magnitude claim（+1.5pp p<0.05）+ 其余 mechanism claim（D150）。Abstract 措辞策略 "correctly modulates"（mechanism）而非 "significantly improves"（magnitude），是诚实克制的。

**遗漏的 negative results**：
- π0.5 Object adaptive 实际 -1.8pp（D154 / D155）——论文有 Table 2 写出，但 Discussion 弱化为 "Rule 5: near-expert baseline boundary"
- OpenVLA 0% / OFT 失败 → 已挪 boundary analysis appendix（D183），论文 main contribution 不再 claim cross-architecture
- K=1 CRM 失败 → 写入 K-value curve appendix
**整体诚实度高**：未发现重大隐瞒，但有 reframe 痕迹

  - **未交叉验证就采信下游信息**：M076 接受 Reviewer 错误假设、M077 接受 Agent 错误声明、M091 不等代码审计就 kill 实验。当下游角色提供"看起来合理"的技术声明时，Director 倾向于直接采信
  - **未对照决策历史就部署**：M113 部署了 D124/D055/D176 明确放弃的实验（OpenVLA / perdof）
  - **API 限速 / 反复 reset 期间无法保持 awareness**：5/26 04:05 用户 "能找 manager 要更多卡吗"，与此同时 Reviewer reset、Agent reset 同时发生，无人监控（M072）

### Agent (Main)
- **优**：Tool 调用量大且覆盖工具齐全（13,468 update_registry、8,843 Bash、4,800 read_registry）
- **问题**：
  - **Ghost experiments 高频**：M007/M019/M027/M064/M069/M080/M097/M100/M111/M115 至少 10 次"实验完成但 registry 未更新"，每次都让 5–14 张 GPU 长时间空闲
  - **Idle 时长**：M044（16h 空闲）、M072（102min idle + 63min idle 同日两次）、M033（3h GPU 全空），累计 GPU 浪费保守估计 >500 GPU-h
  - **Worker false-done 接受**：M033/M046/M064/M65/M82/M102 反复接受 Worker "done" 状态而不验证 nvidia-smi
  - **批量部署不去重**：M071/M106 重复部署相同实验，浪费数 GPU
  - **统计混淆**：M020 K=5 与 K=10 数据混淆（exp_id 只差一个 k5 后缀）；M026 把无 seed 实验混入 multi-seed 统计

### Reviewer
- **优**：**项目质量最稳定的角色**。多次抓出 Agent / Director 错误（M020 K=5/K=10 混淆、M027 Spatial CRM 缺 3 个 seed、M095 Table 1 混 batch、M107 Goal 计算错误）。每次大数据汇总后都做 cross-validation。具备真正的"独立审计"价值
- **问题**：
  - **过度激进的 ghost 判定**：M058（误判已完成 eval 为 ghost）、M066（Diag Worker 误标活跃实验 failed）——把 nvidia-smi 单点快照当作权威证据
  - **不了解技术细节就下结论**：M076 报告 "CRM 训练需要 4 suite precompute 全部完成"（错误，CRM 是 per-suite 训练），Director 据此发紧急撤回指令

### Paper Agent
- **优**：完成 14 轮迭代（5→6.5+ rating），编译稳定，0 critical warning
- **问题**：
  - **自查能力低**：5/28–5/29 用户多次反复要求"Figure 2 字重叠 用 paper banana 修复"、"figure5 左右图高度对齐"、"间距太大补字"——这些是 Paper Agent 本应自动捕获的视觉问题。说明视觉自检 pipeline（paper-audit-visual）有效但不被主流程触发
  - **数字传播错误**：M107 Goal CRM harm 14.5pp 错误（实际 13.2pp）从 D166 传到 D167 到 ROADMAP 到论文 4 处，无人在 Paper Agent 端做交叉验证
  - **指令-执行延迟**：用户 5/29 06:13 / 06:17 / 06:17 / 06:17 连续 4 次发"figure 4 5 合并"，前 3 次未执行

### Worker
- **优**：3,008 个 session，覆盖所有服务器操作；多数（83%+）正常完成任务
- **问题**：
  - **destructive action 缺乏 pre-check**：M002/M004/M006/M008/M014/M023/M030/M047/M057/M062 — kill 操作没有逐 PID 验证，多次误杀正在运行的实验
  - **deploy false-done**：M033/M046/M64/M65/M82/M102 — 报告 done 但实际进程未启动，每次造成数小时 GPU 空闲
  - **GPU 检查遗漏**：M034/M036/M053/M073/M88/M89/M98/M101/M103/M104/M112 至少 11 次 GPU 碰撞，**C001/C002 约束在 5/26 才作为硬约束建立**——这个本该是 Day 1 约束
  - **环境一致性遗漏**：M042/M043/M061/M108 跨服务器部署不做 pip freeze 对比 / md5sum 对比，导致代码同步后仍是不同环境

### 角色协作摩擦点
- **Director ↔ Agent**：M078 4 次矛盾指令、M054 D112+D113 worker race condition、M081 kill+restart worker 并行竞态
- **Agent ↔ Worker**：Worker 自行选实验部署没有 Agent 协调（M071），多 Worker 同时执行同类任务
- **Reviewer ↔ Director**：M058/M066/M076 Reviewer 给出错误结论，Director 未验证就采信
- **Paper Agent ↔ Reviewer**：Paper Agent 拒绝 / 忽略 Reviewer 审计的现象在 5/28–5/29 多次出现，多次依赖用户驱动而非 Reviewer 驱动

## 5. 关键发现

按严重程度排序：

---

### F1 [HARNESS] Registry 与实际进程状态长期不一致 — Ghost experiments 系统性问题
**证据**：
- M007（eval-obs-only-object-norm01-seed45 报告 3 次未修复，**28h+ GPU 浪费**）
- M019（Loop #13 接手时 13+ 实验完成但 registry RUNNING，5–6 GPU 空闲数小时）
- M027（统计脚本遗漏 seed42/46/48，CRM Spatial 数字虚高）
- M069（11 个 PREPARING 状态实验实际在跑，触发"14 GPU idle"假警报）
- M080（bjb2-28827 5 个崩溃实验未更新 FAILED）
- M097/M100/M111/M115（重跑/分批/手动 update_registry 都绕过 submit_training_job 的 cron 注册）
- 关键 root cause：submit_training_job 是唯一会注册 cron 的入口；任何"手动 update_registry → RUNNING"或"绕过 submit"的部署都不创建 cron，**实验完成后无回调**

**严重程度**：极高。**估计累计 GPU 浪费 >500 小时**（仅 M007/M019/M044/M072 四项保守估算）。投稿 deadline 紧张时这是致命问题
**改进建议**：
- 强制约束：禁止手动 update_registry 切 RUNNING 状态，必须经 submit_training_job
- Agent 每次 boot 第一步运行 registry-vs-ps 交叉审计
- 增加 PREPARING → RUNNING 超时自动审计（>5min PREPARING 无进程 → 标 FAILED）
- 增加 RUNNING → DONE 超时审计（无 cron 注册的 RUNNING 实验自动标 stale）

---

### F2 [HARNESS] Cron 完成检测系统性失灵 — exit file / sentinel 机制脆弱
**证据**：
- M012（DeprecationWarning 让 cron 误判 failed，影响 ≥3 实验）
- M029/M031/M032/M035/M058/M082/M099 反复 cron false alarm（complete/failed 双向）
- M032 极端案例：cron 读旧 exit file → tmux session 替换 → 杀死正在运行的进程（plan_702 三次部署全部失败）
- M105：评估脚本 try-catch CUDA OOM 后 EXIT_CODE=0，200 rollout 全 OOM 但 "成功" 报 0% SR

**严重程度**：高。复合效应是 (a) 真 failed 实验被忽略 + (b) 真 success 实验被误标 failed + (c) 进程被误杀
**改进建议**：
- Cron 判定逻辑：必须以 JSON 输出文件存在 + per-task 数据完整为成功条件，禁止仅依赖 stderr / exit code
- eval 脚本统一在 finish 时写 sentinel（一行 SUCCESS / FAILED + JSON 路径）
- OOM 在脚本层面要 raise → 让进程非零退出
- 重新部署前自动清理 exit file（M032 fix）

---

### F3 [HARNESS] Worker false-done — 部署/Kill 类任务缺乏后置验证
**证据**：
- M033（3 个 Worker 连续报 done 但 bjb1-32546 6 GPU 空闲 3h）
- M046（"17/17 GPU 满载" 实际 6 GPU 空闲）
- M64/M65（spatial-adaptive-s43 两次报 done 均未部署）
- M82（4 个成功实验被 harvest worker 标 failed）
- M102（westd 6 GPU 报已部署实际 5 空闲）
- 6+ 次相同模式

**严重程度**：高。Worker status=done 不可信，但 Agent 总在采信
**改进建议**：
- Worker 部署类任务必须 mandatory post-check：`sleep 30 && nvidia-smi | grep "evaluate.py"` 验证 ≥1 进程
- Worker harvest 类任务必须列出每个 exp_id 的判据（log / json / sentinel 哪一项确认）
- Agent 收到 Worker done 后对部署/kill 类任务必须自己用 ssh_read_only 二次验证

---

### F4 [HARNESS] GPU 碰撞 — 直到 5/26 才升级为硬约束
**证据**：
- 至少 11 起 GPU 碰撞事故（M002/M004/M023/M030/M034/M036/M053/M73/M88/M89/M98/M101/M103/M104/M112）
- M101/M103/M104 触发用户层面的 C001 约束（5/26 13:36）："**提交实验前必须 nvidia-smi 确认目标 GPU 显存 < 500 MiB**"
- 11+ 起累计代价：包括 (a) 实验慢 3× — 10×，(b) OOM kill 数据损坏，(c) 静默 0% SR 假结果（M105），(d) M023 类大规模意外 kill

**严重程度**：极高（合计损坏数据 + 浪费 ≥100 GPU-h）。这是项目第一天就该有的约束，**13 天后才正式立硬约束是系统性疏忽**
**改进建议**：
- submit_training_job 在 server-side 强制 pre-check（nvidia-smi 验证），不通过则拒绝提交，**不依赖 Worker 主动检查**
- 这条应当是 framework-level 默认行为，不能是 project-level 约束

### F5 [HARNESS] 跨服务器/跨环境部署一致性 — 5+ 起代码/包/数据版本不一致事故
**证据**：
- M042（py 文件部分同步）
- M043（lerobot 0.5.1 vs 0.5.2，缺 376 keys remap，**~6 GPU-h 浪费**）
- M061（CRM checkpoint 路径硬编码与当前使用版本不一致）
- M063（eval n_action_steps=50 vs 其他实验 10）
- M075（rsync checkpoint 未校验时间戳）
- M108（模型部署/实验提交竞态，模型目录还没创建就开始跑）
- M114（git pull 引入 regression，新 batch 全 0% SR）

**严重程度**：高。每次都是 sequence-of-events 类 bug，定位困难
**改进建议**：
- 跨服务器部署 Worker 必须做 environment audit：`pip freeze | grep <key_pkgs> + md5sum <key_files>` 对比
- 部署前先跑 1 task quick verify（SR > 0），通过才扩到全量
- evaluate.py 关键参数（K / max_correction_norm / checkpoint / mode）禁止默认值，必须命令行显式

### F6 [HARNESS] Director 决策反复 — 队列管理与"覆盖前指令"机制薄弱
**证据**：

**严重程度**：高。每次反复都 (a) 浪费 GPU + (b) 让下游角色失去信任
**改进建议**：

### F8 [HARNESS] 长会话上下文损失 — handoff 反复重写相同约束

### F9 [MODEL] 当下游提供"看起来合理"的技术声明时，Director 缺乏交叉验证
**证据**：
- M076：Reviewer 说"CRM 需要 4 suite precompute 全部完成"（错误）→ Director 直接发紧急撤回

**严重程度**：高。是 model 层面而非 harness — 即使 Director 系统配齐了交叉验证工具，**模型表现出"采信看起来合理的下游声明而非主动核实"的认知模式**

**改进建议**：

## 6. 评估总结（非报告结构，仅供裁决）

**Harness 设计缺陷的严重程度：高**。Registry 状态机不可靠（F1）、cron 检测失灵（F2）、Worker 自验证缺失（F3）、GPU 碰撞 13 天才立硬约束（F4）、跨环境部署 audit 缺失（F5）——这 5 项构成了 ~80% 的资源浪费。这些都是可通过 framework-level 改造解决的工程问题。

**模型能力边界的严重程度：中**。F9 / F10 / F11 三项揭示了真实的认知边界：(a) 信任下游声明不交叉验证 (b) 长程实验设计能力弱 (c) Worker 优先把环境 bug 归因为科学发现。这些通过 prompt 工程可缓解，但**不能完全消除**。

**人工参与的不可替代性：高**。从证据看，没有用户介入：(a) CoRL 投稿大概率失败（D011→D021 撤回是用户单条消息推动）、(b) 方法贡献会停留在 K=10 + obs_only 弱版本（D072 是用户硬要求）、(c) Table 1 K-matched confound 不会被消除（D177 是用户 catch）、(d) 论文最终质量会停在 4.5–5/10 而非 6.5/10。**当前 agent 系统作为"科研自动化"还远未达到"无人介入可投稿"的水平**，更接近"高级研究助理"——可以执行、可以记录、可以诊断，但需要持续的人工战略掌舵与质量审查。

**研究产出的真实价值**：mechanism insight（unconditional correction is harmful on frozen flow-matching VLAs）是真实贡献，且通过 8/8 cells degradation + ρ=0.9979 K=2 L2 calibration 这两组实证支撑。但方法本身（K=2 + percentile threshold）trivial，且仅在 LIBERO + flow-matching VLA 上验证。6.5/10 的自评与 25–30% accept 概率与实际科研贡献边界匹配——这是诚实的自我认知，不是包装失败。
