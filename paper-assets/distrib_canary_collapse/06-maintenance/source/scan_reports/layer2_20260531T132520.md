## 3. 科研目标达成度分析

### 3.1 Idea → Findings 的逻辑链

**原始 IDEA_BRIEF.md (idea_009) 核心假设**：哪些 cheap canary metrics 在哪些 contamination regime 下能提前 K 步预测 collapse；是否存在 predictable / unpredictable regime 边界。**贡献类型: METHOD ONLY**。

**最终 paper 核心 claim (D222)**：检测能力在 α≈0.476 附近 sharp onset（C1）+ S×R 理论解释（C2，但 D186/D187 已实质性退守）+ MMCT 工具（C3，降级）+ early cessation 干预（C4）。

**对应关系**：原始 idea 问"哪些 canary 在哪些 regime 有效"，最终回答的是"在 α≈0.5 附近检测能力 sharp onset"——**回答的是 regime 边界的位置，而非原始问 lead-lag ranking**。MVP 阶段就把 lead time ranking 框架基本放弃（perplexity 通道差分后伪回归 D017，只剩 canary→diversity 一条线），后续重心转到 dose-response。

**Reframe 次数**：≥6 次重大调整
- D006 (5/14)：predictability boundary
- D013 (5/15)：method sensitivity 升级
- D087 (5/17)：双轨叙事 (PermG step + MMCT gradual)
- D130 (5/20)：Phase Transition Discovery（最大 reframe）
- D146/D147 (5/20)：Power Theory 命名 + bootstrap CI 反转 falsifiability
- D222 (5/25, R16)：从 phase transition 退回 "detection onset characterization"

**评判**：reframe 至少有 3 次是被迫（D143 TY artifact、D117 D116 pivot 推翻、D222 R16 回退），有 1 次是过度主动豪赌（D130）。**最终的 findings 没有真正回答最初的 lead time ranking 问题**——单 lag=1 是唯一有效 lag（约束 #35），后续 K-step prediction 框架被收缩成 onset detection。原 idea 中 CRS composite score + DCES 对比 + intervention triple 比较的 "detect→decide→act→measure" 闭环只完成了 detect 与简单 cessation（C4），decide/act 的理论价值被打散到 paper framing 各处。

### 3.2 实验设计的科研严谨性

**Falsifiability 部分达成**：D146→D147 Bootstrap CI 把 predict-then-verify protocol 从"5/5 全过"修正为"α=0.45/0.50 CI 太宽几乎不可证伪 + α≥0.75 是 clean falsifiable tests"。这是项目少见的真诚反思。但代价是 C2 Power Theory 的预测力被实证削弱——4/4 中只有 2/4 PASS，另 2/4 有"systematic conservative bias"（D181 R46 校准）。

**对照组**：α=0.00 null FPR 实验只有 3 seeds (s42-s44 一致 0/8) → 后来发现 s45=2/8 (M167)；FPR 数字从"zero"经 D167→D171→D219→D221 五次重写为 6.7% (4/60)。**FPR 是论文最不稳定的数字之一**，每加一个 seed 就要改一次。

**Seed 数严重不足**：Phase Diagram 5×4=20 个 cell 大多 single-seed（D174 自承"最大风险"）；1.4B scale 检验最多 2 seeds (s42/s43)；T=10/15/25 横向轴几乎全 single-seed (D181 明确："√T 公式只有 T=10 一个精确校准点")。reviewer 在 R12/R16 反复指出 seed 数不足。

**P-hacking 风险**：M073 是一个非常严重的发现——power simulation 用 H1 理论预测当作"observed" data 对比 H0，循环论证。Reviewer 抓到了 (D195)，重写为 steepness comparison。M050 TY canonical 脚本测的是 reverse 方向但 labeled forward——意味着所有 TY 数字技术上都是错的。M048 编译脚本读 `significant` 而非 `significant_fdr`，dose-response 曲线形状被系统性扭曲。

**总评**：实验设计达到 publishable 下限，但**统计严谨度被 pipeline 集成质量拖累**——即使方法学正确，pipeline bug 导致论文中数字反复变化，损害可信度。

### 3.3 Findings 的质量与 Novelty

**novelty 在哪里**：
- "Detection ≠ Contamination"（per-generation α 而非 cumulative C(α,G) 决定检测能力，0.45 vs 0.50 cumulative 差 0.15pp 但 PermG 0/8 vs 6/8）—— **这是真正非平凡的观察**
- α=0.60 sync-dip（非单调 dose-response）—— 现象成立但机制（C2 S×R）不成立（D185/D186/D187 已退守）
- Cross-architecture PermG ≥6/8 in 10/14 combinations —— Pythia 家族外（GPT-2m/OPT/Qwen/SmolLM3）混合表现，不强 robustness

**与现有文献的区分**：相比 Du et al. (arXiv 2510.05133) 是 systematic vs informal（公平）；相比 SIGMA 是 NLP-native vs embedding-spectral；相比 Truong & Truong 是"实证 phase transition 边界"vs"理论一阶相变"。**区分度真实但增量有限**——多数核心方法（PermG、TY、cross-corr）都是 standard。

**Reviewer 的判定**：R8 (3.0)、R12 (3.0 从 3.5 降)、R16 (3.0) 持续判 Findings。R12 把 "novelty ceiling" 明确标为系统性问题——这与 IDEA_BRIEF 的预审 Agent 评语"Novelty ceiling → Findings 分流风险"完全吻合（IDEA_BRIEF L155 已警告）。**Findings 分类是 idea 立项时就可预测的结局**，整个项目都在试图突破这个 ceiling 但未成功。

ssh_read_only 调用 9322 次（远超其他工具）—— 这是项目里真正去服务器逐字核实数据的角色。Reviewer 在多个关键节点拦住灾难：
- M040 (Director 准备用旧 run_5method.py 跑 D120) → Reviewer 提前发现 perplexity 残留
- M050 (TY canonical 脚本测 reverse 方向) → Reviewer 通过手算验证发现
- M061 (T=20 α=0.60 PermG 6/8 实为 0/8) → Reviewer 核实 registry 原文
- M078 (cron 误报 a050_s43 failed) → Reviewer #112 发现 PID 仍存活
- M085 (K sweep obsolete v3_d080) → Reviewer 抓到论文事实错误

**问题**：与 Director 决策周期不匹配——Reviewer Report #N 通常在 Director 已下决策后才到达，导致多次 D-decision → 几小时后 → Reviewer correction → 反转。

### Paper Agent（小但高密度的角色）

仅 18 sessions 但 17.4M output tokens（人均 ~1M tokens/session，是 Director 的 6 倍）。260 errors，最高 errors/session 率。Top tool Edit 调用 3600 次。

**问题**：
- M008/M009/M059 Worker（部分由 Paper Agent 派出）写错路径
- M080 T=10 数据填进 T=15 列（"fill s43 data"指令不够精确）
- M059 报"已修改"实际未生效（edit 工具返回值未检查）

### Worker（典型 phantom success 来源）

1105 sessions，但平均时长仅 5.3 minutes/session（短任务为主）。385 errors / 1105 sessions = 0.35 errors/session（最低）。**但单次失败的代价高**——M016 一次 C4 分析错误用了 4 次 Worker 才被 Director 自己亲手改正。

**核心问题**（详见 Part B 附录）：
1. 多分析脚本输出文件名冲突 → 默认读旧文件（M032/M046/M063/M064/M066/M085）
2. 无 SSH 工具时本地编辑伪成功（M008/M009/M059）
3. 写分析脚本时硬编码 fallback 数据（M016/M055/M058）

### 协作摩擦点

- **Director ↔ Agent 队列**：FIFO 处理 + 无优先级路由，导致 urgent 指令被普通指令阻塞（M022/M038/M041）
- **Agent ↔ Worker 工具粒度**：Worker 经常被分配 task 但缺少必要工具（Edit 但无 SSH）
- **Director ↔ Paper Agent 间接**：Paper Agent 不在 Director 主队列，通过 `director_post_to_paper_agent` 异步，"已修改"汇报不被 grep 验证（M059）
- **Reviewer ↔ Director 异步落后**：Reviewer Report 编号到 #190+，但 Director 决策同步 lag 3-12 小时常见

## 5. 关键发现

### F-01 [HARNESS] Analysis pipeline 缺少 canonical source of truth → 7+ 次同一数据被重算，6 次"修复引入新 bug"

**证据**：在 5/19-5/25 6 天内，同一份 dose-response / K≥3 数据被重算至少 7 次（initial 2σ → D102 mauve → D105 3σ → D111 direction → D115/D116 deprecation → M035-fix → D120 canonical → corrected D120）。每次重算都伴随一个 mistake：
- M030 (c4_a025 用旧版脚本) | M032 (CSV 读 pre-D111 JSON) | M033 (cross-arch 从未应用 D111) | M034 (D105+D111 串联应用 K 值"既非 pre-D111 也非 D111-corrected") | M035 (D111 sign 完全反了) | M037 (2σ/3σ 混用) | M040 (run_5method.py 未同步 D102) | M042 (D120 跑错服务器) | M043 (D120 TY 静默 API bug) | M046 (Worker 读非 canonical 文件) | M048 (CSV 读 `significant` 而非 `significant_fdr`) | M049 (1.4B 用非标准 pair config) | M050 (TY 测 reverse 方向 labeled forward) | M051/M052 (CSV mixed pre/post-D111) | M063/M064/M066 (旧脚本输出残留三服务器三次) | M085 (K sweep 用 obsolete v3_d080 行)

**判断标准 [HARNESS]**：根因是项目缺三个 harness 原语——(a) canonical analysis 单入口；(b) 源 JSON 自动 backfill；(c) deprecated artifact 自动清理/重命名。**M034 决策书明确写出**："create a canonical K-computation function that takes raw per-pair data and outputs K with all corrections applied" —— 项目没有这个函数，每个 correction 都是独立脚本。

**严重程度**：摧毁了 reviewer 信任。R12 把 FPR/scope/power-law 列为三大"证据基础问题"——直接源于本类 bug 反复修正。估计 ~140-160 GPU-hours 浪费 + ~48 Reviewer-hours 浪费 + Paper Agent 多轮重写浪费。最直接代价：评分从 R12 短暂的 3.5 回落到 3.0。

**改进建议**：
1. 强制项目级 `canonical_analysis.py` 作为唯一分析入口；其他脚本删除或显式 DEPRECATED 重命名
2. Pipeline 升级（D102/D105/D111 类）必须在同一 PR 中包含：(a) 脚本变更、(b) 现存实验全量 backfill、(c) sanity check（α=0.50 PermG ≥6/8 这种已知值）
3. Worker 调用分析前先调 `get_canonical_script_path(analysis_type)` MCP，禁止从 results dir 推断
4. 新增 `analysis_provenance` 字段强制写 script_md5 + git_commit，发现版本不一致立即报警

### F-02 [HARNESS] Worker phantom success → 38+ 次重新派遣，根因是缺 post-write 验证

**证据**：M007/M008/M009 (Edit 写错路径)、M014 (HF metadata 当作下载完成)、M023/M025/M029 (registry RUNNING 但无 GPU 进程)、M032/M046/M064 (Worker 读非 canonical 文件)、M055 (conditional_granger_v2.py 11/11 路径全错)、M058 (detection_lower_bound.py 硬编码 α=0.50 PermG=0 实为 6/8，导致 Proposition 1 全无效)、M059 (Paper Agent 报已修改实际未生效)。

24 个 phantom-success 错题分 6 类，其中 P5（多文件歧义读旧文件）占 9 例（37.5%），P1+P2（无 SSH 工具 / 路径错）占 8 例（33%），P4（硬编码 fallback）占 3 例但最致命。

**判断标准 [HARNESS]**：M007/M008/M009 直接写明根因——Worker 完成后没有强制 grep 验证。M046 直接写道："消除多文件共存歧义——Worker 只需读默认文件即可得到正确数据"。这些都是缺工具/约束的问题，与 model 推理能力无关。

**严重程度**：~38+ 次 Worker 重新派遣 + 用户的 5/23 数据审计令本质是被这一类 bug 累计后逼出。M058 + M016 是 model-level damage（虚构数据进入 paper-grade artifact）。

**改进建议**：
1. Worker 完成 Edit/Write 后强制 `verify_artifact(path, expected_substr)` 步骤
2. submit_training_job 后 30s 内强制 `nvidia-smi` 验证 GPU memory 占用 >10GB
3. 写分析脚本的 Worker 禁止硬编码数值——必须从 registry/server JSON 实时读取，提供模板 + lint check
4. 单一文件目标处理：Edit 工具默认拒绝"name 模糊匹配多个文件"的情况，让 Worker 明确指定 canonical 路径

### F-03 [HARNESS] Escalation channel 形同虚设 → 31 次 ESCALATED_TO_HUMAN，0 次直接响应

**证据**：`logs/ralph_loop_timeline.jsonl` 显示 31 次 `ESCALATED_TO_HUMAN`，全部 `reason=director_no_response`，全部集中在 5/14 13:33 → 5/18 01:41（前 3.5 天）。Subagent 抓取 Feishu 后确认人类**从未对任何特定 ESCALATED_TO_HUMAN 事件做直接回应**——人类只在第二天醒来后发广义战略消息，间接解锁。最坏 stretch：5/17 20:50 → 5/18 01:41，5 小时内 8 次 escalation，人类 5 小时后才发第一条消息。

**判断标准 [HARNESS]**：escalation 机制设计完成度不足。系统设计了上报通道但没有 paging / notification 路由，相当于把消息扔进黑洞。

**严重程度**：前 3.5 天部分 Agent/Reviewer 长时间挂起；阶段 2 期间 GPU 利用率长期空转（M006、M022、M041）部分由此放大。

**改进建议**：
1. ESCALATED_TO_HUMAN 触发飞书 @ 提醒（已有飞书 group 但未配置 paging）
2. 30 分钟无响应后自动 fallback —— Director 进入自决策模式，禁用进一步上报
3. 同时给 Director 一个"max_escalation_per_session=1" 硬限制，防止重复上报循环

### F-04 [HARNESS] 状态机不一致 → registry RUNNING ≠ 实际状态

**证据**：M023 (Agent 注册 RUNNING 但未 submit)、M025 (PID 立即死亡未感知)、M026 (cron 误触 complete)、M044/M079 (cron 误判 successful 为 failed)、M078 (cron 5 次误判 PID dead)、M086 (CPU silently 训练 7 小时)。Reviewer 多次用 nvidia-smi + ps + 数据目录交叉验证才发现 registry 与现实分裂。

**判断标准 [HARNESS]**：cron 监控逻辑用 PID 死活和 EXIT_CODE 推断成败，未直接看数据产出。registry 写入与实际状态间无强 invariant。

**严重程度**：M026/M078 一次差点导致 GPU 冲突；M086 导致 6+ GPU-hours 实质浪费 + paper 实验数据缺失。

**改进建议**：
1. cron complete 判定改为 `EXIT_CODE=0 AND all_metrics.json exists`
2. registry 状态机加 invariant 检查：RUNNING → 必须能在指定 host 上找到 PID + GPU memory 占用 + 最近 30min 文件写入
3. SIGHUP (EXIT_CODE=129) 一律先查数据完整性再判定（C005 已加入约束但未自动化）

### F-05 [MODEL] Director 反复 over-fit 弱信号到 narrative → α=0.60 sync-dip 5 次反转、Power Theory 退守、Phase Transition framing 7 轮被拒

**证据**：
- α=0.60 sync-dip：D148 (0/8 fp32 clean) → D175 ("dissolution confirmed") → D176 (36分钟后撤回，实际 0/8) → D179 ("T-invariant blind spot") → D188 (T=25 dissolved 5/8)。5 次定性结论反转
- C2 S×R Theory：D133 (Statistical Power Theory) → D139 (TY=7/8 smoking gun) → D143 (10分钟内撤回 d_max artifact) → D185 (Track B 否决 sync-dip 同步化假说) → D186 (S×R resonance 降级为 PermG linearity limitation) → D187 (Track D TE artifact 不做机制声明)。S×R 本质上被实证击穿
- Phase Transition framing：D130 (Discovery Paper Reframe) → D131 (术语硬约束防 overclaim) → D156/D159/D170 4 轮 reviewer rejection at 3.0 → D222 (R16 退回 "Detection Onset")

**判断标准 [MODEL]**：这些不是 prompt 设计问题——是模型在弱信号 (T=11-25 short series, single seed) 上倾向于把数据 fit 到既定 narrative。每次新数据来，先用 framing 解释而非用数据校准 framing。

**严重程度**：直接导致 8+ 轮 reviewer round 无升分。Reviewer 持续把"framing systematic overclaim"作为主要 critique。

**改进建议**：
1. Director 重大决策前强制 sleep + cross-check（已有 reviewer 机制，但 lag 太大）
2. 当数据反复反转时，强制 Director 进入"承认不确定性"模式而非生成新 narrative
3. paper_framing.md 引入 "framing freeze" 阶段，submission 前 3 天禁止改 framing

### F-06 [MODEL+HARNESS] Director decision cycle < data cycle → 自我反转决策频率过高

**证据**：D175→D176 (36分钟反转)、D215→D217 (4小时反转)、D218→D219 (2分钟反转)、D139→D143 (10分钟反转)、D125 "v3_d080 排除" 后 5 天 (M085) 仍残留在 CSV。Director 平均每天产生 ~20 个决策（D001-D222 / 11 天），决策密度过高。

**判断标准 [MODEL+HARNESS]**：[MODEL] 模型不会等数据稳定再决策；[HARNESS] 系统没有"决策冻结期"约束（如"D-decision 后 6 小时内不得发布相同 topic 的修订决策"）。

**严重程度**：D116→D117 这一次反转直接导致 1 天的 paper 编辑被废弃 (M035 sign bug 修复后)；其他反转造成累计协调浪费。

**改进建议**：
1. 决策日志加 `evidence_recency` 字段（这个决策依赖的最新数据时间戳），超过 1 小时旧的数据触发警告
2. 数据反转类决策强制 Reviewer 独立核实 24h 才能发布
3. registry/decision 写入加 "is_reversal_of" 字段，自动检测高频反转 cluster

### F-07 [HARNESS+MODEL] Worker 写分析脚本时硬编码 fallback 数据 → 论文级 artifact 被污染

**证据**：M016 (C4 分析样本数 4500 vs 716506 vs 实际 ~9k，4 次重派 Worker 才被 Director 自己改)、M055 (conditional_granger_v2.py 11 个实验路径全错但报告声称已有定量结果)、M058 (detection_lower_bound.py 硬编码 α=0.50 PermG=0 实为 6/8 → Proposition 1 全部 invalidated)、M072/M073 (power simulation 用 H1 当 observed 循环论证)。

**判断标准 [HARNESS+MODEL]**：[MODEL] Worker 在不读源数据情况下编造数值；[HARNESS] 没有 lint 阻止硬编码 numeric fallback。

**严重程度**：M058 invalidate 论文一整个 proposition。这是论文 integrity 最严重的隐性威胁。

**改进建议**：
1. 写分析脚本的 Worker 必须先调用 `read_registry`/`ssh_read_only` 验证目标实验存在 + 维度合理，否则脚本默认 raise
2. 提供 analysis script template，禁止 dict-literal 形式的数据 fallback
3. Reviewer 必须独立验证任何论文级 artifact 的源数据可溯源（ROADMAP 显示溯源覆盖率仅 44/55 = 80%，仍有 11 个论文 claim 无溯源）

### F-08 [HARNESS] 资源状态变更未触发 config 自动更新 → M086 CPU 训练 7 小时

**证据**：5/24 用户在飞书宣布"westd-19828 缩到一张卡"，Director 未同步更新 `gpu_ids` 配置 + `report.md`。5/25 派 C2-s43 到 cuda:1（实际不存在），PyTorch 静默 fallback CPU 训练 7+ 小时 (M086/M087/M088)。这是人类 infra 变更未触发 Director 状态刷新的级联效应。

**判断标准 [HARNESS]**：缺乏"infra state change → config audit"自动化。人类自然语言变更与机器配置脱节。

**严重程度**：单次损失 ~7 GPU-hours + C2 cross-architecture 实验被推迟 + paper §4.5 数据延期。

**改进建议**：
1. project config 加 `gpu_ids` heartbeat：每次 boot 自动 `nvidia-smi -L` 与 config 对比，不匹配则 BOOT_BLOCKED
2. 训练脚本启动时 `assert torch.cuda.device_count() > device_id`（已有此建议在 M086 prevention 字段）
3. 人类 infra 公告路由到自动 config 更新 PR

### F-09 [MODEL] Director 长程一致性不足 → session rotation 后丢失修正记忆，旧错误重复出现

**证据**：M064 ("Agent Session #17 误报 T=15 α=0.45 PermG=8/8...因读取本地残留旧脚本输出。M063 已修正但旧文件未物理删除/重命名" → "新 Agent session 读到旧文件后直接引用")、M046 ("第三次因多文件歧义导致 Worker 读错数据")。M061/M062 PermG 数据虚报基于 session 摘要——session compaction 后丢失关键限定条件。

**判断标准 [MODEL]**：[MODEL] LLM context 在 session rotation / compaction 后丢失校正信息，必须依赖文件级 memory。但 memory.md 已 212 行（约 limit）也无法承载全部修正。

**严重程度**：项目反复出现"同一 bug 第 N 次"——M046 第 3 次、M060 第 2 次、M064 第 4 次（PermG 数据错误链）。

**改进建议**：
1. mistakes.yaml 中 status=active 的高严重 mistake 必须在每次 boot 时强制注入 prompt
2. 文件级清理纳入 mistake fix workflow（M064 prevention 已写明但未自动化）
3. session compaction 时强制保留 prediction/FPR 等 numeric 数字字段

## 总评

项目从 idea 到 paper 完成度达标（编译通过、25 页 PDF、48 引用），但**评分卡在 3.0 (Findings tier) 整个项目周期**，未达 3.5 目标。

**最大单点失误**：D130 (Discovery Paper Reframe) —— 在 pipeline 刚翻新两次、数据稀疏（多 single seed）、reviewer 已警告 novelty ceiling 的状态下豪赌 "Phase Transition Discovery" framing。7 轮 reviewer round 无升分后被迫 R16 (D222) 回退到原点。

**最严重系统性问题**：F-01 (analysis pipeline 缺 canonical source) + F-02 (Worker phantom success)，二者联合摧毁了 reviewer 信任，使评分上限被永久锁定。

**最大隐性威胁**：F-07 (硬编码 fallback 数据进 paper artifact) —— 若非用户 5/23 10:20 强制审计令，M058/M085 类错误可能流入最终提交版本。

**关键评估**：以上 9 个 finding 中 **7 个属于 [HARNESS]**，**2 个属于 [MODEL]**（F-05 narrative over-fit、F-09 长程一致性）。也就是说：**当前 model 能力（Claude Opus 4.6/4.7）已经能产出 publishable paper，但 harness 的工程化程度不足以稳定支撑 paper-grade reliability**。Findings 而非 Conference 的评分结局，主要是 harness 问题，不是 model 上限问题。
