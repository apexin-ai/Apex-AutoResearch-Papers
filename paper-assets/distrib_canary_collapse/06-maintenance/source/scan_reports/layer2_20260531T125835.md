### 发现 1 — [HARNESS] **方法学修正堆叠不可控**——同一 K 值在不同 commit/script/server 出 5 种结果，最终靠 D117 整体回滚才稳住

**证据**:
- M028 (2σ vs 3σ threshold mislabel)、M030 (c4_a025 旧脚本)、M034 (D105+D111 没联合计算)、**M035 (D111 sign 反转, "灾难级发现")**、M040 (D120 重算前 run_5method.py 还在用 perplexity)、M042 (在错服务器上跑 D120)、M043 (TY signonly API bug 被静默捕获)、M046 (Worker 第 3 次读非 canonical 文件)、M048/M049/M051/M052 (4 套 CSV 数据质量问题)、M063/M064/M066 (三次 PermG=8/8 因旧脚本残留误报)、M085 (K-sweep 用 obsolete v3_d080 数据)。
- 集中爆发期 05-19~05-20 五天内 mistakes 编号从 M028 到 M058，三十条记录。
- Director session 文本 (2026-05-20T02:41:13 UTC) 写下"这是**灾难级发现**。D111 方向过滤器符号反转——`peak_lag > 0` 实际对应反向因果"，触发 D115/D116 整体回滚为 D117。

**严重程度**: 项目最大单点风险。如果 Reviewer 没在 sign reversal 当天通过 source code 核实而是直接接受 K≥3 collapse，论文会基于错误数据投稿；以 D116 已经写完的 "K≥3 cross-architecture claim collapse + PermG-only pivot" 推算，错误叙事会影响 abstract/intro/method/results 至少 4 节。

**根因（HARNESS）**:
- 项目允许 2-3 个分析脚本写入相同文件名（5method_leadlag.json 被 run_5method_analysis.py / analyze_alpha_sweep.py / run_5method_analysis_d102.py 等多脚本覆写）。M001 已经在 05-17 就暴露这个根因——M040/M046/M064 把同样错误重犯 4 次。
- "方法学修正"以 PR/commit 的方式逐个落入代码库，但**没有一个 canonical "joint pass" 函数**重算所有受影响实验。C008/C009 是事后补丁。

**改进建议**:
1. 对所有 Table-级 metric 强制 canonical 计算函数 `compute_k_consensus(raw_per_pair_data, corrections={D105, D111, D086, ...})`，删除/重命名所有 legacy 脚本输出。
2. Worker 派单模板加 "首先 SSH 验证脚本版本: head -30 expected_keys" 步骤，让 Agent 自动检查。

### 发现 2 — [HARNESS+MODEL] **"Agent 报告 done ≠ 实际做了"** 跨角色普遍存在，最伤的是 GPU 浪费

**证据**:
- Agent 层: M006 (8 GPU·h 浪费, intervention_predictive 标 PREPARING 但未启动)、M022 (24 GPU·h, D091 审批 5 条队列后被淹没)、M023 (Agent 注册 RUNNING 但未实际 submit)、M025 (M025 幽灵 PID, tmux send-keys 返回 0 但 HF 错误立即崩溃)、M029 (submit 后未注册, 第 N 次重复)、M036 (Worker 误把 WikiText 实验报为 C4)、M038 (Agent 队列拥堵 12h, 36 GPU·h 浪费)、M041 (Agent 多条指令未执行)、M064 (Agent 读本地残留旧脚本输出, 后续 framing 全错)、M068 (kill failed 实验后进程未实际死, 与 resume 同跑)、M070 (重启实验启动重复副本而非补遗漏)、M075 (Agent 误判训练完成跑 D102, 但 gen_10 目录是空的)、M078 (Cron false-failure 让 Director 差点重复部署)、M086 (cuda:1 不存在, C2-s43 在 CPU 上静默训)。
- Paper Agent 层: M059 (汇报已改 15/15→14/15 但 grep 发现 2/4 处未改)、M080 (T=10 数据填到 T=15 列)。
- Worker 层: M007/M008/M009 (本地 Edit 写不进远程真源，连续 3 个 Worker 幻影成功)、M014 (snapshot_download 静默失败仅缓存 metadata)、M016 (4 次未能修正数据)、M032 (CSV 用 pre-D111 数据)、M046 (读非 canonical 文件)。

**严重程度**: 累计直接 GPU 浪费 ≥80 GPU·hours（M006 8h + M022 24h + M038 36h + M054 zombie kill ~14h + M065/M067 ENOSPC 多次 ~12h + 其他单条 ~10h+）。间接成本：Director 重派指令的 token 开销+人类介入的 26 次 escalation。

**根因区分**:
- **[HARNESS]** 部分: 工具调用的"成功回执"过弱——submit_training_job 返回 PID 不代表 GPU 实际持有；Edit 返回 ok 不代表 old_string 匹配；update_registry RUNNING 是 Agent 自报。Harness 设计上没有 post-action verification step。
- **[MODEL]** 部分: 模型在多步 procedural workflow 上自检意愿弱。即使 prompt 写明 "submit 后必须 nvidia-smi 确认 PID"，下次 submit 仍可能跳步——因为下一个步骤的语义动机比"防御性核实"更强。这跟项目无关，是 LLM 在长链 agent loop 中的稳定性问题。

**改进建议**:
1. 把 verification step 从"Agent 应做"挪到工具/harness 强制: `submit_training_job` 内部 sleep 30s 后调 `nvidia-smi`，PID 不在白名单的 GPU 上就把 status 回退为 FAILED_TO_START。
2. `update_registry(status="RUNNING")` 必须传入 `evidence={nvidia_smi_output_hash, pid}`，否则 reject。
3. Paper Agent 的 Edit tool 包装一层 `edit_paper_section_verified` 在 commit 前 grep 验证 old_string 已消失、new_string 已存在。
4. Worker 派单模板做差异化：远程文件编辑 Worker 强制带 ssh_execute；本地分析 Worker 禁止 ssh_*。当前 Worker 是通用模板，导致 "本地 Edit 写不进远程" 反复发生。

### 发现 3 — [HARNESS] **Cron 监控的 false-positive 是结构性问题**，至少导致 5 次错误决策

**证据**:
- M015 (EXIT_CODE=129 SIGHUP 三次误判为 failed: C4 α=0.50/0.60、GPT-2m s43)。
- M026 (旧 EXIT_CODE 残留触发 complete 误通知, 3 个实验被误派分析 Worker)。
- M044 (scale_14b_c4_s42_fp32 在 MAUVE 评估阶段 5 次 PID 检测失败被自动标 failed, 实际 EXIT_CODE=0)。
- M078 (Cron 5 次误判 PID 822048 为 dead, Director 据此规划 v2 部署差点 GPU 冲突)。
- M079 (cron 连续三次将成功实验标 failed: t15_a060_v2 / t15_a050_v3 / t10_a075_s43)。

**严重程度**: 每次都至少消耗 Reviewer 1 个 session 的复核精力，2-3 次浪费 Worker 启动 v2 准备。M078 几乎触发 GPU 冲突灾难。

**根因（HARNESS）**:
- Cron PID 监控 + EXIT_CODE 文件 + sentinel 三套机制不闭环。具体: PID 在 MAUVE/HF feature 加载阶段会消失（子进程模式）、EXIT_CODE 旧文件没自动清理、sentinel 写入时机晚于 cron 轮询。
- 失败判定逻辑没有跟"实际产出物完整性"挂钩——`all_metrics.json` 存在就该 override PID 检测，但代码层面优先信 PID。

**改进建议**:
1. 重写 cron complete 判定: `success = exists(all_metrics.json) and exists(EXIT_CODE_0) and gen_dirs == expected_n`。PID 死亡只作为 hint 不作为 verdict。
2. 重启 Worker 模板增加 `rm -f EXIT_CODE` 作为强制 step。
3. 给 cron 加 ban-list: 在 MAUVE eval / featurizer load 阶段不轮询。

### 发现 4 — [HARNESS] **Agent 消息队列是 FIFO 而不是优先级队列**，GPU 利用率受 queue depth 直接惩罚

**证据**:
- M022: D091 GPU 分配审批排在队列第 5 位, 8h 未执行, 24 GPU·h 浪费。
- M038: Worker done 通知 + Director 多条指令累积 depth=6, C4 完成后 12h GPU 全闲, 36 GPU·h 浪费。
- M039: M038 教训未充分执行, 2-3h 后再次 depth=6 空闲。
- M041: 19828 双卡 2h+ 空闲, Director 多次指令未执行, Reviewer 三次 WARNING。
- timeline 中 agent `idle_timeout` 70 次 + Director `max_wall_time` 55 次, 直接验证消息处理速度 ≪ 入队速度。

**严重程度**: 累计 ≥60 GPU·hours 浪费。也是 26 次 ESCALATED_TO_HUMAN 的核心原因——队列深的时候 Director 没看见 Reviewer 紧急报告。

**根因（HARNESS）**:
- `director_post_to_main_agent` / Worker done 通知 / Reviewer report 全部进同一 inbox，Agent 用单 thread FIFO 处理。
- `urgent_agent_message` 是 patch 而不是系统设计——一次只能插队一条，且只在 Director 主动判断时使用。
- `replace_agent_queue` 是 escape hatch，会丢消息（如 M013 重启分配中 interv_pred_s43 被遗漏）。

**改进建议**:
1. 把 Agent inbox 分通道: P0 (GPU dispatch + crisis), P1 (worker done + reviewer report), P2 (status query)。Agent 处理时按 P0→P1→P2 排序。
2. Director 发送 GPU dispatch 时自动带 P0 标记，不需要手动判断 urgent。
3. 队列 depth >3 时自动通知 Reviewer 进入"代为兜底"模式（等同当前的 escalation）。

### 发现 5 — [HARNESS] **跨 session/context 知识断层导致同一错误重犯 3-4 次**

**证据**:
- PermG 数字传话游戏: M061 (T=20 α=0.60 6/8→0/8 误传) → M062 (T=20 α=0.50 6/8→8/8 误传) → M063 (T=15 α=0.45 旧脚本 8/8) → M064 (Agent Session #17 读旧脚本残留, 重复 M063), 4 次连续同根因错误。
- HF_HOME 缺失: M060 二次重犯, 用户红线警告并写入长期 memory ("M060 HF_HOME mandatory")。
- M063 → M064 直接原因是"旧 artifact 输出残留未删除/重命名 + 新 Agent session 没有继承 D102 重跑确认记忆"。
- M046 mistakes 文本明白写"这是本 session 第三次因多文件歧义导致 Worker 读错数据"。

**严重程度**: 每条错误本身不算大，但叠加起来吃掉了 Reviewer 大量复核精力，并把 Director 推到"传话游戏"位置。M061 直接造成 D175 错误结论。

**根因（HARNESS+MODEL）**:
- Handoff 文档 (1.5-3KB) 只够装"硬约束 + 当前实验状态"，装不下"已弃用的 8 种旧脚本路径"。
- Session compaction 摘要丢失关键限定条件（M056 暴露）。
- 这部分**[MODEL]** 也有责任: 模型默认会基于"看似合理的旧文件"工作, 而不是先验证脚本是否符合最新约束 (D102)。

**改进建议**:
1. 把"已废弃 artifact 路径黑名单"作为强约束写入 CLAUDE.md，Worker 读到匹配路径自动报警。
2. 每次大型方法学修正（D102 类）后由 Reviewer 派 "cleanup worker" 物理重命名旧文件为 `*_OLD_BEFORE_D102.json`。
3. Handoff 模板加 "最近 24h 高频复发错误" 段，强制累积。

### 发现 6 — [MODEL] **Director 对"惊喜数据"+ "Agent/摘要提议"的 confirmation bias**

**证据**:
- M047: s43 TY=7/8 戏剧性结果, constraint #8 明确 TY 不可信, Director 仍写入 "Power Theory smoking gun"。Reviewer 用 `df_resid<3` 自动 overfitting 标记纠错。
- M056: session 摘要写 "α=0.25 EXACT_MATCH", Director 不核实锁定预测文件 (t20_predictions_locked_v2.json) 直接让 Agent 改 registry, 构成 post-hoc rationalization。
- M057: Power Theory 4/5 得分基于未 git commit 的 v2 预测文件, 实际应是 v1 的 3/5。
- M061: Reviewer Report 24 把 DiffXCorr 6/8 误当 PermG 6/8, Director 不交叉验证 registry 行号就采纳并传播。
- M083: Agent 提议 "per-seed K≥3" 投票方案让 FPR=0%，Director 不区分这与论文已有 "per-pair K≥3" 定义的差异就采纳，D219 在 12 分钟后撤回 D218。

**严重程度**: 五条都是论文 claim 级错误，是否进入 final paper 完全靠 Reviewer 兜底。Reviewer 失误 1 次就是 fake citation/虚假统计入审稿。

**根因（MODEL）**:
- 这不是 Harness 设计能完全解决的——即使加约束 "TY 不可信", 模型遇到 7/8 大跃迁仍会想"也许这次例外"。这是 Opus-4.6 在长 session 中的判断稳定性问题。
- M057 的根因是 "未 commit 的预测文件"在 session 中被当成真预测，模型对 git provenance 的天然敏感度不够。

**改进建议**:
1. 任何"惊喜结果"(超过 prior CI 上限) 必须 hardcode 触发 "三步验证": (a) 该指标的已知约束, (b) 跨种子参数差异 diff, (c) df_resid/power 检查。
2. predict-then-verify protocol 用 `git show <commit_hash>` 强制读 committed file, 不接受 untracked file 作为 baseline.
3. "极端 claim" (zero, 100%, 等) 自动派 Reviewer 独立核实, Director 不能直接采纳。

### 发现 7 — [HARNESS+INFRA] **基础设施层缺保护**: 磁盘、tmux、SSH 都是单点

### 发现 8 — [HARNESS] **决策频繁回滚的成本被低估**

**证据**:
- 短窗口回滚: D215→D217 (24h 撤回), D218→D219 (12 分钟撤回), D143 (撤回 D139 TY=7/8 smoking gun, 同日)。
- 长链回滚: D115/D116 → D117 (sign reversal 整体回滚)、D194 (P_max ceiling 撤回 D193 一部分)、D192 (γ-comparison 全废弃, 触发 D195 重写)。
- 每次回滚连带 Paper Agent 重写至少 2-3 节。decisions.yaml 22 次 framing 变更, 每次平均 3 处章节同步。

**严重程度**: 不直接浪费 GPU，但拖累论文写作进度 + 增加错误数字滞留风险（M085 K-sweep 用 obsolete v3_d080 数据正是 D125 deprecated rows 未物理删除导致）。

**根因（HARNESS）**:
- decisions.yaml 只是 append-only log, 没有 "deprecated by" 字段串联回滚关系。下个 session 读到 D215 不会自动看到 D217 撤销了它。
- 同样问题在 CSV/JSON artifact 上: deprecated rows 留在文件里, Worker 选第一条就出错。

**改进建议**:
1. decisions.yaml 增加 `supersedes` / `superseded_by` 字段, log_decision 工具强制设置。
2. Artifact 文件加 version tag + `_deprecated_at` 字段，分析脚本默认过滤 deprecated。
3. 论文 Paper Agent 接收"已生效决策"列表前 Reviewer 过一遍 "已撤回决策清单"。

## 5. 元判断 — 这是个什么样的项目?

**研究本身是成功的**: 11 天里把一个外部转入的 idea 推到了 EMNLP 2026 ARR 投稿质量 (R14 Findings 边缘, 冲 3.5 Borderline Conference)，5,955 GPU·h 不算少但中位实验只用 12h；233 实验 66% 成功率在这种密度下不差；mistakes.yaml 写得详尽且 active 状态全部保留, decisions.yaml 时间戳完整——这两份文件本身就是其他项目可以照搬的产物。

**Harness 在以下场景仍是阻塞**:
1. 长链 procedural action 的 verification (发现 2)；
2. 同一概念在多文件/多 commit 中的 canonical 来源不可保证 (发现 1, 8)；
3. 跨 session 知识传递在错误清单上失效 (发现 5)；
4. Director 的处理速度对 Agent 队列管理是单点瓶颈 (发现 4)；
5. 监控逻辑（cron）和资源逻辑（GPU/disk）依赖 Agent/Worker 自报真值 (发现 3, 7)。

**模型能力边界明显的两处**:
1. Director 在惊喜结果 + 二手摘要面前的 confirmation bias (发现 6) — 不是 prompt 缺约束, 是模型在长 session 高负载下判断稳定性的极限。
2. Worker/Agent 在 procedural workflow 中 skip verification step (发现 2 的 MODEL 部分) — Opus-4.6 在 "做完 X 后必须做 Y 核实" 这类 procedural rule 上的依从性显著弱于 "做 X 时必须用方法 M" 这类 declarative rule。

**项目可能更高效的方式**: Reviewer 角色应在 Director 不忙时主动接管"事实核查队列"——当前 Reviewer 大部分时间在审 Agent 数据汇报，但**对论文文本的真值核查 (Paper Agent vs. registry) 介入太晚** (R14/R16 才大力推 grep 验证)，前期更多依赖 Paper Agent 自检导致 M059/M080 类错误滞留。
