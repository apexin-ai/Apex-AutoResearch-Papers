## 2. 项目叙事重建

### Stage 1 — MVP 闪电通过（5-14 → 5-15 早晨）
Idea brief 在 5-14 立项，目标 dual contribution：**(A) Schema Confusability 控制实验**（fix count、vary BCS）+ **(B) SDGD 框架**（confusability-aware schema decomposition）。D001 选 exp-002 (Confusability Controlled) 为 MVP，5-15 02:34 即 PASS：count_12 内 BCS↔F1 r=0.501 p=0.008、pairwise BCS-confusion ρ=0.254 (n=1953)、high-BCS extreme batches 的 type confusion rate 是 low-BCS 的 10-28×（D005）。**核心机制确认**：confusability 通过 type substitution 通道而非 omission 通道驱动降级。

这一阶段的关键转折是 D002→D003→D004：MVP 设计先以"Δ(solo-batch)"为主指标，发现 count=1 时模型 over-predict 严重（pred/gold=8×），solo baseline 行为模式异常 → 改用 within-count Pearson；又发现 F1 受 precision over-prediction 污染 → 改用 recall 作为更干净的 channel proxy。**Director 此处展现了良好的科学判断**：根据每个实验暴露的混淆变量主动调整指标。

### Stage 2 — SDGD 全面失败 + 多模型补救灾难（5-15 中下午）

## 3. 科研目标达成度分析

### 3.1 Idea → Findings 的逻辑链

| 原 idea（5-14） | 最终 paper（5-25） |
|---|---|
| 标题：*"Does Type Confusability Drive Schema-Induced Degradation in LLM IE? An Empirical Study and Principled Decomposition Framework"* | *"How Does Schema Complexity Predict Performance in Training-Free LLM IE?"* |
| Dual contribution: (A) 控制实验 + (B) SDGD 框架 | Single contribution: 控制实验 + SDGD 作为 negative result |
| Claim "confusability is dominant factor" | "confusability is detectable but secondary signal (typical 2.2pp); count is primary degradation factor (up to −49pp)" |
| 5 个数据集、4 个 baseline / decomposition method | 4 个数据集，BCS 独立效应只在 FewRel RE 干净成立 |
| 目标：metaphorical "Lost in the Middle" of IE | 实际：empirical observational study + bounded interaction TOST |

**关键 reframe 次数**：
- D008 (5-15)：pairwise 升为主要证据，per-type 因 type frequency confound 降级
- D012-D013：从 "embedding domain boundary" 改为 "pairwise vs aggregation level confound"
- D019：drop SDGD claim
- D044 (5-16)：Title "Drive" → "Shape"；effect size framing 倒置（典型 2.2pp 而非 31.2pp 为 headline）
- D055 (5-17)：70B NER 评估协议统一后 "紧密跟踪" → "方向一致"
- D068 (5-20)：v14 回滚 v13 的错误 claim 收窄（M009 触发）
- D070 (5-21)：从 "到处加 caveat" 改为 "strong core (FewRel R²=22%) + bounded scope"

绝大多数 reframe 是**被审稿迫使的**，不是主动发现更好角度。R32-C1（仍未解决）暴露最终落点的不一致：title 仍说 "IE"，但**BCS 独立效应在 4 个数据集中只有 FewRel 干净成立**（DocRED VIF=50.9, Few-NERD r=0.069 p=0.219, MAVEN centrality confound）。

### 3.2 实验设计的科研严谨性

**优点**（这部分是项目最好的地方）：
- VIF 检查排除 multicollinearity（VIF=1.18 vs 50.9）
- Percentile bootstrap CI 避免正态性假设
- Cluster-robust SE 处理 batch 内非独立性
- TOST equivalence testing 量化交互效应上界
- Power analysis 诚实报告 NER null 的 65% power
- Format independence (paired constrained vs unconstrained, r=-0.45 vs -0.44)
- D047 D048 D049 D050 多轮 framing 校准每次都引用具体证据

**问题**：
- **R32-W2 scale shopping 嫌疑**：TOST probability scale p=0.003 通过、logit scale p=0.209 不通过——选有利的作 primary 是 reviewer 攻击点
- **C3 极端 batch N=1 per condition**：Fig 1b 是 illustrative，证据强度被 Reviewer 反复质疑（最终降为 "illustrative" caption）
- **D026 exp006 2×2 factorial**：BCS 与 count 不正交（high count 的 BCS floor 被推高），10 个 high_count/high_bcs batch 的 BCS 完全相同（伪重复）。结果 inconclusive，被弃用
- **D028 Channel 2 cross-model 弱复现**：LLaMA-8B FewRel exp2 只 5pp 而 Qwen3 31.2pp，floor effect + BCS 压缩，但论文仍写入"replicated"

### 3.3 Findings 的质量与 Novelty

最终 paper 的核心 claim：FewRel 上 BCS 独立解释 ~27% batch-level RE accuracy variance（semipartial R²=0.273, VIF=1.18, n=204）。这是**single-dataset, single-task 的 quantitative finding**，附带 4 数据集的定性方向一致。

**Reviewer 共识（R32 final）**：
- S1-S6 strengths：实验设计精巧、统计工具链上乘、诚实报告负面、count-degradation 跨任务稳健、appendix 质量极高、BCS 作为 pre-hoc proxy 实用
- **R32-C1 (open)**：Title 声称 IE，BCS 独立效应只 FewRel RE 干净——逐数据集检查 4 个里仅 1 个支撑
- **R32-C2 (open)**：核心定量 claim semipartial R²=0.273 仅 Qwen3-32B 单模型，跨模型只有 count-curve 和 BCS gap
- **R32-C3 (open)**：SDGD/RQ3 分析深度不足（半栏篇幅）

最终评分 **3.5 Borderline Conference**，commitment 走 Findings (≥3.0) 几乎稳。Main 接收率 Director 自评 <30%。**论文质量瓶颈是 novelty 本身而非写作**——D061 (5-19) 直接写明 "writing 层面提分空间归零，结构性 limitation 无可行方案、modest 效应量、SCS=既有度量"。

### 4.6 角色协作的摩擦点

- **Director ↔ Reviewer 的 cross-check 失效**：M009 是典型 case，本应 Director 在采纳 Reviewer claim 前 read_registry 验证，但跳过了。Director 把 Reviewer 当 oracle 而非 second opinion
- **Agent → Director 的状态反馈延迟**：M008 phantom data 误报让 Director 不得不亲自 grep 本地文件
- **Director ↔ User 的频道堵塞**：40 次 ESCALATED_TO_HUMAN 表明 Director 经常无法及时响应 Agent/Reviewer。一个典型 case：5-17 ~21:00 → 5-18 ~02:00 期间 agent_loop_10 + reviewer_loop_11 反复 ESCALATED_TO_HUMAN 共 8 次，没有任何决策推进
- **跨 session 信息流失**：每次 RESET 后 handoff 写入 task_context/*.md（限 150 行），上下文压缩损耗。M009 的"未核实 registry"可能与此相关

## 5. 关键发现

按严重程度排序。

### F1. [HARNESS, 严重] Director 高频被动触发，关键决策缺失催生数十次 ESCALATED_TO_HUMAN

**证据**：
- `ralph_loop_timeline.jsonl` 中 40 个 ESCALATED_TO_HUMAN 事件，全部 `reason: director_no_response`
- Director 13 次 HARD_LIMIT_REACHED（全是 max_wall_time，意味着是因长时间运行而非 idle 触发），但 13 次比 Reviewer 的 71 次少得多——**问题不是 Director 自己卡，而是 Director 没接收/没处理消息**
- 5-17 21:00 → 5-18 02:00 期间，agent_loop_10 连续 8 次 ESCALATED_TO_HUMAN，跨度 5 小时无任何 Director decision

**根因分析**：Director session 在 feishu 群中收到大量交错消息（Agent 回复、Reviewer 回复、用户消息、CRON 通知、Manager 通知、RESET_REQUEST），队列处理优先级机制不明，关键 RESET_REQUEST 容易被淹没。

**影响**：保守估计累计浪费 20+ 小时（Agent/Reviewer 卡在等待 director_decision 的状态）。

**改进建议**：
- 引入 RESET_REQUEST 的快速决策路径（默认 60 分钟自动 RESET_AGENT，避免无限等待）
- Director session 加 priority queue，将 RESET_REQUEST 提到 user message 之上
- 或者：消除 Director 这一层——RESET 决策完全自动化，Director 不需要批准

### F2. [MODEL+HARNESS, 严重] 同一数据错误穿透多轮审稿与多个文档（M011）

**证据**：M011（mistakes.yaml L150-164）—— `pearson_bcs_acc=-0.2206` 被作为 R²=0.218 同时写入 Abstract、results.tex、Appendix N Monte Carlo、author response template。错误从 D033 (5-16) 进入，到 5-22 才被 Reviewer 独立审查 C3 时溯源到原始 JSON 修正。**经过 ≈10 轮内部审稿、4 轮 fresh review、Paper Agent 多次 self-consistency check 均未发现**。

**根因分析**：
- 模型对 r vs R² 的字段名混淆（fields are next to each other in JSON, easy to grab wrong one）
- 错误一旦写入 paper，后续轮次都基于现有数字而非原始数据"verify"
- `check_paper_consistency` 工具检查文档内一致性，但没追溯到原始数据

**影响**：差点带着 2.4× 高估的 effect size 提交 ARR。Fix 之后头条数字从 R²=0.218 改为 pooled semipartial R²=0.273，叙事结构需重排。

**改进建议**：
- 论文数字写入时必须强制 trace-to-source（registry 中每个数字关联 raw data path + field name）
- Paper Agent 每轮 audit 时 sample 5-10 个数字回原始 JSON 验证
- 当看到 R² 时立刻验算 r² 一致性（`abs(R² - r²) < 1e-3`）

### F3. [MODEL, 严重] LLM 大规模幻觉 BibTeX 作者名（M001/M002）

**证据**：43 条 BibTeX entries 中 3 条共编造 19 个作者名：rastogi-2020 (3 个: Sber/Guber/Nakhost)、oneke-2025 (14/17 个虚构)、volkanovska (2 个)。

**根因分析**：LLM 生成 bib 时对不熟悉的多作者论文倾向于编造 plausible 但虚构的中间作者。多作者论文 (>5 人) 尤为高发，因为 LLM 训练时只看到前几位作者名。

**影响**：投稿前最后一轮 audit 才捕捉到。若 reviewer 发现可能直接 desk-reject。

**改进建议**：
- 全自动化 reference validation：每个 bib entry WebSearch 验证作者名+标题+年份+venue
- LLM 写 bib 时不能从 memory 生成完整 entry，必须从已验证 source 复制
- 多作者论文（>5 人）触发额外验证

### F4. [HARNESS+MODEL, 严重] 跨 session/role 的状态同步缺陷（M009）

**证据**：M009 ——Reviewer 声称 "8B FewRel RE Dim2 未测试"，Director 直接采纳，Agent 修改 4 个 .tex 文件收窄 claim。实际 registry 里 exp012_llama_fewrel_ch2 (LLaMA-8B, FewRel RE Dim2, Δ=-27.1pp, success) 早在 05-15 完成。v13 之后全部回滚。

**根因分析**：
- Reviewer 在某个 session 没有 registry 的最新状态（可能因 handoff 压缩导致信息损失）
- Director 默认信任 Reviewer 的 claim，没有"先 read_registry 验证"的硬要求
- 三个角色对实验状态的 "共享内存" 实际是 task_context/*.md (150 行限制) + 偶尔的 registry 查询，不是单一真相源

**影响**：v13 的全部 claim 收窄修改被回滚，浪费一轮审稿周期的工作量。

**改进建议**：
- Reviewer 对实验覆盖范围的任何 claim 必须 cite registry/provenance 中的具体 exp_id
- Director 接收涉及实验覆盖范围的 Reviewer 建议时，强制先 `read_registry` 或 `read_provenance`
- 角色之间共享真相源应该是 registry.yaml，task_context 只放策略而非事实

### F5. [HARNESS, 中-严重] 跨服务器实验部署的脆弱性（M003/M004）

**证据**：M003 ——70B 实验 batch_config_exp2.json 未同步到 westd，导致 Exp 2/3 中断、GPU 空闲。`run_llama70b_cross_model.sh` 用 `set -e`，单文件缺失级联跳过两个实验。M004 ——westd 缺 datasets 模块，部署时只验证 vLLM 环境。

**根因分析**：
- Worker 把 "环境就绪" 验证简化为 "vLLM 能跑"，但不同实验有不同 import 依赖
- Shell 脚本 `set -e` 是默认做法，但对多实验序列产生级联失败
- 跨服务器同步是手动 `rsync` / `scp`，没有 dependency manifest

**影响**：exp012 70B 系列 6 次 attempt 失败，累计浪费 ~5 GPU-hour（虽然单次 fail 很快，但相当于一整天没产出有效数据）。

**改进建议**：
- 跨服务器部署前生成 dependency manifest（代码 + 模型 + 数据 + 配置），逐一确认目标存在
- 多实验 shell 脚本对每个实验独立 try-catch，不要 `set -e`
- 每个实验脚本启动前做 dry-run（`python -c "import ..."` 验证所有 import）

### F6. [HARNESS, 中] PaperBanana / 图表生成工具迭代效率低

**证据**：5-24 → 5-25 用户对 Figure 4 SDGD pipeline 图反复否定：
- 曹晓玉："Figure 4 这个图感觉很适合用 PaperBanana"（v0）
- 曹晓玉："低级"（v1-3）；"用 PaperBanana 去做一个精美的"（v4）
- 周俊伟："感觉太素，廉价"（v4）；"绝对禁止用手工设计，迭代不出来不许停"（v5）
- 周俊伟：v5 接受"风格可以，要增大信息量"
- 曹晓玉：v6 接受"放到论文编译我看看"

**根因分析**：
- Gemini Imagen 生成的图本质是 flat/clipart 风格，质感有天花板
- Agent 不能用手工设计工具（Figma/Illustrator）—— 用户硬要求 PaperBanana
- PaperBanana critic 有已知 bug（Gemini 返回 None → json.loads(None) crash）

**影响**：5 天迭代周期，5 个版本，最终 v6 被接受但流程消耗了大量用户耐心。

**改进建议**：
- 图表生成 skill 加入 "user preference" 标定阶段（先看 1-2 个参考样本再生成）
- PaperBanana critic bug 修复
- 接受用户允许时切换到手工 SVG/matplotlib 流程

### F7. [HARNESS, 中] 32 轮审稿是过度迭代，边际收益负

**证据**：
- Round 12-22 连续 11 轮 stuck at 3.0 Findings
- D061 (5-19) 已经写明 "writing 层面提分空间归零"
- 实际从 v9 (5-19) 到 v35 (5-22) 多轮修改仅把分数从 3.0 推到 3.5，但每轮都引入新风险（如 v13 错误收窄触发 M009 回滚）

**根因分析**：
- 没有"足够好就停"的停止条件——审稿循环默认 inf 迭代直到 DDL
- 每轮 fresh review 给的分数稳定在 3.0-3.5 区间，但每轮 Action Matrix 都列出 5-15 个 fix，看起来仍有空间
- Reviewer 不区分 "fix 让论文 substantially better" vs "fix 让论文不那么 obviously bad"

**影响**：审稿循环本身消耗了 290+ Reviewer 小时 + 220+ Paper Agent 小时（合计 ≈22 天 wall-time），其中相当部分是 marginal improvement。

**改进建议**：
- 连续 3 轮 score 不变即强制冻结写作（D062 已对单次实验做了类似判断，应该制度化）
- 区分 "substantive fix" vs "polish"，后者降级到 batched diff
- Reviewer 给 3.0 Findings 时应直接 freeze 而不是继续 nitpick

### F8. [HARNESS, 中] 11 个 PREPARING never-run 实验暴露任务管理缺陷

**证据**：registry 中 12 个状态为 PREPARING：bcs_max_to_mean_fix, exp_fewrel_v2_n25, exp_cross_embedding_sensitivity, exp017_gpt4o_mini_fewrel, exp_fewrel_contamination_check, exp_scs_name_def_ablation, exp_aggregation_monte_carlo, prompt_sensitivity_dry × 5。其中部分（如 prompt_sensitivity_dry 系列）conclusion 是 "none" 但 status 不更新到 abandoned。

**根因分析**：
- 实验注册和 schedule 是耦合的——注册后必须 schedule，否则一直停留在 PREPARING
- 没有 "deprioritized" 或 "abandoned" 终态
- 多次出现 "PREPARING but conclusion: success" 的矛盾状态（应当是实验完成但状态机没更新）

**改进建议**：
- registry 加 ABANDONED / DEFERRED 状态
- 状态机自动 GC：超过 24h 在 PREPARING 状态的实验自动询问 director

### F9. [MODEL, 中] 多阶段实验间的数据流断裂（M007）

**证据**：schema intervention 实验 Phase 1 (SCS verification) 用一组 rename，Phase 2/3 实际实验脚本硬编码另一组更自然的 rename（"nationality" 等）。两阶段间没有共享配置文件。最终 `rename_count` 与 delta 的 Pearson r=-0.625，表明效应完全来自 renaming 本身而非 BCS 变化。

**根因分析**：
- Agent 在编写多阶段脚本时倾向于 inline 配置（每个脚本独立硬编码）
- 没有 "phase output → next phase input" 的契约

**影响**：整个 schema intervention 实验 inconclusive。Greedy Auto-Renaming（D059）基于同样逻辑被砍。Main track 冲击失败。

**改进建议**：
- 多阶段实验必须由 Phase N 的 output 文件驱动 Phase N+1（rename map JSON），不能硬编码
- 实验审批 checklist 加一条：phase 间数据流是否有断裂？

### F10. [MODEL, 中] 统计概念混淆——基础但致命

**证据**：
- M010 ——semipartial R² 用 `r_partial²` 替代 `ΔR² = R²_full - R²_reduced`；DocRED VIF=50.9 下高估 2.17×
- M011 —— |r|=0.22 当 R²=0.22；p=0.027 当 p<0.001
- D025 —— Table 3 NER Missed 12/14/16% 是从 RE 数据外推编造

**根因分析**：LLM 对统计学的形式化推导能力薄弱，特别是：
- r² vs R² vs partial r² vs semipartial R² 的区分
- p-value 在不同 N、不同 effect size 下的合理范围

**影响**：所有错误都已修复，但若不被 Reviewer 抓到将直接出现在投稿版本。

**改进建议**：
- 论文中所有统计量必须显示完整公式 + 计算路径
- Reviewer 审稿时强制 "any R² that exactly equals r² is suspicious — verify"
- 引入外部统计 lint 工具（如 statcheck）

### F11. [HARNESS, 轻-中] 触发 CRON 人工判断的频率较高

**证据**：在 human_msgs 提取中至少有 5+ 条来自 `[CRON 需要判断]`，例如 5-15 07:12 "实验 exp004_maven_bcs 的进程已退出但无 W&B 数据，日志内容模糊，无法自动判断成功/失败"。Director 必须 SSH 检查日志后才能 update_registry。

**根因分析**：本项目大部分实验不用 W&B（aml-train 镜像）—— CRON 默认依赖 W&B 数据判断成功/失败，没有 W&B 时直接 escalate to human。

**改进建议**：
- CRON 加 fallback：如果没有 W&B，扫描 log file 中的 `success_marker` / `error_pattern`
- 项目级配置 success/failure detection rules（e.g., "exit code 0 + JSON output file exists" 即 success）

### F12. [MODEL, 轻] Agent 在多源数据查找时默认远程优先（M008）

**证据**：Agent 收到 "确认 Gemini Flash 状态" 任务，仅 SSH 到 cqa1 检查，发现只有一个 failed dry run log，遂判定 registry 中的 metrics 为 phantom data。实际数据完好存储在本地 `artifacts/exp_gemini_flash/part1/`，与 registry 完全匹配。

**根因分析**：API 类实验（Gemini/GPT 等）的数据通常在本地而非远程，但 Agent 默认远程 SSH。

**改进建议**：
- "查找实验数据" 这个任务必须同时检查：(1) 远程服务器、(2) 本地 artifacts/、(3) registry 中记录的数据路径
- API 类实验在 registry 中标记 `data_location: local`，Agent 据此优先本地

### F13. [PROCESS, 轻] 论文 title 最终与证据范围不匹配（R32-C1 仍 open）

**证据**：最终 title "How Does Schema Complexity Predict Performance in Training-Free LLM Information Extraction?" 声称 IE 范围，但 BCS 独立效应在 4 个数据集中只有 FewRel RE 干净成立。R32-C1 标记为 critical/open，未在 ARR 提交前解决。

**根因分析**：D054 (5-17) 明确选择"保持 IE title（Dim1 是 cross-task）但 abstract/discussion 显式限定 Dim2=RE-specific"。这是一个 strategic 决策——Title 范围广有助于 reviewer match，但留下了证据-标题不匹配的攻击面。

**影响**：R32-C1 是 Reviewer 在最后一轮（5-25）仍标记的 critical issue。Rebuttal 阶段需要正面回应。

**改进建议**：
- Title 应反映"最强证据"而非"研究范围"——本项目本应 "How Does Schema Confusability Predict Performance in Relation Extraction" 然后 Abstract/Intro 论证 NER/ED 的 boundary
- 提交前过 "Title vs Strongest Claim" sanity check
