## Core Problem

Execution traces provide rich runtime diagnostic information, yet 'Do Code Semantics Help?' (EMNLP 2025 Findings) found that naively integrating trace information has limited benefit — traces boost Code LLM prediction confidence without improving correctness. At inference time, only the Concise format consistently avoided degradation (11/14 cases), while richer formats like SemCoder achieved the best repair performance during fine-tuning but at the cost of unreliability across configurations. This suggests that reliability through noise reduction matters more than peak performance through richer semantics — exactly what learned, structure-aware filtering should provide. We hypothesize that the issue is not trace utility but trace noise: fixed-format trace representations include irrelevant execution state that pollutes the context window. Can a lightweight learned filter that exploits execution trace structure identify diagnostically-relevant trace segments, transforming traces from a noisy signal into a reliable repair advantage?

## Opportunity / Why Now

'Do Code Semantics Help?' (EMNLP 2025 Findings) tested five trace formats (NExT, SemCoder, CodeExecutor, Concise, Scratchpad) and found that only SemCoder contributed to repair during fine-tuning — but with limited improvements (0.3-1.4 points). At inference time, Concise was the only format that consistently avoided degradation (11/14 cases), while richer formats sometimes hurt. This reveals that noise reduction reliability is the key bottleneck, not richer semantics. TraceCoder (ICSE 2026) showed traces improve Pass@1 by 34.43% on moderate-complexity programs but degrade on complex ones. 'Debugging Code World Models' (arXiv 2602.07672) identified token-budget exhaustion from long traces as the dominant failure mode. The context compression study (arXiv 2604.13725) demonstrated that learned compression can beat full context by 28.3% on code tasks. Meanwhile, a family of learned context pruners has emerged for static code and tool outputs: SWEzze (arXiv 2603.28119) trains a 0.6B model for static code context compression via Oracle-guided Code Distillation; SWE-Pruner (arXiv 2601.16746) trains a 0.6B CRF-based skimmer for task-aware static code pruning (23-38% token reduction on SWE-bench, 29-54% on SWE-QA); Squeez (arXiv 2604.04979) trains Qwen 3.5 2B for line-level pruning of heterogeneous tool outputs (92% token removal, 0.86 recall across 27 tool families); and TACO (arXiv 2604.19572) learns compression rules for terminal agent observations. However, none of these methods exploit the inherent structure of execution traces — function-level call hierarchies, loop iteration semantics, exception propagation chains, and variable state evolution. They operate on static code (SWEzze, SWE-Pruner), flat text tool outputs (Squeez), or terminal observations (TACO) using line-level or span-level granularity without trace-specific structural awareness. This structural gap is especially significant because the 'Do Code Semantics Help?' finding — that noise reduction enables reliable trace utility — directly implies that structure-aware filtering should outperform structure-agnostic pruning on execution traces. The principle that structure-aware compression outperforms structure-agnostic approaches is further validated by CodeComp (arXiv 2604.10235), which uses Code Property Graph priors to guide KV cache compression for agentic coding, consistently outperforming attention-only baselines under equal memory budgets — demonstrating at the inference level what DTD targets at the input level. A concrete illustration: when a ValueError propagates through three function calls before triggering a test failure, a line-level pruner may retain the final exception line but drop the intermediate call frames that reveal the root cause — fragmenting the exception propagation chain into diagnostically useless snippets. Structure-aware segmentation preserves the complete chain as an atomic unit. Beyond repair, this structural filtering should preserve not just fix-relevant signals but explanatory signals — the causal chains that enable LLMs to generate accurate root cause explanations, broadening DTD's utility to code understanding tasks.

## Landscape (SOTA & Limitations)

TraceFixer (Bouzenia et al., arXiv 2304.12743, 2023) trains a CodeT5-based model on (partial trace excerpt, correct state) pairs for single-line Python repair, achieving 13-20% improvement — but requires user-specified correct program states and uses fixed trace excerpts. TraceCoder (ICSE 2026) adds fine-grained runtime tracing with a multi-agent framework, achieving 34.43% Pass@1 improvement but suffering substantial token consumption scaling on complex programs. TraceRepair (arXiv 2604.02647, Apr 2026) uses heuristic variable snapshot capture with multi-agent debate, fixing 392 Defects4J bugs but relying on hand-designed extraction rules. 'Towards Effectively Leveraging Execution Traces for Program Repair' (arXiv 2505.04441, May 2025) found that LLM-optimized trace formats outperform raw traces but all tested formats are hand-designed. 'Do Code Semantics Help?' (EMNLP Findings 2025) tested five trace representations — finding that SemCoder is the best choice for repair during fine-tuning (limited 0.3-1.4 point gains), while at inference Concise was the only format avoiding consistent degradation (11/14 cases). The key insight: richer formats can achieve peak performance but are unreliable; only aggressive noise reduction yields consistency. In the learned context compression space: SWEzze (arXiv 2603.28119, Mar 2026) trains Qwen3-Reranker-0.6B via Oracle-guided Code Distillation for static code context compression (6x compression, 5-9% resolution improvement). SWE-Pruner (arXiv 2601.16746, Jan 2026) trains a 0.6B CRF-based model on 61K synthetic data for task-aware code context pruning (23-38% token reduction on SWE-bench while maintaining success rates, 29-54% on SWE-QA; uses natural language goal hints to adapt pruning to the agent's current task). Squeez (arXiv 2604.04979, Apr 2026) trains Qwen 3.5 2B with LoRA for task-conditioned line-level pruning of heterogeneous tool outputs (including stack traces and build logs), achieving 92% token removal with 0.86 recall across 27 tool families — the closest methodological analog, but operates at line-level granularity over heterogeneous text without exploiting trace-specific structure (call hierarchies, loop semantics, exception chains). TACO (arXiv 2604.19572, Apr 2026) learns self-evolving compression rules for terminal agent observations in a training-free paradigm. CodeComp (arXiv 2604.10235, Apr 2026) uses Code Property Graph priors (extracted via Joern) for structural KV cache compression in agentic coding, preserving structurally critical tokens (call sites, branch conditions, assignments) and consistently outperforming attention-only baselines under equal memory budgets — validating the principle that structure-aware compression outperforms structure-agnostic approaches for code, though operating at the KV cache level rather than input text filtering. In the adjacent domain of agent trace analysis, CodeTracer (arXiv 2604.11641, Apr 2026) reconstructs code agent execution as hierarchical trace trees with failure onset localization, demonstrating the value of hierarchical structure for trace diagnosis — though applied to agent trajectories rather than program execution traces. TraceSIR (arXiv 2603.00623, Feb 2026) introduces TraceFormat, a structured abstraction for compressing agent execution traces via a multi-agent framework, showing that structure-preserving compression aids root cause analysis in agentic systems. Both CodeTracer and TraceSIR validate the principle that structural trace analysis outperforms flat-text analysis, but neither applies learned filtering to program execution traces for repair. The April 2026 context compression study (arXiv 2604.13725) shows learned compression can surpass full context by 28.3% on repository-level code tasks. LDB (ACL 2024) segments programs into basic blocks at fixed granularity — providing a validated intermediate granularity between function-level structural segments and individual lines. Execution Tuning (arXiv 2503.05703, Feb 2025) trains models on traces for understanding, not compression. 'Less is More' (AAAI 2025) compresses loop traces via ellipsis patterns — a useful heuristic but not learned. The Precise Debugging Benchmark (arXiv 2604.17338, Apr 2026) evaluates whether models genuinely debug or simply regenerate. On the evaluation front, SWE-bench Verified (500 Python tasks) has been the standard repair benchmark, but OpenAI's Feb 2026 audit found 59% of audited tasks had flawed tests and confirmed training data contamination across all frontier models (GPT-5.2, Claude Opus 4.5, Gemini 3 Flash), prompting OpenAI to recommend SWE-bench Pro (arXiv 2509.16941) — a 1,865-task multi-language benchmark using GPL-licensed and proprietary repositories for contamination resistance, where top models scoring 80%+ on Verified drop to ~46-59% on Pro's public set.

## Proposed Approach

We propose Diagnostic Trace Distillation (DTD), which trains a lightweight model to perform structure-aware filtering of execution traces for LLM-based program repair and code understanding. DTD's key differentiator from existing learned pruners (SWEzze, SWE-Pruner, Squeez) is that it segments traces into semantically meaningful structural units — function-level call subtrees, loop iteration groups, and exception propagation chains — rather than operating at line or span level over flat text. This structural segmentation exploits the inherent hierarchy of execution traces, enabling filtering decisions that respect diagnostic boundaries (e.g., keeping an entire exception chain rather than individual lines that lose context in isolation). The principle that structure-aware compression outperforms structure-agnostic approaches is independently validated by CodeComp (arXiv 2604.10235), which shows structural Code Property Graph priors outperform attention-only baselines for KV cache compression in agentic coding — DTD applies the analogous insight at the input filtering level for execution traces. Concretely, consider a bug where a malformed input triggers a TypeError in a helper function, which propagates through two wrapper functions before causing a test assertion failure: a line-level pruner scoring each line independently may retain the final AssertionError but drop the intermediate frames showing where the type mismatch originated, while DTD's structural segmentation treats the entire exception propagation chain as an atomic scoring unit, preserving the causal path from root cause to observable failure. Phase 1 (Oracle Trace Filtering — data construction): For buggy Python programs from SWE-bench Verified (500 instances) and BugsInPy (493 bugs), we collect execution traces using VizTracer (leveraging Python's sys.monitoring on 3.12+). We parse traces into structural segments (function-level call subtrees, loop iteration groups, and exception propagation chains). A teacher model (DeepSeek-V4-Flash, $0.14/M input tokens) performs pointwise relevance scoring: given (issue description, buggy code, trace segment), it outputs a binary keep/drop label indicating whether the segment contains repair-relevant diagnostic information. We validate teacher quality on a 200-instance subset using DeepSeek-V4-Pro. This direct-scoring approach avoids the expensive iterative delta-debugging used in SWEzze's OCD, cutting API costs to ~$150-300. Phase 2 (Student Distillation): We QLoRA-fine-tune Qwen3-Reranker-0.6B (same architecture as SWEzze and SWE-Pruner's student, LoRA rank=16, alpha=32) on the teacher-labeled (trace-segment, buggy-code, issue) -> keep/drop dataset. The student is a pointwise classifier scoring each trace segment for diagnostic relevance. At inference, segments scoring below a learned threshold are dropped. We target compression ratios comparable to SWEzze (6x on static code) and Squeez (~12x on tool outputs), with the actual ratio on execution traces to be empirically validated through a 50-instance pilot before full-scale experiments. The 0.6B model runs in <1s per program on a single GPU. Pilot contingency: if the 50-instance pilot reveals that function-level structural segments are too coarse (compression <3x) or too large for the 0.6B model to score accurately (<65% agreement with teacher), we fall back to sub-function basic-block-level segmentation as in LDB (ACL 2024), which provides a validated intermediate granularity between function-level and line-level; if segments are too fine-grained (yielding >15x compression with low recall), we merge adjacent same-function segments into larger units. Phase 3 (Evaluation): We evaluate on two axes: program repair and diagnostic explanation quality. For repair, we use three repair LLMs (DeepSeek-V4-Pro, Claude Sonnet 4.6, Qwen3-Coder-Next via API) across seven conditions: (a) no trace, (b) full trace, (c) DTD-filtered trace (structural segments), (d) DTD-line-level ablation (same 0.6B student trained on same trace data but with line-level instead of structural-segment granularity — the critical experiment isolating structure-aware segmentation's contribution), (e) Concise format (from 'Do Code Semantics Help?'), (f) Squeez applied to raw traces (off-the-shelf line-level pruner baseline — testing domain transfer of a pruner not trained on execution traces), (g) random trace sampling at matched compression ratio. The DTD-line-level ablation (condition d) is the key controlled comparison: it shares training data, model architecture, and optimization with DTD but uses line-level granularity, directly isolating whether structural segmentation itself (not just trace-domain training data) drives performance gains. Squeez (condition f) serves as a complementary baseline testing whether a strong generic pruner transfers to the trace domain. For diagnostic explanation, we add a code understanding evaluation: for 100 SWE-bench instances, each repair LLM generates both a natural-language root cause explanation and a repair under three conditions (DTD-filtered trace, full trace, no trace). Explanation quality is evaluated via LLM-as-judge (DeepSeek-V4-Pro) on three criteria: (1) causal accuracy — does the explanation correctly identify the root cause? (2) conciseness — is the explanation free of irrelevant trace artifacts? (3) completeness — does it capture the full causal chain from root cause to observable failure? We validate the LLM-as-judge reliability on a 30-instance subset with manual human annotation (expected inter-annotator agreement: Cohen's kappa >0.7). This evaluation demonstrates that DTD's structural filtering preserves not just repair signals but explanatory signals — a stronger, more general claim about trace utility for code understanding. Benchmark and contamination strategy: We use five benchmarks spanning contaminated and uncontaminated evaluation. SWE-bench Verified (500, real-world Python) serves as a widely-reported reference point, but we explicitly acknowledge the OpenAI Feb 2026 audit finding 59% flawed tests and training data contamination across all frontier models. Crucially, DTD's experimental design measures relative improvement (DTD-filtered vs. full trace vs. no trace vs. baselines) within the same benchmark, so contamination inflates absolute repair rates equally across all conditions without affecting the DTD-vs-baseline delta — the quantity we actually claim improves. Nevertheless, to provide contamination-resistant validation, we designate BugsInPy (493, real-world Python) and DebugBench Python subset (1,414 instances covering 4 major bug categories and 18 minor types across 3 difficulty levels) as primary uncontaminated benchmarks. We additionally include a 50-instance spot-check on SWE-bench Pro's public set (Python tasks only, drawn from the 731-instance public partition; arXiv 2509.16941), which uses GPL-licensed repositories as a contamination-resistant alternative where top models scoring 80%+ on Verified drop to ~46-59% on Pro. This spot-check validates that DTD's relative improvement holds on contamination-resistant tasks without requiring full-scale multi-language evaluation. Finally, HumanEval/MBPP with bug injection (~500) enables direct comparison with 'Do Code Semantics Help?' setup. We stratify repair results by trace complexity: short (<2K tokens), medium (2-8K), long (>8K). The key falsifiable hypothesis is that DTD-filtered traces with structural segmentation outperform both the DTD-line-level ablation and fixed formats in the >8K regime where raw traces fail.

   11 个条件按研究问题组织为递进式证据链：trace 是否有用 → 噪声消减是否有效 → 学习型过滤是否优于启发式 → 结构粒度是否优于行级 → 优势来自边界还是粒度 → 过滤是否优于抽象 → 距完美过滤多远。建议在论文中用 Figure 1 / Table 1 可视化此 hierarchy。

9. **[Experimental Design] — 增加统计检验方案** — [Technical Soundness]
   原始 proposal 完全缺失统计检验。修改后加入 paired bootstrap test (n=1000) for primary comparisons, sign test for cross-benchmark consistency, 并将 complexity-strata 和 bug-type 分层标记为 exploratory（避免多重比较负担）。

10. **[Experimental Design] — 修正 Contamination 论证逻辑** — [Technical Soundness]
    原始 proposal 声称 "contamination inflates absolute rates equally without affecting delta"——逻辑错误。修改为：contamination 使 memorized instances 在所有 trace 条件下趋同，压缩而非保持 delta，因此 SWE-bench Verified 上的 DTD 效果是保守下界。修正后的论述反而更有力地论证了 BugsInPy 和 DebugBench 作为 primary benchmarks 的必要性。

11. **[Experimental Design] — SWE-bench Pro 50 实例重新定位为 qualitative sanity check** — [Technical Soundness]
    原始 proposal 将其作为正式 benchmark 呈现（"validating that DTD's relative improvement holds"）。50 实例分层后统计功效几乎为零。修改后明确定位为定性 case study，不做分层、不报 p 值，诚实说明 50-instance limitation。

12. **[Experimental Design] — 修改 Key Falsifiable Hypothesis 纳入 fixed-window 对比** — [Technical Soundness + Novelty]
    原始假设仅涉及 structural vs. line-level 和 fixed formats。修改为："DTD-structural outperforms both DTD-line-level and DTD-fixed-window, with the structural advantage concentrated in traces with deep call stacks or multi-frame exception propagation, specifically in the >8K token regime." 更严格、更可证伪。

13. **[Analysis Depth 新增] — 增加 Compression-quality Pareto Frontier 分析** — [Analysis Depth + Novelty]
    原始 proposal 仅报告单点 compression ratio。修改后扫描 teacher scoring threshold，绘制 structural / line-level / fixed-window 三条 Pareto 曲线。预期在低压缩率(<3x)三曲线重合、高压缩率(>6x)结构化严格优于——graphically 证明结构边界的价值在压缩越激进时越大。这是论文潜在的 signature figure。

14. **[Analysis Depth 新增] — 增加 Bug-type 和 Segment-type 分层分析** — [Analysis Depth + Significance]
    原始 proposal 仅按 trace complexity 分层。修改后增加：(a) exception-driven vs. logic-error bugs 分层（利用 DebugBench 现有分类）；(b) call stack depth 分层；(c) segment-type contribution analysis（哪类结构单元贡献最大）。将论文贡献从 "DTD works" 升格为 "we understand when and why structural trace filtering helps"。

15. **[Code Understanding Evaluation] — 定位下调 + 增加 Grounded Evaluation Protocol** — [Technical Soundness + Methodology]

19. **[整体结构] — 从单段落重写为清晰的 section 结构** — [Clarity]
    原始 proposal 是一个约 600 词的巨型段落。重写为 Motivation → Key Insight → Method → Experimental Design → Related Work → Contributions → Broader Impact → Timeline 的分节结构。虽然 proposal 不等于论文，但清晰的组织有助于后续写作和审稿人快速抓住逻辑线。

【主要风险】:
1. **"Trivially true" 质疑**：即使通过 fixed-window baseline 控制了粒度混淆，"structure-aware > line-level for traces" 这一核心假设在直觉上仍可能被认为是 expected result 而非 surprising finding。论文的 novelty 最终成败取决于 Pareto frontier 和 bug-type 分层能否产出**非直觉的 nuanced findings**（如特定 bug 类型下结构化优势消失、或低压缩率下 line-level 反而更好）。如果所有结果一致指向"structural wins everywhere"，审稿人可能写 "I would have guessed this"。
2. **Teacher quality ceiling**：整个 pipeline 的上限由 DeepSeek-V4-Flash 的 trace segment 打分质量决定。如果 teacher 本身不擅长判断 trace segment 的修复相关性（这并非 LLM 的常规标注任务），student 学到的是噪声。Pilot 中的 teacher validation 是必要的前置检查——如果 precision@top-k < 0.7，需要启动 fallback（换 teacher 或改用 weak supervision），这会影响 timeline。

【实施评估】:
- **计算资源**: ~130 H100-hours（HIL 模式）或 ~210 H100-hours（全自动模式）。主要消耗：11 条件 × 5 benchmarks 的 repair evaluation（含 LLM 推理）、QLoRA 训练 0.6B student（约 4-8 H100-hours）、teacher scoring（DeepSeek-V4-Flash 推理）、Pareto frontier 多阈值扫描。需要至少 4×H100 节点或等效云实例。
- **数据需求**: BugsInPy (493 instances, 公开)、DebugBench Python subset (1,414 instances, 公开)、SWE-bench Verified (500, 公开)、SWE-bench Pro public (731, 公开取 50 subset)、HumanEval/MBPP (~500, 公开 + 需 bug injection 脚本)。所有数据集公开可得，无访问障碍。需自行收集各 benchmark 的 execution traces（通过 `sys.settrace` 或解析 pytest 输出）。
- **人工介入**: (1) Teacher quality validation: 30-50 trace segments 的 repair-relevance 标注，约 2 person-hours；(2) Oracle baseline: 50 instances 的 gold segment 标注，约 4 person-hours；(3) Code understanding human validation: 50 instances 的 explanation quality 评判，约 6 person-hours。总计约 12-15 person-hours，无需专家级标注者（CS 研究生即可），但建议至少 2 人独立标注以计算 inter-annotator agreement。
- **训练需求**: 需要训练一个 0.6B 模型（Qwen3-Reranker-0.6B via QLoRA）。训练规模小，估计 4-8 H100-hours（含 structural 和 line-level 两个版本 + fixed-window 版本，共 3 个 student model）。不需要预训练，只需 QLoRA 微调。
- **新 Benchmark**: 不需要构建新 benchmark。使用现有公开 benchmark。但需要构建 trace 收集 infrastructure（`sys.settrace` 包装器 + format normalization 层）和 structural segmentation 工具，这属于工程实现而非 benchmark 构建。
- **预估周期**: HIL 模式 13-15 天，全自动模式 11-14 天（从 pilot 启动到论文可投稿）。关键路径：pilot study (3 天, 含 teacher validation) → 全量训练 + evaluation (5-7 天) → 分析 + 写作 (3-5 天)。ARR May cycle deadline 可达。
