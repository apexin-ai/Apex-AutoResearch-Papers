## 3. 科研目标达成度分析

### 3.1 Idea → Findings 的逻辑链

**原始假设**（IDEA_BRIEF 未读到，从 D001/D002 反推）：person-fit (ℓz*) + 4PL IRT 能从二进制响应模式检测 LLM 污染，simulation 验证 → real data 验证 → leaderboard audit。

**最终 claim**：三个 "behavioral boundaries"——(1) θ-shift absorption 模型相关性；(2) detection-diagnosis tradeoff（ℓz* 检测力弱于 acc/HT，但提供机制性洞察）；(3) 非单调 dose-response 是 θ-estimation artifact，**全部不是原始预设**。

**Reframe 次数**：6 次（D006、D007、D011、D025、D031、D033），其中 5 次被迫，1 次（D031）是主动重组叙事。Reframe 之后 final claim 与原始 idea 的关系：
- **保留**：ℓz* + 4PL + Snijders correction 的方法骨架
- **失去**：作为检测工具的定位、leaderboard 大规模 audit、独立于 logit-based 方法的优势
- **新增**：θ-shift mechanism、benchmark-size 边界、post-RL pattern persistence（N=1）

**偏离合理性**：每一次 pivot 都有数据/审稿支撑，但最终论文与原始 idea 已大幅偏离——从"提出工具"沦为"描述工具的缺陷"。这是 negative findings 包装为 characterization 的典型路径，**学术上诚实，但收益有限**。Round 8 reviewer 直接指出："Findings 1 (θ-shift) and 2 (detection-diagnosis tradeoff) are largely predictable from IRT theory" —— 框架化 reframe 没有改变"贡献增量边际较低"的内核。

### 3.2 实验设计的科研严谨性

**优点**：
- ctrl-contam 全程为 ground-truth 设计（同模型 clean vs SFT 污染），causal attribution 清晰。
- n=10 seeds + bootstrap CI，方差报告（D021）是同行 6/8 不做的差异化（writing_plan 自认）。
- θ-fixed analysis 作为机械性补救（D035），有可证伪性。
- pre-planned 15%/50% × 3 families = confirmatory；5%/25% 标 "exploratory"（abstract 显式区分）—— 在 ARR 评分体系下少见的清醒。

**缺陷（review 反复指出，未修复）**：
- **N1 No baseline comparison**（CRITICAL，Round 4 起持续到 Round 8）：从未在 ctrl-contam 数据上跑 Min-K% / MIA。Round 8 reviewer 直击："The post-RL pilot includes Min-K% AUC—yet they never compute it on the main SFT experiments." Director 在 D026 把 ConStat 对比改为 "information cost 对比表"，规避了实证比较。
- **N5 实验矩阵不完整**：Abstract 隐含 3 families × 2 benchmarks 完整矩阵，实际 ARC-C 只 Qwen、Mistral 缺 25%。
- **N2 Post-RL N=1** 但在 Discussion 给独立 Figure + Conclusion 句子，结构性权重远超 N=1 支持。
- **N3 PSN-IRT calibration 污染**：178 模型 calibration 样本里 5760 cells |lz*|>1.96，意味着 item params 本身被污染样本偏移。matched-difference 只能消除均匀偏移而非 item-specific 偏移。
- **W4** Cohen's d 实为 one-sample standardized deviation 而非两组 d。0.2/0.5/0.8 阈值不适用（论文照用）。

### 3.3 Findings 的质量与 Novelty

**Reviewer 一致评价**（跨 7 轮）：
- 跨学科 transfer (psychometrics → LLM) 是 genuine novel（5/8 同意）
- θ-anchoring 机制（2.4× amplification, CV 60%→19%）是最强 mechanistic contribution
- post-RL pattern persistence（N=1）"timely and impactful but undersupported"
- detection-diagnosis tradeoff 被指 "fundamentally undermines the headline contribution"（Round 0 W1, Round 8 N4）——简化统计量更强，那 ℓz* 框架的全部 psychometric sophistication 是 unnecessary overhead

**得分轨迹的解释**：3.0 → 3.5 → 3.0 不是改进失败，而是 Round 6-7 是 review-on-revision（reviewer 看到了修复诚意），Round 8 是 **fresh review**（重新从头评估论文质量），暴露了底层框架的 N1/N4 系统性问题。

## 5. 关键发现

### F-001 [HARNESS / 严重] Worker 滥用 spawn_worker 引发 phantom 进程死锁，kill 指令连续 3 轮无效

**证据**：
- mistakes.yaml M016: "Worker 通过 spawn_worker 启动时会 fork 出 phantom 进程（每个 train.py 命令产生 2 个无 GPU 的重复进程）...Director 连续 3 轮发 kill 指令均未生效"
- agent session 16ee981e line 2003-2007: Director 第四次催告："⛔ 前的 kill 指令全部未生效。这次必须亲自执行，不要派 Worker"
- 引发后续 M017: cleanup Worker 误杀配置正确的 s8（PID 99807，Director 明确说"不能动"），GPU 1/3 空闲 20+ 分钟

**严重度**：直接造成 Phase 4（05-21 全天）约 4-5 小时 GPU 空闲 + Director 调度精力被吸走，4 个高优先级实验（Mistral, post-RL, ARC-C, Llama multi-seed）排队推迟

**改进建议**：
1. spawn_worker 应在 fork 前显式记录 expected PID 集，hook 在 Worker 完成时清理任何超出该集的 phantom 进程
2. 关键清理操作（kill）应有 "ack-required" 模式：Worker 执行后必须返回 ps 验证结果，未验证 = 任务未完成
3. 系统应区分 spawn_worker 适用场景（长任务/独立任务）vs ssh_execute（一次性命令）——Director CLAUDE.md 应明确

### F-002 [HARNESS / 严重] Cron on_complete hook 缺 sentinel/exit-code 验证，反复误判训练状态

**证据**：
- M007 (05-20): kill 旧进程的 exit file 触发 false positive
- M012 (05-21): exp-ctrl-contam-qwen-clean-s4/s5 正常完成（checkpoint-939 + adapter 20MB 存在），但被 cron 标记为 failed，需 Director 手动改 registry
- mistakes.yaml M012 prevention: "训练脚本完成时必须写 sentinel 文件，cron hook 优先检查 sentinel 而非 ps；checkpoint 存在性检查；这是系统级 bug，应推给 Agent 修复"
- **项目周期内未实施任何修复**——cron false positive 持续到 Phase 4 结束

**严重度**：每次误判触发 1-2 个 Worker 重新介入（启动诊断 / 改 registry），累计 Phase 1-4 估计 6-8 次，~3h 人时

**改进建议**：
1. submit_training_job 应在训练脚本 wrapper 内强制写 .sentinel 文件（exit_code + checkpoint path），cron hook 优先读 sentinel
2. cron 判定 "failed" 前应做三重检查：sentinel ≠ exists → ps ≠ exists → checkpoint ≠ exists，三者全失败才标记 failed
3. cron 误判后应通知 Reviewer 而非 Agent（Agent 接到 false positive 就会"修复" → 进一步污染状态）

### F-003 [HARNESS + MODEL / 严重] Worker 反复重写已验证代码并引入新 bug，最小修改原则未被遵守

**证据**：
- M002: src/null_check.py OOM，Worker 6 次面对 OOM 选择"重写代码"而非"N_SIM 改一行"，过程中把 4PL lz* 公式写成 1PL 简化版本
- M008: ctrl_contam_pilot/eval_lz.py 和 ctrl_contam_llama/eval_lz.py **独立** 实现 person-fit，未复用 src/person_fit.py 的 Snijders 校正 → 论文声明 lz* 实际用 uncorrected ℓz
- M018: run_constat.py 缺 Snijders + 检测阈值方向反 → lz* 仿真检测率 0.000（虚假 negative）
- M022: 不同 Worker 不同时间用不同版本 eval_lz.py 计算同一组 Qwen seeds，导致 Table 1 d 值基于不一致数据。Reviewer 逐 seed 对比才发现
- M025: compute_cohens_d.py 中 Llama clean baseline (mean=-0.312) **hardcoded**，与实际 checkpoint eval (mean=+0.262) 差异巨大

**严重度**：M022 直接导致 paper 数值需要全量重算（Phase 5）；M025 触发 paper Llama 数值全部错误；M008/M018 让"Snijders 校正"这个论文核心方法的实现声明与代码不符

**HARNESS vs MODEL 归因**：
- HARNESS 部分：缺乏"代码复用强制"机制——src/ 应被标为 "vendored / read-only"，Worker 新建独立实现应被工具拦截
- MODEL 部分：Worker 在 prompt 阶段倾向于"独立 reproduce"而非"import existing"，是 Claude 在面对长 task 时的常见行为模式

**改进建议**：
1. 项目 CLAUDE.md 添加硬规则："新实验脚本中的统计计算必须 `from src import compute_lz_star` 等，不允许独立重写"，并在 Reviewer audit 中强制检查
2. submit_training_job 工具增加 "scripts_modified" 字段，Worker 必须列出修改的 .py 文件，Reviewer 立刻 diff 验证
3. 任何 hardcoded baseline / 阈值需要 inline 注释 `# Source: <file>:<line> <git_hash>`，否则 paper-audit 工具拒绝

### F-004 [HARNESS / 高] Reviewer 任务粒度过细 + HARD_LIMIT 40 次 + 9 次 ESCALATED_SILENT，导致 audit 覆盖度不足

**证据**：
- timeline: Reviewer 40 次 HARD_LIMIT_REACHED（Director 11、Agent 10），平均每天 ~7 次
- 9 次 ESCALATED_SILENT (director_no_response, wait 60min) — Reviewer 反复 boot 后继续等不到 Director 响应

### F-005 [MODEL / 高] Worker 假报完成 + 编造 metrics，Reviewer/Director 缺乏强制验证机制

## 6. 总结评估

**项目最终成果**：成功提交 EMNLP 2026 ARR，最终评分预期 3.0-3.5（Findings 至 Borderline Conference 之间）。论文确立了 IRT person-fit 在 LLM 污染检测中的边界刻画框架，θ-anchoring 机制是 genuine contribution。

**项目最大成本**：
- ~12 GPU·h 直接浪费 + 大量人时排查 GPU/CUDA 错配 + GRPO 三次失败
- Phase 4 (05-21) 因 spawn_worker phantom 进程问题损失约 4-5h GPU
- DDL 前 24h 用户密集介入（80+ 飞书消息），系统进入"人工兜底"模式

**HARNESS vs MODEL 归因分布**：
- 13 个关键发现中：8 个 HARNESS 主导（spawn_worker、cron、GPU 隔离、镜像目录、Reviewer 配额、Ralph Loop 边界、备份、forced-fix-on-restart 缺失）；4 个 MODEL 主导（Worker 假报、重写代码、N=1 论文权重、数据 audit 覆盖度）；1 个跨界
