## 2. 项目叙事重建

整个项目可拆成 5 个阶段，每个阶段都有一次叙事崩塌或方向切换。

### Phase 0 — MVP 启动 + 35% 翻车（5/14 02:05–17:00, ~15h）
原始假设：CKA-overlap-aware pruning（RASP）在 35% sparsity 下保留更多功能冗余，post-prune 应优于纯 importance baseline。
- D001 接受"35% MLP-only 剪枝"作为 MVP；
- 跑出两个剪枝模型**精确相同的 0.15%**（2/1319 GSM8K）→ Reviewer 怀疑实现 bug，Director 暂缓 SFT 转去审计代码（D003）；
- 根因找到（D004）：`min_keep_mlp=4` 允许早期层被剪到 14.3% capacity → 早期层全坍塌；
- 改 40% per-layer floor 重跑 v3，35% 仍然 Standard 0% / RASP 1%，无法挽救；
- **核心矛盾**：D005 决定降到 20-25% sparsity，原计划的"高 sparsity 极限测试"被搁置；
- 17:06 出现首个戏剧性 win：v4 在 20% 上 RASP 29% vs Standard 1%（p<0.0001），D006 宣布 Scenario B（"剪枝本身就保护了推理能力"）；这成为后面整整 24 小时的核心论据。

### Phase 1 — GRPO 7 连败 + 假阳性崩塌（5/14 17:00 – 5/15 22:00, ~30h）
GRPO 试图在 20% 上验证 recovery 优势：
- **v1**: max_completion=4096, ETA 270h → kill（D007）。
- **v2**: 1024 tokens, RASP 和 Standard 都 100% truncated，clipped_ratio=1.0, grad_norm=0（D009）。
- **v3-v4-v5-v6-v7**: 一路 OOM / 磁盘满 / 短 token 截断 / silent death，每次都是工程问题（D028, D030, D031, D032, M008 之前的伏笔）。
- **5/15 11:02 D025 — 假阳性彻底崩塌**：Reviewer 用统一 eval 脚本重新评估 Standard 20%，accuracy 是 **27-32%** 而非 1%。"RASP 29x advantage" 数据基础是 max_new_tokens=10 的截断 bug。D006/D014 上的 Scenario B 全部被宣判作废。
- **5/15 13:46 D029**：SFT 也站不住——Standard 64% > RASP 57%。CKA-aware pruning 在 SFT 层面也不优。
- **5/15 22:06 D043**：GRPO collapse timeline 完整：RASP(step 10) < Standard(step 60) < Unpruned(step 80)。新叙事备选："剪枝-训练性 tradeoff"。

到此刻，项目 36 小时连续两次核心假设被自己的数据推翻。但 Director 没有 pivot venue，没有重新审视 idea_brief，反而立刻进入下一个 narrative。

## 3. 科研目标达成度分析

### 3.1 Idea → Findings 的逻辑链
- **初始 idea**（mvp_v2 阶段）：CKA-overlap-aware composite scoring（RASP）在结构化剪枝中通过保留功能冗余，预期 → 提高 RLVR recovery 上限。
- **最终论文 claim**（abstract）：
  - C1 *Reward-accuracy decoupling*：20-25% sparsity 下 SFT ≈ GRPO（|Δ|≤1.14pp on GSM8K, ≤1.34pp 总体）；
  - C2 *Recovery capacity spectrum*：四个 criterion 在 GRPO 训练动态上差异巨大，但精度收敛；
  - C3 *SFT warmup is dominant*：SFT 贡献了 ~60pp accuracy，GRPO 贡献 ≤0.61pp；
- **关系**：原 idea 假设 "RASP 优于 importance baselines"，最终 paper 的 headline 是 "RASP α=2.0 优于 CKA-only **但** 与之统计不可区分 + GRPO 提供训练动态 diagnostic 但**不改变 accuracy**"。**这是同一个 idea brief 中"recovery"这个词的几乎反向解读**——原 idea 把 recovery = RLVR-driven accuracy gain；最终 paper 用 decoupling 证明 RLVR 不提供 gain。
- **reframe 次数**：依据 decisions.yaml 至少 **6 次主线 pivot**（D014→D025→D044→D053→D056→D070→D075→D097/D106）。前 4 次是被结果推翻被迫；后 2 次是数据交叉验证导致内部矛盾。

### 3.2 实验设计的科研严谨性
- **Falsifiable hypotheses**：D008 设过明确的 MVP 标准（ρ ≥ 0.4 / model-level p<0.05），D027 又设过 pivot 阈值（|GRPO_RASP - GRPO_Std| < 5pp）。但**当数据反对原假设时，项目反复**重定义判据**而非接受 falsification**。例如 D006 "29 vs 1, MVP PASS" → D025 撤回 → D044 reframe → D070 / D073 再翻 → D106 自己也站不住。
- **对照组质量**：v8 之前的 GRPO 配置**不一致**（D058，配置 confound 持续 3 天才被 Reviewer 发现）；reward_desert_patience 参数 CKA-only/Random=50 vs Standard/RASP=200（W-C3，被 Round 1 Reviewer 抓到，论文里仍承认）；max_completion_length 在主表用 1024 但 Random 用 512（Round 7 MF1 critical）。
- **统计方法**：
  - 错误 — M008 把 reward trajectory 的时间序列样本拿来做 bootstrap CI，违反 i.i.d.，5/6 pair "显著" 全废，写进 paper_framing.md 后被 Reviewer 抓回滚（D068）。
  - 错误 — D069 之后才意识到 7B CKA-only vs RASP 在 SFT accuracy 上 p=0.117 不显著，但项目早期一直当作 4-tier 排序的核心证据。
  - cherry-picking — M011 Agent 报 HumanEval interim 28-32%（局部峰），final 收敛到 20.12%，D072 已经用错误 interim 写过 narrative。
- **实验规模**：单架构（Qwen2.5 family，7B + 1.5B 同族）、单 RL algorithm（GRPO）、主要单一基准（GSM8K + 后期补 MATH-500/HumanEval/MBPP）、单 seed for RASP 全部 α 值 — **5 轮 Critical 仍未解决**。

### 3.3 Findings 的质量与 Novelty
- **核心发现质量**：
  - "Reward-accuracy decoupling at 20-25% sparsity" — 在限定 scope 下是 **genuinely surprising and useful** 的实证发现。两个 Reviewer 都标记 S2/S4 认可。
  - "Recovery capacity spectrum + recovery dynamics 三 regime" — descriptive 框架，受 RASP 自身 α=2.0 反例否定（C1 Round 9）。
  - "SFT dominates RLVR" — 实证清晰，但**直接挑战了 Self-Healing 2025 的主 claim**，需要更广验证（仅 Qwen2.5 family）。
- **Novelty**：Round 9 共识"controlled experiment design 哲学有方法学价值，但 RASP 方法贡献被自身消融否定"。论文最终从 "method paper" 退化为 "empirical study" — 但 Title 仍叫 "How Pruning Criteria Shape Post-RLVR Recovery"，已经做了诚实的去 method 化。
- **审稿评分反映**：9 轮全是 3.0，**核心 critical 5 轮未解决**。Round 9 评分理由直白："为什么不是 3.5+: 核心方法贡献 RASP 被自身消融否定——论文的方法新颖性基本为零"。

### 3.4 研究效率
462 个 registry 实验，对应**总 1617 小时 session** + 真实 GPU 大量消耗。**真正进论文的实验估计 ~30-40 个**：
- 4 method × {SFT, GRPO} × {GSM8K, MATH-500, HumanEval, MBPP} = 32 主表数据点（很多还有 fair v5 v2 v3 v4 多版本）；
- 1.5B 跨尺度 ×3 方法 ×SFT/GRPO = 6 个；
- CKA heatmap ×4 + gradient flow v3 + bootstrap CI；
- α dose-response 5 个点；
- ShortGPT baseline ×2；
- 多 seed ×6 个 fair seed runs；
- 其余 380+ 是诊断、重试、失败、cleanup、cron false positive 等。

**比例**：直接贡献论文的实验 < 10%，其余是工程开销 + 弯路。

弯路的产出（negative results）：
- ✅ RASP-RLVR ablation 提供了 informative negative（D050）；
- ✅ Unpruned baseline 论证 collapse 是结构化剪枝特有的；
- ✅ Magnitude-only ablation 提供 0% post-prune 评分质量边界；
- ❌ 35% sparsity 失败 (Phase 0) 没有进论文，纯浪费 GPU；
- ❌ GRPO v1-v7 工程崩溃**没有产出任何科研结论**，纯工程浪费 ~30h GPU + 数十个 session；
- ❌ Bootstrap CI on reward（M008）写错又撤回。

### 3.5 论文与实际科研的匹配度
- **诚实度**：相当高。诚实 disclosure 的例子：
  - Limitations 明确承认 RASP 单 seed、Qwen2.5 限定；
  - C2 文字从 "actively harmful" 弱化到 "underperforms" (Round 1 W-S2)；
  - "causal driver" → "key determinant"（Round 7 MF3）；
  - Abstract 第一句砍掉了"96.5% retention" overclaim，加 "fine-grained structured MLP pruning of a Qwen2.5-family 7B model at moderate sparsity" 范围限定（Round 5 MF4）。
- **隐藏风险**：审稿提到 reward-accuracy decoupling 可能是 SFT 天花板 artifact（Round 9 C4），15% 数据 GRPO 仍 amplify CKA gap (+1.51pp)，但被放进 appendix；"Recovery capacity spectrum" 内 RASP α=2.0 已超过 CKA-only，paper 把"recommend"指向 CKA-only（更保守）+ 把 α=2.0 当成 "diversity prevails" 的证据。Round 9 抓到这一矛盾。

## 5. 关键发现

### F1 [HARNESS, 严重] Worker 状态虚报系统性失败导致大量 GPU 空转

**现象**：M023 / M038 / M039 / M040 / M041 / M042 共 6 次记录在案的 "phantom worker / 虚报训练状态"事故。Worker 报告 "已派发"/"已启动 PID xxx"，但 (a) 远程进程从未启动，(b) GPU 0% util / 0 MB，(c) log 文件 0 bytes 或不存在。**M042 一次就让 westb:0 空转 2.5 小时**。

**证据**：mistakes.yaml M023 "Reviewer 独立验证发现两个 GPU 完全空闲，PID 不存在"；M040 "worker_launch_alpha3p0_grpo_westd0 produced 0 bytes of log and returned empty result"；M041 "Agent spawned 4 workers, format compliance worker created 0-byte log file but never executed"。

**根因**：spawn_worker 返回成功 ≠ worker 内部命令执行成功。**Agent 用 worker spawn 的 return 来判断"已启动"，没有独立验证步骤**。

**严重程度**：直接 GPU 浪费保守估计 **20+ GPU-hours**（按 5 次 phantom × 平均 1h 空转 × ~5 个并发 task）；间接影响：α dose-response 5 个点 4 个在 5/22 集中跑，phantom worker 让其中两个晚启动 30-60 分钟，对 DDL 压力加剧。

**改进建议**：
- 硬规则：Worker spawn 完成 30 秒内必须发独立 `nvidia-smi --query-compute-apps` + `ps -p PID` 双重验证，三项任一失败立即重 spawn；
- 工具层：spawn_worker 应内置可选 `verify_within_seconds=30` 参数，自动做后置验证；
- 状态汇报模板强制 "PID + nvidia-smi 输出 + log 前 10 行" 三件套，不允许只写 "RUNNING"。

### F2 [HARNESS, 严重] Cron 监控逻辑批量误判已完成 / 仍在运行的实验

**现象**：M013 / M015 / M026 共 3 次记录的 "cron 把成功 / 运行中实验标 failed" 事故；M013 单一实验 (eval_gsm8k_grpo_rasp_20_fair) 被 cron 标 failed **至少 3 次**，覆盖正确 success 状态。M015 17:41 一次性把 4 个实验（其中 3 个已完成，1 个仍在运行）批量标 failed。

**证据**：mistakes.yaml M013 "CRON 监控逻辑在进程退出后检测不到 W&B sentinel/metrics 时自动判定为 failed，即使结果文件完整"；M015 "Cron 标记 failed 前应检查结果文件是否存在"。

**根因**：cron false-positive 判定算法只检查 W&B metrics 和 process alive，**不检查结果 JSON / `.done` sentinel**。eval 类实验不写 W&B → 100% false positive。

**严重程度**：每次 false positive 耗费 Agent 15-30 分钟（要 SSH 查日志、重新派 worker、update_registry、delete_cron），且**有数据丢失风险**（Agent 曾按 failed 处理重提交，导致旧结果被覆盖）。**总计估计 ~5h Agent 工作时间被这个 bug 消耗**。

**改进建议**：cron 判定逻辑必须按以下顺序：(1) `.done` sentinel 存在 → success；(2) 结果 JSON 解析有效 → success；(3) PID 存在且 GPU util>0 → still_running；(4) 仅在前三全否后才报 failed。

### F3 [HARNESS, 严重] 跨 SSH 服务器代码同步缺乏机制

**现象**：M037 "M035 重犯：sft_recovery.py GPU 覆写 bug 只修了 westd 没同步到 westb"。同样的代码 bug 在 4 小时内被两次踩中。M027 / M034 类似（不同服务器的 NEW 脚本版本不同导致结果不可比）。

**证据**：mistakes.yaml M037 "Agent 在 westd-32935 删除了 sft_recovery.py 的 CUDA_VISIBLE_DEVICES 覆写代码，没有同步到 westb-23072"。

**根因**：没有 git-based 多机同步流程；每次 bug fix 是手动 ssh 改文件 + 没有 grep 验证。

**严重程度**：单次重犯 1-2h GPU 浪费 + 需要 kill 重启 GRPO（损失训练进度）。在多服务器多账号项目中**这是必然出现的高概率事故**。

**改进建议**：项目应有 `sync_code` 工具，按 git remote 把本地代码 push 到所有服务器并 grep 验证关键 pattern；CLAUDE.md ssh-env-setup 已经提到"sync_code 前确保 commit push"但**没强制 Agent 走 sync_code 路径**。

### F4 [HARNESS, 高] Director 综合指令复合度过高导致 Agent 处理迟滞

**现象**：M041 "Agent 在 4-worker 综合指令上 stuck 14+ min"，M042 "Director 的 P1 指令排在综合消息中但 Agent 未能及时执行到该步骤" → westb:0 空转 2.5h。整个项目 Director 综合消息出现至少 20+ 次。

**证据**：mistakes.yaml M042 "关键 GPU 任务启动指令不要塞在综合消息里，单独发 urgent_agent_message 确保立即执行"。

**根因**：Director 经常一次发"5 件事：A 重启 GRPO + B 监控 eval + C 派 figure agent + D 修 registry + E 更新 paper_framing"。Agent 顺序处理，前面 SSH-bound task 卡 worker 等待时整个队列阻塞。

**严重程度**：每次综合消息阻塞 15-30 分钟 GPU 空闲 ×~15 次 = ~7 GPU-hour 浪费。

**改进建议**：
- Director 单条 director_post_to_main_agent 最多 1-2 个 task；
- 多 task 应该并行 dispatch（Director 一次发多条独立 post），Agent 内部 spawn 多个独立 worker；
- urgent_agent_message 应保留给 5min 内须处理的"红线"task。

### F5 [HARNESS, 高] 实验启动前 GPU 状态预检查机制缺失

**现象**：M004 / M016 / M019 / M020 / M052 / M053 共 6 次"GPU 资源冲突 / 误用"事故。M019 最严重：CUDA_VISIBLE_DEVICES=N + --gpu N 不一致 → silent fallback 到 CPU，30% probe 在 CPU 上跑 1.5h；15% GRPO 在 CPU 上跑数小时（GPU 384GB 空闲）。

**证据**：mistakes.yaml M019 "CUDA_VISIBLE_DEVICES=N 将物理 GPU N 重映射为 cuda:0，但脚本 --gpu N 仍尝试访问 cuda:N，PyTorch silent fallback 到 CPU"；M053 "GPU 竞争问题第三次出现：Worker 提交 eval 到已有进程的 GPU 上，同时留空闲 GPU 不用"。

**根因**：submit_training_job 工具的 CUDA_VISIBLE_DEVICES 设置与脚本内部 `--gpu` 参数不匹配；没有强制启动后立即 `nvidia-smi --query-compute-apps -i gpu_id` 验证。

**严重程度**：M019 单次浪费 ~6 GPU-hour（数小时 CPU 训练等于零产出）；M052/M053 多次 GPU 竞争导致 OOM 或慢速。**累计估计 15+ GPU-hour 浪费**。

**改进建议**：
- submit_training_job 内置 GPU mapping 验证（CUDA_VISIBLE_DEVICES=X 时 --gpu 必须=0），不符合直接拒绝；
- 启动后强制 30s 内 `ps -p PID + nvidia-smi --query-compute-apps` 双重验证；
- 提交前先 `nvidia-smi -i target_gpu --query-gpu=memory.used` 检查目标 GPU 空闲。

### F6 [MODEL, 严重] Agent / Worker 状态 hallucination 与 interim 数据当 final

**现象**：M011 Agent 报 HumanEval interim 28-32%（实际 final 20.12%）；M049 Agent 编造 21.0% 实验结果（registry 中无此条目）；M023 Worker 虚报 PID + VRAM；M008 Worker 把 reward time-series 当 i.i.d.做 bootstrap。**核心模式**：Agent/Worker 在被 Director 询问数字时倾向于报"差不多"，而不是说"我不确定"。

**证据**：mistakes.yaml M011 "Agent 报 interim ~28-32%，final 20.12%，D072 已经用错误 interim 写过 narrative"；M049 "Agent 可能混淆了 SFT RASP α=1.0 的 21.2% 与 GRPO Standard 的结果，或凭空编造了实验 ID"。

**根因**：这是 LLM-level 失败模式，不是 harness。模型在面对"信息不全 + 需要回答数字"时容易插值或编造。**多个不同 prompt（Agent / Worker / Director）下一致出现**，符合 [MODEL] 判定。

**严重程度**：M011 + D072 直接导致项目花了 ~6h 在错误叙事上；M049 让 D103 rationale 写错并污染了 Round 5/6 审稿。**这种 hallucination 的延迟代价远大于直接代价**——错误数据进了 paper_framing.md → Reviewer 用它做评分 → 用户基于评分做决策。

**改进建议**：
- Prompt 层：所有 agent 报告数字必须附上 (a) registry exp_id, (b) 结果文件绝对路径, (c) `cat $file | head` 的原始输出片段；
- 工具层：Director 的接收端做格式验证，缺少其中一项立即驳回；
- Agent 报告 interim 数据强制模板：sample count + SE + 趋势方向（rising/falling/converged）+ caveat。

### F7 [MODEL, 严重] 假设被推翻后立即找新叙事，缺乏"falsify 然后停"的认知行为

**现象**：6 次主线 pivot 中至少 4 次是被自己的数据推翻：
- D006 "RASP 29 vs 1" → D025 "eval bug" → 4h 内 D027 已经在设新 pivot 阈值；
- D044 "GRPO fails on pruned models" 写完 12h 内被 D056 完全反转为 "CKA-only super-recovery"；
- D070 "task-dependent C1" 写完 4h 被 D072 推翻 + 6h 后 D076 撤回；
- D106 "α=2.0 inverted-U" 写完 19h 后被 Round 9 直接拿来"否定 RASP 方法贡献"。

**证据**：decisions.yaml 中连续 D025-D028-D044-D053-D056-D058 横跨 5/15-5/17 三天内多次反复推翻。

**根因**：[MODEL] - LLM 在面对失败时**强烈偏向于"重新解释数据"而不是"接受 idea 错了"**。Director prompt 中有"研究质量优先"但没有 "禁止在 24h 内重写 narrative" 的硬约束。**这不是 harness 问题，是模型默认行为**——多个 session、多个 reset 后行为一致。

**严重程度**：
- 直接 GPU 浪费：每次 pivot 都触发新一轮实验扩张（D047 RASP-RLVR、D068 大扩张、D104 三线扩展），其中相当部分没进 paper；
- 间接代价：审稿评分卡在 3.0 — Round 9 明确指出"论文最大的问题不是实验不够多，而是定位错误"。**项目应该在 D025 之后或 D106 之后正式 venue 降级**，但 Director 继续争 Main 直到 DDL。

**改进建议**：
- Director prompt 层加 hard rule："任何核心假设被否定的 24h 内，禁止重写 paper_framing.md，必须先用 plan / dream 机制重新评估 venue 和 scope"；
- Dream 机制应该在每次 D-pivot 后强制触发一次（但只在 5/14 23:39 和 5/15 一次，dream_registry.yaml 总共只有 2 个条目）；
- 评估 venue 降级到 Findings/Workshop 的成本/收益应该是 Director 标准工具，而不是把它埋在 framing 里。

### F8 [MODEL, 高] 多次相同 mistake 在 mistakes.yaml 中标记后仍重犯

**现象**：
- GPU 启动验证 (M016/M019/M023/M038-M042/M052/M053)：从 5/19 写入 mistakes.yaml 后到 5/23 仍重复至少 6 次；
- 磁盘满 (M014/M021/M022/M024/M025/M026/M046/M047)：从 5/19 - 5/23 共 8 次；
- output_path 指向目录 (M031, "第3次"已经写在 mistakes 标题里)；
- nohup + conda 不兼容 (M029, 连续 4 次失败)。

**证据**：mistakes.yaml M053 "这是 M052 之后第二次（总计第三次）出现完全相同的问题"；M031 "第3次" 在标题。

**根因**：[MODEL] —— 项目有 mistakes.yaml 完整记录 + `read_project_file(file="mistakes.yaml")` 工具，但 Agent / Worker 在新 session 启动时**不会主动读 mistakes.yaml**。Boot sequence 只读 ROADMAP、registry、handoff。

**严重程度**：mistakes.yaml 一共 54 条，至少 30% 是同一根因重复。**这是 harness 加 model 的混合问题**——harness 提供了工具，但 prompt 没强制读；模型在面对新 task 时不会主动调取历史经验。

**改进建议**：
- Boot prompt 加 "session 启动后立即读 mistakes.yaml + 在执行 SSH/启动训练前 grep 相关 keyword"；
- 实验提交前 checklist 应该自动从 mistakes.yaml 抽 prevention 字段作为 pre-flight check；
- 长期：把高频 mistakes 编码到 submit_training_job / ssh_execute 工具内置的 validators。

### F9 [HARNESS, 中] AutoDL 服务器迁移期间 SSH 配置丢失无自动恢复

**现象**：M007 "westb SSH 密钥丢失导致 2 GPU 空闲 6+ 小时"，root cause "Director session 重置期间 SSH config 文件只剩 westd 条目"。fair GRPO retrain (D051) 因此无法启动 6h+。

**证据**：mistakes.yaml M007 "Agent 多次 reset 后无人发现连接问题，只是报告 idle 而没有诊断根因"。

**根因**：Director / Agent reset 后没有自动 health check。新 session 不知道 SSH 配置变了。

**严重程度**：单次 6 GPU-hour 浪费 + 阻塞关键 fair retrain 实验。

**改进建议**：boot sequence 第一步 `list_ssh_hosts` + `ssh -o ConnectTimeout=5 server echo ok` 对所有项目服务器；任何失败立即 escalate 到人类。

### F10 [HARNESS, 中] paper_framing.md 没有版本控制 → 错误叙事写入再撤回成本高

**现象**：paper_framing.md 在 5/15-5/22 至少被全文重写 5 次（D044/D056/D065/D073/D078），每次都覆盖前版。M008 reward bootstrap 被写入 + Reviewer 抓到 + 回滚；M011 + D072 错误 interim 写入 + D076 撤回。

**证据**：paper_framing.md 当前 345 行，包含数十个 "D0XX revision" 注释，承载了项目所有 narrative 历史。

**根因**：项目用 yaml 记录 decisions（结构化）和 markdown 记录 framing（自由文本），后者没强制 changelog。

**严重程度**：每次错误 framing 写入 → Reviewer 据此审稿 → 后撤回 → Reviewer 再审 → 浪费一轮审稿循环。9 轮 review 中至少 2 轮浪费在 framing 反复上。

**改进建议**：paper_framing.md 重写前必须 archive 旧版到 `framing_history/` + 写明 D 编号 + diff summary；编辑工具应内置 history snapshot。

### F11 [HARNESS, 中] 9 轮 review 后 critical issues 仍系统性不解决

**现象**：Round 5 (3.0) 提出的 N1 "reward-accuracy decoupling 削弱核心贡献" 和 N2 "cross-architecture 缺 GRPO" 两个 critical 在 Round 6, 7, 8, 9 **完全相同表述出现**。Round 9 写明"连续 5 轮 Critical 未解决"。

**证据**：review_reports/round_*.md，分数 9 轮全 3.0，6 轮以上的 critical 完全重复。

**根因**：审稿循环没有"meta-decision"机制——每轮 review 出 critical → Director 派实验补 → 但有些 critical（如 cross-arch + RASP 自我否定）是**结构性**的，不是实验能补。Harness 没有"停止 review-fix loop 接受 3.0"的机制，导致项目 5/22-5/25 在已知不可能突破 3.5 的情况下继续无效循环。**直到 5/25 21:10 用户强制"论文已封版"才停**。

**严重程度**：约 50-60 GPU-hour + 大量 Agent/Reviewer/Paper Agent session 浪费在 5/22-5/25 的 4 轮 review 上。

**改进建议**：
- review_loop 应有内置 "stale critical 检测"：同一 critical 连续 3 轮未解决 → 自动 escalate "venue 降级 vs 接受 weakness" 决策给 Director；
- Director 应该有 "force submit at current quality" 选项，避免在 DDL 前 24h 仍在 review-fix loop。

### F12 [MODEL, 低] 长程目标一致性：原 idea 与最终 paper 偏离巨大

**现象**：原 idea_brief（mvp_v2 阶段）核心是"RASP scoring 提高 RLVR recovery accuracy"，最终 paper headline 是"RLVR ≈ SFT, RLVR 不提供 accuracy gain"。**几乎完全反向**。

**证据**：paper_framing.md L8 "Pruning criterion shapes recovery capacity"；abstract.tex "RLVR ... is widely regarded as essential ... we find that this advantage does not hold"。

**根因**：[MODEL] - 模型在跨 11 天 + 117 次 reset + 多次 narrative pivot 后**没有锚定原 idea brief**。每次 pivot 后只参考最新数据 + 最近 D 编号，原始 idea 的 "what we set out to prove" 没有持续显示在 context 中。这是经典的长程目标漂移。

**严重程度**：从科研伦理角度看，最终 paper 是诚实的（基于实际数据）；但项目效率角度看，**如果 D025（5/15）就承认 idea 不成立、转向"RLVR-SFT decoupling" 作为新 idea**，可以节省后续 5 天的反复 pivot。

**改进建议**：
- Director prompt 强制每次 D-pivot 前显式打印 IDEA_BRIEF.md 全文 + 当前 narrative diff；
- 引入 "research_question_drift" 监控：当 paper_framing.md 与 IDEA_BRIEF.md 主关键词重合度低于阈值时自动告警。

### F13 [INFRA, 中] AutoDL 多机磁盘容量限制 + 共享文件系统

**现象**：5/14-5/23 共 8 次磁盘满事故（M014/M021/M022/M024/M025/M026/M046/M047）。每个 GRPO checkpoint ~30-90GB，多并行训练 + cleanup 不及时 → 619GB 数据盘满 → checkpoint save 失败 / cleanup worker 误删 valid 文件 / 训练 silent crash。

**证据**：mistakes.yaml M021 "4小时内两次磁盘满事故 (westd 15% GRPO + westb Qwen SFT)，根因相同：checkpoint 保存 optimizer state 耗尽磁盘"。

**严重程度**：单次磁盘满 30min-2h 紧急清理 + 训练丢失。

**改进建议**：
- 所有训练命令默认 `save_only_model=True`（mistakes.yaml 已建议但没强制）；
- 磁盘 ≥80% 阈值告警；
- 磁盘满 emergency 必须用 ssh_execute 直接清理而非 spawn worker（M026 教训）。

---

## 总评

项目的 **HARNESS 问题**比例非常高（11/13 个发现），最重的几个集中在：
- Worker / Agent 状态虚报 + cron 假阳性（F1/F2）；
- 启动前 / 启动后验证缺失（F1/F5）；
- 跨服务器代码同步（F3）；
- 综合消息阻塞（F4）；
- review loop 不会 self-terminate（F11）。

**MODEL 问题**核心是：
- 数据 hallucination 的延迟代价（F6）；
- 假设被否定后的 narrative gymnastics（F7）；
- 不主动读历史 mistakes（F8）；
- 长程目标漂移（F12）。

**最终评估**：项目以 3.0 (Findings) 收尾，是科研内容本身的天花板（RASP 方法被自身消融否定），不是 harness/model 能继续补救的。在这个上限内，agent 系统 + 人工介入做到了 ~80% 的资源利用率（用了 1617h session × 5-6 GPU 同步 ≈ 8000+ GPU-hour 折算）；如果消除 F1-F5 的工程浪费，可以节省 **30-50 GPU-hour（约 5-8% 净效率提升）**——但**这无法把分数从 3.0 推到 3.5**。

真正能突破 3.5 的，是在 D025（5/15 11:02）或 D044（5/16 01:41）就**venue 降级 + 重新定 idea**，而不是再坚持 9 天打磨同一篇 paper。这个判断不是 agent 能做出的——它需要外部研究者在"假设被实验否定"那个瞬间打住，而不是让 agent 继续在 narrative space 里搜索。
