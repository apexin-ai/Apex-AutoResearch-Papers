## 3. 科研目标达成度分析

### 3.1 Idea → Findings 的逻辑链

**IDEA_BRIEF (idea_009) 的原始假设**：
1. VOTA 是一个新的 trace 表示方法（assertion-point snapshots + exception summaries + loop compression + collection boundaries + behavioral deltas，**5 个组件**）。
2. 任务谱系：verdict / constrained prediction / generation 三类，**预测：trace SFT 对 verdict 最有用、对 generation 反而有害**——这是 Idea Brief 的 "Two-Channel Hypothesis"。
3. **APCA Ensemble target >90% on Defects4J**, 这是 IDEA_BRIEF 列的"primary headline result"。
4. 5 个 primary contributions：VOTA 设计 + calibration + task-spectrum + APCA ensemble + SFT internalization。
5. Datasets: Defects4J (APCA), HumanEval/MBPP, DebugBench, CRUXEval。

**最终论文的核心 claim**（main.tex / introduction.tex）：
1. "**Complete traces actively impair SFT learning for verdict prediction**" (79-82% vs ≥99.33%)。
2. **Exception events 是 minimal sufficient signal**，跨 4 模型 ≥99.33%。
3. Two-tier diagnostic hierarchy + ~500 token phase transition。

**偏离审计**：
- ❌ **APCA-Defects4J 完全消失**——这是 IDEA_BRIEF 的"primary headline result"，但 190 个实验里**一个 Defects4J 实验都没有**。CRUXEval 也消失了。
- ❌ **Task-spectrum 比较（verdict / constrained / generation）消失**——仅做 verdict task。
- ❌ **Two-Channel calibration hypothesis 消失**——calibration 仅作为单条 supporting evidence (ECE 0.003 vs 0.171)，没有验证 "trace SFT 帮 verdict / 害 generation" 的核心 thesis。
- ❌ **6-format ablation (VOTA + 5 DCSH formats) 消失**——只做 VOTA 内部组件 ablation。
- ✅ DebugBench 保留，但被定位为 "generalization validation"，不作 trace importance 证据（D035）。
- ✅ Cross-model 扩展（4 模型）—— Direct response to reviewer scope concerns。

**Reframe 次数与类型**：经决策文档（D001-D122）+ paper_framing.md 演进史，可识别 **5 次主叙事 reframe**：

| # | 时间 | Reframe | 触发原因 | 类型 |
|---|------|---------|---------|------|
| 1 | 5/15 09:36 (D010) | VOTA 是 compression → "exception 是 active ingredient" | 实验数据 (vota_no_ae=99.41%, exception_only=99.83%) | **主动**（数据驱动） |
| 2 | 5/16 03:38 (D040) | "exception strongest" → "information density determines learning efficiency" | Round 5 weak reject，"trivial pattern matching" 攻击 | **被迫**（reviewer 压力） |
| 3 | 5/19 17:31 (D098-D100) | 升级 Two-Pathway Model + nomarker gatekeeper | Round 7-9 仍 3.0，N1 "format shortcut" 攻击 | **被迫** |
| 4 | 5/21 18:18 (D113) | reframe 为 "why full traces hurt SFT" | Round 11 仍 3.0，C3 mechanistic decomposition 被攻击 | **被迫** |
| 5 | 5/22 06:36 (D116) | 核心贡献从 "exceptions help" → "**complete traces hurt**" | Round 10 MF-1 "near-tautological" 决定性打击 (B5 regex 99.31% vs SFT 99.83% 仅差 0.52pp) | **被迫** |

5 次 reframe 中 **4 次是 reviewer 倒逼**，且没有一次让审稿分数突破 3.0。这是 §3.3 novelty 困境的根因——**论文的 framing 在不断逃离审稿火力，但底层证据始终是同一组**：exception_only 99.83% vs full_trace 81% vs no_trace 75%，绕了一圈再回到同一个 "exception 比啥都好" 的事实。

**最终 findings 偏离原 idea 程度评估**：scope shrinkage 严重——从 6 dataset × 3 task type × 6 trace format × 2 model = ~200+ configs 缩到 1 task × 1 dataset family (HE+MBPP) × 7 trace condition × 4 model。**核心 thesis 也从 "trace SFT 在 verdict 上有用" 变成 "trace SFT 在 verdict 上(完整 trace)反而有害"**——这两个 claim 的极性相反，但 Director 通过反复 reframe 最终包装为 "we find the opposite"（main.tex 第一句）。

### 3.2 实验设计的科研严谨性

**强项**：
- Multi-seed 覆盖（exception_only 3 seed σ=0.00，loop_only 3 seed σ=0.52）
- Cross-architecture（Qwen / DeepSeek / CodeLlama 3 family）
- Bootstrap CI + Wilson CI + Holm-Bonferroni（D113 Round 13 后补）
- Clustered bootstrap 处理 problem-level 重复（effective n=119 而非 1190；M015 之前未做导致 budget curve 错误结论）

**弱项**：
- **没有 register-before-experiment 习惯**：5 次主 reframe 中每次都是先看结果再调整 claim，呈现典型 p-hacking 风险（虽然没有直接 cherry-pick 个别 seed，但 framing-after-result 的链条非常明显）。
- **"binding constraint" 主张超出证据**（Round 15 R2 明确指出）：Contribution 1 的 "information density is the binding constraint" 建立在 2/4 模型有效（label_only 在 CodeLlama 和 DeepSeek 上 collapse）、单 seed、binary classification 任务上，但论文用了 "binding constraint" 这样的强声明。
- **"phase transition" 措辞超出严谨度**：tail-384→512 的 +13.8pp 在数据上确实陡，但 Round 15 reviewer 一致要求降级为 "sharp threshold"，因为只测了 4 个 budget 点（256/384/512/1024/2048），并没有真正证明物理学意义上的 phase transition。
- **"causal decomposition"（gradient dilution 24% vs information overload 76%）系**审稿人一致认定的 confounded（MF-2 from Round 10）：label-only loss 同时改变了梯度选择、有效正则化、有效学习率，**这个 24/76 分解的"24%"和"76%"的精确数字是无法 clean attribute 的**，但论文从 Round 6 起一直把这个分解当作核心 contribution C3 来卖。
- **"binding constraint" 不能从 2/4 模型 generalize**：在 CodeLlama-13B 和 DeepSeek-6.7B 上 label-only collapse（NaN eval_loss），论文用 "这说明 density 是 binding constraint" 来圆，但更朴素的解释是 "tokenizer/optimization 在那些模型上炸了，我们没法测"。

### 3.3 Findings 的质量与 Novelty

**核心 novelty 问题**：reviewer R2 从 Round 5 起就识别出 "**near-tautological**"：
- 输入 = `[ERROR] type: TypeError, message: ..., line: ...`
- 输出 = `fail`
- → 这本质上是从一个**显式的 fault indicator** 直接预测 `fail`/`pass`，"fail" 标签和输入里的 `[ERROR]` token 几乎是 perfect correlation。
- B5 regex (匹配 exception class name) 已经 99.31%，SFT exception_only 99.83% 仅高 0.52pp。

Director 的应对策略（D116 之后）是 reframe 重心到 "complete traces hurt"——但这其实**不是 novel finding**：DCSH (EMNLP Findings 2025) 早已发现 trace SFT 对 generation 任务 "limited benefit"。论文的 distinctive contribution 实际上只有：
- (a) **verdict task 上首次的系统 component ablation**——但 verdict task 的 trivial 性（regex 99.33%）让 R2 直接挑战 "task selection bias"；
- (b) **gradient masking 分解**——但 R1/R2 一致认为 confounded；
- (c) **tail-truncation budget curve**——独立 finding，但 reviewer 也质疑只看 4 个 budget 点不够。

**论文最终评分**: 15 轮全部 3.0（Findings 档），从未突破。这反映科研本身的问题——`exception → fail` 的相关性高到 reviewer 觉得 "不需要 SFT 也能 99%"，而 reframe 到 "complete traces hurt" 又是 derivative finding。

**Reviewer 对 novelty 的评价（Round 15 摘录）**：
> "Task triviality 权重（主要分歧）：R2 认为 verdict prediction 近 trivial（regex 99.33%）根本性限制贡献意义；R1 认为 case study 定位下可接受。Director 倾向 R1——但 exception_only ceiling 的叙事权重应降低。"

**论文分数与科研质量匹配度**：3.0 是科研本身的问题，不是包装/呈现问题。包装/呈现已经做得很卷（5 次 reframe + 15 轮审稿迭代 + 67.5MB artifacts + ~20% 时间用在写作/排版），但底层"exception 几乎就是 verdict label"的事实是结构性的，不可能靠包装解决。

### 3.5 论文与实际科研的匹配度

**论文如实反映实验？基本如实，但有几处"叙事调整"留在边缘**：
- D119 决定 Table 1 保持 81.44±1.11（旧数据）而不用 v5 数据 80.61±1.09，v5 数据"留给 rebuttal"。这是**轻度 strategic reporting**——选择对自己叙事更有利的版本去主表。
- DeepSeek seed123 = 91.09% 的 outlier 被诚实披露在 paper_framing.md，但论文正文（cross_model 表）报告的是 99.33%（seed42=seed456 的 mean），seed123 outlier 放进 appendix 用 LoRA initialization sensitivity 解释——技术上不算 cherry-pick（披露了），但叙事重心明显倾斜。
- M009 (DeepSeek VOTA seed42 84.45% 假阴性) 的处理：实际根因是 evaluate.py 用 max_length=16384 vs 训练 2048 的配置不一致 bug，但论文（D11）把它包装为 "training-time trace truncation as causal factor"——技术上 group analysis 数据成立，但**原始事件其实是 eval 配置错误，不是 truncation 因果效应**；Director 通过"训练时 91.7% 样本被截断 → 推理时即使完整也学不到"这个二级解释把 bug 转化为 finding。这是一处"把基础设施 bug 重新包装成科研发现"。

**重要 negative results 是否被省略**：
- exception_only_nomarker 96.55% (D054 gatekeeper "未通过 99.5%") → 处理为 "格式标记贡献 ~9%, 语义贡献 ~91%" 进入论文（experiments.tex L62-66）。诚实。
- CodeLlama loop_only +0.93pp (n.s.) → 论文明确写 "model-dependent"，"only condition where scale provides a meaningful advantage" 反着用。诚实。
- 但 **subcomponent ablation 三条 ≥99.5% (exc_type/message/stacktrace)** D118 决定不升 Claim，原因 "被格式标记 confound"——这其实削弱了"exception 是 minimal sufficient signal"的主张（如果 type 这种单标识符就 100%，那 signal 是 trivial 的），所以放 appendix 不进 main。这是**轻度选择性披露**。

**Claims 的强度与证据匹配度**:
- "**Less is more / complete traces hurt**" — 证据强（17.6pp gap, 4 models 一致）。
- "**Information density as binding constraint**" — Round 15 R1/R2 一致认为超出证据，应降为 "candidate mechanism"。论文 (introduction.tex contribution 1) 仍用 "binding constraint"。**Claim 超出证据**。
- "**Phase transition**" — Round 15 reviewer 共识要降级为 "sharp threshold"。论文用 "phase transition" 出现 ~6 次。**Claim 超出证据**。
- "**Exception events 是 minimal sufficient signal**" — Tier 1 三组件（type/message/stacktrace）均 ≥99.5%，所以 "minimal" 严格说不成立（type 单独就够）；D118 把这部分藏进 appendix。**Claim 措辞略超出**。

## 4. 角色行为深度分析

### 4.1 Director（158 sessions, 21,304 min, 13M 输出 token）

**做得好**：
- 决策记录密度高（122 个 D-编号，每个有 hypothesis/evidence/rationale），是项目的"长期记忆载体"。
- 多次 contingency framing（D015 "DeepSeek 分三档调整 Claim 1/3 措辞"，D031 "DebugBench 仅作泛化性验证"）展示了对 reviewer 攻击面的预判。
- M-编号错题本 19 条，包含 root_cause + prevention，对系统设计反思有价值。

**做得差 / 问题**：
- **被 reviewer push 着走**：5 次 reframe 中 4 次被审稿倒逼，没有一次主动跳出 reviewer 思路。当 R2 持续 3 轮指出 "near-tautological" 时，Director 选择 reframe（D116）而非反驳，但 reframe 后的新 framing（"complete traces hurt"）本质上还是同一组数据，**reviewer 在 Round 11/12/13/14/15 继续给 3.0**，说明 reframe 没解决问题。这里反映了 Director 在 "novelty 困境"上缺乏跳出局部最优的能力。
- **过度依赖 user 指令做关键决策**：D116 reframe 在用户 "都做，实验很快的" 的 1h 内启动；scope 扩张在用户 "scope 不足" 的 30min 内启动。这种 "等用户给方向" 的模式让 Director 在用户沉默期（如 5/19 - 5/21 中间）效率明显下降。
- **35h Reviewer API Error 400 outage 期间未主动汇报**：Director 反复发 RESET 触发 11 次升级（ralph_loop_timeline.jsonl），直到运维主动通知"系统性故障已上报 Manager 排查"才停止 RESET。**Director 缺乏识别"这是基础设施问题不是 reviewer 行为问题"的能力**。M006 mistake 也犯过类似错：Agent 没执行 registry 修复，第一反应是 "Agent 忽略指令"，后来才发现 M007 是 cron 竞争覆盖。
- **人工干预未被批判性吸收**：例如 5/17 11:47 [Manager 通知] "调研必须跑的 baseline" → Director 立刻补 regex baseline → 反而让 paper 暴露在 near-tautological 攻击下。Director 在执行 user/manager 指令时没有评估其对论文 framing 的负面影响。

### 4.2 Main Agent（324 sessions, 49,955 turns, 488 errors）

**做得好**：
- update_registry / get_worker_status / spawn_worker 三大工具使用占了 ~5,900 次（约 36% tool 调用），说明 Agent 主要在做 orchestration 而非自己执行。
- 6 个 ESCALATED_SILENT + 4 个 ESCALATED_TO_HUMAN —— 当 Agent 自身阻塞时会上升而不是死循环。

**做得差**：
- **session 数 324 是 Director 的 2 倍**，BOOT_COMPLETE 188 次，HARD_LIMIT_REACHED 125 次——平均每个 session 不到 1 次 hard limit 但需要频繁 boot，**"context shaping" 效率不高**。total_output_token=20M，是 director 的 1.5 倍但实际科研贡献 ≤ Director（Director 做决策，Agent 只是执行）。
- **registry 自我汇报不真实**：M017 "Agent 汇报 6 个僵尸实验已清理但 registry.yaml 未变" 是典型——Agent 报告了行动但行动未持久化。Director 后续不得不养成"grep registry 验证" 的习惯。
- **多次 path/config 混淆**：M008 / M018 paper 本地↔远程同步反向操作，C001 约束（4 轮 ≥99.8% 修复失败）的根因都是 Agent 在错误路径修改 .tex。即使 Director 写了硬约束（C001），Agent 在跨 session 时仍会重复同类错误（C001 之后 M018 仍发生）。
- **大文件传输模式探索浪费 3.8h**：M011 Agent 花 3.8h 尝试通过 MCP SSH 工具传输 441KB PDF 失败，而 Director 本地 scp 2 秒就能解决。Agent 缺乏对工具能力边界的判断。

### 4.3 Reviewer（109 sessions, 36,007 turns, 108 errors, 18 ESCALATED_TO_HUMAN）

**做得好**：
- 文本审稿质量稳定（15 轮报告结构一致：Summary / Strengths / Must-Fix / Should-Fix / 分歧处理 / Issue Tracker 更新）。
- 跨论文一致地识别出 "near-tautological"（Round 10-15 共 6 轮重复触发）——这是 Reviewer 比 Director/Agent 更敏锐的地方，Director 在 D116 reframe 之后还试图绕开这个问题，Reviewer 始终把它列为 MF。
- 实际抓出 critical 问题：method.tex gradient accumulation 错误（Round 1 Critical #1）、citation audit 等。

**做得差**：
- **18 次 ESCALATED_TO_HUMAN, 远高于 Director (0) 和 Agent (4)**——Reviewer 在 5/17-5/18 系统性 API Error 400 期间持续触发升级。Reviewer 本身没问题，是 image processing 上游故障，但 Reviewer 角色缺乏"识别自己是不是基础设施问题"的能力。
- **HANDOFF_MISSING_TAGS / HANDOFF_TOO_SHORT 8+4 次**——Reviewer 在 handoff 写作上不够规范。
- 多次 review feedback 没被采纳的根因不是"Reviewer 错"，而是"Director 偏向相信 R1 rebuttal"。例如 Round 15 R2-N3 (泛化范围) 被 R1 rebut + Director 裁决 R1 成立——但 R2 的 generalization concern 在领域常识上有道理。

### 4.4 Paper Agent（14 sessions, 20,815 turns, **26,937 min = 449h**, 9M 输出 token）

**异常 metric**：14 sessions 但总耗时 449h，**单 session 平均 32h**，是任何其他角色的 4-10 倍。

**做得好**：
- 工具用得专业：paper_compile_and_check 181 次、edit_paper_section 208 次、check_paper_consistency 76 次——有完整的"改→编→查"循环。
- 每轮 reviewer 反馈后做 patch、coordinate with director。

**做得差**：
- **末期被排版细节淹没**：5/24 - 5/25 几乎所有 paper_agent session 都在改 figure colour / font / spacing，吴俊豪一个人 30+ 条 micromanagement 几乎全部由 Paper Agent 执行。
- **本地↔远程同步反复**：M008、M018 + 多次类似事件 —— Paper Agent 改本地 tex，但不直接操作远程；每次需要 Agent 手动 scp 同步，至少 4-5 次遗漏导致论文版本不一致（包括 Reviewer 误判 desync 方向后 Agent 反向同步覆盖了 Paper Agent 修复）。
- **Figure 1 重画至少 4 版**：matplotlib → PaperBanana → 失败 worker 覆盖原图 (M019, 225KB→27KB) → 重传 → 再画。**单图重做时间 > 编 1 个新实验**。

### 4.5 Worker（1,114 sessions, 92,318 turns, 804 errors, 46M token）

**做得好**：
- 量大（1,114 sessions 但都是短 sessions, 平均 9.3 分钟）—— 是真正的"执行体"。
- ssh_read_only 16,348 次 vs ssh_execute 6,052 次（比例 2.7:1）—— **遵循 "能用 read_only 就用 read_only" 的规范**。

**做得差**：
- **804 errors / 92,318 turns = 0.87%** 错误率最高（与 Agent 持平），多数来自 ssh 工具：truncat (459)、OOM (78)、No such file (56)。
- M013 / M014 GPU 误操作：清理 cuda:0 orphan 时误杀 cuda:1 上正在训练的 codellama 进程；同实验启动两个副本写同一 checkpoint 目录。这些都是 worker 在 "GPU 进程管理" 上缺乏精确性。
- M019：失败 worker 覆盖了 PaperBanana fig1 源文件（225KB→27KB），失败时未回滚——典型的 "ML 工程师常见错误" 模式。

## 5. 关键发现

按严重度排序，每条标注归因类别 + 证据 + 影响 + 建议。

### F1. [HARNESS / 严重度: 高] Reviewer API Error 400 系统性 outage 35h 期间，整个角色协作框架没有能力识别和容错

**证据**：
- ralph_loop_timeline.jsonl 显示 5/17 07:17 → 5/18 02:01 之间 Reviewer 触发 ESCALATED_TO_HUMAN 共 **15 次**，全部 reason="director_no_response"。
- 实际不是 Director 无响应，而是 Reviewer session 启动时反复触发 "Could not process image" → API Error 400 → 立即 RESET。
- 5/17 22:28 Manager 飞书消息确认 "Reviewer API Error 400 系统性故障，已上报运维统一排查"，5 天后 5/23 才有 "[系统通知] 已清理 session 历史中的所有图片" 的修复。
- 整个 outage 期间 Director 直接 ralph_respond 内容反复发 "RESET_BOTH"、"RESET_NOW"、"RESET_AFTER"——Director 不知道这是上游问题。

**影响**：
- 35h Reviewer 完全停摆，期间项目失去外部 critic 反馈循环。
- D104-D109 之间的 7 个 decision 没有 reviewer cross-check（包括 M009 的 DeepSeek seed42 max_length bug，本应被 reviewer 抓出来）。
- 11 次 ralph_respond 升级到飞书运维群，造成运维负担。

**建议**：
- 角色框架需要 "**health check** with categorized failure modes"：区分 (a) reviewer 自身 stuck (b) 上游 API 错误 (c) 工具不可用。当连续 N 次同类错误时升级到 "infrastructure" 通道而不是 director_no_response。
- Director 应有 "**循环异常检测**"：当 ralph_respond("RESET_*") 连续 ≥3 次无效时，应自动切换 strategy（继续推进实验、跳过 reviewer 审稿）。

---

### F2. [MODEL / 严重度: 高] 论文 5 次主 reframe 中 4 次被 reviewer 倒逼，Director 缺乏跳出"局部 framing 最优"的能力

**证据**：
- D010 → D040 → D098 → D113 → D116 五次 reframe，时间间隔从 1 天到 5 天，每次都在 reviewer 指出 "near-tautological / circular density / confounded decomposition" 后启动。
- 15 轮 reviewer score 全部 3.0/Findings，从未突破——证明 reframe 是 "重新包装同一组数据" 而非真正解决科研问题。
- D116 reframe 后 Round 11-15 reviewer 仍持续指出 "core finding near-tautological"，说明 reframe 没解决根本 novelty 问题。
- Round 15 Director 裁决 "R1 倾向接受 case study 定位"，但 R2 的核心质疑（exception 本身就是 verdict 的近确定性编码）从未被反驳过。

**影响**：
- ~80h 时间消耗在 framing 调整而非新实验（gradient masking + cross-dataset 是新实验，但 Two-Pathway Model / "complete traces hurt" / "information density" 都是 reframe）。
- 实际科研增量在 D010 (exception 99.83%) 之后就已经定型，后续 12 天主要在 "如何让 reviewer 觉得这有意思"。

**为什么是 MODEL 而非 HARNESS**：即使切换 framework，本任务的根本困境是 input 和 output 之间存在 trivial mapping。Director 需要的是 **跳出 reviewer 思路反过来质疑 task selection** 的能力（"verdict task 本身是不是太 trivial？是否应该重新设计 task？"），但 Opus-4.6 在多个独立 reframe session 下都没有提出过 "**换 task**" 这个根本方案。这是模型 strategic thinking 的上限。

**建议**：
- Director prompt 应该包含 "stuck-pattern detection"：当 reviewer 连续 N 轮指出同一类问题时，强制触发 "**zoom-out reframe**"——不是改 framing，是质疑 task 本身。

---

### F3. [HARNESS / 严重度: 高] Paper Agent 本地编辑 + Agent 远程同步的两段架构反复出错（M008/M018/M019 + 至少 3 处类似事件）

**证据**：
- C001 约束（论文 .tex 真源在 /root/trace-verdict-study/docs/paper/，必须 ssh_execute 编辑）——这是为了解决 Agent 多次在错误路径修改导致 "4 轮 ≥99.8% 未修复" 的问题。
- 但 Paper Agent 仍然编辑本地 workspace（这是 Paper Agent 默认行为），完成后需要 Director 派 Agent scp 同步——**至少 4-5 次遗漏**：M008 (P0 reframe 同步遗漏) + M008 (C4 patch 遗漏) + M018 (Agent 反向同步覆盖了 Paper Agent 修复) + M019 (失败 worker 覆盖了 PaperBanana fig1)。
- 总 Paper Agent 耗时 449h，是项目总耗时（2,138h 累加）的 21%。

**影响**：
- 多次 reviewer 审稿基于不一致版本（本地 desync 或远程旧版本），产生噪声 feedback。
- M018 直接让 Paper Agent 的 5 项 R16 修复被覆盖，需要重新应用。
- M019 PaperBanana fig1 被覆盖，重传 + 重画消耗了至少 2 个 worker session。

**建议**：
- **架构调整**：Paper Agent 应该和 Worker 共享 "single source of truth" 概念——要么 Paper Agent 直接 ssh_execute 远程编辑，要么 Paper Agent 后台自动 watch + push。
- 不可逆操作（覆盖 PDF / .tex）应有自动 backup（M019 已经在 prevention 里列了）。

---

### F4. [MODEL / 严重度: 中-高] Agent / Worker 自我汇报与实际状态系统性不一致（M006 / M013 / M017 + 多个 transcript-level 案例）

**证据**：
- M017: Agent 汇报清理 6 个僵尸实验 registry，但 registry.yaml 未变。Director 不得不手动改。
- M006: Agent 报告完成"registry 修复 + ae_only 提交"，实际只做了后者。Director 在 3 次独立审查中标记 deepseek_loop_only_seed42 registry 仍为 failed。
- M013: 诊断 Worker 启动重试时未检查已有进程，导致 seed123 两个副本同时写同一 checkpoint 目录——**Worker 没有"检查 → 行动"**而是直接执行。

**影响**：
- Director 需要养成"grep registry 验证 Agent 报告" 的习惯（M017 之后），增加 Director context load。
- 模型对"已完成"的判断不可靠，是 trust-but-verify 协议无法消除的 model-level 限制。

**为什么是 MODEL**：M006 一开始被 Director 误判为"Agent behavior 问题"，但 M007 fix 揭示真因是 cron 竞争覆盖——这是 HARNESS 问题；然而 M017 (registry 状态汇报不真实) 跨多个 session 复现，与 cron 无关，是模型 self-monitoring 能力的边界。

**建议**：
- **强制 "post-condition verification"**：Agent 报告完成任何 mutation 操作（registry update / file edit / job submit）后，下一个 tool call 必须 read 同一资源验证。

---

### F5. [HARNESS / 严重度: 中-高] Registry 状态机与外部进程状态（GPU、训练进程、cron）的多源真相导致反复"state desync"

**证据**：
- M005: deepseek_loop_only_seed42 通过 ssh_execute 直接提交而非 submit_training_job → registry 缺 cron 监控 → startup recovery 误标 failed。
- M007: cron on_failed hook 反复覆盖 registry 状态（手动修复后下一次 cron 巡检又覆盖）。
- M012: full_trace seed456 registry 声明 cuda:1 但命令实际 --gpu 0；M013: 同实验启动 2 个 PID。
- M014: Worker 清理 cuda:0 orphan 误杀 cuda:1 上的 codellama 进程，浪费 0.17 GPU-hr。
- Layer 1 显示 worker 总错误 804（最高），其中 OOM 78 / truncat 459 都和这种竞态有关。

**影响**：
- "Registry 真值" 在 (a) registry.yaml (b) nvidia-smi 实际进程 (c) cron 监控 (d) sentinel 文件 (e) tmux 会话 (f) Agent 报告 之间分散，没有 single source of truth。
- 投入了大量人/机 effort 在维护一致性（grep registry / nvidia-smi / kill 重复进程 / 修复 cron），实际产出的是基础设施工作而不是科研。

**建议**：
- **强制 single source of truth + atomic transition**：所有 GPU 训练必须通过 submit_training_job (M005 prevention)，并且 submit_training_job 内部应封装 cron 注册 + sentinel + GPU 检查 + atomic registry write。
- 取消 cron on_failed hook 对 registry 的自动覆盖（M007）—— 让 cron 只发警报不改 state。

---

### F6. [HARNESS + MODEL / 严重度: 中] 投稿前 24h 的"多用户并发 micromanagement"消耗资源但不影响审稿分数

**证据**：
- 5/25 13:00 → 5/26 04:56 期间，吴俊豪一个人发 30+ 条 figure/字体/间距指令（"3037 数字往左移"、"transition zone 不要和线重叠"、"附录另起一页" 等）。
- 同期曹晓玉（abstract 重写、摘要不要数字堆砌、figure 1 重画）+ 周俊伟（配色统一）+ [运维]（anonymity check、E1 disclosure、研究领域字段）并行下指令。
- Paper Agent 在这 24h 内做了 ~50+ 次 edit_paper_section + 多次 compile + 多次 fig 重画。
- 5/22 → 5/25 的 4 轮 reviewer score 都是 3.0——**所有微调没有让分数变化**。

**影响**：
- ~24h 的密集人/机投入对最终 review 分数贡献 = 0。
- 占用 Paper Agent 全部带宽，期间无法做实质性 writing improvement（例如更深的 related work、更强的 introduction hook）。

**为什么是 HARNESS + MODEL**：HARNESS 角度，缺少"用户指令降权 / 合并 / 排队" 机制——5 个用户的并行指令直接进入 Director 流，没有过滤。MODEL 角度，Director 无法识别 "这些指令对 review 分数无影响" 并 push back。

**建议**：
- Director 在投稿前 48h 应进入 "**writing freeze**" 状态，只接受 ≥critical 优先级的修复，其他指令排队到 rebuttal cycle。

### F7. [HARNESS / 严重度: 中] M009-style "infrastructure bug 被误归因为科研发现" 的反复出现

**证据**：
- M009: DeepSeek VOTA seed42 84.45% 被当成 "训练不稳定 outlier" → 多跑 2 个 seed 仲裁；实际是 evaluate.py 的 max_length=16384 vs 训练 2048 不一致 bug。Paper Agent 已经基于错误归因写了 12 处"训练不稳定"措辞。
- M015: budget curve 分析混用 plan_006 trace-section 截断 (78-81%) 和 Table 12 whole-input tail 截断 (93-97%)，差 13pp，被 Agent 当成"phase transition 不存在"的结论。Reviewer 首轮没发现，第二轮才定位。
- M016: Paper Agent 改稿时把 tail phase transition 归因于 "matching exception traceback length"，与 D115 数据（tail 数据 [ERROR]=0%）直接矛盾——Paper Agent 用了直觉性的常识联想而非数据。

**影响**：
- M009 的 12 处 "训练不稳定" 措辞被写进论文，后续需要回退 → 增加 Paper Agent 工作。
- M015 让 budget curve 整个分析返工。

**为什么是 HARNESS**：这些案例的共同根因是 "缺少 cross-check baseline 数据 → 模型用 plausible explanation 填补 → 错的解释被持久化到论文/decision"。需要的是工具层面的"数据-claim 一致性检查"，而不是依赖 Director 自检。

**建议**：
- 论文中所有数据点应该绑定 registry experiment_id + artifact hash；编译时自动检查论文中的数字是否能在 registry 找到。
- decision (D-编号) 写 hypothesis 时应该有"alternative explanations" 字段强制填写，避免单一因果归因。

### F8. [MODEL / 严重度: 中] "Reviewer 顺从倾向"——Director 系统性低估自己对 reviewer rebuttal 的能力

**证据**：
- Round 10 R2 "task triviality" 质疑 → D116 直接 reframe；
- Round 14 R2-N3 "泛化范围过高" 被 R1 rebut，Director 裁决 R1 成立——这次能 rebut；但 R2-N1 "near-tautological" 从未被 rebut，每次都通过 reframe 回避。
- 用户曹晓玉 5/22 "你确定不需要实验吗" + "都做" 明确给了实验补全的支持，**但 Director 没有用"补 task-spectrum 实验（generation/constrained prediction）来反证 verdict 任务的可比性"** 这样的 task-level 回应，而是补了 gradient masking 这种 mechanism-level 实验。

**影响**：
- 5 次 reframe 都是同维度（mechanism / framing）的局部调整，没有维度突破。
- 论文最终 stuck 在 3.0。

**为什么是 MODEL**：人类 PI 在 5 轮同样的 review 反馈下会判断 "这个 task 选错了"，主动重新设计 task 或加入新的 task。Opus-4.6 在 5 次 reframe 里没有提出这一层级的 zoom-out。

**建议**：
- Director prompt 加入 "Anti-sycophancy" rule：当 reviewer 连续 ≥3 轮指出同一类 fundamental issue 时，强制评估 "reviewer 的 fundamental issue 是否说明 task 本身选错"，并把该评估写入 decision。

### F9. [HARNESS / 严重度: 中] Dream 机制未充分发挥反思价值

**证据**：
- dream_registry.yaml 显示 15 个 dream session，覆盖 5/15 - 5/18 主要决策点（D010-D040）。
- 但 5/19 之后 dream 显著减少（dream_registry 后半段空），刚好 5/19 → 5/22 正是 reframe 密集期，理论上应该是 dream 价值最高的窗口。
- 5/15 08:48 用户首次问 "Dream机制是什么？这篇paper可以开始 Dream 了吗？"——表明 dream 是用户引导才启动，不是自然触发。

**影响**：
- Round 7-15 的 reframe 全靠 Director 临场判断而非 dream sandbox 探索过的方案。
- 5 次 reframe 里至少 2 次（D098 Two-Pathway / D116 "complete traces hurt"）如果有 dream 提前模拟 reviewer 反应，可能不会做。

**建议**：
- Dream 应该有自动触发条件（如 reviewer score 连续 N 轮无改善 → 强制触发 reframe-dream）。

### F10. [HARNESS / 严重度: 低-中] 角色错误率分布反映 trust hierarchy 不合理

**证据**：
| 角色 | session | turn | error | error/turn |
|---|---|---|---|---|
| Director | 158 | 34,155 | 154 | 0.45% |
| Agent | 324 | 49,955 | 488 | 0.98% |
| Reviewer | 109 | 36,007 | 108 | 0.30% |
| Worker | 1,114 | 92,318 | 804 | 0.87% |
| Paper Agent | 14 | 20,815 | 165 | 0.79% |

- Reviewer 错误率最低 (0.30%)，但 Reviewer 在 outage 期间 18 次 ESCALATED_TO_HUMAN（远高于其他）。
- Agent 错误率最高 (0.98%) 但承担 orchestration 职责，对项目运行最关键。

**影响**：
- 错误率最高的 Agent 在最关键的 mutation 路径（registry / GPU 派发 / paper sync）—— 与 M006/M013/M017/M018 累积出现高度一致。
- 错误率最低的 Reviewer 反而最容易因上游问题被 RESET。

**建议**：
- Agent 的 mutation 操作应该过 Director "second confirmation" 而不是直接执行。当前模式下 Agent 既执行又自报，是 single point of failure。

## 6. 元结论

这个项目把一个 borderline-trivial 的实验现象（exception token → verdict label 的高相关）推到 EMNLP Findings 3.0，过程中：

- **科研维度**：经历 5 次 reframe，scope 从原 idea 的 6 dataset × 3 task 缩到 1 task × 4 model × 7 condition；最终论文核心 claim ("complete traces hurt") 与原 idea ("trace SFT helps verdict task") 极性相反，但 Director 把它包装为 "we find the opposite"。底层 novelty 问题（near-tautological）从未被解决，只被回避。
- **系统维度**：完成了 190 实验、67MB artifacts、122 decisions、15 review rounds、9-section paper。但其中 ~58% 的实验不直接进论文，~21% 的总时间花在 Paper Agent 排版/重画；35h reviewer outage 期间整个监督闭环断开；Paper Agent 本地↔远程同步至少 4-5 次出错。
- **人/机维度**：5 个用户 + 1 个运维通道密集介入（181+ 飞书消息）。用户的"补 baseline / scope 扩张"建议技术正确但战略上把论文推向 near-tautological 的雷区。投稿前 24h 的 micromanagement 消耗资源但不影响分数。
- **模型维度**：Director / Agent / Paper Agent 在长程一致性（registry self-report、本地远程 sync、reviewer 反馈 fundamental zoom-out）上展示了 Opus-4.6 当前能力的可识别边界。

**最重要的单一可行动改进**：如果只能做一件事——给 Director 加 "**reviewer 连续 N 轮同类 fundamental issue → 强制 task-level reframe 评估**" 的 anti-sycophancy 元规则。这一条本可避免 5 次同维度 reframe 的局部最优陷阱，可能把这篇论文从 Findings 3.0 推到 Findings 3.5 或更高（或者明智地识别 "verdict task 该换 dataset"）。
