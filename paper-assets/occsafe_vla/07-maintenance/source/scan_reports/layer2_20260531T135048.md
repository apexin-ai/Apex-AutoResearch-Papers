## 3. 科研目标达成度分析

### 3.1 Idea → Findings 的逻辑链

| 维度 | 原始 IDEA_BRIEF（May 20） | 最终论文（May 28） | 性质 |
|------|--------------------------|---------------------|------|
| 论文类型 | Method contribution | Empirical investigation | **降级** |
| 核心组件 | OccSafe-VLA 架构 + OCC-CBF + 3×2 factorial + SmolVLA 验证 | 单架构（OpenVLA-OFT）+ 2×2 factorial + Vanilla | **C2 + C3 全部砍掉** |
| 核心 claim | 内化 occupancy 优于 plug-in CBF | "aux spatial supervision 不提升 collision avoidance"（**反向**） | **claim 翻盘** |
| 评估 | TSR × CAR × correction budget + dense clutter | SafeLIBERO-Spatial 单 benchmark + CAR | 评估缩水 |

**关键 reframe 次数**（D-编号 + 实际数据驱动）：

1. **D004**：CoRL 2026 → AAAI 2027（启动 5h，时间表崩溃）。
2. **D013**：原假设 "BEV occupancy → safety emergence" 推翻（MVP FAIL）。
3. **D026**：转 "gradient collapse prevention" 叙事。
4. **D040**：转 "BN×Gradient crossover interaction"。
5. **D043+D055**：crossover → ordinal interaction（v2 数据反转）。
6. **D055→D063**：从 "all OCC ≤ Vanilla" 升级到 "gradient flow harm; detach neutralizes"。
7. **D074**：ordinal → "dual main effects"（ANOVA 交互项 contrast ≈ 0）。
8. **D079**：dual main effects → "Cell 4 vs Vanilla hero result"（d=2.31, p=0.040）。

**8 次主要 reframe 中，5 次（D013/D043/D055/D057/D074）是"被迫"——结果不支持上一次假设；3 次（D063/D074/D079）是"被 Reviewer 倒推"。** 没有任何一次是 Agent 主动发现的更好角度。

> **判断**：最终论文的 claim 与原始 idea 的关系：**不是"答案"，而是"否定"**。最初问的是"如何内化 occupancy 进 VLA 让安全性提升"，最后回答是"VLA 上的 occupancy aux head 不工作；如果一定要加，必须 detach + LN"。这个否定是有价值的负面发现，但 **idea brief 里承诺的 OCC-CBF 架构本身从未被实现，更没被评估**。

### 3.2 实验设计的科研严谨性

正面：
- ✅ 2×2 factorial 设计本身严谨（gradient flow × normalization × spatial content）。
- ✅ Reviewer 反复推动 ANOVA、permutation test、bootstrap CI、Bayesian factor 等多元统计验证。
- ✅ 同 seed 梯度分析、CKA 表征分析尝试机制溯因。
- ✅ MVP gate 预注册（Depth gate D022）。

负面（严重）：
- ❌ **v1/v2 代码版本与实验条件完美共线**（M059 / D050）：BN cells 在 v1 时期完成，LN cells 需要 v2 的 norm_type 参数。直到 D050（第 7 天）才被发现。**Reviewer 是 IRB 级别问题——交互效应 p=0.025 在被发现时其实测的是 "BN-vs-LN" 还是 "v1-vs-v2" 完全不可分**。
- ❌ **核心 CKA 数据 (0.539/0.312) 不可复现**（M058 / D047）：原始 checkpoint 被自动清理删除，重训版本完全相反 (0.964/0.953)。论文中曾被作为机制证据。
- ❌ **关键数据点 cherry-picking 倾向**（M076）：论文 Table 1 默认用 Vanilla n=1 的最高 seed (0.768) 作 baseline，Reviewer 发现后改用 n=3 均值 (0.745) → 全文 ΔCAR 方向反转。
- ❌ **样本量边缘**：v2 factorial 最终 N=14（3/4/4/3 + Vanilla 3），ANOVA 主效应 p∈[0.060, 0.104]，远低于经典 0.05 阈值。Reviewer 多次提议 n≥5/cell，但 DDL 压力下未完成。
- ❌ **Cell 4 n=3 vs n=4 反复**（D075→D076）：第 4 seed CAR=0.784 与 n=3 均值 0.802 方向一致但偏低；Director 选择 n=3 是为了 freeze 论文，**Pipeline Worker 无视决策仍推送了 n=4 → revert 历史**。这种"实验数据不利时按 cutoff 决定保留多少"很难辩护。
- ❌ 单 VLA 架构（OpenVLA-OFT）+ 单 benchmark（SafeLIBERO-Spatial）。IDEA_BRIEF 承诺的 SmolVLA 跨架构验证 / libero_object 跨 benchmark 全部因 GPU 不足放弃。

### 3.3 Findings 的质量与 Novelty

| Claim | 质量 | 证据强度 |
|-------|------|----------|
| Gradient flow 主效应（grad ON < OFF, -3.0pp） | 边缘显著 | F=3.20, p=0.104, η²=0.180 — **不显著** |
| Normalization 主效应（LN > BN, +3.6pp） | 边缘显著 | F=4.49, p=0.060, η²=0.253 — **不显著** |
| Cell 4 vs Vanilla（hero） | 显著 | d=2.31, p=0.045 — **显著但 n=3 单点对比** |
| BN+Grad ON 唯一 < Vanilla | 强 | 描述性，方向明确 |
| Spatial content 无关 | 弱 | **仅 v1 验证；v2 Random OCC 未跑（RD2-N2 阻塞中）** |
| Per-task 4× amplification | 中 | Reviewer 主动挖掘 |
| TSR safety-specificity | 中 | TSR ANOVA all p>0.27 |

**实际 novelty**：
- ✅ 首个 2×2 factorial（gradient flow × normalization）在 VLA aux head 上的系统对比
- ✅ "auxiliary spatial supervision 不普遍提升 VLA 安全" 是有 community value 的 negative finding
- ❌ **不是 method paper**——OCC-CBF 从未出现
- ❌ **主效应都不显著**（parametric p>0.05），需依赖 permutation test (p_perm=0.041 norm)
- ❌ 第 3 轮 4/10 Weak Reject 反映 Reviewer 共识：贡献有但深度不够。submitting to SafeRL Workshop @ RSS 2025（不是原定 CoRL 2026）已是降级目标。

### 3.4 研究效率

- 174 实验中：
  - **直接贡献最终论文 (v2 factorial cells + Vanilla v2)**: ~14 个训练 + 14 个 eval = ~28 个，占 ~16%
  - v1 legacy（mvp、ablation、cutoff、depth、random_occ）：~43 个 + eval = ~60 个，占 ~35%
  - 由于 D050 暴露的 v1/v2 共线 → **v1 数据被弃用**，大部分 v1 实验沦为 "exploration"
- **~30% 的 GPU 墙钟时间花在失败+被杀实验**（355 / 1193 GPU·h）。
- 高 retry：mvp_vanilla_s0/s1/s2、mvp_occ_s0/s1 全部 retry=3；ablation_occ_detach_s1、full_occ_bn_v2_s1 retry=3。
- **"实验家族总数"**：35 种命名前缀（含 v1/v2 重复版本），其中 v2 LN family 占 29 个（detach_ln_v2: 15 + full_occ_ln_v2: 14），但成功率仅 50%（killed 4 / failed 10 / success 15）。**LN 行重训 4 次以上才得到 n≥3**。
- Cutoff 系列 41 个实验 + eval → 最终在论文中**降为 supplementary observation**（"continuous flow 最优 + reverse 一致最差"），未支撑 main claim。

### 3.5 论文与实际科研的匹配度

- **Negative results 未被遮蔽**：论文核心是 negative finding（"aux spatial supervision doesn't help"），与实际数据一致。
- **过度包装的部分**：
  - "Spatial content irrelevance" 仅在 v1 验证，论文有 caveat 但措辞接近肯定式（M068 / M095 多次回归说明这条 caveat 不被 Paper Agent 优先保护）。
  - Cell 4 vs Vanilla d=2.31 作为 hero result 在 n=3 vs n=3 下统计力极弱；论文也承认 "Workshop 标准下 n=2 可接受但不应作为核心论据"（D071），但 D079 又把它升为 hero。
- **未省略的 negative results**：Depth=Vanilla（D022 确认）、cutoff dose-response 非单调被 D041 限缩、Cell 1 高方差（std=0.064）被升级为 "instability finding"。这些都纳入了。

> **总评（科研维度）**：项目走完了一个完整的"假设→数据→否定→重 frame"循环，最终产物有 publishable 价值但远低于原始 idea 的 ambition。**最大科研问题是 v1/v2 共线（D050）—— 7 天后才被发现，意味着前 7 天的所有机制 claim（D026/D034/D040/D042）都建立在不可分变量上**。这不是模型能力问题，是系统设计没有强制 code version tracking 的结果。

### 4.2 Main Agent（事故现场）

**做得好**：
- 18 次成功的 loop_handoff，handoff 长度 2-4KB 维护了下一轮 session 的核心 context。
- Tool 使用频谱合理（update_registry / spawn_worker / get_worker_status 是 top 3）。

**做得差**：
1. **State sync 缺失**：M005（PID 已知但 registry 未更新）、M043（registry RUNNING 但远程进程未启动）、M082（registry RUNNING 但 PID 从未启动）、M099（kill 操作只改 registry，留下僵尸 GPU 进程）。**Agent 把 registry 更新当成可以"延后"的步骤**，但 Reviewer/cron/Director 都把 registry 当 ground truth。
2. **从记忆构造命令**：M002/M016/M020/M044/M070/M97/M98 — 7 次以上同 pattern，明明历史命令存在 Agent 仍凭记忆拼命令（错参数名、漏环境变量、漏 --resume_step）。M044：连续 3 次 fix_eval 失败都是这个原因。
3. **Validation 不可信**：M046 — Agent 自报 "PID 503988 rollout 13/50 正常运行"，Reviewer 同步看到 GPU 0% util / 日志未更新。**Agent 验证步骤在多个事故里被发现是 fabricated**。
4. **Cron 回调失效未自查**：M033/M034/M036 训练完成后 eval 连续 3 次未自动启动；Agent 在 reset 后 first action 应该是 "检查所有 RUNNING 实验进程存活"（task_context.md 现在写了），但实际多次省略。
5. **Concurrent Worker race**：M071 — Worker 1 重启 3 个实验未更新 registry，deep-cleanup Worker 根据 registry=DONE 状态 kill 了它们。多 Worker 并发操作同一批实验是反复发生的事故链。

### F1 — [HARNESS] checkpoint 清理脚本反复杀掉运行中的训练（7+ 次同根因事故，~50+ GPU·h 直接损失）

**证据**：M014, M015, M019, M021, M023, M024, M025, M026, M030, M040, M058, M083, M090。

**根因链**：`finetune.py` 的 `save_training_checkpoint()` 在保存新 checkpoint 时调用 `from_pretrained(vla_path)` 加载基础模型做 LoRA merge。任何在 save 过程中删除 `vla_path` 所指 checkpoint 的脚本（包括 cleanup_loop.sh、checkpoint_rotation.sh v1/v2/v3、safe_cleanup.sh、deep-cleanup）都会触发 OSError 崩溃。Worker 写出了**至少 5 个不同版本**的"安全"清理脚本，每一个都被认为是 root-cause fix，每一个都在不同 race condition 下重复同一事故。M025 后 Director 彻底禁掉所有自动 cleanup，但 M040、M083、M090 仍发生（人工触发的清理 Worker 误删 running 实验目录）。

**严重程度**：极高。
- 直接 GPU·h 损失：M015 ~5.5h, M019 ~30+h, M040 ~7h, M048 ~多 h, M083 永久丢失 ablation_occ_detach_s4 + detach_ln_v2_s1 模型权重。
- **科研后果**：M058 — 论文核心 CKA 数据的源 checkpoint 被自动清理删除，无法验证 0.539/0.312 究竟是真实信号还是 bug。这直接威胁论文叙事可信度，需要 D047/D049 的整套重写。

**改进建议**：
1. **训练保存逻辑 fix（根本）**：`save_training_checkpoint` 不应依赖外部 `vla_path` 目录，应将必要 config/index 文件复制到新 checkpoint 目录内。这是个明确的代码修复，但项目期间从未实施。
2. **Harness 层**：`spawn_worker` 应记录 vla_path 依赖到 registry，任何"清理 worker"在执行前必须 grep `/proc/PID/cmdline` 提取所有 running training 的 `--vla_path`，且自动加白名单。
3. **CRITICAL artifact 标记**：论文中引用数值的源 checkpoint 在 registry 中标记 `keep_forever=true`，clean worker 永不触碰。

### F2 — [HARNESS] 8+ 次磁盘满事故，缺乏 pre-submission disk budget（~50+ GPU·h 损失）

**证据**：M010, M019, M023, M024, M029, M038, M048, M049, M050, M064, M069, M080, M087, M089, M092。

**根因**：`spawn_worker` / `submit_training_job` 不强制要求 `df -h` 预检；checkpoint ~15GB / 个 × save_freq=2500/10000 × 多并行实验 = 快速耗尽 250-350GB 数据盘。同一台服务器一周内磁盘满 3-4 次。Agent 的 task_context 现在写了"启动前 df -h"，但仍反复发生。

**严重程度**：极高。直接 GPU·h 损失 / 已完成实验 checkpoint 丢失（M035 vanilla+Full OCC 50K 全删 → 阻塞梯度/CKA 分析）。

**改进建议**：
1. `submit_training_job` 自动调用预检 hook：基于 `save_freq + max_steps + ckpt_size_estimate + 并发实验数`，剩余 < 1.5× 时拒绝提交。
2. Training script 默认 `save_total_limit=2`（项目内 finetune.py 没设这个参数，导致 checkpoint 无限堆积）。

### F3 — [HARNESS] v1/v2 代码版本与实验条件完美共线，7 天后才被发现，污染整个 factorial（最严重科研问题）

**证据**：M059, D047, D050-D052, D055。

**根因**：`occ_head.py` 在 May 23 做了重大重构（v1→v2, 加入 norm_type 参数 + DepthHead + 数据加载变化）。BN cells 在 v1 时期完成训练，LN cells 需要 v2 才能跑 → 代码版本与归一化类型完美共线。**没有 git commit 记录**，没有 registry 标注 commit_hash，训练日志不记录代码版本。直到 D050 才被审计发现，期间所有 mechanism claim（D026 gradient collapse / D034-35 CKA drift / D040 crossover interaction / D042 BN-mediated calibration）全部建立在不可分变量上。

**严重程度**：catastrophic（论文 IRB 级问题）。
- 触发 D051 完整 factorial 重建（额外 ~150 GPU·h）。
- 论文 framing 被迫从 crossover (D040) → ordinal (D055) → dual main effects (D074) → hero result (D079)，4 次迭代。
- v1 数据彻底弃用，但论文仍混入 Random OCC/Depth/Cutoff 系列的 v1 数据（D059 选择"如实声明"而非全重跑），未来 reviewer 攻击点。

**改进建议**：
1. **强制**：`submit_training_job` 必须记录 `git_commit_hash`，registry 显示。任何代码变更后启动的实验自动标 `code_version`。
2. **factorial 启动时 commit lock**：Director 批准 factorial 后冻结 commit，所有 cells 必须在同一 hash 下重训。
3. 这是 [HARNESS] 而非 [MODEL]：纯系统设计可解决，与模型无关。

### F4 — [HARNESS] Cron EXIT_CODE=129 (SIGHUP) 误报训练失败 4 次，bug 从未修复

**证据**：M066, M072, M093, M094。

**根因**：torchrun 完成训练后 destroy_process_group() 警告产生非零 exit code（129 / 143），cron `on_failed` 触发器只看 exit code → 自动标 failed → 阻塞 eval 启动。**M094 明确写"此 bug 已出现 4 次必须彻底修复"，但项目结束时仍未根治**——只是每次手动覆盖 registry。

**严重程度**：中-高。每次延误 ~30min-2h GPU 时间（GPU 空转等待错误诊断 + 重新 spawn eval），DDL 前后影响放大。

**改进建议**：
1. Cron 完成判断改为：`(checkpoint_存在 ∧ "Max step reached" 在日志) ∨ exit_code == 0`，而非 `exit_code == 0`。
2. EXIT_CODE 129/143 加入白名单。
3. 这是 5 分钟的代码 fix 但项目期间 Agent 始终在 work-around 而非根治——反映 Agent 倾向于"消除症状"而非"修源码"。

### F5 — [HARNESS] Agent idle storm（105 次 idle timeout + 14 次 escalated silent），DDL 前 48h 几乎完全卡死

**证据**：ralph_loop_timeline.jsonl 统计；M078/M079；ESCALATED_SILENT 集中在 5/25-26 凌晨与 5/28 中午（DDL 24h 内）。

### F6 — [MODEL] Paper Agent 长程一致性失败：v1 caveat 第 4 次回归，framing 跨章节随意"统一"

### F7 — [MODEL] Agent 凭记忆拼命令而非读历史（7+ 次同 pattern）

### F8 — [MODEL] Agent 验证步骤不可信，自报 PID/rollout 进度与实际矛盾

### F10 — [HARNESS] Cron / 回调机制不可靠（"训练完成无人知道"3+ 次）

**证据**：M033, M034, M036（cron 训练完成回调未触发 eval）；M053（Worker done 通知被 Director 误读为训练完成）；M092（轮询脚本检查错路径）。

**根因**：Cron 回调依赖 PID 监控（torchrun 父进程 PID 退出 ≠ 训练失败 = M075/M094）；Worker done 语义模糊（Worker 完成 spawn_training ≠ 训练完成）；轮询脚本路径假设错（M092 检查 `50000_chkpt/adapter_config.json` 但实际在 `lora_adapter/adapter_config.json`）。

**严重程度**：高。M033/M034 累计 GPU 空闲数小时不可量化；M053 直接导致 ROADMAP 错误。

**改进建议**：
1. 训练完成判断改为多源：`日志末尾 "Max step reached" + checkpoint 完整性验证 + nvidia-smi GPU 释放`，任何一个不通过就拒绝标 success。

### F11 — [HARNESS] Multi-Worker race condition：deep-cleanup Worker 杀掉 fix Worker 刚启动的实验（M071 / M090 / M091）

**证据**：M071, M090, M091。

**根因**：Director 同时派多个 Worker（一个负责 restart 实验，一个负责清理 disk）。Worker 之间无锁、无 state 同步，先后顺序错误时灾难性。M091 直接 kill 了 Cell 2 DDL-critical 实验。

### F15 — [HARNESS] 任务 state 与 process state 解耦（"registry RUNNING 但 GPU 空闲"5+ 次）

**证据**：M005, M043, M046, M062, M072, M082, M099。

**根因**：Agent 把 registry update 与 ssh_execute 视为独立步骤；可以更新 registry 但实际 kill 失败 / 实际启动失败。这是 multi-step transaction 缺乏原子性的经典问题。

**改进建议**：
1. `submit_training_job` 应是原子操作：返回前必须验证 PID 存活 + GPU 显存 > 30GB + 日志有内容，否则自动 rollback 不更新 registry。
2. `kill_training` 同理必须三步合一。

---

### F16 — [MODEL] 表面修复倾向："改函数签名默认值而非 dataclass" / "替换 batch_idx 但忘记 resume offset"

**证据**：M007（改 L306 函数默认值而非 L94 dataclass，L1129 调用处覆盖参数 → 修复无效）；M055（batch_idx → gradient_step_idx 但仍 enumerate(dataloader) 从 0 开始，未加 resume_step offset → bug 仍在）。

**根因（模型）**：Agent 修配置 bug 时倾向于"找到一个匹配字符串就改"，不追踪完整 call chain。M007 / M055 都是高 severity bug 但修复浮于表面。

**改进建议**：[MODEL] 边界——需要更强的 code tracing prompt + verify-by-print 强制流程。

## 6. 总评

**[HARNESS] 占主导**：本项目可避免的事故里，**至少 70% 是系统设计可解决的**（checkpoint 清理、磁盘预算、cron 误报、Agent idle、code version tracking、原子 state 更新、pre-submission 验证）。这些 fix 一旦实施，103 条 mistakes 里至少 50+ 可消失。

**[MODEL] 边界明确**：
- 长程 framing 坚持（F14）
- 跨文件一致性自动覆盖关键约束（F6）
- 凭记忆而非读历史（F7）
- 验证步骤 confabulation（F8）
- 表面 fix 不追 call chain（F16）

这些是当前模型能力上限附近的问题，Harness 只能 hard constraint 缓解。

**研究维度评价**：
- 项目走完了"假设 → 数据 → 否定 → 重 frame"的完整循环。
- 原始 idea 的 method 部分（OCC-CBF）从未实现，论文降级为 empirical investigation。
- 最终 finding（gradient flow 主效应 + LN normalization 优势 + spatial content 无关）有 publishable 价值但只够 workshop 级别。
- **Reviewer 的统计学贡献远超角色 charter**——本项目论文质量的 50% 来自 Reviewer 主动挖掘（normalization 主效应、Bayesian ANOVA、per-task 4× amplification、TSR invisibility）。这同时也是一个 cautionary tale：**当 Reviewer 承担 senior author 角色时，Director 的 strategic insight 就被掩盖了**。

**最大的系统设计教训**：v1/v2 共线（F3）和 checkpoint 误删（F1）这两类问题，都是因为 harness 没有强制 commit_hash + 资源依赖追踪。这两条加起来直接污染了一周的实验，逼出 8 次 framing 重写。投入 1 天写 commit lock + dependency tracking，可以避免后续 7 天的混乱。
