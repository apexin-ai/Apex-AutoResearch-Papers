## Core Problem

Repository-level bug repair requires selecting relevant context from large codebases. Existing context selectors fall into three paradigms, each with fundamental limitations: (1) Neural selectors like SWE-Pruner train on LLM-generated labels that are coupled to a specific teacher model's biases and selection patterns—labels are stochastic, non-reproducible, and encode the teacher's blind spots. (2) Retrieve-and-rerank methods like SweRank (ICLR 2026) achieve strong text-based localization but miss structural dependencies—lexically similar but structurally unrelated code becomes a false positive. (3) Graph-guided agents like LocAgent, RANGER, and CodexGraph capture structural edges (import/call/inheritance/USES) but omit fine-grained data-flow (def-use) edges, and operate purely at inference time without using structural signals to improve model training; ARISE uses intra-procedural def-use but only at runtime via tool calls, not as distilled knowledge, and explicitly does not cross call boundaries. On SWE-bench Pro (where top SEAL-standardized scores range from ~42-59%—GPT-5.4 at 59.1%, Claude Opus 4.6 at 51.9%—leaving 41-58pp improvement headroom, and context selection accounts for 4-10pp swings), context quality remains a key differentiator with substantial room for improvement. Can we build a context selector that leverages inter-procedural data-flow signals for structurally-grounded, interpretable, and model-independent selections—using deterministic program analysis rather than stochastic LLM judgments?

## Opportunity / Why Now

SWE-Pruner (arXiv:2601.16746) demonstrated a 0.6B neural skimmer can reduce tokens 23-54% with <1pp degradation, but its supervision comes from Qwen3-Coder-30B-A3B-Instruct (an MoE model with 3.3B active parameters)—while inference is cheap (~$10-35 to label 61K samples), the labels are coupled to that model's biases, non-reproducible across runs, and provide no interpretable rationale for selections. LocAgent (ACL 2025) showed graph-guided localization achieves 92.7% file-level accuracy using import/invocation/inheritance edges with fine-tuned Qwen2.5-32B, but omits data-flow edges. SweRank (ICLR 2026) achieves SOTA retrieve-and-rerank localization but is purely text-based. RANGER (arXiv:2509.25257) builds comprehensive repository knowledge graphs with MCTS-guided exploration and bi-encoder + cross-encoder cascade, achieving strong results on RepoBench (0.5471 Accuracy@5) and CrossCodeEval—but uses only structural/syntactic edges (CONTAINS, HAS_METHOD, INHERITS, USES) without data-flow, and is purely an inference-time system with no model training. CodexGraph (NAACL 2025) bridges LLMs and code repos via Neo4j code property graphs with Cypher queries (22.96% Pass@1 on SWE-bench Lite)—but again is purely inference-time with no data-flow edges, and the paper itself acknowledges room for 'schema completeness' improvements. ARISE (arXiv:2605.03117) confirmed data-flow slicing yields +17pp Function Recall@1, but (a) uses only Python's ast module for intra-procedural analysis (explicitly does not cross call boundaries), and (b) keeps analysis as runtime tool calls adding latency per agent step. SWE-Fixer (ACL Findings 2025) combines BM25 with a fine-tuned 7B retriever for coarse-to-fine file retrieval but uses no structural program analysis features. Sliceformer (arXiv:2604.26961) validated that data-flow knowledge transfers to neural models with 22% ExactMatch gains on slicing tasks. The opportunity: no existing work (a) uses inter-procedural def-use analysis for repair context selection, (b) distills data-flow signals into a fast retrieval model via contrastive training, or (c) exploits structural connectivity for contrastive hard negative mining. ARISE's intra-procedural limitation, RANGER/CodexGraph's inference-only graph use without data-flow edges, and SweRank's text-only approach leave a clear gap for inter-procedural data-flow-aware retrieval with structural training signal.

## Landscape (SOTA & Limitations)

**Neural context selectors**: SWE-Pruner trains a 0.6B skimmer on 61K samples labeled by Qwen3-Coder-30B-A3B-Instruct (an MoE model with 3.3B active parameters per forward pass, costing ~$10-35 for labeling at $0.07-0.19/1M input tokens), achieving <1pp degradation on SWE-bench Verified (70.6%->70.2%)—though SWE-bench Verified is known contaminated (OpenAI, Feb 2026). Squeez (arXiv:2604.04979) fine-tunes Qwen 3.5 2B for task-conditioned tool-output pruning (0.86 recall, 92% token removal) but targets tool outputs, not repository context. LongCodeZip (ASE 2025) achieves 5.6x compression via perplexity-based ranking, training-free but code-agnostic. **Retrieve-and-rerank approaches**: SweRank (ICLR 2026, arXiv:2505.07849) achieves SOTA issue localization via SweRankEmbed (bi-encoder retriever) + SweRankLLM (listwise LLM reranker), trained on the SweLoc dataset—purely text-based with no structural signals. SweRank+ (arXiv:2512.20482) extends to multilingual multi-turn ranking with 155K training instances. SWE-Fixer (ACL Findings 2025) combines BM25 with a fine-tuned 7B retriever (SWE-Fixer-Retriever-7B) for coarse-to-fine file retrieval, achieving 24.7%/32.8% on SWE-bench Lite/Verified with P2P filtering—architecturally the closest prior work to our retrieval fusion, but uses learned embeddings without structural program analysis features. **Graph-guided approaches**: LocAgent (ACL 2025, arXiv:2503.09089) parses codebases into directed heterogeneous graphs with import/invocation/inheritance edges, achieving 92.7% file-level accuracy with fine-tuned Qwen2.5-32B—but omits data-flow (def-use) edges and requires a 32B model at inference. RANGER (arXiv:2509.25257) constructs repository knowledge graphs with six node types (Module, Class, Function, Method, Field, GlobalVariable) and structural edges (CONTAINS, HAS_METHOD, HAS_FIELD, INHERITS, USES), employing MCTS-guided graph exploration with a bi-encoder (mxbai-embed-large-v1, 335M) + cross-encoder (bge-reranker-v2-m3, 568M) cascade—achieves 0.5471 Accuracy@5 on RepoBench with Qwen-3-8B embeddings, but uses no data-flow edges and is purely an inference-time system with no model training using structural signals. CodexGraph (NAACL 2025, arXiv:2408.03910) bridges LLMs and code repositories via Neo4j code property graphs with Cypher queries, using a similar structural schema (MODULE, CLASS, METHOD, FUNCTION, FIELD, GLOBAL_VARIABLE nodes; CONTAINS, HAS_METHOD, HAS_FIELD, INHERITS, USES edges)—achieves 22.96% Pass@1 on SWE-bench Lite with GPT-4o, but is purely inference-time with no model training, no data-flow edges, and the paper itself acknowledges room for improvement in 'schema completeness' including 'adding edges related to function calls.' KGCompass (arXiv:2503.21710) constructs repository knowledge graphs (58.3% repair) but with heavy construction overhead. GraphCoder (ASE 2024) uses code context graphs with control-flow and data-dependence for coarse-to-fine retrieval in code completion—related but targets completion, not repair context selection. SaraCoder (ICLR 2026) orchestrates semantic and structural cues for code completion with a graph-based structural similarity metric—demonstrates the value of structural signals in retrieval but does not address repair or use def-use data-flow. **Data-flow-specific approaches**: ARISE (arXiv:2605.03117) augments SWE-agent with statement-level def-use edges via Python's ast module, gaining +17pp Function Recall@1 and +4.7pp Pass@1 (22.0% on SWE-bench Lite with Qwen2.5-Coder-32B)—but is limited to intra-procedural analysis (explicitly does not cross call boundaries), keeps analysis as runtime tool calls, and requires a 32B model at inference. LLMxCPG (USENIX Security 2025) uses Code Property Graphs for vulnerability detection (67-91% code reduction, 15-40% F1 gain) but targets security, not repair context. Sliceformer (arXiv:2604.26961) distills DFG knowledge into CodeT5+ for slicing tasks via dataflow-aware pretraining objectives, validating structural knowledge transfer but not addressing repair. **Contrastive learning for code**: CoCoHaNeRe (TOSEM 2025) demonstrates that hard negative mining significantly improves contrastive code search (+7-11% MRR over baselines), but uses random or embedding-distance-based negatives without structural awareness. No existing work uses program-analysis-derived structural connectivity to mine hard negatives. **Compression paradigms**: An empirical study (arXiv:2604.13725) shows continuous latent vector compression surpasses full-context by up to 28.3% BLEU at 4x compression. **Benchmarks**: SWE-bench Pro (Scale AI, 1865 tasks total, 731 public) is the recommended hard benchmark—top SEAL-standardized scores: GPT-5.4 (xHigh) 59.1%, Claude Opus 4.6 (thinking) 51.9%, Gemini 3.1 Pro 46.1%; custom scaffolding goes higher (Claude Mythos Preview 77.8%). The 41-58pp gap between SEAL scores and perfect resolution means context selection has proportionally large impact—unlike near-saturated SWE-bench Verified where SWE-Pruner's <1pp degradation suggests diminishing returns. SWE-bench Lite (300 instances) remains widely used. RepoBench-R (ICLR 2024) directly evaluates cross-file context retrieval. **Gap**: No existing work combines inter-procedural data-flow analysis with contrastive hard negative mining for repair context retrieval. ARISE is intra-procedural only; SweRank and SWE-Fixer are text-only; LocAgent uses coarser structural edges without def-use; RANGER and CodexGraph use structural graphs at inference only, not for training; CoCoHaNeRe shows hard negatives work for code search but without structural awareness. The fusion of inter-procedural data-flow features with lexical retrieval via data-flow-aware contrastive learning is unexplored.

## Proposed Approach

We propose StructFuse, a two-stage context retrieval system that combines inter-procedural data-flow analysis with a novel data-flow-aware contrastive learning objective for repository-level code repair context selection.

**Stage 1: Scope-Bounded Inter-Procedural Data-Flow Extraction (Days 1-3).** For ~5K SWE-smith training instances, we extract inter-procedural data-flow features using a two-phase CodeQL strategy designed to prevent query-evaluation blowups. **Phase 1a (call-graph pre-computation):** For each instance, we first run a lightweight CodeQL query to extract the call graph and identify all functions within 2 call-graph hops of the buggy function. This is fast (seconds per repo) because call-graph queries are relational joins, not data-flow tracking. **Phase 1b (scope-bounded data-flow query):** We then configure CodeQL's inter-procedural data-flow API with sources restricted to parameters and return values of only the functions identified in Phase 1a (within 2 call-graph hops), and sinks restricted to variable reads within those same functions. This bounds the analysis scope *before* query evaluation begins, preventing the Cartesian-product blowup that occurs with broad 'all parameters as sources' definitions—the reviewer correctly identified that post-hoc graph-distance filtering does not prevent evaluation-time blowups. We enforce strict resource limits: --timeout=300s and --ram=8192 per repo query. **Graceful degradation:** For repos where CodeQL times out (>300s) or produces insufficient coverage (<5 reachable files from bug location), we fall back to Beniget for intra-file def-use chains and record a binary label-source indicator (inter_procedural=True/False) for each instance. We budget Day 1 specifically for CodeQL query development and validation on 10 pilot repos—testing query precision, recall against gold patches, extraction throughput, and critically: timeout rates and memory consumption. We report three pilot statistics before scaling: (a) mean/max query time per repo, (b) fraction of repos that timeout, (c) average files reachable within 2 call-graph hops + data-flow from bug location. If >30% of repos timeout, we tighten to 1 call-graph hop before scaling. For each candidate file/function, we compute: (a) shortest data-flow path distance to the buggy location, (b) number of distinct data-flow paths, (c) dependency type (inter-procedural def-use, call-graph, import), (d) label-source indicator (CodeQL inter-procedural vs. Beniget intra-procedural). We also extract lexical features (BM25 scores, SweRankEmbed similarity) and structural metadata (git co-change frequency, import distance).

**Stage 2: Data-Flow-Aware Contrastive Retrieval Training (Days 4-6).** This is the core methodological contribution. We train a Qwen2.5-Coder-3B bi-encoder retriever with a two-component objective:

(a) *Data-flow-aware hard negative mining*: For each training instance, hard negatives are files that are lexically similar to the bug-relevant files (high BM25/embedding similarity) but structurally disconnected (no data-flow path within the scope-bounded analysis from the buggy location). This is inspired by CoCoHaNeRe's (TOSEM 2025) demonstration that hard negatives dramatically improve code search, but we replace their embedding-distance-based mining with program-analysis-derived structural connectivity—a fundamentally different and more principled signal. **Theoretical justification:** Embedding-distance-based hard negatives (as in CoCoHaNeRe) are partly redundant with the model's own learned similarity: the contrastive encoder already computes embedding similarity, so negatives selected by embedding distance provide gradient signal along dimensions the model has already partially learned to separate. In contrast, structurally disconnected negatives provide an *orthogonal* learning signal—the model cannot derive inter-procedural data-flow connectivity from lexical features alone, so these negatives force the model to internalize a structural relevance concept that is inaccessible through text-based training. In information-theoretic terms, this increases the effective diversity of the negative set in the InfoNCE objective, tightening the mutual information bound between queries and truly relevant code.

(b) *Structure-conditioned contrastive loss*: We use an InfoNCE-style loss where positive pairs are (issue description, data-flow-connected code) and negatives include both random negatives and the structurally-mined hard negatives above. We weight the contrastive loss by data-flow path strength: code reachable via short, direct def-use chains receives higher positive weight than code connected only via long transitive paths. This encodes the inductive bias that direct data-flow connections are stronger relevance signals than transitive ones.

(c) *Label-source-aware training*: To address heterogeneity from the Beniget fallback, we include the binary label-source indicator (inter-procedural vs. intra-procedural) as an explicit input feature to the fusion head. We weight instances with inter-procedural labels slightly higher (1.2x) in the contrastive loss, reflecting higher label quality. We include a dedicated ablation: training with vs. without Beniget-only instances, and with vs. without the label-source indicator.

(d) *Multi-signal fusion head*: On top of the contrastive encoder, a lightweight MLP fusion head combines the learned embedding similarity with explicit features (data-flow distance, BM25 score, co-change frequency, label-source indicator) for final ranking. This allows the model to leverage both learned representations and interpretable structural features.

Training takes ~3-5 hours per run on a single H100. We run 8 ablation configurations: (i) contrastive with data-flow hard negatives, (ii) contrastive with random negatives only, (iii) contrastive with embedding-distance hard negatives (CoCoHaNeRe-style, as direct comparison), (iv) standard cross-entropy SFT (as in SWE-Pruner's paradigm), (v) full fusion with MLP head, (vi) inter-procedural features only vs. intra-procedural only (testing whether crossing call boundaries matters), (vii) data-flow features only vs. lexical only, (viii) with vs. without Beniget-only instances + label-source indicator.

**Stage 3: Evaluation (Days 7-11).** At inference, StructFuse operates as a two-stage cascade: (1) coarse file selection via BM25 + data-flow reachability (retain files within scope-bounded data-flow analysis OR top-30 BM25), then (2) fine-grained function ranking via the trained 3B contrastive model. This cascade adds architectural novelty over flat ranking approaches like SweRank while being directly comparable to SWE-Fixer's coarse-to-fine paradigm—with the key difference that our coarse stage uses structural reachability, not just BM25. Unlike RANGER and CodexGraph, which use graphs only at inference time, StructFuse uses structural signals during training to produce a model that has internalized data-flow relevance patterns.

**Primary evaluation** (budget-safe): (a) SWE-bench Lite (300 instances, full)—the most widely compared benchmark with established baselines including ARISE (22.0% Pass@1). We estimate ~5-12min per instance with Qwen3.6-27B on H100 using vLLM serving under a 50-turn agent budget (consistent with SWE-agent's recommended cost-conservative configuration of $1/instance and 50-turn limit), yielding ~25-60h total. (b) RepoBench-R (cross-file retrieval evaluation, no LLM needed, ~15h).

**Secondary evaluation** (if timeline permits): SWE-bench Pro (300-instance stratified sample of 731 public instances, ~25-60h). This provides signal on harder tasks where the 41-58pp SEAL gap means context selection has proportionally larger impact.

Metrics: localization recall@k (file and function level), end-to-end Pass@1 repair rate, token efficiency, and a new metric: *structural precision*—what fraction of selected files are reachable via data-flow from the actual fix. End-to-end evaluation uses Qwen3.6-27B exclusively (open-weight, no API costs). We compare against: (i) SweRank/SweRankEmbed (ICLR 2026, SOTA text-based retrieval), (ii) SWE-Pruner (LLM-labeled selector), (iii) SWE-Fixer-Retriever (BM25 + neural, ACL Findings 2025), (iv) BM25 baseline, (v) ARISE's graph tools (intra-procedural def-use, 22.0% on SWE-bench Lite), (vi) no-pruning full-context.

**Improvement ceiling analysis:** We explicitly address expected improvement magnitude. On SWE-bench Verified, SWE-Pruner's <1pp degradation suggests text-based context selection is near-sufficient for the remaining solvable instances—but this is a ceiling effect on a near-saturated benchmark. On SWE-bench Lite and Pro, where ARISE achieves only 22.0% and SEAL scores plateau at 42-59%, the headroom is 41-78pp. We hypothesize structural signals help precisely in cases where text-based retrieval fails: bugs caused by data-flow through indirect dependencies (e.g., a function modifies a shared data structure consumed 2 call-graph hops away, with no lexical overlap between the modifier and consumer). We include a qualitative failure analysis of 50 SWE-Pruner/SweRank failures on SWE-bench Lite, categorizing failures by whether data-flow analysis would have identified the correct context. We frame the primary contribution as the *training methodology* (data-flow-aware contrastive hard negatives)—generalizable to code search, vulnerability detection, and other code intelligence tasks—not just absolute improvement on one benchmark.

**Stage 4: Writing (Days 11-15).** The paper presents four contributions: (1) *Methodological*: data-flow-aware contrastive hard negative mining—using program analysis to generate training negatives that are structurally disconnected from the bug despite lexical similarity, providing an orthogonal learning signal that embedding-distance negatives cannot offer. (2) *Technical*: scope-bounded inter-procedural data-flow extraction via two-phase CodeQL queries (call-graph pre-computation then bounded data-flow), with graceful degradation and label-source indicators for heterogeneous extraction quality. (3) *Empirical*: demonstration that inter-procedural def-use edges (crossing call boundaries) provide gains beyond ARISE's intra-procedural analysis, LocAgent's import/call/inheritance edges, and RANGER/CodexGraph's inference-only structural graphs, with the contrastive objective outperforming standard SFT on the same data. (4) *Practical*: a model-independent pipeline (CodeQL to contrastive training to 3B retriever) with deterministic, reproducible labels, interpretable selections with traceable data-flow paths, and zero marginal cost when scaling to new repositories (only CodeQL extraction needed, no LLM inference).
