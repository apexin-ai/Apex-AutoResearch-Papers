# §4 Experimental Setup

## §4.1 Dataset

We construct our training corpus from SWE-smith \cite{yang2025swesmith}, a large-scale dataset of synthetic Python bug-fix instances generated by applying program mutations to real-world GitHub repositories. The full SWE-smith collection provides 50,869 instances across 131 unique (repository, commit) pairs. After excluding 6,696 instances from 8 repositories that failed clone or checkout, 44,173 instances across 123 repositories remain.

We run the StructFuse extraction pipeline (§3.2) on all 44,173 instances. The extraction pipeline proceeds as follows:

| Stage | Instances | Notes |
|-------|-----------|-------|
| SWE-smith (raw) | 50,869 | 131 (repo, commit) pairs |
| After clone/checkout filtering | 44,173 | 6,696 dropped from 8 failed repos |
| Successful extraction | 15,897 (36.0%) | 15,133 via CodeQL; 764 via beniget fallback |
| Failed extraction | 28,276 (64.0%) | Buggy file path resolution failures during batch processing |
| Usable training instances | 14,288 | Require $\geq$1 resolvable positive file |

Extraction succeeds for 15,897 instances (36.0% of 44,173): 15,133 via CodeQL inter-procedural dataflow analysis and 764 via beniget fallback. The remaining 28,276 instances fail due to buggy file path resolution errors during batch extraction—a runtime engineering limitation rather than a method constraint, as manual spot-checks confirm the source files exist in the repository checkouts [Source: D022]. Of the 15,897 successfully extracted instances, 14,288 yield at least one resolvable positive file (a structurally connected file distinct from the query file that exists in the repository checkout). The remaining 1,609 instances have successful extraction but no usable positive pairs after file resolution, and are excluded from training [Source: m1_extraction registry, plan006_full_scalability.json, build_m1_training_data.py].

For each random seed, we perform a per-repository stratified split to produce training and validation partitions. The per-seed split ensures that no repository appears exclusively in one partition, preserving the distribution of repository sizes and structural properties. Exact split sizes:

| Seed | Train | Val | Total |
|------|-------|-----|-------|
| 42 | 11,308 | 2,980 | 14,288 |
| 43 | 11,236 | 3,052 | 14,288 |
| 44 | 11,264 | 3,024 | 14,288 |

[Source: plan_018 registry, confirmed identical across all four strategies (random, embedding, dataflow, BM25)]

## §4.2 Models

We select two decoder-only pretrained code models with distinct pretraining regimes and representation geometries, enabling us to study how encoder properties mediate the effectiveness of different negative mining strategies.

**Qwen2.5-Coder-3B** \cite{hui2024qwen25coder} is trained primarily with Fill-in-the-Middle (FIM) on a curated multilingual code corpus. It exhibits a near-saturated pretrained representation space: mean positive cosine similarity of 0.986 and mean margin (pos_sim − neg_sim) of only 0.074 with random negatives at 2,048-token context [Source: neg_difficulty_analysis registry, qwen_2048]. This saturation—where nearly all file pairs receive high similarity scores—makes the baseline representation space challenging for contrastive learning and provides a stress test for negative mining strategies.

**StarCoder2-3B** \cite{li2023starcoder} uses a multi-task pretraining objective including FIM on The Stack v2. It maintains healthy representation separation: mean positive cosine similarity of 0.799 and a margin of 0.194 with random negatives—2.6× larger than Qwen's [Source: neg_difficulty_analysis registry, starcoder_2048]. This well-separated space allows us to contrast the behavior of mining strategies under fundamentally different geometric conditions.

The two encoders' divergent pretraining corpora and representation geometries provide a meaningful comparison axis: if a strategy improves both encoders, the benefit is likely encoder-agnostic; if it shows differential effects, the interaction may reveal how representation geometry mediates strategy effectiveness.

## §4.3 Training Configuration

All hyperparameters are shared across strategies and encoders unless otherwise noted. The configuration was fixed before the full multi-seed experiment based on pilot runs.

| Parameter | Value |
|-----------|-------|
| Optimizer | AdamW |
| Learning rate | $2 \times 10^{-5}$ |
| LR schedule | Cosine annealing with linear warmup |
| Warmup ratio | 0.1 |
| Weight decay | 0.01 |
| Gradient clipping | Max norm 1.0 |
| Batch size | 8 |
| Negatives per query ($K$) | 7 |
| Max sequence length | 2,048 tokens |
| Temperature ($\tau$, initial) | 0.07 (learnable) |
| LoRA rank ($r$) | 16 |
| LoRA scaling ($\alpha$) | 32 |
| LoRA dropout | 0.05 |
| LoRA target modules | $W_q$, $W_v$ (all attention layers) |
| Projection dimension | 256 |
| Gradient checkpointing | Enabled |
| Evaluation interval | Every 500 steps |

[Source: m2_full_qwen registry spec and notes]

**Epoch schedule.** Seed 42 trains for 3 epochs without early stopping to provide a complete overfitting curve. Seeds 43 and 44 train for 2 epochs with early stopping (patience = 2 evaluation cycles based on validation loss). This asymmetric design was adopted after observing consistent overfitting past epoch 1 in the seed 42 exploratory run [Source: D026 decision].

**Checkpoint selection.** We maintain dual checkpoints: $\theta^*_{\text{loss}}$ (minimum validation loss) and $\theta^*_{\text{R@1}}$ (maximum validation Recall@1). Primary results use $\theta^*_{\text{R@1}}$; both are reported for metric-loss disagreement analysis [Source: D036 decision].

**Seeds.** 42, 43, 44. The core experiment consists of 3 strategies × 3 seeds × 2 encoders = 18 runs. BM25-mined negatives are evaluated as a supplementary comparison (additional 2 encoders × 3 seeds = 6 runs) [Source: plan_018 registry].

**Hardware.** All experiments are conducted on a single node with 2× NVIDIA RTX PRO 6000 (96 GB VRAM each). Qwen and StarCoder training chains run on separate GPUs (cuda:0 and cuda:1) in parallel. Each individual run (single strategy, single seed, single encoder) requires approximately 5–7 hours. The core 18-run matrix requires approximately 120 GPU-hours [Source: m2_full_qwen and m2_full_starcoder registries].

## §4.4 Evaluation Metrics

**Retrieval metrics.** We report Recall@$k$ for $k \in \{1, 5, 10\}$, computed over a candidate pool of size 50 (1 positive + 49 negatives sampled per evaluation query). Recall@1 serves as the primary metric for checkpoint selection and strategy comparison. We also report validation loss (InfoNCE) as a secondary training diagnostic.

**Statistical reporting.** All comparisons report:

- **Aggregate**: mean ± standard deviation across 3 seeds per condition.
- **Confidence intervals**: bootstrap 95% CIs for pairwise strategy comparisons (embedding vs. random, dataflow vs. random, dataflow vs. embedding).
- **Effect size**: Cohen's $d$ for key comparisons, providing a standardized measure of practical significance independent of sample size.
- **Per-seed consistency**: individual seed results reported alongside aggregates to assess stability. [TBD: exact CI and Cohen's d values pending M2 completion]

**Checkpoint criterion.** Primary results use the $\theta^*_{\text{R@1}}$ checkpoint. We additionally report $\theta^*_{\text{loss}}$ results to characterize the disagreement between optimization-aligned (loss) and task-aligned (R@1) checkpoint criteria [Source: D036].
