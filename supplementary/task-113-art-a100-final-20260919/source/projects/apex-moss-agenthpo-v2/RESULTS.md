# Task-Conditioned Harness Pilot — 实验结果

日期：2026-07-27
协议：正式评测 3 遍取平均；执行模型锁定 `claude-haiku-4-5`；判定线沿用
`docs/plans/2026-07-27-task-conditioned-harness-builder-pilot.md` 第 7 节。

## 结论先行

本轮没有得到支持或反驳「任务专化 Harness 更好」的有效证据，主要原因是**天花板效应**：
朴素通用 v001 在四个基准格子上开局即全部 100%，进化循环因此按规则提前停止，没有产生真正
的专化版本。

- Q1 前提（训练集提升 ≥15 点）未满足：`+0`，所以无法判断学到通法还是应试。
- Q2 两个方向的主场减客场都是 `0`：未观察到专化红利；但被比较的实际是同一 v001。
- Q3 两个 Builder Harness 都与基准持平为 100%，但没有任一族提升 ≥10 点，按冻结判定线为
  「无信号」。它证明了零样本生成物能在当前简单题集上工作，但题集没有留下超越基准的空间。

因此最可靠的实验结论不是「专化无用」，而是：**当前 assay 已饱和，不能识别三项研究假设。**

## 有效性审计与无效运行

Builder 阶段前两次运行属于基础设施无效，未纳入上述结论：

1. 原 `builder.py` 用非贪婪正则提取第一个 Python 围栏；生成 Harness 的内部提示词也含围栏，
   导致代码在内部围栏处被截断。四格均显示 0%、0 token、1.5–2.2 秒，实际是导入语法错误。
2. 第一次恢复候选错误地把 `run_tests` 的 dict 返回值当字符串调用 `.lower()`。bugfix 在修改前
   崩溃；tddgen 修改后崩溃，虽部分最终测试通过，仍全部带 harness error 且记录 0 token。

恢复只使用了固定工具合同和候选自身错误，没有把 train/val 题目、分数或 trace 反馈给
Builder。题库、评分、防作弊、模型锁、重复次数和判定线均未改变。最终加入了生成物门禁：
外层代码块提取、AST/语法、冻结签名、工具调用形式、参数键和返回类型检查，以及最多两次
基于合同错误的零样本修复。

## 后续：BigCodeBench-Hard 5 题难度 canary

为验证“只需换成更难的单文件题”是否足够，追加了一个**非正式、单遍** canary。选取
`bigcode/bigcodebench-hard` v0.1.4 中 5 道依赖较轻、无持久外部副作用的任务，仍使用通用
v001 和冻结的 `claude-haiku-4-5`。导入时逐题确认 stub 失败、官方 canonical solution 通过；
canonical solution 未写入题库。

|---|---|---:|---:|---:|---:|
| BigCodeBench/273 | HTTP JSON handler | PASS | 6 | 24,730 | 20.1s |
| BigCodeBench/274 | HTTP + SMTP handler | PASS | 8 | 43,466 | 33.6s |
| BigCodeBench/854 | 排列与阶乘 | PASS | 4 | 9,881 | 13.4s |
| BigCodeBench/928 | 二字符组合频率 | PASS | 4 | 8,653 | 11.6s |
| BigCodeBench/990 | 多种文本编码 | PASS | 6 | 24,536 | 24.0s |

合计 5/5（100%），111,266 executor tokens，0 harness error，0 tamper。目标难度区间是
50–80%，所以这批题仍然太容易，不应扩大为正式实验。

关键原因不只是题目本身：BigCodeBench 原本主要测“一次生成后用测试评分”，当前 Harness
却能直接读取完整 `test_solution.py`、运行测试并按失败反馈重试。这种反馈闭环显著降低了题目
难度。下一轮若要测出 Harness 差异，应优先考虑**公开规格/少量可见测试 + 隐藏终验**，或转向
真实仓库级任务，而不是继续堆更复杂但测试完全可见的单函数题。

### Q2：反馈信息形态条件化

| Harness | 主场 val | 客场 val | 主场 − 客场 | 冻结判定 |
|---|---:|---:|---:|---|

作为探索性信号；它尚未严格证明“不同反馈形态需要不同 Harness”。后续用同一底层任务的
有/无行为反馈配对版本确认。

## 第四轮：Q2 同题配对反馈形态确认

为消除旧 Q2 的题池难度混淆，把原 20 道 val 任务各生成 V0/V1 两个版本；同一任务仅
`test_solution.py` 不同，solution 与完整隐藏终验逐字一致。主比较为通用 v001（G）与已在
Q1 满足训练专化前提的 tdd v005（S）。旧有效的 tdd/V1 与 spec/V0 两格按任务文件哈希复用，
新增四格仍为 3 遍。

| block | G/V0 | S/V0 | G/V1 | S/V1 | `(S−G)V1 − (S−G)V0` |
|---|---:|---:|---:|---:|---:|
| tdd 底层题 | 33.3% | 40.0% | 56.7% | 53.3% | −10.0 点 |
| spec 底层题 | 16.7% | 20.0% | 40.0% | 40.0% | −3.3 点 |

两个 block 等权的主交互效应为 **−6.7 点**，固定 seed、10,000 次 task-paired bootstrap
95% CI 为 **[−15.0, +1.7] 点**。按预注册规则 `interaction_all <= 0`，结论为
**方向反证**：当前 v005 相对通用 v001 的效果没有在 V1 行为反馈下变得更好。旧 Q2 的
+33.3 点 raw 主场差主要是题池难度信号，不能作为反馈形态专长证据。

解释上限：该结果反证的是当前 v005 的预期方向，不证明所有 task-conditioned Harness
无效；20 道任务来自促成设计修订的旧 val 全集，所以这是同池消混淆，不是独立外部复制。

四个新增有效格共 120 task-run、3,946,778 executor tokens，0 tamper、0 contract
violation、0 infra-invalid。首次 G/S×tdd/V0 两格各有任务在 test failure 后的 teardown
抛错；旧分类器把 pytest `returncode=1` 的候选错误误标为 `env_error`。两格
339,634 / 1,447,262 tokens 整体隔离后，评分器用通用退出码边界修复并从头重跑：普通
test/setup/teardown error 计 capability，只有 timeout/collection/internal/usage/no-tests
计 infrastructure。无效分片未复用、未进入分析。

### 现象与成本

- R2 从 quick 100% 回落到 formal 91.7%，R1 从 quick 75% 变为 formal 83.3%，证明 8 题
  单遍反馈噪声很高；独立谱系和正式重复不可替代。
- R0/R2 都在 train 明显提升，但 external 分别只 +2.8/0 点。当前证据不是“稳定泛化”，
  也未强到能判“稳定过拟合”；更准确的描述是训练专化可复制、迁移效果仍未识别清楚。
- R0/R2 external 分别使用 v001 的约 4.1/6.4 倍 tokens，却没有越过泛化线，延续了
  “复杂 Harness 成本膨胀但收益不单调”的现象。
- R0 的 external 增益只来自 241 的一次额外通过；R2 在 241 上 +1/3、502 上 −1/3，
