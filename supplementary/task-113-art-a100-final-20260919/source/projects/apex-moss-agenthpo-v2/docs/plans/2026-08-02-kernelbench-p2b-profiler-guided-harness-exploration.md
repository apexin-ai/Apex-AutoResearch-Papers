# KernelBench P2b：Profiler 引导的任务专用 Harness 大范围探索

日期：2026-08-02  
状态：方案已在对话中授权，先实现与预检，再执行；P3 仍保持关闭

## 1. 为什么增加 P2b

P1 固定 Harness，只让模型连续修改 Kernel。P2 在每轮得分后改写 Harness，但外层循环仍然
固定，而且优化器主要只看到“能否编译、是否正确、最终速度”三类短反馈。

真实结果说明这种做法有价值，但不够稳定：

- LayerNorm 的 P1 最好为 19.86×；P2 两条路线接近 19×，一条停在 5.70×；
- Matmul+Sigmoid+Sum 的 P1 最好仅 1.006×；P2 三条路线分别达到 1.85×、4.10×、3.45×。

P2 后期 Harness 越写越长，并倾向于只改 `num_warps`、`num_stages` 等局部参数。这样能保护
正确性，却可能把一条路线过早锁在局部最好。P2b 的目标是让 Harness 真正改变工作方法：
它可以选择诊断工具、切换代码起点、放弃历史结构、分配探索预算和执行强制重启。

P2b 是新的搜索阶段，不改写原 P2。P3 仍只负责冻结版本的独立确认。

## 2. P1、P2、P2b、P3 的关系

```text
P1：固定做题方法，连续改 Kernel
                  │
                  ▼
P2：根据短分数反馈，逐轮改提示与决策规则
                  │
                  ▼
P2b：Harness 可选择诊断工具、代码起点、探索模式和重启动作
                  │
                  ▼ 冻结全部候选，不再搜索
P3：新环境交错复测，只确认正确性和速度是否可信
```

P2b 的成功只表示“在这两道具体题上找到了更好的搜索方法”。它不证明方法能泛化到其他题，
也不触发通用 Builder 更新。

## 3. 不可变边界

- KernelBench commit、任务文件哈希、输入形状、精度、正确性次数和性能次数保持不变；
- 固定 `gpt-5.6-sol` 和 `a100jump` 的 GPU4（A100-SXM4-80GB）；
- 不修改 benchmark、评分器、计时协议或旧 `eval.py`；
- 只有先通过编译和正确性的候选才能得到速度或 Profiler 结论；
- Profiler 只能分析本项目候选，不读取其他用户进程；
- 不读取、复制或推断私有正确性测试实现；
- 原 P1/P2 账本和产物只读；P2b 使用新的追加式账本；
- 失败、无效、中断和缺失指标全部保留；
- P2b 没有 P3、P4、Atrex 或 Builder 的执行入口。

## 4. 当前服务器能提供什么诊断

| 能力 | 当前状态 | P2b 用法 |
|---|---|---|
| `nsys` / Nsight Systems | 可用 | Kernel 时间线、launch 数量、CUDA API 和同步开销 |
| Triton 编译产物 | 可用 | 编译元数据、生成的 PTX/二进制摘要 |
| `ptxas` | 可用 | 能取得时记录寄存器、spill、共享内存报告 |
| `cuobjdump` / `nvdisasm` | 可用 | 只提取结构摘要，不把完整机器码塞进模型上下文 |
| 运行时间重复分布 | 可用 | 区分明显提升和 0.001ms 级噪声 |
| `ncu` / Nsight Compute | 未安装 | 适配器先实现为可选能力 |
| 硬件性能计数器 | 管理员专用 | `RmProfilingAdminOnly=1`；不得绕过策略 |

因此先执行 Tier A：时间线、编译资源、静态代码和重复计时。管理员未来开放计数器后，Tier B
再增加 achieved occupancy、DRAM/L2 吞吐和 warp stall；缺失字段必须写 `unavailable`，模型
不得用理论猜测冒充观测值。

## 5. P2b Harness 不再只是一段长提示词

每一版 Harness 由一个结构化策略和一段短指令组成。结构化策略至少包含：

- 当前模式：利用、结构重建、反向假设或重组；
- 本轮代码起点：参考实现、P1 最好、某条 P2 最好或本 lane 前沿候选；
- 已观测瓶颈证据，以及哪些内容仍只是推测；
- 本轮需要的诊断级别；
- 允许改变的结构范围；
- 禁止重复的已证伪方案；
- 是否触发强制重启；
- 下一候选必须和哪个版本做结构比较。
- 本轮启用/停用哪些任务内 Skill，例如分数趋势、代码差异、时间线、编译资源、显存访问、
  架构重建、反向假设、前沿重组、数值正确性和结构新颖度；
- 本轮实际调用哪些工具，以及硬件不支持时的缺失处理；
- 本轮读取“起点、最近、历史最快、稳定前沿、结构最新颖、冻结前沿、已证伪思路”中的哪些
  记忆视图；
- 至少三步、至多十步的可执行工作流。

外层控制器根据策略真正选择起点、上下文和工具，而不是把策略当作无效备注。Harness 正文限制
在 8,000 字符以内，结构化策略限制在固定字段内，防止规则无限膨胀。

## 6. 每轮的角色和动作

1. **Task Analyst**：从任务卡和参考实现提取固定形状、数学语义和合法专化边界；
2. **Profiler Controller**：根据策略决定轻量还是完整诊断；
3. **Compiler Analyst**：整理寄存器、spill、共享内存和编译产物摘要；
4. **Performance Diagnostician**：把观测事实与推测分开，提出主要瓶颈；
5. **Strategy Portfolio**：在利用、重建、反向假设、重组之间选择下一动作；
6. **Kernel Generator**：按当前策略只生成一个完整候选；
7. **Correctness/Score Gate**：依次执行编译、正确性、速度；
8. **Harness Optimizer**：综合代码差异、短反馈和可用 Profiler 证据，生成下一版策略；
9. **Experiment Memory**：保存所有版本、证据、失败、成本和前沿候选。

## 7. 八条真实路线

每道题运行四条不同路线，不再从相同策略起步：

| 路线 | 初始代码起点 | 主要职责 | 必做动作 |
|---|---|---|---|
| `profile_exploit` | 本题 P2 最快候选 | 用诊断证据改善强解 | 至少一次完整诊断 |
| `architecture_reset` | 参考实现和任务语义 | 允许完全放弃历史 Kernel 结构 | 至少两次结构重建 |
| `counterfactual` | 本题 P2 最快候选 | 主动尝试与当前瓶颈判断相反的路线 | 至少两次反向假设 |
| `recombinant_frontier` | P1/P2 多个前沿候选 | 比较、重组不同正确结构 | 至少比较三个历史候选 |

每条最多 8 个 Kernel；第 2–8 轮各允许一次策略改版，总计最多 15 次模型调用。四条路线的
历史彼此隔离，但 `recombinant_frontier` 可读取方案预先冻结的本题 P1/P2 前沿集合，不能读取
其他 P2b lane 的进行中结果。

## 8. 反局部最优规则

- 速度差小于 2% 时标为“噪声区”，不作为确定改进证据；仍保留原始分数；
- 每轮 Harness 优化器必须看到当前分数、上一正确候选分数、更新前历史最好和冻结起点分数，
  同时看到四个相对变化；若没有 2% 可信提升，下一版必须改变工具、Skill、记忆视图、代码
  起点、瓶颈假设或 Kernel 主结构中的至少一项，不能只改措辞；
- 不因连续三轮无提升提前结束；路线必须完成预注册的结构探索动作；
- 第 6 轮前仍没有超过起始最好时，第 6 轮强制从不同代码起点重启；
- 至少四轮预算用于结构探索，不得全部用于 launch 参数微调；
- 代码哈希相同直接复用，近重复候选记录为重复尝试，不再评分；
- 同时保留“最快、最稳定、结构最新颖”候选，不让单一快值垄断后续上下文；
- Harness 优化器可以回滚策略，但不能禁止下一次预注册的重建或反向假设；
- 到第 8 轮、预算上限、环境故障或评分器异常时停止。

## 9. Profiler 分级

### 轻量诊断

对每个正确候选执行或整理：

- 候选与 reference 时间、speedup；
- 代码哈希和结构签名；
- 与起点/历史最好之间的结构化差异；
- Kernel 数量、主要 launch 名称和时间线摘要（可用时）；
- 编译元数据、warps、stages、共享内存和寄存器字段（可用时）；
- 缺失指标列表。

### 完整诊断

只用于以下候选：每条路线起点、新历史最好、强制重启候选、诊断器明确请求且预算允许的正确
候选。完整诊断可增加 `nsys` trace、PTX/SASS 结构摘要和重复计时分布。

### 管理员计数器增强

若管理员安装 `ncu` 并开放本账号性能计数器，则在不改变既有分数的前提下增加：

- achieved occupancy；
- DRAM/L2 实际吞吐及命中率；
- warp stall 分类；
- 指令与内存工作量摘要。

这些指标是增强项，不是 Tier A 开跑门禁。

## 10. 预算和硬停止

- 8 条 lane，每条最多 8 个 Kernel、15 次模型调用、3,600 GPU 秒；
- 全局最多 64 个新 Kernel、120 次模型调用、14,400 GPU 秒；
- API 和 GPU 分别设置 100 美元硬帽，不互相借用；
- 优先使用已登录的 Codex/ChatGPT，账本仍记录 usage；
- 不自动切换 TokenRouter 或其他模型；
- 任何未完成的模型调用仍计入硬帽；
- Profiler 预留和实际耗时都计入 GPU 预算；
- 环境无效时全局熔断，候选错误只影响当前 lane。

预计实现和预检 3–5 小时，真实搜索 4–8 小时。实际墙钟时间受 Codex 响应和共享 A100 负载影响。

## 12. P3 在 P2b 开跑前预注册

P3 现在只冻结规则，不执行：

1. P2b 完成后，冻结 P1 同预算最好、三条 P2 最好和四条 P2b lane 最好；
2. 在全新容器中重新编译，不复用 P2/P2b 的 Triton/torch 编译缓存；
3. 每道题以轮换顺序做 9 个交错区块，每个版本在每个区块重新检查正确性并测速；
4. 任一次正确性失败，该候选不得被确认；
5. P2b 相对 P1 的中位时间至少快 2%，且至少在 9 个区块中的 7 个更快，才称为“确认提升”；
6. 差异不足 2% 或胜负不足 7/9，称为“基本持平/不明确”；
7. 明显变慢或正确性失败，称为“未确认”；
8. P3 分数不得反馈回 P2b，也不得据此生成新候选；
9. P3 必须另行获得用户授权后才实现和运行。

## 13. 实现与验证顺序

1. 为策略、ProfileSummary、缺失指标和隐私边界写红测；
2. 实现 P2b plan、不可覆盖策略档案和冻结起点清单；
3. 实现 fake profiler、SSH Tier A profiler 与能力预检；
4. 实现八路线控制器、前沿选择、强制重启和预算恢复；
5. 实现独立 HTML 看板；
6. 用 fake generator/adapter/profiler 跑完整八路线；
7. 在 A100 上只对一个冻结正确候选做 Tier A 预检；
8. 审计无 P3 入口、原 P2 哈希未变、硬帽可恢复；
9. 才启动真实 P2b；
10. 完成后冻结、报告并停在 P3 授权门。

## 14. 后续扩 Task 门禁

当前 P2b 预算只覆盖上述两道冻结 Task。若两题都相对各自 P1/P2 历史最好得到至少 2% 的正确、
非单次波动提升，且至少一题达到 5%，则可以另行冻结下一批 4–6 道 KernelBench Task，优先覆盖
归约、矩阵计算、归一化、卷积/访存等不同结构。每批继续记录提升率、正确率、成本和 Harness
结构多样性；扩大到 KernelBench 全量或切换下一个即时看分 Benchmark 前，必须先列出新的总
候选、模型调用、GPU 时间和费用预算，不能把当前 120 次调用硬帽静默扩张。
