# 实验计划一：面向具体调优任务的 Harness 进化

> 日期：2026-07-31
>
> 状态：方案已完成，尚未实现，未启动付费模型调用或 GPU 实验
>
> 核心变化：本轮不再要求 Harness 先学会一个领域的通用方法，而是允许它熟悉某个
> benchmark 里的具体任务、输入形状、常见失败和历史最佳做法。第一目标是确认：
> **同一个模型配上一套会根据分数反复调整的专用工作流，能否在一个固定任务上稳定爬分。**

---

## 0. 先说结论

第一轮建议从 [KernelBench](https://github.com/ScalingIntelligence/KernelBench) 开始，
而不是从大型机器学习竞赛或开放式科研任务开始。

原因很简单：KernelBench 让 AI 把一个常见的 PyTorch 计算改写成更快的 GPU 程序。
每交一份候选程序，评分器会马上回答两个问题：

1. 算得对不对；
2. 如果算对了，比原来的 PyTorch 实现快多少。

这种反馈非常适合调整 Harness。Harness 可以学会什么时候先修编译错误、什么时候检查
数值误差、什么时候使用性能分析工具，以及什么时候回退到历史最好版本。整个过程像一位
专门负责同一道工程题的教练，反复看成绩、改训练方法，而不是要求它一开始就能教所有题。

首发选择两个明确任务，每个任务拥有完全独立的 Harness 和历史：

- `KernelBench/level1/40_LayerNorm.py`：优化大张量上的 LayerNorm；
- `KernelBench/level2/9_Matmul_Subtract_Multiply_ReLU.py`：把矩阵乘法后的减法、
  乘法和 ReLU 尽可能合并。

计划冻结的 KernelBench 版本是提交
[`423217d9fda91e0c2d67e4a43bf62f96f6d104f1`](https://github.com/ScalingIntelligence/KernelBench/commit/423217d9fda91e0c2d67e4a43bf62f96f6d104f1)。
正式开跑前先做不调用模型的环境检查；如果云 GPU、编译器或官方评分脚本不能稳定工作，
实验停在准备阶段，不消耗正式模型预算。

第二阶段优先考虑
[Atrex-Bench](https://github.com/alibaba/atrex-bench)。它同样评估 GPU 程序的正确性和
速度，而且来自更接近生产的算子，但项目在 2026 年 7 月仍标注为早期阶段，适合作为
KernelBench 跑通后的独立确认，不适合承担第一版框架的全部集成风险。

## 1. 为什么要换方向

MOSS 过去问的是：“在一批训练题上改出来的 Harness，能不能迁移到从未见过的新题？”
已有实验已经证明，Harness 确实能让训练题成绩明显上升，但新题上的收益很小且不稳定：

- 两条有效谱系在训练 benchmark 上分别提高了 20.8 和 16.7 个百分点；
- 换到新的 external benchmark 后，合并提升只有 1.39 个百分点，仍无法确认真实迁移；
- 同题配对实验也没有找到可靠的任务族专化优势；
- Builder 能生成可运行的 Harness，但零样本成绩没有超过通用起点。

这些结果不等于 Harness 没价值。它们更像是在说明：**有限题目上的专化容易发生，
跨题迁移则昂贵且难测。**

新路线直接利用前半句话。我们先把“对具体任务越做越好”做成一个可靠能力，再决定要不要
研究这种能力能否迁移。这样可以把反馈从“最后只知道过或没过”，变成“每次都知道对错和
快慢”，更容易看出 Harness 的哪种结构真的有用。

本轮有意允许：

- 在 Harness 中写明具体任务名称和固定输入形状；
- 保存这个任务历次尝试、错误类型和最佳方案；
- 针对该任务安排专用工具顺序和重试方式；
- 只在当前任务上选择最佳 Harness。

本轮仍然禁止：

- 读取官方答案、隐藏测试输入或评分器私有文件；
- 修改计时器、正确性检查或运行环境来制造假成绩；
- 更换更强模型后把收益算到 Harness 头上；
- 用更多时间和更多调用冒充“工作流更聪明”。

换句话说，我们允许认真备考一门明确科目，不允许偷看答案或改成绩单。

## 2. 候选 benchmark 调研结果

以下列表只收录有官方论文、官网或代码库可核实的项目。这里的“反馈快慢”是相对判断；
正式选择仍以在我们的云 GPU 上实测为准。

| 候选 | 实际要优化什么 | 得分反馈 | 与本轮的适配度 | 处理决定 |
|---|---|---|---|---|
| [KernelBench](https://github.com/ScalingIntelligence/KernelBench) | 把 PyTorch 计算改写成正确且更快的 GPU kernel | 单题可本地或通过 Modal 评估，直接返回正确性和速度 | 任务小、分数清楚、官方明确建议研究者修改 agent scaffold | **首发** |
| [Atrex-Bench](https://github.com/alibaba/atrex-bench) | 为生产来源的 AI 算子生成 Triton 等 GPU kernel | 编译、正确性、速度三段式反馈 | 很贴近真实 AI 系统，也自带 agent 运行方式；但 2026-07 才发布早期版 | **第二阶段确认** |
| [KernelBenchX](https://github.com/BonnieW05/KernelBenchX) | 生成 Triton kernel，并统一检查可运行性、正确性和效率 | 本地 GPU 评分 | 评分严格、可复现性设计较完整，但生态和使用量仍小 | 备用评分器 |
| [CompilerGym](https://github.com/facebookresearch/CompilerGym) | 为具体程序选择编译优化步骤，减少指令数或代码大小 | 每做一步即可得到 reward | 反馈非常密，CPU 也能做；但官方仓库已归档，最后一个 README 发布版本停在 2022 年 | **无 GPU 时的框架演练** |
| [PIE](https://github.com/madaan/pie-perf) | 在保持输出正确的前提下让 Python/C++ 程序运行更快 | 本地沙箱可比较修改前后运行时间 | CPU 即可、反馈快；但优化对象不是专门的 AI 系统 | 低成本备用 |
| [EffiBench](https://github.com/huangd1999/EffiBench) | 衡量生成代码的时间和内存效率 | 本地运行后出效率报告 | 题目多、适合大规模评测，但不是为多轮 agent 调优设计 | 后续扩题候选 |
| [SWE-Perf](https://github.com/SWE-Perf/SWE-Perf) | 在真实代码仓库中提交不破坏功能的性能补丁 | 运行测试并测量耗时 | 很接近真实软件工程，但环境重、单次反馈慢、计时噪声更难控制 | Kernel 实验成功后再做 |
| [MLAgentBench](https://github.com/snap-stanford/MLAgentBench) | 让 agent 反复实验并改进一个机器学习模型 | 训练和评估后得到任务分数 | 任务形式合适，但一次实验通常比单个 kernel 慢得多 | 中期候选 |
| [MLE-bench](https://github.com/openai/mle-bench) | 完成 75 个 Kaggle 机器学习竞赛 | 可用本地 grader 计算提交分数 | 能看到连续分数，但官方标准运行时间长、数据量大；官方在 2026-04-24 暂停接收新 leaderboard 提交 | 不作为首发 |
| [ResearchGym](https://github.com/Anikethh/ResearchGym) | 完成开放式 AI 研究任务并超过论文基线 | 由任务脚本给出客观分数 | 很符合长期“AI 做 AI 研究”的愿景，但标准任务持续 12–24 小时 | 长期终点，不适合快速调 Harness |
| [RE-Bench](https://github.com/METR/RE-Bench) | 完成 kernel、训练脚本、模型修复、缩放规律等 AI 研发任务 | 每项都有数值分数 | 任务内容几乎完美匹配，但官方明确请求避免过拟合，并限制将材料用于提升前沿模型能力 | **未经书面许可不运行** |

### 2.1 田渊栋相关项目的核实结论

田渊栋的[个人主页](https://yuandong-tian.com/)把 CompilerGym 列为其参与的重要项目；
CompilerGym 论文的作者列表也包含 Yuandong Tian。这个项目把编译优化包装成类似游戏环境：
选一个优化动作，环境立刻返回程序变化和分数，因此在“用高密度反馈调工作流”这件事上很有
启发。

不过，[CompilerGym 官方仓库](https://github.com/facebookresearch/CompilerGym)当前已经
归档，README 的最新发布记录是 2022 年的 `v0.2.5`。它依赖较旧的编译器和 Python 组合，
把它当主实验会让大量时间花在恢复环境，而不是研究 Harness。

因此本计划吸收 CompilerGym 的核心思想——**把优化任务包装成可以反复行动并即时得分的
环境**——但把首发对象换成仍在更新、且直接服务于 AI 计算的 KernelBench。

田渊栋主页还提到 LaMCTS 曾被 NeurIPS 2020 黑盒优化挑战参赛队扩展使用。这进一步说明
“不断试候选、根据连续分数选择下一步”是合适的技术传统，但该挑战本身较老，也不专门衡量
今天的 agent Harness，所以不单独纳入正式实验。

### 2.2 为什么暂不使用 RE-Bench

RE-Bench 包含两个尤其诱人的任务：

- 优化 LLM Foundry 微调脚本的运行时间；
- 优化 Triton prefix-sum kernel 的运行时间。

两者都有清楚的连续分数。但 RE-Bench 的官方 README 和许可证附注明确请求使用者避免
过拟合，不要把评测材料用于提升前沿模型能力，除非用于危险能力评估及其安全措施。
本轮恰恰要反复利用一个具体任务的反馈来改进 Harness，和这项请求存在直接张力。

所以 RE-Bench 只作为任务设计参考。除非 METR 书面确认我们的使用方式可以接受，否则不把
它下载到模型可见环境、不运行它的受保护答案，也不发表针对具体任务的解法。

## 3. 首发任务

### 3.1 任务 A：LayerNorm

文件：
`KernelBench/level1/40_LayerNorm.py`

它代表许多大模型中都会出现的归一化计算。候选程序需要在一个大张量上计算均值、方差和
归一化结果。这个任务适合观察 Harness 会不会形成如下工作习惯：

- 先确保数值一致，再谈速度；
- 看清楚张量形状和内存访问方式；
- 用性能分析证据判断慢在哪里；
- 修改后及时和历史最佳版本比较；
- 一旦退步就回滚，而不是继续在坏版本上修补。

### 3.2 任务 B：Matmul + Subtract + Multiply + ReLU

文件：
`KernelBench/level2/9_Matmul_Subtract_Multiply_ReLU.py`

这个任务先做矩阵乘法，再做三段简单计算。它的机会通常不是重新发明矩阵乘法，而是减少
中间结果和多次 kernel 启动。它可以检验 Harness 是否会区分“真正值得自己写的部分”和
“应该交给成熟库的部分”。

### 3.3 为什么同时选两个

两个任务分别偏向“归一化/归约”和“矩阵乘法后的操作融合”，优化思路明显不同。我们不会
把它们混成一个通用 Harness，而是为每个任务建立独立谱系。两个任务都成功，说明新框架不
只是碰巧适合一种算子；只有一个成功，也能告诉我们应先在哪类任务上继续投入。

如果某个首发任务因为固定 GPU 内存、编译器缺陷或官方脚本错误而无法有效评分，可以使用
预先列出的备用任务：

- `KernelBench/level1/92_cumsum_exclusive.py`
- `KernelBench/level2/56_Matmul_Sigmoid_Sum.py`

替换只允许发生在正式模型调用之前，必须记录原因并重新冻结任务清单。看过正式分数后不得
换题。

### 3.4 P0 执行记录：首发任务 B 已按预登记规则替换

2026-07-31，在任何做题模型调用之前，全零负例在原任务 B 上通过了官方 5/5 正确性检查，
并产生约 215 倍的异常速度。原因是该题当前默认初始化和 ReLU 组合会让参考输出退化为全零，
因此它无法区分真实计算和空算捷径。该题及原始日志永久保留为评分器门禁证据，但从所有最佳
成绩和实验结论中排除。

根据本节预登记清单，任务 B 改为
`KernelBench/level2/56_Matmul_Sigmoid_Sum.py`。新任务的全零负例被正确拒绝，正确参考实现
可以获得速度反馈。固定 commit、文件哈希和任务卡已重新冻结；替换发生在任何模型/API
调用前，没有根据模型成绩挑题。

## 4. 新架构：把 MOSS 变成一间“可反复试验的优化实验室”

旧系统把一道题交给模型，最后看测试是否通过。新系统需要在模型和 benchmark 之间增加一层
翻译，让不同 benchmark 都能用同一种“提出候选—评分—复盘—再试”的方式运行。

```text
具体任务说明
    ↓
专用 Harness 安排模型读代码、写候选、检查和分析
    ↓
Benchmark 适配器在隔离环境中运行官方评分器
    ↓
反馈卡：能否编译、是否正确、速度如何、花了多久
    ↓
优化器决定保留、回滚或改变 Harness
    ↓
版本档案保存每次尝试和历史最好结果
```

### 4.1 五个核心部件

#### 任务卡

任务卡是本次实验的“合同”，写清楚：

- benchmark 名称、固定版本和具体文件；
- 固定 GPU、驱动、PyTorch、CUDA/Triton 版本；
- 候选程序可以看到什么、可以修改什么；
- 对错和快慢如何判断；
- 每轮可以使用多少时间和模型调用；
- 哪些行为算篡改成绩。

它和旧 family card 不同：旧卡刻意不含具体题目；新卡必须明确写出具体任务和输入形状。

#### Benchmark 适配器

适配器只负责把候选程序交给官方评分器，再把结果整理成统一反馈。第一版只实现
`KernelBenchAdapter`，以后才接 Atrex、PIE 或 SWE-Perf。

适配器分成两间隔离的工作区：

- 做题工作区：模型只能看到任务参考代码、允许的工具和自己生成的候选；
- 评分工作区：保存评分器、计时配置和完整日志，模型不能修改。

这种隔离不是为了阻止任务专化，而是为了避免“改计时器比改程序更容易”的假进步。

#### 专用 Harness

Harness 是一套会执行的工作流程，而不只是提示词。它可以决定：

- 先读什么信息；
- 什么时候编译；
- 编译失败后给模型看多少错误；
- 正确性没过时是否禁止做速度测试；
- 什么时候调用 profiler；
- 每轮保留哪些历史经验；
- 连续失败时回滚还是换思路；
- 剩余时间应该探索新方案还是打磨当前最好方案。

本轮允许 Harness 记住具体任务的经验，但冻结底层模型，不允许 Harness 自行换模型。

#### 反馈卡

不同工具的长日志先由控制器整理成一张短反馈卡，再交给 Harness：

- 候选是否成功编译；
- 正确性是否通过；失败时只给必要的误差摘要；
- 运行速度和参考实现相比如何；
- 和本谱系历史最佳相比是进步还是退步；
- 本轮花费的模型调用、GPU 时间和实际等待时间；
- 是否发生超时、环境故障或违规修改。

反馈卡既让模型容易理解，也避免它从评分器路径和私有文件名中寻找捷径。

#### 版本档案与账本

每次候选都保存，不覆盖旧版本。档案至少包含：

- 父版本；
- Harness 源码；
- 生成的 kernel；
- 原始模型响应；
- 反馈卡和完整私有评分日志；
- 模型、依赖、GPU 和随机设置；
- 花费与运行时间；
- 接受、拒绝或环境无效的原因。

历史最好版本始终单独登记。新候选变差时不会把最好版本丢掉。

### 4.2 建议的代码布局

新方向不应直接改写旧的 `eval.py` 和 `scripts/three_tier_runner.py`。它们是历史
pass/fail 与 sealed-test 协议的可信记录，硬改会让新旧实验互相污染。

建议另建：

```text
optimization_lab/
  adapters/
    base.py
    kernelbench.py
  protocols/
    kernelbench_task_a.yaml
    kernelbench_task_b.yaml
  harnesses/
    kernelbench_layernorm/
    kernelbench_matmul_fusion/
  task_cards/
    kernelbench_layernorm.md
    kernelbench_matmul_fusion.md
  runner.py
  optimizer.py
  feedback.py
  registry.py
  budget.py

results/optimization_lab/<experiment_id>/
  ledger.jsonl
  state.json
  lineages/
  private_evaluator/
  final_confirmation/
```

可以复用的旧能力：

- `config.py` 的网关配置方式；
- `harness_source.py` 中“先提取完整代码，再检查合同”的经验；
- 正式 runner 的追加式账本、断点恢复、预算熔断和无效运行隔离；
- 当前项目保存模型原始输出和内容哈希的做法。

不直接复用的部分：

- `eval.py` 的 pass/fail 汇总，因为新任务需要正确性和速度两段评分；
- 当前只允许读写 `solution.py` 的 Harness 合同；
- 三层资格实验的 instance 特判 linter，因为本轮明确允许 instance conditioning；
- 旧 `archive.jsonl` 的“扫描最大 vNNN 就当当前版本”方式。

## 5. 实验步骤

### P0：先证明评分器值得用

这一阶段不调用做题模型。

1. 在一台租用的固定型号 GPU 上安装官方 KernelBench。
2. 记录 GPU、驱动、PyTorch、CUDA、Triton 和仓库提交。
3. 跑通官方参考实现、一个故意错误的候选和一个能工作的简单候选。
4. 对同一候选反复评分，确认结果不会忽快忽慢到足以改变候选排序。
5. 记录从提交候选到拿到反馈的实际等待时间。
6. 验证全新容器能够重现结果。

绿色出口：

- 错误候选会被正确拒绝；
- 正确候选能稳定得到速度反馈；
- 单次反馈足够快，可以支持一轮里多次尝试；
- 全新容器复测不会出现方向相反的结果。

如果做不到，就停止。可以转到 CompilerGym 或 PIE 做 CPU 版框架演练，但不得把 CPU
演练结果写成 KernelBench 成功。

当前开发机没有 `nvidia-smi`，只有 2 个 CPU 和约 8 GiB 内存，因此不能在本机完成这道
门禁。正式实验需要云 GPU；优先选择 KernelBench 已提供参考计时的 GPU 类型，并在首次
正式评分前固定下来。

### P1：建立公平基线

对每个任务先跑三种起点：

1. **通用起点**：只知道“写一个正确且快速的 kernel”，不带任务历史；
2. **同预算通用起点**：给通用流程同样多的模型调用和 GPU 时间，但不让它改变 Harness；
3. **人工朴素模板**：固定执行“读参考—写候选—查正确性—测速—修一次”的简单流程。

这一步回答一个很重要的问题：后面如果专用 Harness 更好，究竟是工作流学会了东西，还是
仅仅因为它试得更多。

三个起点都使用同一个底层模型、同一套工具、同一 GPU 和同一时间上限。基线重复运行，
保留每次原始结果，不挑最好的一次冒充平均水平。

### P2：让 Harness 针对单个任务进化

每个任务开三条互不共享历史的谱系。三条谱系从逐字相同的 Harness 起步，只改变随机性。

每条谱系最多进行八轮：

1. 当前 Harness 让固定模型生成或改进 kernel；
2. 先编译，再检查正确性；
3. 只有正确时才测速；
4. 控制器生成反馈卡；
5. 优化器查看当前 Harness、历史反馈卡和失败记录；
6. 优化器提出下一版完整 Harness；
7. 新 Harness 进入下一轮，历史最好 kernel 和 Harness 始终保留。

优化器可以改提示、工具顺序、失败处理、上下文摘要、任务记忆和时间分配。它不能改底层模型、
官方评分方法、GPU 类型或总预算。

提前停止条件：

- 连续三轮没有产生新的正确候选；
- 连续三轮速度没有超过历史最好；
- 八轮用尽；
- 到达预算或时间上限；
- 出现任何评分器篡改迹象。

### P3：在干净环境中确认最佳版本

搜索阶段的最快成绩可能只是一次计时运气。每条谱系结束后，先冻结它的最佳 Harness 和
最佳 kernel，再在新容器中重新评分。

确认时：

- 不再允许修改 Harness 或 kernel；
- 使用同一型号 GPU 和完全相同的软件版本；
- 多次交错运行通用基线、同预算对照和专用版本，避免机器温度或负载顺序偏袒某一方；
- 正确性每次都重新检查；
- 任一次出现错误，都不能只保留其余快的结果。

最终报告同时展示“能不能算对”“有多快”“花了多少调用和 GPU 时间”，不只展示最漂亮的
单次速度。

### P4：拆开看是哪种 Harness 结构有效

只在 P3 成功后进行。以最佳 Harness 为基础，每次拿掉一个能力：

- 不保存任务历史；
- 不允许 profiler；
- 不允许回滚；
- 编译、正确性和测速不再分阶段；
- 不提供历史最佳对比；
- 把专用任务说明换回通用说明。

如果拿掉某个能力后成绩明显退步，才有理由把它当作下一版 Builder 应该学会生成的结构。
如果所有删减都没影响，则很可能收益主要来自更多尝试，而不是 Harness 设计。

### P5：可选的同 benchmark 小范围迁移

这一阶段不是首轮成功门槛。它只回答一个附加问题：

> 针对 LayerNorm 或融合任务学到的工作流，换到同一 benchmark 的相邻任务后还有没有用？

测试必须使用已经冻结的 Harness，不能根据新任务分数继续修改。无论结果好坏，都不能把
它扩大解释成整个 AI 工程领域的通用能力。

## 6. 怎样判断这条路线值得继续

### 继续投入

满足以下条件时，进入 Atrex-Bench 独立确认：

1. 每个候选都经过正确性检查，没有靠错误结果换速度；
2. 至少一个首发任务的三条独立谱系中，有两条能找到比通用起点更好的专用 Harness；
3. 在干净容器的确认阶段，专用版本仍保持至少约 20% 的速度优势，且不是偶发的一次快值；
4. 同预算通用对照追不上专用版本，说明收益不只是“多试了几次”；
5. 评分器、GPU 和模型成本仍允许在一天内完成一次完整复现。

这里的 20% 不是要证明行业领先，而是避免把 GPU 计时的细小波动误认成 Harness 进步。
P0 如果显示实际计时波动更大，正式实验必须先回到方案阶段重定成功线，不能开跑后移动。

### 暂停或换 benchmark

出现以下任一情况就不继续扩大：

- 同一候选反复测试时，快慢排序经常颠倒；
- 单次反馈太慢，八轮搜索无法在可接受时间内完成；
- 三条谱系只有一条偶然成功，另外两条无法复现；
- 给通用 Harness 相同预算后就能追平专用 Harness；
- 收益来自改评分脚本、利用固定测试值或跳过正确性检查；
- 最佳版本只在搜索容器里快，干净容器中消失；
- API 或 GPU 成本超过预先批准的硬上限。

### 允许使用的结论

成功时可以说：

> 在固定模型、固定 KernelBench 任务和固定 GPU 环境下，面向具体任务进化的 Harness
> 比通用工作流更稳定地找到正确且更快的候选。

不能说：

- Harness 已经学会通用 GPU 优化；
- 它能迁移到所有 KernelBench 任务；
- 它提升了底层模型本身；
- 它已经具备自主 AI 研究能力。

## 7. 预算与时间安排

第一轮只批准到 KernelBench P3，不自动启动 Atrex 或 SWE-Perf。

| 阶段 | 预计时间 | 主要花费 | 硬停止点 |
|---|---:|---|---|
| P0 环境和评分器 | 0.5–1 天 | 云 GPU，不调用做题模型 | 两个 GPU 小时内仍无法稳定评分则停 |
| P1 三种基线 | 0.5 天 | 模型调用 + 云 GPU | 任一基线无法得到可审计结果则停 |
| P2 两任务、三谱系进化 | 1–2 天 | 主要模型和 GPU 预算 | 每谱系八轮，不补跑第九轮 |
| P3 干净环境确认 | 0.5 天 | 以 GPU 为主 | 只确认冻结版本，不根据结果继续搜索 |
| P4 结构拆解 | 0.5–1 天 | 仅在 P3 成功后另行批准 | 每次只移除一个能力 |

建议首次授权采用两个独立硬帽：

- 模型/API 费用不超过 100 美元；
- 云 GPU 费用不超过 100 美元。

任何一项预计越界都必须先暂停并向用户申请，不得用另一项的余额补。实际价格和可用 GPU
型号会变化，所以 P0 完成后应给出基于真实账单的剩余预算表，再决定是否启动 P2。

## 8. 风险与处理方式

### GPU 计时不稳定

同一个程序可能因为机器共享、预热、频率和缓存状态出现不同时间。解决方式是固定 GPU
型号和软件版本，先预热，再交错复测基线与候选，并在新容器确认。

### 只会投机评分器

专用 Harness 很可能发现固定测试的捷径。模型工作区不能包含评分器、私有输入或计时脚本；
正确性使用官方随机输入，候选只能提交规定的 kernel 文件。任何修改环境或跳过计算的行为
都记为无效，而不是低分。

### 把更多计算当成更好 Harness

所有对照使用同一模型，并设置同样的总调用和 GPU 时间。报告同时写成绩和成本。专用方案
只有在同预算通用对照追不上时，才能归因到工作流。

### 只保存幸运结果

搜索过程可以保留历史最好版本，但正式结论只看冻结后在新容器中的多次确认。失败和退步
同样进入账本，不能删除。

### benchmark 版本持续更新

KernelBench 主分支仍在更新，因此必须冻结 commit、任务文件哈希和依赖。Atrex 等后续实验
也各自冻结，不能用不同版本的分数直接横比。

### 许可证和使用意图

- KernelBench 和 Atrex 的代码许可证允许研究修改，但仍需保留原许可证和作者声明；
- MLE-bench 的代码许可证不覆盖它下载的外部 Kaggle 数据，每项竞赛规则要单独遵守；
- RE-Bench 的非正式使用请求比代码许可证更严格，本项目选择尊重该请求；
- 不自动向远程 leaderboard 高频提交，第一轮只用本地或自有云环境的官方评分器。

## 9. 与旧三层资格方案的关系

`docs/plans/2026-07-28-three-tier-benchmark-qualification.md` 保留为旧研究问题的冻结方案，
不删除、不改判定线，也不继续自动进入 P3 模型调用。

两条路线的区别是：

| 旧三层资格路线 | 本计划 |
|---|---|
| 重点防止 Harness 记住具体 instance | 明确允许 Harness 熟悉具体任务 |
| 主要看训练提升能否迁移到 fresh test | 主要看固定任务能否稳定爬分 |
| test 只允许解封一次 | 同一任务的分数就是搜索反馈，可反复使用 |
| instance 特判会被 linter 拒绝 | 任务名称、形状和历史经验可以写入 Harness |
| 成功后才研究 Builder | 先找出有效的专用 Harness 结构，再考虑 Builder 如何生成它 |

旧代码和结果仍然有价值，特别是合同校验、账本、恢复、预算熔断和无效运行隔离。新计划只是
更换研究问题，不重写历史。

## 10. 实施顺序

用户批准执行后，按以下顺序开发：

1. 新建 `optimization_lab/`，先写假的 benchmark adapter 测试；
2. 写 KernelBench adapter，并用假候选验证编译失败、正确性失败、有效测速和环境失败；
3. 写反馈卡和不可覆盖的版本档案；
4. 写固定预算、回滚和断点恢复；
5. 建立两个任务卡和通用起点 Harness；
6. 完成 P0，只交付环境与评分器报告；
7. 用户确认 P0 和实际预算后，再启动 P1–P3；
8. P3 成功才另写 Atrex-Bench 确认方案，不在本轮顺手扩大。

代码实现时必须先补测试，再修改功能；不得为了新方向放宽旧 `eval.py` 的反作弊合同。

## 11. 开跑前仍需用户批准

本方案交付不代表授权付费运行。执行前还需要用户明确确认：

1. 是否接受 KernelBench 作为第一 benchmark；
2. 是否接受首发两个具体任务和两个备用任务；
3. 是否允许使用云 GPU，以及可用供应商/账号；
4. 是否接受模型费用 100 美元、GPU 费用 100 美元的独立硬帽；
5. 固定使用哪个 executor 模型；
6. P0 通过后，是一次性批准 P1–P3，还是每阶段单独批准。
