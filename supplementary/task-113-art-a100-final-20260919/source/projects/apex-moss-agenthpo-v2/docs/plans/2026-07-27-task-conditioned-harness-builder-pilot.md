## 0. 用一段话说清楚这个实验

附件的核心主张是:**不要指望造出一个万能的 Harness 解决所有任务;正确的路线是让每类任务拥有自己的专用 Harness,而让"根据任务描述生成 Harness 的 Builder"去承担泛化。**这个主张很大,没法一次验证,所以本实验把它拆成三个能在一天内回答的小问题。每个问题不管答案是"是"还是"否",都对应明确的下一步——这就是"快速跑出效果看看情况"的意义:先花一天和几十美元,搞清楚这条路线的三根支柱各自有没有信号,再决定往哪里加码。

一个贯穿全文的比喻:把模型比作学生,Harness 比作老师给学生定的**做题流程**——先读什么、能用什么工具、错了怎么重试。附件问的就是:该培养一套万能流程,还是给每类题各定一套流程、再培养一个"会定流程的教务主任"(Builder)。

## 1. 三个小问题,以及每个问题背后的逻辑

### Q1:反复改进出来的流程,学到的是"这类任务的通法",还是"这套题的应试技巧"?

**为什么先问这个。**附件第 6–7 节设计了一个判定办法:改进流程时只允许看训练题库,改完后拿一套没见过的验证题库来考。这个办法是整个研究的地基——如果连"通法还是应试"都区分不了,后面一切主张都无从谈起。所以 Q1 既在检验流程改进本身,也在检验这个判定办法能不能用。

**怎么做。**在 A 类任务的训练题库上反复改进流程(共 6 轮,改进过程绝不接触验证题库),改进前后各考一次验证题库。

**三种结果各说明什么:**

| 结果 | 含义 | 对应附件 |
|---|---|---|
| 训练分↑ 验证分↑ | 学到了通法——专精是"任务级"的,这是最好的结果 | Case 2 |
| 训练分↑ 验证分↓ | 学到了应试技巧——但这**也是正结果**:它证明这套判定办法真的能抓住"假进步",二期的重点就变成让训练题库更多样 | Case 1 |
| 训练分不涨 | 改进机制本身有问题,先修好它,后面实验暂停 | — |

### Q2:给任务"定制"流程,真的比通用流程强吗?

**为什么问这个。**附件的大前提是"Harness 应该专精,不该万能"。如果 A 类任务专精出来的流程和 B 类的互相换着用,成绩没差别,那"专精"就是伪需求,整个 Builder 路线的必要性就动摇了。

**怎么做。**Q1 会产出两个专精流程(A 族一个、B 族一个),让它们互换考对方的验证题库,再加上通用基准版,三方对比。看"主场分"(考自己那族)比"客场分"(考对方那族)高多少。

### Q3:只看一段任务描述、不做任何试错,能不能直接生成一个像样的专用流程?

**为什么问这个。**这是附件第 5 节 Builder 的最小雏形。完整的 Builder 需要从大量任务中学习"什么任务配什么流程",一天做不完;但它的第一步——"任务描述里的信息够不够推出一个合理流程"——今天就能测。如果强模型只看描述就能生成不差于通用基准的流程,说明"任务描述 → 流程"这条映射有信号,值得往学习型 Builder 投入。

**怎么做。**为每类任务写一张**任务说明卡**,字段就是附件 5.1 定义的五要素:任务目标、工作环境、反馈方式(怎么知道对没对)、需要的工具、适合的思考模式。卡片只描述任务类型,**不含任何具体题目**。让强模型只看卡片生成流程,直接考验证题库。

**三个问题的关系:**Q1 验证"判定办法"这个地基,Q2 验证"要专精"这个前提,Q3 验证"能生成"这条路——正是附件框架(任务 → Builder → 专用 Harness → 训练/验证分离评估)的三根支柱各取最小可测的一段。

## 2. 实验对象:两类任务、四个题库

| 任务类别 | 训练题库(改进时可见) | 验证题库(只用于考试) |
|---|---|---|
| **修 bug**:给一段有 bug 的代码和测试,改到测试全过 | 本仓库现有 10 道自制题 | QuixBugs 选 12 题(公开题库,真实算法程序里的经典 bug,风格与自制题明显不同) |
| **按测试写代码**:只给函数框架和测试,从头实现 | HumanEval 选 10 题(公开题库) | MBPP 选 12 题(另一个公开题库,题面和测试风格都不同) |

**为什么是两类:**Q2 要互换考试,至少两类。
**为什么选这两类:**判分方式完全一样(测试全绿=通过),不用为两类任务写两套判分;但最优做题流程有真实差别——修 bug 吃"先读代码、定位、小步修改",按测试写代码吃"先读测试、整体实现、按报错迭代"。差别足够让"专精"有内容,成本又最低。
**为什么训练/验证分开、且验证选外部题:**考试不能考原题。验证题库特意选风格不同的来源,就是要逼出"通法还是应试"的真相。
**为什么题量这么小(10–12 题):**目的不是刷绝对分数,是在一天内读出方向。题少带来的分数抖动用"考 3 遍取平均"来压(第 5 节)。

所有题目转成统一格式:每题一个目录,内含 `solution.py`(待修/待写)和 `test_solution.py`(测试)。

## 3. 第一版 Harness 怎么搭

### 3.1 v1:故意朴素的通用流程(进化起点 + 对照组)

v1 有双重身份:所有改进的**起点**,以及三方对比中的**对照组**。所以它必须"朴素但完整"——太聪明会掩盖改进空间,太残缺则对照不公平。本仓库已有雏形(`harnesses/v001`),微调即可用。具体构造:

```
输入:一道题的目录(solution.py + test_solution.py)

流程:
1. 给干活模型一句任务说明,和三个动作:读文件 / 写文件 / 跑测试
2. 系统提示只给最通用的建议:先读代码和测试 → 理解意图 → 修改 → 跑测试验证
3. 模型自主循环:每轮选一个动作,拿到结果后决定下一步
4. 停止:测试全绿、模型自己宣布完成、或到 10 轮上限

输出:改完的 solution.py + 全程记录(每轮做了什么、测试输出是什么)
```

两类任务共用同一个 v1(它对任务类型一无所知)——这正是附件里"通用 Harness"立场的具象化,后面所有专精收益都以它为参照。

### 3.2 每一轮改进怎么进行

```
第 N 轮:
1. 当前流程在训练题库上跑一遍,得到:每题过/没过 + 失败题的全程记录
2. 把「流程代码 + 成绩单 + 失败记录」交给改进模型,要求:
   a. 诊断每道失败题:是流程没让模型看到关键信息?步数不够?策略顺序不对?
   b. 输出新一版完整流程代码,并用一句话自述"这版改了什么"(记入台账)
3. 新版存为 v(N+1),进入下一轮
共 6 轮。全程只见训练题库。
```

### 3.3 改进的边界:允许动什么、锁死什么

| 允许改 | 锁死不许改 | 锁死的理由 |
|---|---|---|
| 提示词内容;动作的先后策略(比如先跑一次测试看报错再读代码);失败后的重试逻辑;每轮给模型看什么信息;轮数怎么分配 | 干活模型的型号;三个工具的实现;判分脚本;题库 | 一旦这些也能改,分数上涨就说不清是"流程变好"还是"换了更强模型/改了考题"。判分脚本会检查流程代码里声明的模型名,不符直接拒绝计分 |

### 3.4 builder0:Q3 的第一版

和 v1 输出同样格式的流程代码,但**输入只有任务说明卡**——没有题目、没有成绩单、没有任何试错记录。它就是"教务主任"的最小雏形:只凭对任务类型的描述开出一套流程。

## 4. 需要什么模型(经现有网关调用,Anthropic 消息格式)

| 角色 | 模型 | 为什么 |
|---|---|---|
| **干活模型**——在流程里实际做题 | `claude-haiku-4-5`(具体带日期的版本名以网关列表为准) | 便宜、快;更关键的是它足够"不完美"——预计基准通过率 50–80%,流程改进才有上升空间。若用最强模型,玩具题直接近满分,什么都测不出来 |
| **改进/生成模型**——诊断失败、重写流程、按卡片生成流程 | `claude-sonnet-4-6` | 写代码和做诊断需要更强能力;全程只调用几十次,贵一点无妨 |

若网关没有这两个确切名字,任选"一个便宜快 + 一个强"的等价组合;开跑第一件事就是对两个模型各发一条测试消息确认可用。

## 5. 只防两个坑(Apex-Tune 全套体系里就借这两条)

**坑一:改进出来的流程可能学会作弊。**流程有写文件的权限,而"测试全绿=通过"——改进模型完全可能产出一个直接改写测试文件的流程。防法:判分前把测试文件从题库原始目录重新复制并核对指纹,除 `solution.py` 外有任何改动记 0 分。(顺带修掉现有跑分脚本里真实存在的这个漏洞。)

**坑二:模型做题有运气成分,单次分数会抖。**防法:所有**用于下结论**的考试一律考 3 遍取平均,同时记录波动幅度;两个版本的差距小于波动幅度,就当作没有差别。改进过程中的快速反馈只考 1 遍(它只指方向,不下结论)。

另外,第 7 节的判定线在开跑前写死,跑完不许挪——防止看到数字后"解释成自己想要的结论"。

## 6. 28 小时时间表

前提:API key 就位。两类任务的改进互相独立、并行跑;每次考试内部 4 道题并发。单道题一次做题约 1 分钟、3–5 分钱。

| 时段 | 干什么 | 产出 / 检查点 |
|---|---|---|
| 第 0–3 小时 | 装依赖、两个模型冒烟;下载并转换 4 个题库;写判分脚本(含防作弊);题目迁移;v1 微调 | 端到端跑通 1 道题 |
| 第 3–6 小时 | **基准考试**:v1 在 4 个题库各考 3 遍 | 基准分四格。若训练题库通过率 >80%(没有改进空间)则调低轮数上限;<40% 则放宽——只允许此刻调,之后冻结 |
| 第 6–10 小时 | **Q1 主实验**:两类任务并行,各 6 轮改进 | 两个专精流程 + 每轮台账 |
| 第 10–14 小时 | **期末考**:两个专精流程各考本族训练+验证题库,各 3 遍 | Q1 判定数据 |
| 第 14–17 小时 | **Q2 互换考**:专精流程互考对方验证题库,各 3 遍 | Q2 判定数据 |
| 第 17–21 小时 | **Q3**:写两张任务卡 → 生成两个 builder0 → 各考本族训练+验证题库,各 3 遍 | Q3 判定数据 |
| 第 21–26 小时 | 机动缓冲:补考、处理网关限速或故障 | — |
| 第 26–28 小时 | 汇总 `RESULTS.md`:三问判定 + 下一步建议 | 最终报告 |

## 7. 判定标准(开跑前定死)

| 问题 | 看什么数字 | 判定线 |
|---|---|---|
| 改进机制有效吗(Q1 的前提) | 专精版 − 基准版,训练题库通过率 | ≥ +15 个百分点且大于波动幅度 → 有效;否则暂停,先修改进机制 |
| Q1:通法还是应试 | 专精版 − 基准版,验证题库通过率 | ≥ +5 点 → 通法(Case 2);≤ −5 点 → 应试(Case 1);之间 → 不明确 |
| Q2:专精有红利吗 | 主场分 − 客场分(两个方向各算) | 至少一个方向 ≥ +10 点且大于波动 → 有红利 |
| Q3:生成有信号吗 | builder0 − 基准版(两族验证题库) | 两族都不低于基准,且至少一族 ≥ +10 点 → 有信号 |

**结果怎么用:**

| 结果 | 下一步 |
|---|---|
| 三问全正 | 立项完整版:接入真实题库(如 SWE-bench 精简子集)、启动学习型 Builder 的数据积累 |
| Q1 = 应试(Case 1) | 判定办法本身被证明有效;二期第一优先级 = 训练题库多样化,再验 Case 2 |
| Q2 无红利 | 两类任务可能太相近;换距离更远的任务对(如 修 bug vs 数据分析)重测 |
| Q3 无信号 | 纯看描述不够,Builder 需要喂做题历史 → 提前启动"描述 + 历史检索"混合式 |

## 9. 刻意不做的事(防止范围膨胀)

- 不接真实大型题库(SWE-bench / RepoBench / TerminalBench)——那是二期的事,先用一天读出方向。
- 不训练、不微调任何模型;Builder 只是提示词驱动的生成器。
- 不做 Apex-Tune 的存档/杂交/并行搜索等重机制——那些解决的是长期大规模搜索的问题,本实验只有 6 轮改进,用不上;只借了它"防作弊、防运气分"两条教训。
- 不用"模型当裁判"打分,一切只认测试运行结果。
