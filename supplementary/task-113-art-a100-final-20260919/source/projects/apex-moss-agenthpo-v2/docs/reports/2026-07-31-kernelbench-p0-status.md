# KernelBench 实验计划一：P0 状态报告

日期：2026-07-31

状态：P0 已通过；等待 P1 模型与预算确认

## 一句话结论

MOSS 已经能把候选程序送到固定 A100 上，先判断能否运行、再判断答案是否正确，只有正确时
才给出速度成绩。两道有效任务的错误答案都被拒绝，正确答案也都能在一分钟左右得到稳定
反馈；因此“针对一道具体任务反复试、即时看分”的下层闭环已经可以工作。

全新 GPU 容器中的复现也已完成，因此 P0 现已通过。本阶段没有调用做题模型，也没有产生
模型 API 费用。

## 已经完成什么

- 通过历史 SSH alias `a100jump` 连接到 8 张 A100 80GB 的服务器；实验固定使用 GPU 4，
  不终止、不迁移同机其他人的进程。
- 把 KernelBench 固定在 commit
  `423217d9fda91e0c2d67e4a43bf62f96f6d104f1`，并逐题核对文件指纹。
- 在数据盘建立独立 Python、PyTorch、Triton 和缓存环境，避免占用已经接近满盘的系统盘。
- 建立不可覆盖的实验账本、候选原始日志、费用/时长硬帽和每 5 秒刷新的 HTML 看板。
- 对每道有效任务跑一个故意错误的候选和一个正确候选；错误候选没有速度分。
- 对相同正确候选重复三次，确认当前共享机器的波动不会把明显进步误判出来。
- 从固定 Ubuntu 镜像和 KernelBench 锁文件创建全新 Python 环境；容器禁网、根文件系统只读、
  删除额外权限，只映射 GPU 4 的设备节点及必要的只读宿主驱动库。
- 在容器中核对 Python 3.10.12、Torch 2.13.0+cu130、Triton 3.7.1，只能看见一张 A100，
  并让 `torch.compile`/Triton 完成现场编译和正确计算。

## 实际结果

| 任务 | 错误候选 | 正确候选三次结果 | 单次等待 | 判断 |
|---|---|---|---|---|
| LayerNorm | 被正确拒绝 | 0.994×、0.970×、0.971× | 约 24 秒 | 可评分；三次差距小 |
| Matmul + Sigmoid + Sum | 被正确拒绝 | 1.000×、1.000×、1.000× | 约 49–53 秒 | 可评分；三次一致 |

这里的 1.000× 不是优化成绩，只是“同样的参考做法应得到约 1 倍”的 P0 校准结果。账本记录
的有效任务 GPU 执行约 5.6 分钟。一次 SSH 结果在本地显示上延迟返回，但远端结果随后完整
写入账本；追加的更正记录保留了这次恢复过程，没有删除或覆盖原事件。

全新容器复现再次得到同样方向：LayerNorm 错误候选 0/5、参考候选 5/5（0.98×）；
Matmul + Sigmoid + Sum 错误候选 0/5、参考候选 5/5（1.00×）。这证明结论不依赖先前宿主机
虚拟环境。

## 为什么替换了一道题

原定的 `Matmul + Subtract + Multiply + ReLU` 题没有进入正式刷分。P0 故意提交全零结果后，
官方检查连续五次都判为正确，并给出约 215× 的异常分数。这说明该题当前输入和初始化让输出
几乎必然退化为全零，无法判断候选是否真的完成计算。

按实验计划事先写明的替换规则，我们在任何模型调用之前启用了备选题
`Matmul + Sigmoid + Sum`。旧题、215× 和完整日志继续留在账本中并显示“已淘汰，不计分”，
不会被删除或包装成实验成绩。

## 现在缺少什么

1. **P1–P3 的费用与模型确认。** 建议继续沿用计划中的两个独立硬帽：模型/API 不超过
   100 美元，GPU 不超过 100 美元；还需明确固定的做题模型，以及是一次批准 P1–P3，还是
   每阶段分别批准。

服务器虽然没有 NVIDIA Container Toolkit，但这已不是阻塞项。我们通过 Docker 的设备白名单
只开放 GPU 4，并只读映射标准驱动库，达到了更窄的隔离范围；不需要管理员继续修改服务器。
