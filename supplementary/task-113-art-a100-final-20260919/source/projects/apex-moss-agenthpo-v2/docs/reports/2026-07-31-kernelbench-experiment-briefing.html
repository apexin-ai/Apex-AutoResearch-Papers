一、核心研究问题

在底层模型、任务、工具和预算都固定的情况下，一套会根据分数不断调整的专用工作流， 能否比通用工作流更稳定地找到“结果正确而且运行更快”的候选？

本轮要证明

专用 Harness 能形成可靠闭环，知道什么时候修错误、什么时候测速、什么时候保留或回滚。

本轮不证明

不声称已经掌握通用 GPU 优化，也不把单道题的进步解释成对整个 AI 工程领域的泛化。

成功后的价值

获得可复现的 Harness 结构和进化记录，为未来通用 Builder 提供真实训练材料。

二、架构选择：长期双层，当前先验证下层

长期目标

上层：通用 Harness Builder

读取一个新任务的说明，构造适合它的专用 Harness。Builder 不会在单题每次得分后更新， 而是在完成一批任务、比较成功和失败记录之后再迭代。

本轮主角

下层：每题独立的专用 Harness

每道任务拥有独立的提示、工具顺序、失败处理、历史最好版本和实验账本；不同任务不共享候选和失败轨迹。

三、专用 Harness 如何调整，通用 Builder 如何运行

P1 与 P2 的迭代对象不同。P1 的 22 轮中三种 Harness 都被冻结；P2 已由 Harness 优化器读取本路线历史，把操作手册从 v001 逐轮改版，再让新版 Harness 生成下一份 Kernel。两阶段结果仍分别记录，P1 的速度成绩不冒充 Harness 自迭代成绩。
P2 · 已完成

专用 Harness：根据本任务反馈改工作流

同一道题开三条彼此隔离的实验路线，三条路线从完全相同的第一版操作手册开始。 每条路线独立生成候选、只接收自己的简短评分反馈，再调整自己的做题步骤；这样可以区分 “方法稳定有效”和“某一次碰巧变快”。

跨任务循环 · 每批次调整

通用 Builder：根据多任务证据造初始 Harness

Builder 不参与单题逐分刷分。它等待多道任务完成 P3/P4，再总结反复有效的结构， 为一个新 Task 零样本生成初始专用 Harness；新任务随后进入自己的下层循环。

这里的“谱系”就是独立实验路线，“v001”就是共同的第一版操作手册。 操作手册规定模型先看什么、按什么顺序检查、收到失败后如何处理、何时保留或恢复历史最好版本； 每轮候选是模型写出的 GPU 程序，而 Harness 是指导模型完成这一过程的工作流。

专用 Harness 每一轮会看什么、做什么

阶段允许看到的信息采取的动作产生的结果
1. 任务定向 任务卡、参考代码、固定输入形状、候选文件合同 识别这道题的主要计算、正确性风险和潜在慢点 本轮单一优化假设
2. 生成候选 当前 Harness、本路线任务记忆、上一候选和历史成绩摘要 按当前工作流生成一个完整 ModelNew 不可覆盖的候选版本和原始模型响应
3. 分段评分 先看编译；编译通过才看正确性；正确才看速度 官方评分边界运行候选，控制器整理短反馈卡 编译/正确性/速度、成本和下一步建议
4A. P1 调整 Kernel 冻结 Harness、上一版 Kernel、本路线短反馈和历史分数 做题模型提出下一版 Kernel；Harness 的提示、顺序和规则不变 新的 Kernel 候选代码
4B. P2 调整 Harness 当前 Harness、本谱系反馈摘要、失败类型和历史最好成绩 Harness 优化器提出下一版完整 Harness；该步骤尚未启动 提示、信息顺序、工具顺序或失败处理的新版本
5. 继续或停止 本谱系轮数、连续失败/无进步次数和剩余预算 继续下一轮，或按八轮/连续三轮/预算规则停止 冻结的历史最好 Harness 与候选

专用 Harness 可以改什么

  • 系统提示和任务信息的呈现顺序；
  • 先读什么、何时编译、何时测速；
  • 编译失败和答案错误时给模型多少反馈；
  • 任务记忆、历史最好对比、回滚和时间分配。

始终冻结或不可见

  • 底层模型、GPU、官方评分方法和总预算；
  • 其他两条谱系与其他任务的候选和失败历史；
  • 私有评分日志、评分器实现和未提供的测试输入；
  • 任何通过修改计时或跳过正确性换来的“优化”。

四、Benchmark 为什么选择 KernelBench

分类说明：“AI for AI”在本项目中是一个上位方向，指让 AI 改进 AI 系统本身； 我们再把它粗分为反馈慢、答案空间开放的研究型任务，以及目标和评分固定、能立即反馈的调优型任务。 KernelBench 要求为固定 AI 计算写出正确且更快的 GPU kernel，因此属于本项目所说的 AI for AI 调优型 benchmark。

反馈快

提交后马上知道能否编译、答案是否正确以及速度变化，适合多轮调整。

与 AI 系统直接相关

任务来自模型计算中常见的 GPU 操作，优化结果对应真实的 AI 运行成本。

能比较细微进步

不仅有“通过/失败”，还有连续速度分，更容易判断某次 Harness 修改是否有效。

Benchmark本轮角色判断
KernelBench首发实验即时反馈、任务明确、与 AI 计算直接相关，适合先打磨闭环。
Atrex-Bench后续独立确认只在 KernelBench P3 成功后立项，用于排除对单一 benchmark 的偶然适配。
CompilerGym / PIECPU 备用可在 GPU 长期不可用时演练框架，但不能替代正式 KernelBench 结果。
RE-Bench暂不使用其公开说明请求避免针对评测材料过拟合，与本轮目标存在冲突。
NanoChat不纳入本轮按当前决策不扩展训练数据链路，先集中验证 KernelBench 专用 Harness。

五、首发任务与评分门禁发现

任务 A · 有效

LayerNorm

代表模型中常见的归一化计算，用来检验 Harness 是否会先保证数值一致，再分析内存访问和归约速度。

任务 B · 有效

Matmul + Sigmoid + Sum

代表大矩阵乘法后的激活与求和，用来检验 Harness 是否能区分成熟矩阵乘法和适合融合的后处理。

一次有价值的 P0 发现：原定任务 B“Matmul + Subtract + Multiply + ReLU”中， 故意返回全零的候选也通过了 5 次正确性检查，并得到约 215× 的异常分数。这说明该题当前输出 会退化为全零，无法区分真实计算和空算捷径。我们按事先登记的备选清单，在任何模型调用前完成换题； 旧结果永久保留并明确标记为“不计分”。

P1 已完整执行

22 次模型调用、22 个归档候选、22 个有效评分；其中 17 个候选正确，没有环境无效运行。

P2 已安全冻结

这些约 1× 的结果不是优化成绩，而是 P0 校准：同样的参考做法应该得到约 1 倍，并且重复测试不应剧烈波动。隔离容器复现中，LayerNorm 参考候选为 0.98×，Matmul + Sigmoid + Sum 为 1.00×，结论方向一致。

P1 总计：22 个计划候选全部完成，17 个正确；GPU 计时累计约 723 秒（约 12 分钟）， 所有调用都走已登录的 Codex/ChatGPT，实验账本记录 API 费用为 0。第一次 LayerNorm 结果曾因 解析顺序问题被误写为环境故障；系统保留原记录并追加纠正事件，没有重跑或多消耗一次模型调用。

应如何解读：LayerNorm 表明固定工作流配合短反馈可以快速修正规则和正确性，并找到高性能 Kernel； 第二道题表明多试几轮并不保证提升。P1 提供可靠对照；P2 随后的三条 Matmul 路线均超过 这个对照，而 LayerNorm 没有超过，说明任务专化有正向信号但并非对每题都自动有效。
