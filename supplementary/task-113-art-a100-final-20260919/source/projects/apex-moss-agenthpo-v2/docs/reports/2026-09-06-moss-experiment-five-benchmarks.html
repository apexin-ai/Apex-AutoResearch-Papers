Moss · Experiment 5 · Re-screened 2026-09-07

用一组真正适合 B-self 的 Benchmark，验证 Builder 能否跨题成长

实验五的重点不是把题目数量堆到十个，而是让每个 benchmark 都能形成同一条可审计的闭环：题内反复改 Task Harness，题目结束后保存 BuilderArtifact，再让后面的新题使用已经改变的 Builder。下面把“优先评估的候选”和“高成本扩展”分开；所有候选都必须先通过资格测试，避免把未核验的资源或榜单信息写成既定事实。

五组实验：先拆清楚“改 Harness”与“记住经验”

所有组使用同一模型、任务顺序、调用预算和 evaluator。差别只在下层 Harness 是否可改、Builder 是否保留跨题信息，以及 Builder 自己是否能变。

A-FIXED

下层不变

Solver 可根据当前题反馈重新生成答案，但角色、工具、路由和工作流冻结。

基线：不改 Harness，只靠重复做题能涨多少？
B-FROZEN

题内改 Harness

Builder 固定，只在当前题内根据分数、公开反馈和历史 Harness 提出 Ht+1；换题时重新开始。

回答：固定 Builder 能否现场把下层 Harness 改得更适合这道题？
B-MEMORY

固定 Builder + 经验库

Builder 本身不变，但可读取前题整理出的脱敏经验；不携带前题答案、私有标签或整段轨迹。

回答：显式经验库是否带来额外跨题收益？
B-SELF

Builder 自己会变

每个源题完成后，Builder 提交并验证新的 BuilderArtifact；后题加载这个 Artifact。默认不额外检索经验库。

回答：经验能否吸收到 Builder 的做事方法里？
B-FULL

自变 Builder + 经验库

同时开启 BuilderArtifact 演化和脱敏 Experience Bank，作为完整 Moss 的上限组。

回答：两种跨题机制叠加是否还有增益？
B-frozen − A-fixedBuilder 现场改下层 Harness 的因果收益
＋
B-self − B-frozenBuilder 自身改变带来的跨题迁移
＋
B-full − B-self显式经验库的额外贡献

重新筛选后的 Benchmark

筛选标准：有多个可顺序处理的 instance；每轮能获得公开分数或可审计反馈；下层 Harness 的变化有明确落点；单轮不应长到无法做 8 次以内迭代。以下时间仅是单候选 evaluator 的粗略估计，不包含模型调用和环境准备，也不是官方限时。GPU 需求和耗时均为规划值，正式启动前仍要以官方版本和 smoke test 为准。

CORE 01

YAHPO Gym

代理模型超参数优化
优先正式CPU
为什么适合：有多个数据集/情境、分数反馈快，适合观察同一 Builder 是否能把搜索、验证和预算控制改成不同的题内策略。
候选生成、采样/早停、历史视图、验证顺序
8–16 vCPU · 32–64 GB；模型走 API
秒级到分钟级；先锁定轻量 scenario
同 scenario、同预算；榜单需核对是否存在官方 LLM 榜
B-self 价值：源题可以教 Builder 何时探索、何时利用，后题可检验 Artifact 是否保留这套判断。
建议：第一批正式接入。
CORE 02

CompilerGym · cBench

编译 pass 序列优化
优先正式CPU
为什么适合：每步动作有明确运行结果，能让 Task Harness 真正选择工具、检查约束、保留最好序列，而不是只换 prompt。
分析器→动作生成→编译验证→回退 workflow
16 vCPU · 32–64 GB；无需 GPU
秒级到数分钟；适合多轮
同 benchmark revision、同 CPU；公开分数可复算
B-self 价值：不同程序可作为顺序任务，检验 Builder 是否学会“先测量再选 pass”的通用流程。
建议：第一批正式接入。
CORE 03

AlgoTune

算法实现与性能优化
优先正式CPU / 依任务
为什么适合：正确性和速度都能反馈，能区分“找到更好答案”和“改出了更合适的工作流程”。
profiling、测试、局部改写、回归检查、回退
16–32 vCPU · 64 GB；GPU 非必需
分钟级；先选短任务子集
同语言/库/CPU；榜单数字需锁版本
B-self 价值：前题可让 Builder 学会如何分配 profiling 与验证预算，后题检验是否能迁移。
建议：先做 2 题资格测试，再进入正式组。
CORE 04

KernelBench

GPU kernel 正确性与速度
优先正式H100 / H200
为什么适合：编译、正确性和速度都是可审计反馈，下层 Harness 的工具调用和工作流改动有清晰证据。
profiling 工具、kernel 起点、测试/测速、回退路径
每条 lane 1×H100 或 H200 · 16 CPU · 64 GB
分钟级；限制 kernel 子集和总 GPU 秒
必须同 GPU、CUDA、编译参数和 evaluator
B-self 价值：验证 Builder 是否把“先保证正确，再追求速度”的顺序沉淀到后题。

CORE 05

  • YAHPO：公开分数与失败记录
  • CompilerGym：动作/回退 contract

什么结果才算支持 Moss

这里把最容易误判的地方提前写死。

必须记录

  • Builder 提出的上层修改与下层 HarnessChangeProposal 分开记录。
  • 保存 Ht / Ht+1 的完整结构、hash、实际加载 receipt 和最终生效节点。
  • B-self 在题目结束时才更新 BuilderArtifact；最终 held-out 题上冻结 Builder 做评估。
  • API、格式、Gate、evaluator 错误单独报告，不能擅自记成 0。

不能这样宣称

  • 同一家族的子集不算多个独立 benchmark。
  • B-self 优于 B-frozen 或外部 SOTA 不是预设结论，必须由结果决定。
  • “候选答案变了”不等于“下层 Harness 变了”；必须有结构与执行证据。
  • 本页的资源、耗时和资格状态是规划值，不代表已完成正式跑分。
推荐主线：先用 SimpleTES、YAHPO、CompilerGym 建立 B-self 的保存/加载和题内提分证据；通过资格测试后加入 AgentHPOBench、AlgoTune、KernelBench；SWE-Perf 与 TritonBench-G 只作为后续扩展。这样能同时支持“Builder 有泛化性”和“只在适合的 benchmark 上追求榜单分数”，又不会把适配失败误判成方法失败。

B-self 的验收与跨题边界

本页为候选计划，不代表 B-self/B-full 已接通或正式跑通。先通过双题测试：前题结束生成并保存新的 BuilderArtifact，后题实际加载，并留下执行证据。B-self 可以利用前题经验修改自身，区别是后题只继承修改后的 Builder，不额外检索前题经验库；B-memory 保持 Builder 不变、仅继承经验库。两者不是“是否参考经验”的区别。

预先划分源题与未见题，各组独立重置新题的下层 Harness 和题内记忆。最终未见题上冻结上层 Builder；另外留出整个 benchmark 检查跨 benchmark 泛化。自更新消耗计入总预算。每个在线任务流内部顺序执行，不同组、seed 和隔离的 benchmark 流可以并行。不得根据是否提分挑题，不得把隐藏标签、测试答案或后题反馈送入 Builder。

这次保留 8 个明确方向，没有为了凑 10 个把同源 LLVM 子集计成独立 benchmark；原本含糊的 GDPevo 项移出。至少 10 个独立 benchmark 的目标尚未满足。SimpleTES 轻量子集不能代表整个套件，现有少量题不足以独自支撑跨题结论；AgentHPOBench 的真实训练成本需另测，不能承诺分钟级。

资料核验限制：本次网络读取不稳定，尚未完成全部候选的最新官方硬件、限时和榜单核验。因此 GPU 型号和耗时仅作资源规划，不作为官方可比性的承诺。优先推荐不等于可以立即正式开跑。
